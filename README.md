# 마스킹 기반 주차장 CCTV 후보선별 서비스

사건 시점을 모르는 긴 주차장 CCTV에서 **차량 파손과 관련된 후보 구간을 찾고, 사용자가 비식별화된 영상을 직접 확인하는 웹 서비스**입니다. 대학교 종합설계 과목의 3인 팀 프로젝트로, PC 웹 기반 데모·시연을 목표로 합니다.

사용자가 지정한 차량·파손 위치를 바탕으로 후보를 선별하고, VLM이 검토 순서를 정합니다. 사용자는 의심 장면을 고정하고 업로드 원본에서의 시간 위치를 확인할 수 있습니다. 최종 사건 판단은 사용자가 합니다.

> **현재 상태 — 2026-11-08:** 백엔드 API와 로컬 가짜 워커, 백엔드 EC2 설치·배포 스크립트, 프론트 화면이 있어 GPU·AWS 없이 업로드부터 결과 조회까지 로컬에서 실행할 수 있습니다. 프론트는 예시 데이터로 화면만 보는 데모 모드와 백엔드에 연결하는 모드(`USE_BACKEND=true`)가 있습니다. Terraform으로 보안 그룹·SQS·S3와 백엔드 EC2를 만들었고, GPU EC2와 IAM 역할은 아직 없습니다. 실제 분석을 하는 `pipeline/`(GPU 워커)과 KPI 평가는 아직 없습니다.

## 주요 기능

- **관리자·피해자 계정과 사건 묶기:** 주차장 관리자가 관리자 계정으로 피해자 계정을 초대해 사건을 묶고, 위탁계약에 동의한 뒤 CCTV를 업로드합니다. 결과 영상은 관리자 계정에서 관리·감독 안내에 동의한 뒤 엽니다.
- **차량·파손 정보 입력:** 비식별화된 첫 장면에서 차량, 파손 위치, 차량 바닥 네 모서리와 정면 쪽 변·파손 변을 지정합니다. 파손 사진·설명은 선택 입력입니다.
- **후보 선별과 필수 VLM 정렬:** 객체탐지·추적·움직임 분석으로 관련 구간을 선별하고, VLM으로 확인 순서를 정합니다. 낮은 점수만으로 후보를 삭제하지 않습니다.
- **비식별화 영상 확인:** 얼굴·번호판 등을 가리고 차량 주변으로 자른 후보 클립을 최대 10개씩 제공합니다. 각 클립은 영상 경계 내 최대 30초입니다.
- **사건 지점 다중 고정:** 여러 의심 장면을 고정하고 원본 영상의 시작·끝 경과시간을 확인합니다. 녹화 시작 시각을 입력했다면 추정 실제 시각도 표시합니다. 확인이 끝나면 피해자 계정에서도 고정한 시간 위치를 다시 볼 수 있습니다.
- **진행 유지와 재열람:** 영상별 입력·고정·확인 진행을 유지합니다. 영상의 열람 기간은 업로드 완료 후 30일이며, 만료 자료는 주기적으로 정리합니다.

일반 회원가입과 영상 다운로드는 제공 범위에 포함하지 않습니다. 요구사항별 완료 조건은 [SRS](docs/SRS.md)에 있습니다.

## 서비스 이용 흐름

```mermaid
flowchart TD
    A["관리자: 피해자 초대 · 사건 묶기"] --> B["관리자: 위탁계약 동의 → CCTV 업로드"]
    B --> D["1단계: 첫 장면 비식별화 · 차량 탐지"]
    D --> E["피해자: 차량 · 파손 위치 · 바닥 네 모서리 · 정면 변 · 파손 변 입력"]
    E --> F["2단계: 전체 영상 후보 선별 · VLM 정렬"]
    F --> S["관리자: 관리·감독 안내 동의"]
    S --> G["관리자 화면에서 피해자가 후보 클립 확인"]
    G --> H["의심 장면 고정 · 추가 후보 확인"]
    H --> G
    H --> I["확인 종료 · 고정 결과와 원본 시간 위치 조회"]
    I --> J["피해자: 피해자 계정에서 사건 시간 다시 보기"]
```

1. 관리자가 관리자 계정으로 피해자 계정을 초대해 사건을 묶고, 위탁계약에 동의한 뒤 영상과 선택 사항인 녹화 시작 시각을 입력합니다. 진행도는 두 계정 모두에 보입니다.
2. 첫 장면이 준비되면 피해자가 피해자 계정에서 탐지된 차량 중 본인 차량을 고릅니다. 차량을 찾을 수 없으면 관리자가 영상을 다시 올립니다.
3. 파손이 보이면 차량 내부의 파손 부위를, 안 보이면 화면에서 파손 위치에 해당한다고 보는 곳을 작은 사각형으로 지정합니다. 바닥 네 모서리와 정면 쪽 변·파손 변도 입력합니다. 저장 전 확인하며 저장 후에는 수정하지 않습니다.
4. 전체 영상 분석이 끝나면 관리자 계정에서 관리·감독 안내에 동의하고, 피해자가 관리자의 관리·감독 아래 후보를 확인합니다. VLM 점수를 얻지 못한 후보는 별도 파싱 실패 목록으로 제공하며, 두 목록의 확인 진행을 구분합니다.
5. 원하는 후보를 여러 개 고정할 수 있습니다. 고정이 1개 이상이거나 마지막 묶음까지 보면 확인을 끝낼 수 있습니다. 끝난 뒤에는 피해자 계정에서도 열람기한 안에 고정한 사건 지점의 시간을 볼 수 있습니다. 영상은 볼 수 없습니다.

기존 영상을 확인하는 도중 새 영상을 업로드할 수 있으며, 화면을 떠나도 기존 분석은 계속됩니다. 일부 클립을 만들지 못하면 열람 불가 수를 표시하고 정상 클립은 제공합니다. 전체 확인 완료는 **열람 가능한 후보의 확인 범위**를 뜻하며 사건이 없다는 판정이 아닙니다.

서비스 오류로 분석이 실패하면 저장된 원본·입력·완료 결과를 유지하여 실패 단계부터 다시 시도하도록 설계합니다. 사용자 재시도는 작업당 누적 최대 3회이며, 원본 문제·부재·기한 만료는 별도로 안내합니다. 상세 기준은 SRS의 D-109~D-113 보완 사항을 따릅니다.

```mermaid
flowchart LR
    U["사용자 · 관리자 브라우저"]
    subgraph CPU["백엔드 EC2"]
        WEB["Flutter Web 정적 파일"]
        API["FastAPI"]
        DB[("PostgreSQL")]
    end
    Q["SQS 작업 대기열"]
    W["GPU EC2 워커"]
    RAW[("S3 원본")]
    MASK[("S3 마스킹본")]
    RESULT[("S3 분석 결과")]
    VLM["Bedrock VLM"]
    U --> WEB
    U -->|"세션 · 입력 · 상태 · 결과 요청"| API
    API --- DB
    API -->|"작업 등록"| Q
    Q --> W
    API -->|"업로드 · 재생용 임시 URL"| U
    U -->|"영상 · 선택 사진 업로드"| RAW
    MASK -->|"비식별화 이미지 · 클립 재생"| U
    RAW --> W
    W --> MASK
    W <--> RESULT
    W <--> DB
    W <--> VLM
```

- **웹·API·DB:** 백엔드 EC2에서 웹 정적 파일, API, PostgreSQL을 운영합니다. API는 상태·권한·작업을 관리하고 영상 분석은 워커에 맡깁니다.
- **비동기 분석:** SQS로 작업을 전달하고 DB에 진행 상태를 기록합니다. 업로드 직후 첫 장면을 준비하고, 사용자 입력이 끝난 뒤 전체 영상을 분석합니다.
- **원본과 열람 데이터 분리:** 워커는 원본을 분석하고 브라우저에는 비식별화된 결과를 제공합니다. 파일은 임시 URL을 통해 S3와 직접 주고받습니다.
- **비공개 S3 버킷 3개:** 원본·마스킹본·분석 결과를 나눕니다. 선택 파손 사진은 원본 버킷의 별도 객체로 저장합니다.

세부 연결·권한·배포 구성은 [시스템 아키텍처](docs/design/02-architecture.md)를 참고하세요.

## 개발 환경 준비

### 필요한 도구와 설정

| 대상 | 준비 사항 |
|---|---|
| 공통 | Git, 담당 코드의 실행 도구 |
| 백엔드 | Python 3.12·uv, 로컬 PostgreSQL 실행을 위한 Docker Compose |
| 프론트 | Flutter SDK·Dart, PC 웹 브라우저 |
| 비전 | Python 3.12·uv, FFmpeg, 확정된 모델·가중치와 해당 실행 환경 |
| AWS 배포 담당 | 승인된 학교 AWS 계정 권한, Terraform·배포 설정, EC2 접속 수단 |

백엔드는 Python 3.12(`backend/.python-version`)와 PostgreSQL 16(`backend/compose.yaml`)을 씁니다. 프론트는 Flutter 3.38 이상입니다(D-164). 파이프라인은 백엔드와 따로 `pyproject.toml`·`uv.lock`을 둘 계획입니다.

### 환경변수와 비밀값

- 백엔드 설정 형식은 `backend/.env.example`에 있습니다. 이 파일을 `backend/.env`로 복사해 쓰고, `LOCAL_URL_SECRET`은 PC마다 새로 만들어 채웁니다.
- 프론트는 `--dart-define=USE_BACKEND=true`를 주면 백엔드에 연결합니다. 이 값을 주지 않으면 데모 모드로 뜹니다. 파이프라인 설정은 팀장이 정합니다.
- 기본 로컬 서비스 개발은 AWS 자격 증명·GPU EC2·Bedrock 실호출 없이 가능하도록 구현합니다.
- AWS 서버는 IAM 역할로 AWS에 접근합니다. DB 인증정보는 별도 설정이 필요합니다. 액세스 키·DB 비밀번호·개인 `.env`를 Git에 올리지 않습니다.
- 로컬에서는 Flutter 개발 서버(8080)가 `/api/` 요청을 백엔드(8000)로 넘깁니다. 그래서 `/api`에는 CORS 설정이 없습니다(D-164).

## 로컬 실행

GPU·AWS 없이 업로드부터 결과 조회까지 실행할 수 있습니다. 명령은 [10장 백엔드 로컬 실행](docs/design/10-dev-guide.md#백엔드-로컬-실행)에 있습니다.

| 순서 | 실행 내용 | 위치 |
|---|---|---|
| 1 | `.env` 준비, Docker Compose로 DB 켜기 | `backend/` |
| 2 | 마이그레이션 적용, 테스트 계정(관리자·피해자) 만들기 | `backend/` |
| 3 | API 서버·가짜 워커·주기 작업 실행 (터미널 3개) | `backend/` |
| 4 | `USE_BACKEND=true`로 프론트 실행, 브라우저에서 localhost:8080 접속 | `frontend/` |
| 5 | 테스트 영상으로 업로드부터 결과 조회까지 확인 | 공유 샘플 영상은 아직 없음 |

API 서버를 띄울 때 `--host 0.0.0.0`을 붙이지 않습니다. 붙이면 같은 네트워크의 다른 PC에서도 API에 접근할 수 있습니다.

로컬에서는 DB만 컨테이너로 실행하고 앱 코드는 각 PC에서 직접 실행합니다. S3·SQS는 로컬 폴더·간단한 작업 실행기로 대체합니다. API의 인증·입력 검증·DB 상태 갱신은 그대로 검증하고, 가짜 워커가 준비된 분석 결과를 제공합니다.

각 개발자는 독립 DB를 사용합니다. 실행 중 생성 파일은 `local_storage/`에 저장하고, 공유 원본 샘플은 `fixtures/`로 구분합니다. DB 구조 변경을 받은 뒤에는 마이그레이션을 별도로 적용해야 합니다. DB 중지와 데이터 초기화는 다른 작업입니다.

## 테스트와 AI 성능 평가

### 로컬 서비스 확인

가짜 워커로 다음 흐름을 검증합니다.

1. 관리자: 피해자 초대·사건 묶기 → 위탁계약 동의·업로드 → 피해자: 정지 장면에서 차량·파손 정보 입력 → 관리자: 관리·감독 안내 동의 → 후보 재생 → 다중 고정 → 확인 종료 → 피해자: 사건 시간 다시 보기.
2. 잘못된 좌표·누락 입력·다른 사용자 자료 접근을 거절하는지 확인합니다.
3. 후보 0건, 여러 묶음, 파싱 실패 목록, 일부 클립 열람 불가를 구분해 표시하는지 확인합니다.
4. 새 영상 업로드·재접속·분석 재시도 시 기존 결과와 확인 진행이 유지되는지 확인합니다.
5. 열람기한 전후의 접근 차단과 안내를 확인합니다.

가짜 결과로 서비스 흐름을 검증하는 것과 실제 AI 성능을 측정하는 것은 구분합니다. 백엔드 테스트는 `backend/`에서 `uv run pytest`로 돌립니다(10장). 공유 샘플 영상은 아직 `fixtures/`에 없습니다.

### 실제 분석 평가 목표

아래 값은 **목표이며 측정 완료 결과가 아닙니다.**

| 지표 | 목표 | 측정 기준 |
|---|---|---|
| 비식별화 누락률 | 5% 이하 | 정답 얼굴·번호판 박스의 중심을 최종 마스크가 가리지 못한 비율 |
| 사고 클립 후보 검출 누락률 | 1% 이하 | 평가용 충돌 클립 중 후보가 하나도 생성되지 않은 비율 |
| VLM 정렬 품질 | ROC AUC 0.80 이상 | 후보 선별을 통과한 평가 자료의 최종 점수 |

후보 클립 10개 묶음의 비식별화는 5분 이내 완료를 목표로 합니다. 데이터 분할·정답 라벨·평가 조건 및 결과 기록은 [KPI 평가 설계](docs/design/09-evaluation.md)를 따릅니다.

## 웹 배포와 CI

백엔드 배포 워크플로와 EC2 설치·갱신 스크립트는 있습니다. GPU 워커 배포는 `pipeline/`과 함께 만들 예정입니다.

- **백엔드 EC2:** Flutter Web 빌드 결과·FastAPI·PostgreSQL을 운영합니다. 처음에는 `backend/deploy/install.sh`로 설치합니다. 켜진 서버는 Actions의 **Deploy backend**(`deploy.yml`)를 수동으로 실행해 갱신합니다. EIP를 쓰지 않아 켤 때마다 퍼블릭 IP가 바뀌므로, 실행할 때 그때의 IP를 입력합니다(D-12). 서버 `.env`는 이 워크플로가 Secrets 값으로 다시 씁니다.
- **GPU EC2:** 초기 설치 뒤 워커를 실행하며, 부팅 때 최신 `main`을 받아 갱신하는 방식입니다. GPU 서버의 DB 설정은 최초 준비 시 SSH로 `.env`에 작성합니다.
- **AWS 연결:** 비공개 S3 버킷 3개, SQS, EC2 역할·네트워크, Bedrock 호출 권한을 담당자가 준비합니다. Terraform(`infra/`)으로 보안 그룹·SQS·S3와 백엔드 EC2를 만들었고, GPU EC2는 아직 없습니다. IAM 역할은 관리자가 만듭니다. 학교 계정에서 추가 권한이 필요하면 멘토 승인 절차를 따릅니다.
- **CI:** `main`에 푸시하면 `ci.yml`이 돕니다. 백엔드 작업(ruff 검사, 임시 PostgreSQL을 쓰는 pytest)과 프론트 작업(`flutter analyze`, `flutter test`, Web 빌드)이 있습니다. 프론트 작업이 모두 통과하면 빌드 결과를 Release `web-latest`의 `web.tar.gz`로 교체하고, 서버 갱신 스크립트가 이 파일을 받습니다(D-154). 비전 기본 검사는 담당자가 명령을 넘기면 추가합니다. 실제 AWS 연동·모델 추론·AI KPI는 별도로 확인합니다.
- **배포 전:** 팀 내 푸시를 잠시 멈추고 최신 `main`의 CI 전체 성공을 확인한 뒤 배포합니다. 배포 후 실제 업로드 → 분석 → 결과 조회를 확인합니다.

일반 로컬 개발에 AWS 배포 권한은 필요하지 않습니다. 담당자는 [배포·운영 설계](docs/design/02-architecture.md)와 [개발 가이드](docs/design/10-dev-guide.md)의 최신 결정을 확인합니다. 배포 주소는 실제 배포 후 추가합니다.
