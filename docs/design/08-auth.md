# 08. 인증·권한

> 마지막 수정: 2026-09-22
> 표시: 🚧 미정 · ⚠️ 확인 필요 · 🔐 멘토 승인 필요

누가 무엇으로 자신을 증명하고, 증명한 사람이 무엇까지 할 수 있는지를 정한다. API 하나하나의 요청·응답 모양은 [05장](05-api.md)에 있고, 여기서는 **그 뒤에서 도는 규칙**을 적는다.

## 8.1 한눈에 보기

이 서비스에 등장하는 사람은 둘이고, 증명 수단도 둘이다.

| 누구 | 증명 수단 | 할 수 있는 일 | 할 수 없는 일 |
|---|---|---|---|
| **피해자** (계정 있음) | 세션 쿠키 `sid` (D-30) | 업로드 링크 발급, 자기 영상의 상태·정지 장면·후보 열람, 입력 저장, 사건 지점 고정 | 남의 영상 열람, 원본 열람, 다운로드 |
| **주차장 관리자** (계정 없음) | 업로드 링크의 `token` (D-28) | 링크 1건으로 영상 1건 올리기 | 그 밖의 전부. 영상 주인이 누구인지도 알 수 없다 |

- **계정은 피해자 것 한 종류뿐이다.** 역할(role) 칼럼도, 관리자 화면도 없다 (D-28, [04장 `users`](04-data-model.md#users)).
- 두 수단은 **서로를 대신하지 못한다.** 업로드 API는 쿠키를 보지 않고, 그 밖의 API는 `token`을 보지 않는다 ([05장 5.1](05-api.md#51-공통-규칙)).
- 증명을 통과해도 **원본 영상에는 아무도 닿지 못한다.** 사람이 아니라 권한 구조로 막는다 (8.8).

## 8.2 계정 만들기

회원가입 화면을 두지 않는다. 계정은 서버에서 스크립트로 미리 만든다. (D-44)

```
python scripts/create_user.py --login-id victim1 --name 홍길동
Password: (입력한 문자는 보이지 않는다)
```

- 비밀번호는 **실행 중에 `getpass`로 입력받는다.** 명령행 인자로 받지 않는다. 인자는 셸 기록과 `ps` 출력에 남는다.
- 스크립트는 8.3의 `hash_password()`를 **로그인 API와 같은 모듈에서 가져다 쓴다.** 두 곳에 따로 구현하면 알고리즘이 갈라진다.
- 시연은 이렇게 만든 공용 계정 하나로 한다. 계정을 지우는 기능은 두지 않는다.

## 8.3 비밀번호 저장 (D-58)

`bcrypt` 패키지를 직접 쓴다. 비용 계수(cost factor)는 **12**([01장 1.6](01-overview.md#16-주요-상수)).

```python
import bcrypt

def hash_password(plain: str) -> str:
    return bcrypt.hashpw(plain.encode("utf-8"), bcrypt.gensalt(rounds=12)).decode()

def verify_password(plain: str, hashed: str) -> bool:
    return bcrypt.checkpw(plain.encode("utf-8"), hashed.encode())
```

- 결과 문자열(`$2b$12$...`, 60자)을 `users.password_hash`에 그대로 넣는다. **소금(salt)은 이 문자열 안에 들어 있으므로 칼럼을 따로 두지 않는다.**
- 평문 비밀번호는 어디에도 저장하지 않고, 어떤 응답·로그에도 넣지 않는다 ([05장 5.3](05-api.md#53-계정-api)).
- **bcrypt는 72바이트를 넘는 입력을 잘라 버린다.** 한글은 UTF-8에서 글자당 3바이트라 24자가 상한이다. 데모 비밀번호는 여기에 닿지 않지만, 계정 스크립트가 72바이트를 넘는 입력을 받으면 경고하고 멈춘다.
- **근거는 법이다.** 「개인정보의 안전성 확보조치 기준」(개인정보위 고시) **제7조① 단서**는 비밀번호를 *복호화되지 아니하도록 일방향 암호화하여 저장*하라고 한다. 해시 저장은 선택이 아니라 의무다.

## 8.4 랜덤 토큰 만들기 (D-59)

세션 토큰과 업로드 링크 토큰(`sessions`·`upload_tokens`)은 **같은 함수**로 만든다.

```python
import hashlib
import secrets

def new_token() -> str:
    return secrets.token_urlsafe(32)   # 32바이트 → 43자

def token_hash(token: str) -> str:
    return hashlib.sha256(token.encode()).hexdigest()   # 64자
```

- `secrets`는 운영체제의 암호학적 난수를 쓴다. `random` 모듈은 쓰지 않는다. 씨앗값을 알면 다음 값을 계산할 수 있다.
- 32바이트는 256비트다. 추측으로 맞히는 것은 불가능하고, 주소창에 들어갈 만큼 짧다(43자). [05장 5.4](05-api.md#54-업로드-링크업로드-api)의 예시 토큰이 이 길이다.
- URL-safe 문자만 나오므로(`A~Z a~z 0~9 - _`) 링크 주소에 그대로 넣을 수 있고, 쿠키 값으로도 인코딩이 필요 없다.
- **두 토큰 모두 해시해서 저장한다.** 평문은 쿠키와 링크 주소로 한 번 내보내고 버린다. DB에는 `token_hash`만 남는다 ([04장](04-data-model.md#sessions)). 메타데이터는 이미 일어난 일의 기록이지만 토큰은 **앞으로 쓸 수 있는 열쇠**여서, 평문으로 두면 DB 덤프·스냅샷·에러 로그에 찍힌 행 하나로 그 피해자로 로그인된다.
- **조회 방법은 평문일 때와 같다.** 들어온 값을 해시해 `WHERE token_hash = :h`로 찾는다. UNIQUE 인덱스를 그대로 타고, 요청당 43바이트 SHA-256 한 번이 더 들 뿐이다.
- **비밀번호와 달리 bcrypt를 쓰지 않는다.** bcrypt가 느리게 설계된 이유는 사람이 고른 낮은 엔트로피를 지키기 위해서인데, 토큰은 256비트 난수라 대입도 레인보우 테이블도 성립하지 않는다. 소금 칼럼도 필요 없다 — 입력 자체가 유일하고 무작위다 (D-59).

## 8.5 로그인 세션과 쿠키

로그인 상태는 **`sessions` 테이블 + HttpOnly 쿠키**로 관리한다 (D-30, D-19). API 모양은 [05장 5.3](05-api.md#53-계정-api)에 있다.

**로그인이 하는 일**

1. `login_id`로 `users` 행을 찾고 `verify_password()`로 확인한다. 어느 쪽이 틀렸는지 구분하지 않고 401 `LOGIN_FAILED`를 준다.
2. `new_token()`으로 토큰을 만들고, `token_hash()`를 거친 값으로 `sessions` 행을 넣는다. `expires_at = now() + 7일`.
3. 평문 토큰을 쿠키 `sid`로 내린다. 서버는 이 값을 따로 남기지 않는다.
4. `access_logs`에 `login` 한 행을 남긴다 (8.10).

**쿠키 속성** (D-60)

```http
Set-Cookie: sid=<43자 토큰>; HttpOnly; Path=/; Max-Age=604800; SameSite=Lax
```

| 속성 | 값 | 이유 |
|---|---|---|
| `HttpOnly` | 켬 | JavaScript가 쿠키를 읽지 못한다. XSS가 나도 세션 문자열은 가져가지 못한다 |
| `Secure` | **끔** | HTTPS를 쓰지 않아 켤 수 없다. 켜면 브라우저가 쿠키를 아예 저장하지 않아 로그인이 되지 않는다 (D-31) |
| `SameSite` | `Lax` | 아래 |
| `Path` | `/` | 프론트와 API가 같은 출처다 (D-11) |
| `Max-Age` | `604800` (7일) | 01장 1.6. `sessions.expires_at`과 같은 값이다 |

- **`SameSite=Lax`를 고른 이유**: 다른 사이트에서 보낸 `POST`에는 쿠키가 붙지 않아 CSRF의 주된 경로가 막힌다. 상태를 바꾸는 API는 모두 `POST`/`PUT`이므로(05장) 이것으로 충분하다. **별도의 CSRF 토큰은 두지 않는다.**
- `None`은 쓸 수 없다. 브라우저가 `SameSite=None`을 `Secure` 없이 거부하는데, `Secure`를 켤 수 없다.
- `Strict`는 버렸다. 외부에서 링크를 타고 처음 들어올 때 쿠키가 붙지 않아, 이미 로그인한 사용자도 로그인 화면을 먼저 보게 된다.

**만료와 로그아웃**

- 요청마다 쿠키 값을 해시해 `sessions`를 찾고 `expires_at > now()`인지 본다. 아니면 401 `UNAUTHENTICATED`다.
- **유효 시간을 연장하지 않는다.** 7일이 지나면 쓰던 중이어도 다시 로그인한다 (D-30). 갱신 규칙이 없어 코드가 짧아지고, 훔친 세션의 수명에 상한이 생긴다.
- **로그아웃은 행을 지우는 것이다.** 쿠키도 `Max-Age=0`으로 지운다. 유출된 세션도 같은 방법으로 즉시 끊을 수 있다 — HTTPS가 없는 상태에서 JWT 대신 DB 세션을 고른 이유다 ([02장 2.11](02-architecture.md#211-한계와-알려진-제약)).
- 만료된 행을 지우는 정리 작업은 두지 않는다 (04장).

## 8.6 업로드 전용 일회용 링크

관리자는 계정 없이, 피해자가 발급한 링크 하나로만 영상을 올린다 (D-28, D-45). 테이블은 [04장 `upload_tokens`](04-data-model.md#upload_tokens), API는 [05장 5.4](05-api.md#54-업로드-링크업로드-api)다.

**링크로 할 수 있는 일의 범위**

| 할 수 있다 | 할 수 없다 |
|---|---|
| 링크가 유효한지 확인 (5번) | 영상 주인의 이름·아이디 확인 |
| 업로드용 presigned URL 1개 발급 (6번) | 올린 영상의 분석 결과·상태 조회 |
| 업로드 완료 알림 (7번) | 재생용 URL 발급, 다른 영상 접근 |

- 이 세 API는 **쿠키를 보지 않는다.** 주소의 `token`이 유일한 증명이다.
- 주소의 `token`을 해시해 찾은 행에서 `owner_user_id`를 읽어 영상의 주인으로 삼는다. 관리자는 그 값을 보지도, 고르지도 못한다.

**쓸 수 있는 조건과 만료**

- `used_at IS NULL AND expires_at > now()`일 때만 쓸 수 있다. 유효 시간은 24시간(01장 1.6)이다.
- `used_at`은 **업로드용 URL을 발급할 때** 찍는다. 그래서 업로드가 중간에 끊기면 링크는 이미 쓴 것이 되고, 새 링크를 받아야 한다.
- **다시 발급하면 아직 쓰지 않은 이전 링크가 무효가 된다.** 살아 있는 링크는 사용자당 항상 하나다. SQL은 05장 5.4에 있다.
- 무효가 된 링크와 시간이 지난 링크는 에러 코드가 같다(`UPLOAD_TOKEN_EXPIRED`). 관리자가 할 일이 "새 링크 받기"로 같기 때문이다.
- 발급은 **버튼을 눌렀을 때만** 한다. 화면을 여는 것만으로 발급하면 이미 보낸 링크가 죽는다 (07장).

## 8.7 남의 영상 접근 차단

`/api/videos/{video_id}/...`는 **요청마다** `videos.owner_user_id`가 로그인한 사용자인지 확인한다. 아니면 **없는 영상과 똑같이 404 `VIDEO_NOT_FOUND`**를 준다. (D-39)

- 403이 아니라 404인 이유: `video_id`는 순서대로 매기는 번호라 추측할 수 있다. 403은 "그 번호의 영상이 존재한다"는 사실을 알려준다.
- 확인은 **조회 직후, 다른 어떤 처리보다 먼저** 한다. 공통 의존성(FastAPI `Depends`)으로 한 곳에 두고, 엔드포인트마다 따로 적지 않는다. 한 군데 빠뜨리면 그 API만 뚫린다.
- 남의 영상에 대한 실패 요청은 `access_logs`에 남기지 않는다. 열람이 일어나지 않았기 때문이다 (05장 5.1).

## 8.8 원본 접근 차단

**불변 조건 1**([02장 2.4](02-architecture.md#24-이중-경로와-불변-조건))을 세 겹으로 지킨다. 위에서부터 하나씩 뚫려도 다음 겹이 남는다.

| 겹 | 무엇 | 뚫리면 |
|---|---|---|
| 1. API | 원본 재생 URL을 주는 엔드포인트가 **없다**. 응답에 원본 S3 키를 넣지 않는다 (05장) | 코드 실수로 추가될 수 있다 |
| 2. IAM | 백엔드 EC2 역할에 원본 버킷 `s3:GetObject`가 **없다** ([02장 2.9](02-architecture.md#29-aws-서비스와-권한)) | — |
| 3. S3 | 버킷 3개 모두 비공개이고, 버킷 정책이 HTTP 접근을 거부한다 (D-55, 불변 조건 9) | — |

- **2번이 핵심이다.** presigned URL은 서명한 주체의 권한으로 동작한다. 백엔드가 실수로 원본에 대한 재생 URL을 서명해도 **서명은 만들어지지만 S3가 `AccessDenied`로 거절한다.** 서명은 백엔드 안의 계산이라 AWS가 발급 시점에 막아 주지 않기 때문에, 막히는 지점이 "사용할 때"라는 것을 알고 있어야 한다.
- 원본을 읽는 것은 GPU EC2 역할뿐이다. GPU 워커는 사용자 요청을 받지 않고 SQS에서 작업을 꺼내 가기만 한다 (02장 2.7).
- 백엔드가 원본 영역에 가진 권한은 `s3:PutObject`(업로드 URL 발급)와 `s3:DeleteObject`(파기, D-52)뿐이다. 둘 다 읽기가 아니라 불변 조건 1을 깨지 않는다.

## 8.9 다운로드를 제공하지 않는 방법

불변 조건 8이다. **기능을 만들지 않는 것**이 이행 방법이고, 기술로 완전히 막지는 못한다.

- 화면에 다운로드 버튼·링크를 두지 않는다. 재생은 스트리밍으로만 한다 (07장).
- 재생용 presigned URL은 15분짜리이고 **조회할 때마다 새로 서명한다** (D-41). 주소를 복사해 두어도 오래 쓰지 못한다.
- URL 만료 시각을 응답에 넣지 않는다. 프론트는 403이 나면 원래 조회 API를 다시 부르기만 한다 (05장 5.1).
- **한계**: 브라우저가 받은 바이트는 개발자 도구로 저장할 수 있다. 이 경로는 닫지 못한다. 다만 **그렇게 저장되는 것은 마스킹본뿐이다.** 원본은 8.8의 세 겹 때문에 브라우저에 도달하지 않는다.

## 8.10 열람 기록 남기기

개인영상정보에 닿는 요청은 성공했을 때 `access_logs`에 한 행씩 남긴다 (D-53). 어떤 API가 어떤 `action`을 남기는지는 [05장 5.1](05-api.md#51-공통-규칙)의 표에, 값 목록은 [04장 `access_logs`](04-data-model.md#access_logs)에 있다.

- **법정 기록이다.** 표준 개인정보 보호지침 제44조⑤(열람 기록)·제42조(이용·파기 기록)가 요구한다. 그래서 **끄는 설정이나 건너뛰는 경로를 만들지 않는다.**
- `requested_ip`에 요청자의 IP를 넣는다. 고시 제8조가 말하는 접속지 정보다.
- 기록 쓰기가 실패해도 API는 성공으로 답하고, 남기지 못한 사실을 서버 로그에 남긴다. 기록 때문에 열람이 막히면 사용자가 더 손해다.
- **지우지 않는다.** 영상이 파기된 뒤에도 "누가 언제 무엇을 봤는지"는 남는다 (D-57).

## 8.11 하지 않는 것과 한계

**본인 확인을 하지 않는다.** 표준지침 **제44조③**은 열람 요구자에게 신분증명서를 제출받아 본인·정당한 대리인인지 확인하라고 한다. 후보 클립을 보는 행위가 바로 그 열람이다. 데모는 공용 계정 하나(D-44)로 대신하고, 계정이 진짜 피해자 본인인지는 확인하지 않는다. 실서비스에서는 본인인증을 붙여야 한다. 이유와 범위는 [02장 2.11](02-architecture.md#211-한계와-알려진-제약)에 적었고, 여기서는 구현하지 않는다.

**로그인 실패 횟수 제한을 두지 않는다.** (D-61) 고시 **제5조⑥**은 일정 횟수 이상 인증에 실패하면 접근을 제한하라고 한다. 데모에서는 두지 않고 한계로 남긴다. 이유와 되돌리는 방법은 D-61에 있다.

**그 밖에**

- 비밀번호와 세션 쿠키가 평문으로 오간다. HTTPS가 없기 때문이다 (D-31, 02장 2.11). 고시 제7조① 미이행이며 알고 뺀 것이다.
- 비밀번호 바꾸기·찾기 기능이 없다. 계정 스크립트로 다시 만든다 (D-44).
- 아이디가 없을 때와 비밀번호가 틀렸을 때 응답은 같지만(`LOGIN_FAILED`), **응답 시간이 다르다.** 없는 아이디는 해시 검증을 건너뛰어 더 빨리 돌아온다. 이것으로 아이디의 존재를 알아낼 수 있다. 데모 범위에서 막지 않는다.
- 세션 유효 시간 7일은 길다. 고시 제6조④(일정 시간 미사용 시 자동 접속 차단)는 개인정보취급자를 대상으로 해 사용자 세션에는 적용되지 않지만, 실서비스라면 더 짧게 잡아야 한다.
- 개발자·운영자의 서버 접속은 SSH 키 인증만 허용한다(비밀번호 로그인 비활성화). 설정은 [02장 2.7·2.8](02-architecture.md#27-네트워크와-주소)에 있다.
