# 10. 로컬 개발·테스트 가이드

> 일부 작성. 개발 순서와 로컬 테스트 자료 요건은 D-114·D-115를 반영했다. DB 실행 방식·Python/uv·배포 기본 방향은 D-116~D-125에서 결정했다. CI 검사 범위·실행 흐름은 D-129로 정했다. CI와 배포 연결은 D-130의 수동 확인 방식이다. 실제 명령·담당자 도구는 작성이 필요하다. 아래 자료 파일은 준비 요구사항이며 현재 생성된 산출물 목록이 아니다.

## 합의된 개발 순서 (D-114)

프론트·백엔드는 준비된 테스트 이미지·클립과 가짜 워커로 실제 API·DB를 통한 서비스 흐름을 먼저 개발한다. 팀장은 후보 탐지·클립 추출·비식별화를 로컬에서 검증하고 Bedrock 요청·응답 처리를 준비한다. 데이터 계약을 먼저 맞추며, 권한 준비 후 작은 샘플로 AWS 기본 연결을 중간 확인한다. 주요 기능 완성 후 배포하여 실제 워커로 전체 흐름과 성능을 검증한다.

로컬 S3·SQS 대체는 로컬 파일 저장·간단한 작업 실행으로 정했다(D-115). 로컬 PostgreSQL은 Docker Compose로 실행한다(D-116). 버전·포트·실행 명령은 후속 작성한다. **CI는 D-129의 가벼운 전체 검사로 진행한다. CI 결과와 배포 연결은 D-130의 수동 확인을 따른다.** 아래 작성 항목을 이미 구현하거나 확정한 것으로 보지 않는다.

## 로컬/AWS 전환 원칙 (D-115)

| 구성 | 파일·작업 전달 | 분석 결과 | 목적 |
|---|---|---|---|
| 로컬 서비스 개발 | 로컬 폴더·가짜 작업 실행기 | 준비된 결과 | 프론트·백엔드 서비스 흐름 |
| 팀장 로컬 비전 개발 | 로컬 영상 직접 입력 | 실제 후보 탐지·비식별화, 필요 시 VLM 임시 응답 | 비전 코드 검증 |
| AWS 통합 검증 | boto3 S3·SQS 및 필요한 AWS 호출 | 실제 워커·Bedrock | 배포 환경 검증 |

- 연결 환경과 분석 방식을 별도로 선택한다. 환경변수 이름은 담당자가 정하며 `APP_ENV=local` 등 이전 대화의 이름은 예시다.
- 공통 API·검증·DB 상태 갱신을 복제하지 않는다. 저장/조회 URL 발급과 작업 전달 등 필요한 경계만 로컬용으로 대체한다.
- 로컬 업로드도 발급된 URL에 파일을 보내고 완료 API를 호출하는 흐름을 유지한다. URL은 로컬 주소이며 AWS 서명 URL의 검증 완료를 뜻하지 않는다. 구체적인 로컬 전용 파일 수신·전달 경로는 팀원 2가 작성한다.
- 로컬 파일은 `raw`와 `masked` 영역을 구분한다. 원본과 파손 사진을 웹 정적 경로로 공개하지 않는다. 사용자에게 제공하는 결과는 마스킹된 테스트 자료뿐이며 소유권·기한 검사 경로를 유지한다.
- 로컬 기본 모드에서는 AWS 자격 증명·GPU EC2 기동·Bedrock 실제 호출이 필요 없어야 한다. 가짜 실행기는 상태를 관찰할 수 있게 짧은 대기 또는 수동 진행을 제공하되, 실제 분석 시간을 기다리지는 않는다. 상세 방식은 담당자가 정한다.

## 로컬 PostgreSQL (D-116)

DB만 Docker Compose로 실행한다. 프론트·백엔드·비전 코드는 각 PC에서 직접 실행한다. 팀원 2가 버전을 고정한 Compose 설정, 로컬 연결 환경변수, 데이터 볼륨, 실행·중지·명시적 테스트 초기화 명령을 작성한다. 컨테이너를 껐다 켜는 동작과 DB 데이터 삭제를 구분한다. 실제 Compose 파일은 아직 작성하지 않았다.

- DB 데이터는 named volume에 둔다. bind mount로 저장소 안에 두지 않는다. 평소 끌 때는 `docker compose down`, 볼륨을 지우는 `down -v`는 테스트 초기화 명령으로만 쓴다. (D-121)
- 👤 팀원 2 결정 필요: 볼륨 이름 고정(`name:`) 여부, 위 명령을 안내하는 실제 명령어. (D-121)

EC2에 백엔드·비전을 컨테이너로 배포할지는 별도 CD 결정이다. 로컬 DB 컨테이너 선택만으로 배포 구성을 바꾸지 않는다.

### 개인별 DB와 변경 적용 (D-117)

- 각자 PC에서 독립 DB·데이터 볼륨·실행 결과 폴더를 사용한다. 테스트 미디어·입력/결과 예시·Compose·초기 데이터 생성 코드·마이그레이션 파일은 공유한다. 자료 공유가 실행 중인 DB 공유를 뜻하지 않는다.
- 백엔드 담당자는 DB 구조 변경을 마이그레이션 파일과 관련 코드로 함께 올린다. 팀원은 `git pull` 후 마이그레이션 적용 명령을 실행한다. pull만으로 DB가 갱신되지 않는다. 컨테이너 내부 수동 수정 대신 적용 이력을 관리한다.
- 최초 준비 순서: DB 실행 → 마이그레이션 적용 → 초기 테스트 데이터 입력 → 백엔드·가짜 워커·프론트 실행. 이후 코드 갱신 시 필요한 마이그레이션을 적용한다.
- **실행 중 생성 파일은 모두 `local_storage/`에만 만든다** (`.gitignore` 등록됨, D-121). `raw/` `masked/` `analysis/`는 S3 버킷 3개를 대신하며 안의 경로는 04장 4.9의 S3 키를 그대로 쓴다. 그 밖의 실행 결과는 `local_storage/scratch/<폴더명>/`에 둔다.
- 테스트 초기화는 별도 명시적 명령으로 수행하며 마이그레이션 실행 때 분석 상태·고정 결과를 자동 삭제하지 않는다. 공통 테스트 원본과 AWS 데이터는 초기화 대상이 아니다.
- 팀원 2가 도구 선택 후 최초 실행·변경 적용·데이터 입력·초기화의 실제 명령을 작성한다. 마이그레이션 도구와 명령은 👤 팀원 2 결정 필요 (U-36). PostgreSQL 버전 변경은 기존 볼륨 호환성·이전 방법을 별도로 확인한다.

## 로컬 테스트 자료 명세

### 1. 자료의 구분과 최소 준비물

파일명은 준비용 권장 이름이며 공개 API 필드가 아니다. 자료는 저장소 루트 `fixtures/`에 두고 GitHub로 공유한다(D-122). `fixtures/` 안의 `.mp4`만 `.gitignore` 예외다. 파일 하나 20MB 이하, 전체 100MB 이하, 개인정보 없는 합성·샘플 자료만 넣고, 자주 교체하지 않는다. `fixtures/` 안의 세부 폴더는 자료 준비 담당이 정하되 `data`·`datasets`·`runs`·`outputs` 이름은 쓰지 않는다(`.gitignore`에 걸림). 자료는 하나의 로컬 테스트 자료 묶음으로 관리하고, 실행 중 생성되는 파일·DB 데이터와 분리한다.

| 준비물 | 최소 구성 | 들어갈 내용·조건 | 준비 담당 |
|---|---|---|---|
| `source.mp4` | 짧은 정상 영상 1개 | H.264 MP4, 첫 프레임에 선택 가능한 차량. 실제 width·height·duration을 기록. 긴 CCTV 전체를 넣을 필요 없음 | 팀장 제공, 팀원 2 연결 |
| `still-masked.jpg` | 정지 이미지 1장 | source의 첫 프레임과 같은 원본 해상도, 차량 위치 일치. 식별정보가 있으면 비식별화. 사용자가 선택할 차량을 알아볼 수 있어야 함 | 팀장 |
| `detections.json` | 탐지 결과 1세트 | 실제 이미지에 맞는 `det_id`, `bbox`, `conf`. bbox는 원본 픽셀 좌표. 별도 빈 배열 변형으로 차량 탐지 0건 검증 | 팀장, 팀원 2 형식 확인 |
| `input-examples.json` | 정상 2종·비정상 변형 | schema_version 5, 보임/안 보임 각각의 차량 선택·damage_bbox·floor_corners 4점·damage_edges 예시. 설명·사진 포함/생략 사례 | 팀장 좌표, 팀원 2 검증값 |
| `damage-photo.jpg` | 선택 입력 사진 1장 | 허용된 정상 이미지. 사진 없이 진행하는 사례도 필수. 다른 확장자·초과 크기는 검증 단계에서 추가 | 팀장 또는 팀원 1 |
| `clips/*.mp4` | 재생 가능한 후보 클립 2~3개 | H.264 MP4, 마스킹된 결과, 영상 경계 내 최대 30초. 대응 원본 시간 구간을 기록. 정상·시작/끝 경계 예시 준비 | 팀장 |
| `candidate-results.json` | 정상 목록·파싱 실패 목록 | 아래 결과 계약에 맞는 후보/클립 메타데이터. 후보 0건·소수·다중 묶음은 같은 기본 자료의 시나리오 변형 | 팀장 내용, 팀원 2 적재 |
| `vlm-responses.json` | 정상·형식 오류·호출 오류 사례 | 합의된 VLM 출력 계약에 맞는 임시 응답. 호출 오류는 응답 JSON과 구분해 예외로 주입. 점수는 테스트용이며 AI 성능 근거가 아님 | 팀장 |
| 로컬 DB 초기 데이터 | 소유자가 다른 테스트 계정 2개 | 로그인·소유권·업로드 링크 검증용. 초기에는 작업이 없는 계정으로 실제 업로드 흐름 시작. 비밀값은 저장소에 넣지 않음 | 팀원 2 |
| 실패·만료 시나리오 정의 | 아래 표 | 어느 단계에서 성공/실패하는지, 기대 상태·화면·보존 결과를 기록. 실제 파일을 모두 복제할 필요 없음 | 팀원 2, 팀원 1 확인 |

**최소 착수 조건**: 정상 영상 1개, 대응 정지 이미지·탐지 좌표·입력 예시, 재생 클립 2~3개, 정상 후보 메타데이터, 로컬 계정부터 준비한다. 처음부터 모든 예외용 미디어를 만들지 않는다. 자료 준비 중에는 식별정보가 없는 합성·샘플 자료를 사용할 수 있지만 실제 AI 평가 자료와 혼동하지 않는다.

### 2. 결과 자료의 계약

- 원본 메타데이터: 자료 식별명, 파일 상대경로, 실제 해상도·길이, 녹화 시작 시각(선택). `video_id`·`job_id`·`still_frame_id` 등 DB ID는 업로드/적재 시 생성된 값으로 연결하며 고정 숫자를 복사하지 않는다.
- 정지 장면: `t_sec=0`, 이미지 상대경로, `detections`. `det_id`는 그 이미지 안에서 유일하다.
- 입력 예시: `vehicle.det_id`가 실제 탐지 항목을 가리키게 한다. 보임의 damage_bbox는 선택 차량 내부, 안 보임은 화면 내부다. floor_corners는 정해진 순서의 4개 원본 좌표, damage_edges는 1개 또는 이웃한 2개다. 미정 크기 제한을 새로 만들지 않는다.
- 후보: 04장의 `judged_at_sec`, `list_kind`, `rank`, VLM 결과와 클립 연결에 필요한 값을 사용한다. 미정인 rule_name·병합 규칙은 테스트용임을 구분하고 알고리즘 결정으로 취급하지 않는다.
- 시간: `incident_at_sec = judged_at_sec + 5`, `start_sec = max(0, judged_at_sec - 10)`, `end_sec = min(duration_sec, judged_at_sec + 20)`를 따른다. 정상 샘플은 사건 지점이 원본 범위 안에 있도록 고른다. 원본 끝 5초 이내 후보의 사건 지점 처리처럼 아직 불명확한 경계는 별도 명세 확인 대상으로 남긴다.
- 클립: 파일 경로·start_sec·end_sec·crop_bbox가 실제 샘플과 맞아야 한다. 성공 결과만 재생 파일과 연결하고 열람 불가 결과에는 정상 재생 URL을 만들지 않는다.
- 다중 묶음: 정상 후보 25건과 파싱 실패 후보 3건의 테스트 변형을 준비한다. 정상 목록 10/10/5, 파싱 실패 목록 3건으로 탭·이전·다음·세 번째 묶음 준비를 확인한다. UI 흐름 테스트에서는 소수 미디어를 여러 가짜 후보에 재사용해도 되지만, 시나리오에 중복 미디어임을 명시하고 클립 ID·저장 키는 구분한다. 이를 실제 탐지·시간 정확성 평가에 쓰지 않는다.
- 파싱 실패 목록은 VLM 점수가 없는 후보이며 클립 생성 실패와 다르다. D-109의 열람 불가와 D-112의 사용자 재시도 관련 새 필드·오류 코드는 아직 상세 계약 작성 대상이다. 자료만의 임의 필드로 서비스 계약을 확정하지 않는다.
- API 응답 전체를 정적 JSON으로 반환해 DB 로직을 우회하지 않는다. 가짜 워커 결과를 적재한 뒤 API가 현재 상태·소유권·고정·남은 수·URL을 계산한다.

### 3. 개발 단계별 확인 시나리오

| 순서 | 자료/상황 | 확인할 실제 서비스 동작 |
|---|---|---|
| 1 | 정상 영상·후보 3건 | 링크 발급→업로드→정지 장면→입력 저장→후보 재생→다중 고정→종료. 고정 0개 종료는 서버에서 거절 |
| 2 | 탐지 차량 빈 배열, 본인 차 없는 장면 | 입력을 억지로 진행하지 않고 재업로드 안내 |
| 3 | 잘못된 det_id·좌표·네 모서리 누락·비인접 변, 사진 포함/생략 | 실제 API 입력 검증, 잘못된 입력은 저장하지 않음. 저장된 입력 재수정 차단 |
| 4 | 후보 0건 | “후보가 탐지되지 않음”과 “사건 없음”을 구분 |
| 5 | 정상 25건 + 파싱 실패 3건 | 두 목록의 개별 진행·이전 보기·미리 준비·마지막 확인창·전체 완료 조건 |
| 6 | A 확인 도중 B 업로드 | A 결과·고정·확인 진행 유지, 화면 이탈로 종료/못 찾음 처리하지 않음. B의 대기는 허용 |
| 7 | 일부 클립 실패→2/3번째 자동 시도 성공, 최종 실패, 전부 실패 | D-109의 자동 최대 3회·열람 불가 수·정상 결과 제공. 못 본 후보를 못 찾음 처리하지 않음 |

### 4. 준비·실행·정리 책임

- 팀장: 서로 대응하는 미디어·좌표·후보 메타데이터와 임시 VLM 응답을 제공한다. 실제 탐지·비식별화 결과가 준비되면 같은 계약으로 교체한다.
- 팀원 2: 로컬 저장/전달 연결, 가짜 워커, DB 초기화·자료 적재·시나리오 선택 방법을 작성한다. 실행 명령·환경변수·작업별 저장 경로를 이 장에 추가한다. 특정 사용자 입력을 몰래 바꿔 fixture와 맞추지 않는다.
- 팀원 1: 자료로 화면을 연결하고 상태·재생·좌표 변환·실패·재시도·기한 문구를 확인한다. 프론트에서 fixture를 직접 읽어 API를 건너뛰지 않는다.
- 시나리오마다 시작 조건·실행 조작·기대 결과·가짜인 부분을 적는다. 결과 파일은 실행별 영상/작업 키로 분리해 이전 실행의 고정 결과를 덮어쓰지 않는다.
- 초기화는 로컬 테스트 DB·생성 파일만 대상으로 한다. 원본 fixture와 실제 AWS 자료는 지우지 않는다. 구체 명령은 로컬 DB 실행 방식 결정 후 작성한다.
- 공유 자료에는 출처·사용 가능 범위·샘플/실제 구분을 남긴다. 실제 개인정보가 있는 CCTV와 큰 원본을 Git에 커밋하지 않는다. 공유 테스트 자료는 `fixtures/`로 전달한다(D-122).

### 5. 완료 기준과 남은 결정

준비된 미디어가 재생되고 좌표가 일치하며, 로컬 모드에서 AWS 없이 정상 서비스 흐름을 완료할 수 있어야 한다. 가짜 결과와 실제 API/DB 처리를 구분해 기록하고, 정상 연결 이후 구현된 기능의 관련 시나리오를 검증한다. 실제 AWS 서명·IAM·CORS·SQS 전달/복구·GPU 기동 및 AI 성능은 별도 통합 검증이다.

**남은 결정**: PostgreSQL 버전·연결 설정(👤 팀원 2), 로컬 실행기 구동·시나리오 선택 명령, 환경변수 이름(👤 각 폴더 담당자, 방식은 D-123), Python 외 패키지·도구 버전(Python 3.12·uv는 D-119). D-109·D-112의 API/DB 상세 계약도 담당자 보완이 필요하다. CI 범위는 D-129를 따르고 구체 명령은 담당자가 작성한다. 배포 기본 방향은 D-124·D-125를 따르며 CI 결과와 배포 연결은 D-130을 따른다.

## GitHub Actions CI 실행 방식 (D-129)

### 로컬 개발부터 CI 결과 확인까지

1. 각 담당자는 기능과 필요한 테스트 코드를 함께 작성하고 로컬에서 관련 검사를 실행한다. 모든 함수에 테스트를 붙이지 않고 상태 변경·결과 조회 등 중요한 동작을 검증한다. 공통 DB 구조·작업 메시지를 바꾸면 영향을 받는 담당자와 함께 확인한다.
2. 기존 D-120대로 `main`에 직접 푸시한다. **CI는 푸시가 완료된 뒤 실행되며, CI 통과가 푸시의 선행 조건은 아니다.**
3. GitHub Actions의 GitHub 제공 실행용 컴퓨터(runner)가 해당 푸시의 코드를 내려받는다. 각 검사에 필요한 Python·uv 또는 Flutter와 의존성을 설치한 뒤 지정한 명령을 실행한다. 우리 EC2나 개발자 PC에서 실행하는 검사가 아니다.
4. 변경한 분야만 검사하지 않고 아래 세 분야의 가벼운 검사를 모두 실행한다. 저장소의 모든 테스트 파일을 Actions가 알아서 실행하는 것은 아니다. 워크플로에 지정한 명령과 테스트 도구의 수집 범위에 따라 실행한다.
5. Actions 화면에서 성공·실패 및 실행 로그를 확인한다. 필수 검사 모두 성공해야 CI 성공이다. 실패하면 담당자가 원인을 수정하고 다시 푸시한다.

`main` 직접 푸시 방식에서는 CI에 실패한 코드도 이미 저장소에 들어가 있다. 실패가 푸시를 취소하거나 코드를 자동으로 되돌리지 않는다. 검사 통과를 `main` 반영의 필수 조건으로 강제하려면 PR·브랜치 보호가 필요하지만 이번 결정에서는 도입하지 않는다.

### 자동 검사 범위

| 분야 | CI에서 실행할 검사 | 작성 담당 |
|---|---|---|
| 백엔드 | 의존성 설치, 핵심 동작 테스트. 가짜 워커와 실제 테스트 DB를 이용한 접수 → 상태 변경 → 결과 조회 흐름 | 팀원 2 |
| 프론트 | 정적 검사와 Flutter Web 빌드. 기능에 필요한 테스트를 작성한 경우 해당 테스트도 실행 | 팀원 1 |
| 비전 워커 | Python 문법 검사와 GPU·AWS 없이 실행 가능한 기본 로직 테스트(예: 후보 정렬). 실제 모델·가중치가 필요한 추론은 제외 | 팀장 |

실제 AWS 호출·GPU 모델 추론·영상 전체 분석·성능 평가는 CI에서 실행하지 않는다. 실제 추론은 로컬 또는 GPU EC2, AWS 연동과 전체 서비스 흐름은 실제 배포 환경에서 별도 검증한다. CI 성공을 실제 환경의 정상 동작이나 AI 품질 검증 완료로 간주하지 않는다.

### 테스트 DB와 실행 설정

- DB가 필요한 검사에는 CI 실행 안에서 임시 PostgreSQL을 준비한다. 실제 서비스 DB나 팀원 로컬 DB에 연결하지 않는다.
- 테스트 DB에 마이그레이션과 필요한 테스트 데이터를 적용한 뒤 검사를 실행한다. 실행별로 독립된 데이터를 사용하며 다음 CI 실행에 결과를 보존할 필요는 없다.
- 팀원 2가 `.github/workflows/ci.yml` 같은 워크플로 파일에 `main` 푸시 트리거, 코드 내려받기, 환경·의존성 설치, 임시 DB 준비, 분야별 검사 명령을 설정한다. 파일명과 작업 분할·도구·구체 명령은 담당자가 정한다.
- 팀원 1과 팀장은 자기 분야 테스트 및 필요한 의존성·실행 명령을 팀원 2에게 전달한다. 로컬과 CI에서 같은 검사를 재현할 수 있도록 실제 명령을 이 장에 보완한다.
- 테스트는 기능 구현과 함께 추가한다. 현재 문서는 요구사항이며 워크플로·테스트가 구현되거나 통과했다는 뜻이 아니다.

### 배포와의 관계

D-130에 따라 사람이 CI 성공을 확인한 뒤 배포한다.

1. 팀원들에게 배포·시연 준비 중 `main` 푸시를 잠시 중단하도록 알린다.
2. 최신 `main` 커밋과 해당 커밋의 CI 전체 성공을 확인한다. 실패·진행 중이면 배포를 진행하지 않는다. 새 커밋이 올라오면 그 커밋의 CI를 다시 확인한다.
3. 서버를 켜거나 재부팅하고, 켜진 백엔드는 Actions 배포 버튼으로 갱신한다(D-124·D-125). GPU 최초 배포는 이 장의 `.env` 수동 작성 절차(D-128)를 함께 수행한다.
4. 워커 준비와 실제 업로드 → 분석 → 결과 조회 흐름을 확인한 뒤 푸시 중단을 해제한다. 시연 중에는 해제를 시연 종료 후로 미룬다.

CI 성공 여부를 자동으로 조회해 배포를 막는 기능이나 CI 성공 직후 자동 배포는 추가하지 않는다. 부팅 시 최신 `main` 갱신도 유지하므로 사람이 확인을 빠뜨리거나 준비 중 새 푸시가 있으면 미검증 코드가 실행될 수 있다. 이 절차는 시스템 차단 보장이 아니다.

검수 기준: `main` 푸시 후 세 분야 검사가 실행되고, 테스트 실패가 CI 실패로 표시되며 로그로 원인을 확인할 수 있어야 한다. 테스트 DB가 실제 DB와 분리되고 GPU·AWS 없이 지정 검사가 실행되어야 한다. 구체 워크플로 구현 후 확인한다.

실행 개념 참고: [GitHub Actions 공식 문서](https://docs.github.com/en/actions/get-started/understanding-github-actions).

## 배포 실패와 최종 시연 검증 (D-126)

갱신·설치·필수 설정·DB 변경·서비스 시작 실패는 오류를 남기고 중단한다. 이전 코드 자동 대체는 하지 않으며 담당자가 수정 후 재배포한다. 자동 롤백이나 별도 운영 플랫폼은 추가하지 않는다. 기존 분석 재시도 정책과는 별개다.

최종 시연 구성에서 실제 전체 흐름과 서버 재기동, 합의된 재시도·보류·새 영상 접수를 확인하고 결함을 수정한 뒤 촬영·현장 시연에 사용한다. 상세 구현·명령은 담당자에게 맡기고, 필수 연결 누락과 정상 흐름 오류를 먼저 해결한다.


## GPU 최초 배포 순서(D-128)

GPU `.env`는 최초에 직접 접속해 작성한다. Parameter Store는 사용하지 않는다. 이후 배포 순서를 안내할 때 아래 수동 설정 단계를 포함한다.

1. 팀원 2가 백엔드 PostgreSQL과 GPU용 DB 계정·연결 정보를 준비한다. GPU 접속용 키와 지정 개발자 IP의 임시 SSH 허용 권한도 확인한다.
2. Terraform으로 GPU 인스턴스를 생성한다. user data는 코드·의존성·모델 설치와 자동 실행 서비스 등록까지 수행한다. 비밀값은 넣지 않고, 최초 `.env` 작성 전에는 워커를 시작하지 않는다.
3. GPU 보안 그룹에서 개발자 공인 IP /32의 SSH(22)만 임시 허용하고 키로 접속한다.
4. `pipeline/.env`에 실제 DB 연결 정보와 필요한 워커 설정을 작성한다. 워커 서비스 계정 소유·권한 600으로 저장한다. 비밀번호는 Git·Terraform·user data·로그에 남기지 않는다.
5. 워커를 시작해 DB 연결과 모델 로딩, 작업 수신 준비를 확인한다. 실패하면 오류 로그를 보고 수정한다(D-126).
6. SSH 접속을 종료하고 임시 인바운드 규칙을 제거한다.

일반 재부팅·코드 갱신에서는 기존 `.env`를 보존해 사용한다. 인스턴스를 새로 만들거나 DB 비밀번호·필수 설정을 변경하면 수동 설정을 다시 수행한다. `.env` 누락·잘못된 설정은 로그를 남기고 시작을 중단한다.

오류 발생 시에도 개발자 IP에만 임시 SSH를 열어 설치 로그(`/var/log/cloud-init-output.log`)와 워커 서비스 로그를 확인한 뒤 닫는다. 구체적인 서비스명·로그 조회 명령은 담당자가 구현 후 이 절에 추가한다. 별도 로그 수집 인프라는 만들지 않는다.
