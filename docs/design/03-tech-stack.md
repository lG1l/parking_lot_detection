## 3.2 스택별 주의사항

### Flutter Web

- `video_player` 패키지는 브라우저의 `<video>` 태그로 영상을 재생한다. 브라우저가 재생할 수 있는 형식이어야 하므로 후보 클립은 **H.264 코덱 MP4**로 만든다. (06장 조건)
- 기본 주소 형식이 `/#/경로`라서 새로고침해도 404가 나지 않는다.
- 로컬에서 `flutter run -d chrome`으로 개발하면 프론트와 API의 포트가 달라 CORS 설정이 필요하다. CORS는 출처(주소 + 포트)가 다른 서버로의 요청을 브라우저가 막는 규칙이다. 배포 환경은 같은 출처라 필요 없다. (U-03)
- 단, 브라우저에서 S3로 직접 업로드할 때는 출처가 달라 **S3 버킷에 CORS 설정**이 필요하다. 데모는 허용 출처 `*`, 메서드 `PUT`만 허용한다. (D-18, D-22)
- 첫 로딩이 수 MB로 무겁지만 데모에는 문제없다.
- 키보드 조작(PRD 4장 접근성)은 Focus·Shortcuts 위젯으로 따로 구현해야 한다.

### YOLO (Ultralytics 라이브러리를 쓸 경우)

- Ultralytics 라이브러리는 AGPL-3.0 라이선스다. 학교 프로젝트에는 문제없지만, 실서비스화할 때는 라이선스를 다시 검토해야 한다.
- ByteTrack을 추적기로 내장 지원한다.

### Bedrock VLM

- 영상을 직접 입력받는 모델과 이미지(프레임) 여러 장만 받는 모델이 있다. 입력 방식은 모델 선택과 함께 정한다. 🚧 (U-08)
- ⚠️ 계정의 분당 요청·토큰 한도를 확인해야 한다. 동시 호출 수가 이 한도에 묶인다. 한도를 넘으면 `ThrottlingException`이 나므로 대기 시간을 늘려 가며 재시도한다. (D-06, D-19)

### PostgreSQL

- 설치 절차와 자주 하는 실수는 [11장 D-17](11-decisions.md#d-17-db는-백엔드-ec2에-postgresql을-직접-설치한다)에 있다. 요약: `listen_addresses`와 `pg_hba.conf`를 고치지 않으면 GPU 워커가 접속하지 못한다. 5432 포트는 GPU EC2 보안 그룹에만 연다.
- 접속 주소(연결 문자열)와 비밀번호는 환경변수로 받는다. 저장소에 커밋하지 않는다.
- 백엔드 EC2를 삭제하면 데이터가 사라진다. 중지·시작은 괜찮다.

### SQS

- 반드시 지킬 규칙 6가지(가시성 제한 시간 연장, 중복 전달 대비, 처리 후 삭제, 보관 기간 14일, 실패 처리, 메시지에는 작업 ID만)는 [11장 D-16](11-decisions.md#d-16-작업-전달은-sqs-작업-상태는-db)에 있다.
- 워커는 긴 폴링(`WaitTimeSeconds=20`)으로 꺼낸다. 빈 응답이 줄어 요청 수와 비용이 준다.
- 로컬 개발에서 SQS를 대신할 방법은 🚧 (U-03, 10장)

## 3.3 저장소 구조 (초안)

모노레포(저장소 하나)로 관리한다. 🚧 팀 확인 필요 (U-12)

```
parking_lot_detection/
├── frontend/            Flutter 앱                                     (팀원 1)
├── backend/             FastAPI API 서버                               (팀원 2)
├── pipeline/            분석 파이프라인 Python 패키지                    (팀장)
│                        객체탐지·추적, 룰, VLM 점수, 비식별화, 원본 시간 계산
├── evaluation/          KPI 평가 스크립트 (pipeline 패키지를 가져다 씀)   (팀장)
├── infra/               Terraform 코드                                 (팀원 2)
├── .github/workflows/   CI/CD 워크플로                                  (팀원 2)
└── docs/                PRD, 설계 문서
```

- `pipeline/`을 별도 패키지로 두는 이유: GPU 워커와 평가 스크립트가 **같은 코드**를 쓰게 하기 위해서다. 평가와 서비스가 서로 다른 코드를 쓰면 KPI 수치가 서비스 성능을 대변하지 못한다.
- 백엔드는 `pipeline/`을 쓰지 않는다. 분석을 하지 않기 때문이다. (D-14)
- GPU 워커 실행 진입점(SQS에서 작업을 꺼내 `pipeline`을 호출하고, 자동 꺼짐을 처리하는 코드)을 `pipeline/` 안에 둘지, 별도 폴더에 둘지는 🚧 (U-12)
- 각 폴더 안의 구조는 담당자가 해당 장(04~09장)을 작성할 때 정한다.
