## D-01. 영상 분석에 GPU를 쓴다

- **날짜**: 2026-09-14
- **결정**: 객체탐지(1단계 분석)와 비식별화는 GPU 인스턴스에서 실행한다.

**배경**

처음에는 "24시간 영상을 룰베이스로 탐지하는 게 무겁고, 비식별화는 후보 구간만 하니 가볍다"고 생각했다. 실제로 무거운 부분은 다음과 같다.

| 작업 | 무거운 정도 | 이유 | GPU 필요 |
|---|---|---|---|
| 객체탐지 (영상 전체) | 가장 무거움 | 샘플링한 모든 프레임에 신경망을 돌린다 | 필요 |
| 추적 (ByteTrack) | 가벼움 | 탐지 결과(좌표)를 이어 붙이는 계산 | 불필요 |
| 룰 판정 | 가벼움 | 트랙 좌표와 파손 부위·인접 영역의 위치 비교 | 불필요 |
| VLM 점수 | 외부 호출 | Bedrock이 계산한다. 우리 서버는 기다리기만 한다 | 불필요 |
| 비식별화 (후보 클립) | 중간 | 구간은 짧지만, 보여줄 모든 프레임을 빠짐없이 탐지해야 한다 | 있으면 빠름 |

즉 "룰베이스 탐지"의 무게는 룰이 아니라 룰에 넘길 **객체탐지**에서 나온다. 룰은 탐지 결과가 있어야 동작한다.

**처리 시간 추정** (24시간 영상, 샘플링 5fps = 약 43만 2천 프레임, 소형 YOLO 기준, 추정)

| 구성 | 대략 처리 속도 | 대략 처리 시간 |
|---|---|---|
| CPU 1대 | 초당 약 10프레임 | 약 12시간 |
| CPU 24대 (1시간 청크 × 24, 병렬) | 대당 초당 약 10프레임 | 약 30분 (+ 인스턴스 24대 준비) |
| GPU(T4) 1대 | 초당 약 200프레임 | 약 36분 |

- GPU 1대로 CPU 24대 병렬과 비슷한 시간을 낼 수 있다. 인스턴스 24대를 띄우고 관리하는 부담이 없다.
- GPU를 쓰면 시간을 더 압축할 수 있다. 다만 영상 디코딩(CPU 작업)이 병목이 될 수 있어 실측이 필요하다. (D-02)
- 샘플링 fps가 처리 시간에 가장 큰 영향을 준다. 5fps를 2fps로 줄이면 시간이 절반 이하가 되지만, 빠른 접촉을 놓칠 위험(재현율 하락)이 커진다. (U-06)

**버린 대안**

| 대안 | 버린 이유 |
|---|---|
| CPU만 사용 | 24시간 영상 1개에 약 12시간(추정). 데모 범위를 넘는다 |
| CPU 인스턴스 여러 대 병렬 | 시간은 비슷하게 줄지만 인스턴스 수만큼 권한·한도·관리 부담이 생긴다. GPU 1대가 더 단순하다 |

**적용 위치**: 02장 2.2, 2.9 / 03장 3.1

## D-02. GPU EC2 1대에서 청크를 여러 프로세스로 처리한다

- **날짜**: 2026-09-14
- **결정**: GPU EC2 1대를 쓰고, 그 안에서 청크를 여러 프로세스로 동시에 처리한다. 프로세스 수는 설정값으로 두고 실측해 정한다(추정 2~4).

**이유**

- 테스트와 데모는 짧은 영상 여러 개로 한다. GPU 1대로 충분하다.
- GPU 인스턴스는 멘토 승인과 vCPU 한도가 필요하다. 1대가 승인받기 쉽다.

**알아둘 점: 프로세스를 늘려도 속도가 그만큼 늘지 않는다**

- 프로세스 여러 개가 GPU 1개를 나눠 쓴다. GPU가 이미 100% 일하고 있으면 프로세스를 늘려도 빨라지지 않는다.
- 프로세스를 여러 개 두는 진짜 목적은 **GPU를 쉬지 않게 하는 것**이다. 프로세스 1개로 순서대로 처리하면, 영상을 디코딩(CPU)하는 동안 GPU가 논다. 프로세스가 여러 개면 한 프로세스가 디코딩할 때 다른 프로세스가 GPU를 쓴다.
- 너무 많이 두면 GPU 메모리가 부족하거나 CPU 디코딩이 병목이 된다. 그래서 2~4개부터 실측한다.
- 디코딩이 병목이면 GPU 하드웨어 디코딩(NVDEC)을 검토한다. (06장)

**버린 대안**

| 대안 | 버린 이유 |
|---|---|
| 프로세스 1개로 청크를 순서대로 처리 | 디코딩하는 동안 GPU가 쉰다 |
| 처음부터 GPU EC2 여러 대 | 짧은 테스트 영상에는 과하다. 권한·한도·비용 부담이 크다. 확장 방향으로만 기록한다 (D-03) |

**적용 위치**: 01장 1.6 / 02장 2.6

## D-03. 청크 처리를 독립 단위로 만들고, 확장은 방향만 기록한다

- **날짜**: 2026-09-14
- **상태**: 확정. 단, "SQS를 지금 쓰지 않는다"는 부분은 2026-09-15 [D-16](#d-16-작업-전달은-sqs-작업-상태는-db)으로 바뀌었다. Auto Scaling을 구현하지 않는 것은 그대로다. 아래 원래 기록은 지우지 않는다.
- **결정**
  - 청크 하나를 처리하는 코드는 다른 청크와 상관없이 실행되는 독립 단위로 만든다. 입력은 원본 영상 위치와 청크의 원본 시간 기준 시작·끝, 출력은 청크의 트랙 결과 파일이다.
  - 사용자가 몰릴 때의 확장(GPU EC2 여러 대 × 청크 여러 프로세스)은 설계 문서에 방향만 적고 지금 구현하지 않는다.

**이유**

- 청크 처리가 독립 단위면, GPU EC2를 여러 대로 늘릴 때 "청크를 어느 GPU에 나눠줄지"만 바꾸면 된다. 청크 처리 코드는 그대로다.
- 지금 확장 구조(작업 큐, 오토스케일링)까지 만들면 데모에 필요 없는 작업이 늘어난다.

**버린 대안**

| 대안 | 버린 이유 |
|---|---|
| 지금 SQS + Auto Scaling까지 구현 | 데모 범위를 넘는다. 추가 권한이 필요하다 |
| 확장을 고려하지 않고 영상 1개를 통째로 처리 | 나중에 확장하려면 처리 코드를 다시 짜야 한다 |

**질문: "SQS는 비동기 처리와 성능에 필요한가? 반응속도·트래픽 요구사항을 쓰면 필요해지나?"** (2026-09-15)

- SQS는 작업을 넣고 꺼내는 AWS 관리형 **작업 대기열(큐)**이다.
- **비동기 처리에 SQS가 꼭 필요하지는 않다.** 비동기는 "요청을 받자마자 응답하고, 실제 작업은 나중에 다른 곳에서 처리하는 구조"를 말한다. DB에 작업 표를 두고 워커가 가져가게 해도 똑같이 비동기다.
- **SQS가 처리 속도를 올리지는 않는다.** 처리 속도는 작업하는 GPU가 몇 대인지로 정해진다. SQS는 작업을 전달만 한다.
- SQS가 제값을 하는 경우:

| 상황 | SQS가 주는 것 | 우리 시스템 |
|---|---|---|
| GPU 워커가 여러 대이고 같은 작업을 두 번 가져가면 안 됨 | 한 작업을 한 워커에만 전달, 실패하면 자동으로 다시 전달 | GPU 1대. DB 작업 표로 충분하다 |
| 대기 중인 작업 수를 보고 GPU를 자동으로 늘리고 줄임 (Auto Scaling) | 대기 작업 수 지표를 기본 제공 | 자동 확장 없음 |
| 작업이 한꺼번에 몰림 | 작업을 잃지 않고 쌓아 두었다가 차례로 처리 | DB 작업 표도 쌓아 둘 수 있다 |
| 계속 실패하는 작업을 따로 모으기 | 실패 작업 전용 대기열(DLQ) 기본 제공 | 데모 범위 밖 |

- **반응속도 요구사항**(예: "API는 1초 안에 응답")은 SQS와 관계가 적다. 업로드 API가 무거운 분석을 기다리지 않고 바로 응답하면 되는데, 이것은 DB 작업 표로도 된다.
- **트래픽 요구사항**을 "동시 사용자 N명일 때 분석 대기 M분 이내 → GPU를 자동으로 늘린다"처럼 쓰면, 그때 SQS + Auto Scaling이 자연스러운 선택이 된다. 요구사항 수치가 GPU 여러 대를 필요로 하는지가 기준이다.
- 결론: 현재 범위(GPU 1대, 데모)에서는 필요 없다. 02장 2.10 확장 방향에 기록한다.
- **이후 변경 (2026-09-15)**: 위 판단 자체(SQS가 필수는 아니다)는 그대로 맞다. 다만 데모 규모에서 무료 범위이고, 권한 요청에 문제가 없고, GPU를 켜고 끄는 방식(D-15)과 잘 맞고, 발표의 확장 설명에 도움이 되어 SQS를 채택했다. → [D-16](#d-16-작업-전달은-sqs-작업-상태는-db)

**적용 위치**: 02장 2.6, 2.10

## D-04. 후보 선별은 객체탐지 + 추적 + 룰로 한다

- **날짜**: 2026-09-14
- **결정**: 영상 전체를 YOLO 계열로 객체탐지하고, ByteTrack으로 추적해 트랙을 만들고, 트랙에 룰을 적용해 후보를 고른다.

**배경: "공간좌표를 입력받고 ByteTrack으로 그 영역의 움직임을 감지하면 되지 않나?"**

- ByteTrack은 스스로 물체를 찾지 못한다. 매 프레임 객체탐지 모델이 준 bbox를 이어 붙여 "같은 물체"로 묶어 주는 **추적기**다. 그래서 ByteTrack을 쓰려면 객체탐지가 먼저 있어야 한다.
- 탐지 없이 "영역 안의 픽셀 변화"만 보는 방식은 **움직임 감지**(예: OpenCV의 배경 차분 MOG2)라고 한다.

| 방식 | 장점 | 단점 |
|---|---|---|
| 객체탐지 + 추적 + 룰 (선택) | 차·사람을 구분한다. 어떤 물체가 얼마나 가까이 왔는지 알 수 있다. 룰(PRD 3.3)을 적용할 수 있다 | GPU가 필요하다 (D-01) |
| 움직임 감지만 사용 | 가볍다. GPU가 필요 없다 | 조명 변화·그림자·비·헤드라이트에도 반응해 오탐이 많다. 무엇이 움직였는지 모른다. 멈춰 있는 차의 접촉은 놓칠 수 있다 |

- 움직임 감지는 주 방식으로는 부적합하다. 다만 "아무 움직임도 없는 구간은 탐지를 건너뛰는" **사전 필터**로 쓰면 처리 시간을 줄일 수 있다. 도입 여부는 🚧 (U-07)

**적용 위치**: 01장 1.5 / 03장 3.1 / 06장

## D-05. 업로드와 확인을 분리하고, 분석을 두 단계로 나눈다

- **날짜**: 2026-09-14
- **결정**
  - 관리실에서 관리자가 사용자 계정으로 영상을 업로드하면 분석이 백그라운드에서 돌아간다. 사용자는 나중에 집이나 다른 장소에서 접속해 결과를 확인한다.
  - 분석을 두 단계로 나눈다.
    - 1단계(업로드 직후 자동): 청크 분할, 객체탐지 + 추적, 트랙 저장, 정지 장면 비식별화
    - 2단계(사용자 입력 후): 룰 적용, 후보별 VLM 점수, 정렬, 상위 10개 후보 클립 비식별화
  - 완료 알림(이메일·문자)은 보내지 않는다. 로그인하면 화면에 분석 상태를 보여준다.

**배경**

- 사용자가 결과를 기다리는 시간(병목)을 줄이기 위해 업로드와 확인을 분리하자는 제안이 나왔다.
- 그런데 후보 선별의 룰은 사용자의 차량·파손 부위 입력이 있어야 돌 수 있다. 입력 전에 분석을 "다" 끝내 둘 수는 없다.
- 해결: 가장 무거운 객체탐지·추적은 누구의 차량인지 몰라도 된다. 이것만 먼저 해 두면, 입력 뒤에는 가벼운 작업(룰, VLM, 짧은 클립 비식별화)만 남는다.

**VLM이 오래 걸리는가?**

- VLM 점수는 Bedrock이 계산하므로 우리 GPU를 쓰지 않는다. 후보마다 호출하므로 전체 시간은 대략 "후보 수 × 1회 호출 시간 ÷ 동시 호출 수"다.
- 후보끼리 독립이라 동시에 보낼 수 있어서, 후보가 수십 개여도 수 분 안에 끝낼 수 있다. 제약은 Bedrock 계정 한도와 비용이다. (D-06)

**버린 대안**

| 대안 | 버린 이유 |
|---|---|
| 사용자가 입력한 뒤 전체 분석 시작 | 입력 뒤 수십 분을 기다려야 한다 |
| 관리실에서 사용자가 차량·파손 부위까지 입력하고 분석 완료를 기다림 | 사용자가 관리실에 오래 머물러야 한다 |
| 완료 시 이메일 알림 (SES) | 추가 권한이 필요하고 데모에 꼭 필요하지 않다 |

**적용 위치**: PRD 4장 User Flow 1단계 / 01장 1.5 / 02장 2.5 / 04장 / 07장

**이유**

**질문: "S3 정적 웹호스팅을 하면 그것 때문에 S3가 필요한 거지?"**

- 아니다. 정적 웹호스팅과 무관하게 **영상 저장 때문에 S3가 필요하다.** 정적 웹호스팅은 S3의 별도 용도이고, 이 프로젝트에서는 쓰지 않기로 했다. (D-11)

## D-10. EC2를 백엔드(CPU)와 GPU 2대로 나눈다

- **날짜**: 2026-09-15
- **결정**: 백엔드 EC2(CPU)에서 웹·API·DB를 실행하고, GPU EC2는 분석이 필요할 때 백엔드가 켠다.

**배경: "원래 1대 아니었나? 왜 GPU EC2가 늘어났나?"**

- D-02의 "GPU 1대"는 **영상 분석을 몇 대로 할지**를 정한 것이다. 웹·API 서버를 어디서 돌릴지는 그때 정하지 않았다.
- 이후 "GPU는 필요할 때 백엔드 서버에서 켜고 끄겠다"는 방침이 나왔다. GPU를 켜고 끄는 주체(백엔드)가 GPU와 다른 인스턴스여야 하므로 2대 구성이 되었다.

| 구성 | 장점 | 단점 |
|---|---|---|
| **2대: 백엔드 CPU + GPU (선택)** | GPU는 분석할 때만 켜서 비용이 적다. 웹·API는 GPU와 상관없이 동작한다 | GPU 켜기·작업 전달·끄기를 설계해야 한다 (U-02 → D-14, D-15, D-16에서 해결). GPU 부팅을 기다려야 한다 |
| 1대: GPU 하나에 전부 | 구성이 단순하다. 작업 전달이 필요 없다 | 웹에 접속하려면 GPU를 계속 켜 둬야 한다. GPU 인스턴스는 소형 CPU 인스턴스보다 시간당 비용이 훨씬 비싸다 (예: us-east-1 기준 g4dn.xlarge 약 $0.53/h, t3.small 약 $0.02/h ⚠️ 리전별 확인) |

**적용 위치**: 01장 1.5 / 02장 2.1~2.3, 2.7, 2.9

## D-11. 프론트엔드는 백엔드 EC2에서 서빙한다

- **날짜**: 2026-09-15
- **결정**: Flutter Web 빌드 결과(정적 파일)를 백엔드 EC2에서 API와 함께 서빙한다. 프론트는 API를 상대경로(`/api/...`)로 호출한다.

**결정 과정 (정직한 기록)**

- 처음에는 S3 정적 웹호스팅을 잠정 추천했다. push 한 번으로 프론트 배포를 자동화할 수 있기 때문이다.
- 이후 "EIP를 최대한 쓰지 않는다"(D-12)가 정해졌다. S3 호스팅을 쓰면 프론트가 API 주소를 고정값으로 알아야 하는데, EIP 없이 백엔드 IP가 매번 바뀌면 이 연결이 깨진다. 그래서 백엔드 EC2 서빙으로 추천을 바꿨다.

**비교: S3 정적 웹호스팅 vs 백엔드 EC2에서 함께 서빙**

| 항목 | S3 정적 웹호스팅 | 백엔드 EC2에서 서빙 (선택) |
|---|---|---|
| API 주소 | 프론트와 API의 주소가 달라서 프론트에 API 주소를 고정해야 한다. 백엔드 IP가 바뀌면 프론트를 다시 빌드해야 한다 → **EIP가 사실상 필요** | 같은 주소라 상대경로로 호출한다. IP가 바뀌어도 연결이 깨지지 않는다 |
| CORS | 출처가 달라 설정이 필요하다 | 같은 출처라 필요 없다 (로컬 개발만 필요) |
| 배포 자동화 | GitHub Actions에서 S3로 올린다. GitHub에 AWS 자격 증명(IAM 키 또는 OIDC 역할)이 필요하다 🔐 | GitHub Actions에서 SSH로 서버에 접속한다. SSH 키만 있으면 된다 (D-13) |
| 서버가 꺼졌을 때 | 화면은 뜨지만 API가 꺼져 있어 쓸 수 없다 | 화면도 뜨지 않는다. 어차피 쓸 수 없는 것은 같다 |
| HTTPS | S3 웹사이트 엔드포인트는 HTTP만 된다. HTTPS를 쓰려면 CloudFront가 필요하고, 그러면 HTTPS 페이지가 HTTP API를 부르는 것이 **혼합 콘텐츠로 차단**되어 API도 HTTPS가 필요해진다 | 둘 다 HTTP. 데모 범위에서는 적용하지 않는다 (02장 2.11) |
| 권한 | 영상 버킷과 별도로 공개 버킷 정책이 필요하다 🔐 | 추가 권한 없음 |
| 비용 | 거의 없음 | 이미 켜는 백엔드 EC2를 쓰므로 추가 비용 없음 |
| 이전 경험 | 없음 | 이전 프로젝트에서 EC2 + 배포 스크립트(.sh) 방식을 써 봤다 |

**질문: "트래픽·성능, 백엔드 요구사항, 정량적 측정에 차이가 없나?"**

- 데모 규모에서는 의미 있는 차이가 없다.
  - 프론트 정적 파일은 처음 한 번만 받는 수 MB 크기다.
  - 가장 큰 트래픽인 영상은 두 방식 모두 S3 presigned URL로 직접 받으므로 백엔드 EC2를 거치지 않는다.
  - PRD의 KPI(비식별화 누락률, 후보 검출 누락률, VLM 정렬 품질)는 파이프라인의 정확도를 재는 것이라 프론트 서빙 방식과 무관하다.
- 사용자가 많아지면 S3(+CloudFront)가 유리하다. 확장 방향으로 기록한다. (02장 2.10)

**버린 대안**

| 대안 | 버린 이유 |
|---|---|
| S3 정적 웹호스팅 + 백엔드 EIP (팀원이 이전에 쓴 방식) | EIP를 쓰지 않기로 했다 (D-12). 공개 버킷·배포용 AWS 자격 증명 등 추가 권한이 필요하다 |
| S3 정적 웹호스팅 + EIP 없이 | 백엔드 IP가 바뀔 때마다 프론트를 다시 빌드·배포해야 한다 |

**적용 위치**: 02장 2.2, 2.3, 2.9 / 05장 / 08장

## D-12. EIP를 쓰지 않는다

- **날짜**: 2026-09-15
- **결정**: 백엔드 EC2와 GPU EC2 모두 EIP(탄력적 IP, 고정 공인 IP)를 쓰지 않는다.

**GPU EC2는 EIP가 필요 없다**

- "GPU EC2가 EIP를 써야 서버 코드에서 GPU 주소를 안 바꿔도 되나?" → 필요 없다.
- 백엔드와 GPU를 같은 VPC에 두면 **프라이빗 IP**로 통신한다. 프라이빗 IP는 껐다 켜도 바뀌지 않고, 인스턴스를 삭제할 때만 사라진다.
- 백엔드가 GPU EC2를 켤 때는 IP가 아니라 **인스턴스 ID**로 지정한다.
- 작업을 SQS로 주고받으므로 백엔드는 GPU의 IP를 알 필요조차 없다. (D-16)

**백엔드 EC2는 EIP 없이 운영한다**

- 퍼블릭 IP가 켤 때마다 바뀐다. 그 결과:
  - 사용자 접속 주소가 바뀐다. 시연 때는 켠 뒤 새 주소를 확인해 쓴다.
  - 배포 대상 주소가 바뀐다. 배포 워크플로를 실행할 때 IP를 입력받는다. (D-13)
- 프론트를 백엔드 EC2에서 서빙하므로 프론트↔API 연결은 IP가 바뀌어도 깨지지 않는다. (D-11)

**EIP 비용 참고**

- 2024년 2월부터 AWS는 모든 공인 IPv4 주소에 시간당 $0.005를 받는다. 자동 할당 퍼블릭 IP도 인스턴스가 켜져 있는 동안 같은 요금이 붙는다.
- EIP는 인스턴스가 꺼져 있어도 주소를 잡고 있으므로 계속 요금이 붙는다(한 달 최대 약 $3.6).

**이유**: 추가 리소스·권한을 최소화한다. 켤 때마다 주소를 확인하는 수고는 데모 범위에서 감수한다.

**버린 대안**

| 대안 | 버린 이유 |
|---|---|
| 백엔드에 EIP | 주소는 고정되지만 추가 리소스·비용이 생긴다. 프론트를 백엔드에서 서빙하면 필수가 아니다 |
| GPU에 EIP | 프라이빗 IP와 인스턴스 ID로 충분하다 |

**적용 위치**: 02장 2.7, 2.9, 2.11

## D-13. CI는 자동, 배포는 수동 실행(`workflow_dispatch`)

- **날짜**: 2026-09-15
- **결정**
  - CI(테스트·빌드 확인)는 push·PR 때 GitHub Actions에서 자동 실행한다. 서버가 필요 없다.
  - 배포(CD)는 `workflow_dispatch`로 만든다. 누군가 GitHub Actions에서 "Run workflow" 버튼을 누를 때만 실행된다.
  - 서버 IP는 실행할 때 입력값(`inputs`)으로 받는다. SSH 개인 키는 GitHub Secrets에 둔다.
  - 절차는 02장 2.8에 적는다.

**배경 질문과 답**

| 질문 | 답 |
|---|---|
| EIP 없이 서버를 껐다 켜면 SSH로 들어가서 배포 스크립트를 실행해야 하나? | 직접 SSH로 들어갈 필요는 없다. GitHub Actions가 대신 SSH로 접속해 스크립트를 실행한다. 단, 매번 바뀐 IP를 알려줘야 한다 |
| push했는데 서버가 꺼져 있으면 SSH 접속이 안 되지 않나? | 맞다. 그래서 push 때 자동 배포하지 않고, 서버를 켠 사람이 수동으로 실행한다 |
| SSH 키를 GitHub에 올려도 되나? | **저장소(코드)에 올리면 절대 안 된다.** GitHub Secrets에 넣는 것은 된다. Secrets는 암호화되어 저장되고, 등록한 뒤에는 다시 볼 수 없으며, 실행 로그에서도 가려진다 |
| SSH 키는 바뀌지 않나? | 인스턴스를 껐다 켜도 바뀌지 않는다. 바뀌는 것은 퍼블릭 IP뿐이다. 인스턴스를 새로 만들면 공개 키를 다시 등록한다 |
| push가 아니라 내가 클릭할 때만 Actions가 돌게 할 수 있나? | 된다. `workflow_dispatch`를 쓰면 Actions 탭에 "Run workflow" 버튼이 생긴다. `gh workflow run` 명령으로도 실행할 수 있다 |
| 재배포할 때 Actions에서 SSH 키 값을 새 IP로 바꾸면 되나? | SSH 키는 그대로 두고, **실행할 때 입력 칸에 새 IP만 넣는다.** 키와 IP는 별개다 |

**버린 대안**

| 대안 | 버린 이유 |
|---|---|
| push 때 자동 배포 | 서버가 꺼져 있으면 실패한다. IP도 매번 바뀐다 |
| IP를 Secrets에 저장하고 매번 수정 | Secrets 수정은 저장소 관리자 권한이 필요하고 번거롭다. 입력값이 더 간단하다 |
| 사람이 직접 SSH로 접속해 `.sh` 실행 (이전 프로젝트 방식) | 가능하지만 팀원마다 키를 나눠 가져야 하고, 누가 언제 배포했는지 기록이 남지 않는다. Actions 실패 시 비상용으로는 쓸 수 있다 |
| AWS SSM Run Command로 배포 | SSH 포트를 열지 않아도 되지만 추가 IAM·SSM 권한이 필요하다 🔐 |

**보안 규칙**

- 배포 전용 키 쌍을 새로 만든다. 개인 SSH 키를 쓰지 않는다.
- 개인 키는 GitHub Secrets에만 둔다. 저장소에 커밋하지 않는다.
- 새 IP 접속 시 host key 확인 실패를 막기 위해 워크플로에서 `ssh-keyscan`으로 먼저 등록한다.
- 키가 유출되면 서버의 `authorized_keys`에서 지우고 새 키로 교체한다.

**적용 위치**: 02장 2.7, 2.8

## D-14. 영상 분석 작업은 모두 GPU 워커가 한다

- **날짜**: 2026-09-15
- **결정**
  - 1단계(정지 장면 비식별화, 청크 분할, 객체탐지·추적, 트랙 저장)와 2단계(룰 적용, Bedrock VLM 호출, 정렬, 후보 클립 비식별화)를 **모두 GPU 워커**가 실행한다.
  - 백엔드 EC2는 **통신과 관리만** 한다: API 응답, DB 읽기·쓰기, 작업을 SQS에 넣기, GPU EC2 켜기, presigned URL 발급.
- U-02의 "2단계 룰·VLM 실행 위치"를 해결한다.

**결정 과정 (정직한 기록)**

- 처음에 Claude가 "2단계의 룰과 VLM 호출은 GPU가 필요 없으니 백엔드에서 실행하자"고 제안했다. GPU가 꺼져 있어도 2단계 앞부분을 바로 시작할 수 있고, GPU가 켜져 있는 시간이 줄어든다는 이유였다.
- 팀장이 반대했다: "사용자가 많아지면 백엔드 서버는 통신과 관련된 작업만 해야 안 터진다. 백엔드 자원을 분석에 쓰면 다른 사람의 요청과 통신에 병목이 생긴다."
- 이 지적이 맞아 제안을 철회했다.

**헷갈렸던 점 정리**

| 질문 | 답 |
|---|---|
| 2단계 룰도 객체탐지가 있어야 하니 결국 GPU가 필요하지 않나? | 2단계에서 **다시 탐지하지 않는다.** 1단계에서 트랙(객체별 시간·bbox 목록)을 S3에 저장해 둔다. 2단계 룰은 저장된 트랙 좌표를 파손 부위·인접 영역 좌표와 비교하는 **좌표 계산**이라 GPU가 필요 없다. 2단계에서 GPU가 실제로 필요한 것은 후보 클립 비식별화뿐이다 |
| 그러면 왜 룰을 GPU 워커에서 하나? | GPU가 필요해서가 아니라, 백엔드가 통신만 하게 하기 위해서다. GPU 워커는 어차피 후보 클립 비식별화를 해야 하므로 룰·VLM까지 이어서 하면 흐름도 단순하다 |
| GPU가 켜지면 백엔드에서 하던 작업을 GPU로 옮기는 건가? | 아니다. 철회한 제안에서도 작업을 "옮기는" 것이 아니라 "나눠 맡는" 구조였다. 같은 작업을 두 곳에서 동시에 하지 않는다. 이번 결정으로 백엔드는 분석을 전혀 하지 않는다 |
| boto3로 구현해야 하나? | 그렇다. GPU 켜기, S3, presigned URL, SQS, Bedrock 호출을 모두 boto3(AWS 공식 Python SDK)로 한다. 자격 증명은 코드에 넣지 않고 EC2 IAM 역할에서 자동으로 받는다 (03장 3.1) |

**비교**

| 방식 | 장점 | 단점 |
|---|---|---|
| **GPU 워커가 전부 (선택)** | 백엔드는 요청 처리만 하므로 사용자가 많아도 응답이 밀리지 않는다. 백엔드에 Bedrock 권한이 필요 없다. 분석 코드가 한곳에 모인다 | GPU가 꺼져 있으면 2단계를 시작하기 전에 부팅을 기다려야 한다 (D-15로 줄임) |
| 백엔드가 2단계 룰·VLM 실행 (철회한 제안) | GPU 부팅을 기다리지 않고 룰·VLM을 시작할 수 있다. GPU 켜진 시간이 조금 준다 | 사용자가 많으면 분석이 백엔드 CPU·메모리를 차지해 다른 요청이 밀린다. 백엔드를 늘릴 때 분석까지 같이 늘려야 한다 |
| GPU 부팅 동안 백엔드가 정지 장면 비식별화 | 업로드 직후 정지 장면이 조금 빨리 나온다 | 같은 이유로 버림. 대신 업로드 시작 때 GPU를 켜서 부팅 시간을 업로드 뒤에 숨긴다 (D-15) |

**이 결정 때문에 바뀌는 것**

- 백엔드 역할에서 Bedrock 권한을 빼고, GPU 역할에 넣는다. (02장 2.9)
- `pipeline` 패키지는 GPU 워커와 평가 스크립트만 쓴다. (03장 3.3)

**적용 위치**: 01장 1.5 / 02장 2.1, 2.2, 2.4, 2.5, 2.9 / 03장 3.1, 3.3 / 06장

## D-15. GPU EC2는 업로드 시작 때 켜고, 15분 쉬면 스스로 꺼진다

- **날짜**: 2026-09-15
- **결정**
  1. **켜기**: 관리자가 업로드를 **시작**할 때(백엔드가 업로드용 presigned URL을 발급할 때) 백엔드가 GPU EC2를 켠다. 그 밖에도 GPU가 필요한 작업을 SQS에 넣을 때마다(2단계 시작, "못 찾음" 뒤 다음 묶음) 켜기를 요청한다. 이미 켜져 있으면 아무 일도 일어나지 않는다.
  2. **정지 장면 먼저**: GPU 워커는 1단계에서 정지 장면을 가장 먼저 처리하고, 그다음 청크별 객체탐지·추적을 한다.
  3. **1단계 중 입력 허용**: 정지 장면이 준비되면 1단계가 끝나기 전에도 사용자가 차량·파손 부위를 입력할 수 있다. 입력은 DB에 저장해 두고, 1단계가 끝나면 2단계가 자동으로 시작된다.
  4. **끄기**: GPU 워커가 **15분** 동안 할 일이 없으면 OS를 종료한다. 인스턴스 설정 `instance_initiated_shutdown_behavior = "stop"` 때문에 OS 종료가 인스턴스 "중지"가 된다(삭제가 아니다). 그래서 백엔드에 `ec2:StopInstances` 권한이 필요 없다.
  5. **시연 날**: 자동 꺼짐을 끄고 GPU를 미리 켜 둔다. ([02장 2.8 "시연 날 설정"](02-architecture.md#시연-날-설정))
- U-02의 "GPU를 켜고 끄는 시점"을 해결한다.

**배경 질문과 답**

| 질문 | 답 |
|---|---|
| 1단계도 GPU가 하면, 업로드하고 차량을 입력하기까지 1~2분(GPU 부팅) 병목이 생기지 않나? | 업로드를 **시작**할 때 GPU를 켜므로 부팅이 업로드하는 동안 끝난다. 24시간 영상은 수 GB라 업로드가 보통 부팅보다 오래 걸린다 ⚠️(관리실 네트워크 속도에 따라 다름). 그리고 정지 장면을 가장 먼저 처리하므로, 바로 입력하려는 사용자도 정지 장면 처리 시간 정도만 기다린다 |
| 업로드하자마자 1단계 객체탐지를 하면 탐지 시간이 엄청 오래 걸리지 않나? | 오래 걸린다(24시간 영상 약 36분, 추정, D-01). 하지만 사용자가 기다리지 않는 백그라운드 작업이다. PRD User Flow대로 사용자는 관리실을 떠나 나중에 접속한다. 사용자가 실제로 기다리는 것은 2단계(수 분)다 |
| 1단계가 끝나기 전에 사용자가 접속하면? | 정지 장면이 준비됐으면 입력할 수 있다. 입력을 저장해 두었다가 1단계가 끝나는 즉시 2단계를 시작한다. 화면에는 "영상 분석 중 (입력 완료)" 같은 상태를 보여준다 (문구 🚧 07장) |

**처리 시점별 사용자 대기** (시간은 추정)

| 시점 | 일어나는 일 | 사용자가 기다리나 |
|---|---|---|
| 업로드 시작 | 업로드 URL 발급 + GPU 켜기 요청. 업로드와 GPU 부팅·모델 로딩이 동시에 진행된다 | 업로드 시간만 |
| 업로드 완료 | 1단계 작업이 SQS에 들어가고, GPU 워커가 정지 장면부터 처리한다 | 관리실에서 기다리지 않는다 |
| 정지 장면 준비 | 사용자가 차량·파손 부위를 입력할 수 있다 | 사용자가 원하는 때 접속 |
| 1단계 완료 + 입력 완료 | 2단계 자동 시작 | 2단계 수 분 |
| 나중에 접속해 입력 (GPU가 이미 꺼짐) | GPU 켜기 → 2단계 | 부팅 1~2분 + 모델 로딩 + 2단계 수 분 |
| 후보 확인 중 "못 찾음" | 다음 10개 후보 클립 비식별화 | GPU가 켜져 있으면 비식별화 시간만. 꺼져 있으면 부팅 시간이 더해진다 |

**15분으로 정한 이유**

| 대기 시간 | 장점 | 단점 |
|---|---|---|
| 5분 | 비용이 가장 적다 | 사용자가 첫 묶음 10개(클립 30초 × 10 = 5분 + 판단 시간)를 보는 도중 꺼진다. "못 찾음"을 누르면 다음 묶음 비식별화 전에 다시 부팅을 기다린다 |
| **15분 (선택)** | 한 묶음을 다 보고 "못 찾음"을 누를 때까지 GPU가 켜져 있을 가능성이 높다 | 마지막 작업 뒤 15분 요금 (g4dn.xlarge 기준 약 $0.13 ⚠️ 리전별 확인) |
| 60분 | 다시 부팅하는 일이 거의 없다 | 쓰지 않는 시간의 요금이 커진다 |

- 다음 묶음을 미리 비식별화해 두면 "못 찾음" 뒤 대기가 줄어든다. 도입 여부는 🚧 (06장)

**구현할 때 지킬 것**

- GPU 워커는 끄기 직전에 SQS를 한 번 더 확인한다. 새 작업이 있으면 끄지 않는다.
- GPU가 꺼지는 도중(`stopping` 상태)에 백엔드가 켜기를 요청하면 AWS가 거부한다. 백엔드는 `stopped`가 된 뒤 다시 켠다(재시도). 작업은 SQS에 남아 있으므로 잃어버리지 않는다. 재시도 방식은 🚧 (U-20)
- 자동 꺼짐 시간은 설정값으로 둔다. 시연 날에는 이 값으로 자동 꺼짐을 끈다. 방법은 🚧 (10장)
- 자동 꺼짐이 고장 나면 GPU 요금이 계속 나간다(g4dn.xlarge 하루 약 $12.6 ⚠️). 비용 알림(AWS Budgets, 선택)과 콘솔 확인으로 대비한다.

**버린 대안**

| 대안 | 버린 이유 |
|---|---|
| 사용자가 입력한 뒤 GPU를 켜고 1단계 시작 | 입력 뒤 부팅 + 1단계 수십 분을 기다려야 한다 (D-05) |
| 업로드가 끝난 뒤 GPU 켜기 | 부팅 1~2분이 업로드 뒤에 그대로 붙는다 |
| 백엔드가 GPU를 끔 (`ec2:StopInstances`) | 백엔드가 GPU 작업 상태를 계속 감시해야 하고 권한이 하나 늘어난다. 할 일이 있는지는 워커가 가장 잘 안다 |
| GPU를 항상 켜 둠 | 한 달 약 $380 ⚠️. 확장 방향(대기 시간을 없애야 할 때)으로 둔다 (02장 2.10) |
| GPU 부팅 동안 백엔드가 정지 장면 처리 | 백엔드는 통신만 한다 (D-14) |

**적용 위치**: 01장 1.6 / 02장 2.5, 2.8, 2.9, 2.11 / 06장 / 07장 / 10장

## D-16. 작업 전달은 SQS, 작업 상태는 DB

- **날짜**: 2026-09-15
- **결정**
  - 백엔드는 분석 작업을 **SQS 표준 대기열**에 넣고, GPU 워커는 SQS에서 작업을 꺼내 처리한다. 🔐
  - 작업의 진행 상태(대기 중, 1단계 분석 중, 확인 가능 등)는 **DB**에 기록한다. DB는 상태 기록용이며 대기열로 쓰지 않는다.
  - 정해진 횟수 이상 실패한 작업은 **DLQ**(실패 작업 전용 대기열)로 옮긴다.
- U-02의 "작업 전달 방식"을 해결한다.

**SQS와 DB가 맡는 일**

| | SQS | DB |
|---|---|---|
| 담는 것 | "처리할 일" (작업 ID) | "지금 어떤 상태인지" (작업 상태, 후보 목록, 입력값 등) |
| 쓰는 쪽 | 백엔드가 넣고, GPU 워커가 꺼내고 지운다 | 백엔드와 GPU 워커 |
| 읽는 쪽 | GPU 워커 | 백엔드 (화면에 상태 표시), GPU 워커 (중복 확인) |

**배경 질문과 답**

| 질문 | 답 |
|---|---|
| SQS는 처리 속도를 올리는 게 아니라, 사용자 병목을 줄이고 서버가 터지지 않게 하는 데 필수 아닌가? | 서버가 터지지 않게 하는 것은 "요청은 바로 받고, 무거운 일은 대기열에 쌓아 두었다가 워커가 자기 속도로 처리하는" **구조**다. 이 구조는 DB 작업 표로도 만들 수 있다. 그래서 SQS가 필수는 아니다. 아래 이유로 채택했다 |
| SQS가 데모 규모에서 무료면 그냥 확정하면 안 되나? | 된다. 그래서 확정했다 |
| SQS를 써도 DB 작업 표로 만든 대기열을 같이 써야 하나? | 아니다. 대기열은 SQS 하나다. DB에는 상태만 적는다 |

**채택 이유**

- 데모 규모에서 무료 범위다. SQS는 월 100만 요청까지 무료다 ⚠️(계정의 프리 티어 조건 확인, C-05). 워커가 긴 폴링(한 번에 최대 20초 대기)을 쓰면 켜져 있는 동안 시간당 약 180건이라 한도에 한참 못 미친다.
- 권한 요청은 괜찮다(팀장 확인).
- GPU를 켜고 끄는 방식(D-15)과 맞는다. GPU가 꺼져 있어도 작업이 SQS에 남아 있다(보관 기간 최대 14일).
- 워커가 처리 중에 죽으면 작업이 다시 대기열에 보인다. 재시도를 따로 만들 필요가 없다.
- 확장 설명이 쉬워진다. GPU 여러 대 + 대기 작업 수 기반 Auto Scaling으로 가는 길이 워커 코드 변경 없이 열린다. (02장 2.10)

**비교**

| 항목 | **SQS + DB 상태 (선택)** | DB 작업 표를 대기열로 | SQLite + 백엔드 내부 API로 전달 |
|---|---|---|---|
| 작업 전달 | SQS에서 꺼낸다 | 워커가 DB를 주기적으로 조회하고 잠금(`SELECT ... FOR UPDATE SKIP LOCKED`)으로 가져간다 | 워커가 백엔드 API를 호출해 작업을 받는다 |
| 실패한 작업 재시도 | 기본 제공 (가시성 제한 시간, DLQ) | 직접 구현 (시작 시각·재시도 횟수 칼럼 등) | 직접 구현 |
| 워커 여러 대 | 기본 지원 | 잠금으로 가능 | 백엔드가 분배 로직을 구현해야 한다 |
| Auto Scaling 연결 | 대기 작업 수 지표 기본 제공 | 지표를 직접 만들어야 한다 | 직접 |
| 백엔드 부담 | 없음 | DB 조회가 계속 들어온다 | 워커 요청을 백엔드가 받는다 |
| 권한·비용 | SQS 권한 🔐, 무료 범위 | 추가 없음 | 추가 없음 |
| 로컬 개발 | SQS를 대신할 수단이 필요하다 🚧 (U-03) | DB만 있으면 된다 | 백엔드만 있으면 된다 |

**구현할 때 반드시 지킬 것**

1. **가시성 제한 시간(visibility timeout)**: 워커가 메시지를 꺼내면 이 시간 동안 다른 워커에게 보이지 않는다. 처리 시간보다 짧으면 처리 도중 다시 보여 **두 번 처리**된다. 1단계는 수십 분이 걸리므로, 처리하는 동안 `ChangeMessageVisibility`로 주기적으로 연장한다(최대 12시간).
2. **중복 전달**: 표준 대기열은 드물게 같은 메시지를 두 번 전달한다. 워커는 처리 전에 DB의 작업 상태를 확인해, 이미 끝났거나 처리 중인 작업이면 건너뛴다(멱등성).
3. **처리 후 삭제**: 끝나면 `DeleteMessage`로 지운다. 지우지 않으면 가시성 제한 시간이 지나 다시 전달된다.
4. **보관 기간**: 기본값은 4일이다. 14일(최대)로 설정한다.
5. **DLQ**: 정해진 횟수(🚧 U-18) 실패한 메시지는 DLQ로 자동으로 옮겨진다. 이 작업은 DB 상태를 "실패"로 표시하고 사람이 확인한다. (방법 🚧 06장)
6. **메시지 내용**: 작업 ID와 작업 종류만 넣는다. 상세 내용은 DB·S3에서 읽는다. 메시지 크기 한도가 있고, 같은 정보를 두 곳에 두지 않기 위해서다. (예시 🚧 04장)

**버린 대안**

| 대안 | 버린 이유 |
|---|---|
| DB 작업 표를 대기열로 사용 | 재시도·잠금을 직접 구현해야 하고 백엔드 DB에 조회 부하가 생긴다. SQS가 무료라 이점이 작다 |
| SQLite + 백엔드 내부 API로 전달 | 워커가 백엔드에 요청을 보내 백엔드 부담이 된다. SQLite는 워커가 접속할 수 없다 (D-17) |
| SQS FIFO 대기열 | 중복 전달이 없고 순서를 보장하지만, 우리는 순서 요구가 없고 표준 대기열 + 중복 확인으로 충분하다 |

- D-03에서 "지금 SQS + Auto Scaling까지 구현"을 버렸다. 이번에는 SQS만 채택하고 Auto Scaling은 여전히 구현하지 않는다.

**적용 위치**: 01장 1.5, 1.6 / 02장 2.2, 2.3, 2.5, 2.9, 2.12 / 03장 3.1 / 04장 / 06장 / 10장

## D-17. DB는 백엔드 EC2에 PostgreSQL을 직접 설치한다

- **날짜**: 2026-09-15
- **결정**
  - PostgreSQL을 백엔드 EC2에 설치한다. 백엔드(API)와 GPU 워커가 같은 DB에 접속한다.
  - GPU 워커는 백엔드 EC2의 **프라이빗 IP**로 5432 포트에 접속한다. 보안 그룹으로 GPU EC2에서 오는 연결만 허용한다.
  - 앱은 DB 접속 주소(연결 문자열)를 환경변수로 받는다. 나중에 RDS로 옮길 때 이 값만 바꾼다.
- U-01을 해결한다.

**비교**

| 항목 | SQLite | **EC2에 PostgreSQL (선택)** | RDS PostgreSQL |
|---|---|---|---|
| 형태 | 파일 하나 | 백엔드 EC2에서 도는 DB 프로그램 | AWS가 관리하는 DB 서버 |
| GPU 워커 접속 | **불가.** 파일이 백엔드 EC2 디스크에 있다. 워커가 상태를 쓰려면 백엔드에 내부 API를 따로 만들어야 한다 | 네트워크로 접속 | 네트워크로 접속 |
| 백엔드 여러 대 | 불가 (파일이 한 서버에만 있다) | DB를 RDS로 옮기면 가능 | 가능 |
| 추가 비용 | 없음 | 없음 (이미 켜는 백엔드 EC2 안) | 약 $14/월 ⚠️ (db.t4g.micro + 20GB 기준. 프리 티어 적용 여부는 계정 조건 확인) |
| 권한 | 없음 | 없음 (보안 그룹 규칙만) | RDS 권한 🔐, DB 서브넷 그룹 |
| 켜고 끄기 | 서버와 함께 | 백엔드 EC2와 함께 켜지고 꺼진다 | 따로 중지해야 한다. 중지해도 **7일 뒤 자동으로 다시 켜진다.** 켜는 데 수 분 걸린다 |
| 백업·장애 대응 | 직접 | 직접 (`pg_dump`) | 자동 백업, 다중 AZ 선택 가능 |
| 설치 난이도 | 없음 | apt 설치 + 설정 파일 2개 수정 (아래) | 콘솔·Terraform으로 생성 |

**배경 질문과 답**

| 질문 | 답 |
|---|---|
| RDS로 설치하는 건 별로인가? | 나쁘지 않다. 실제 서비스라면 RDS가 표준이다. 데모에서 버린 이유는 월 요금, 7일 자동 재시작, 느린 켜기, 추가 권한이다. 연결 문자열만 바꾸면 옮길 수 있어 확장 방향으로 둔다 (02장 2.10) |
| GPU 워커만 분석하기로 했으면 SQLite를 써도 되지 않나? | 안 된다. 워커가 분석을 맡으면 오히려 **워커가** 작업 상태(1단계 진행 중, 완료, 후보 목록)를 DB에 써야 한다. 워커는 다른 EC2라 백엔드 EC2 디스크의 SQLite 파일을 열 수 없다. 백엔드를 여러 대로 늘릴 때도 막힌다 |
| EC2에 직접 설치하는 방식이 어렵나? 알려주면 그대로 수동으로 하면 되나? | 어렵지 않다. 아래 절차를 백엔드 EC2에서 한 번 따라 하면 된다. 나중에 설치 스크립트로 만든다 (🚧 10장) |

**설치 절차** (백엔드 EC2가 Ubuntu라고 가정 ⚠️)

1. 설치: `sudo apt update && sudo apt install -y postgresql`. 부팅할 때 자동 실행되도록 기본 설정된다.
2. DB와 사용자 만들기: `sudo -u postgres psql`로 들어가 아래를 실행한다. 비밀번호는 저장소에 절대 커밋하지 않는다. (관리 방식 🚧 10장)
   ```sql
   CREATE USER app WITH PASSWORD '비밀번호';
   CREATE DATABASE parking OWNER app;
   ```
3. 다른 서버의 접속 받기: `/etc/postgresql/<버전>/main/postgresql.conf`에서 `listen_addresses = 'localhost,<백엔드 프라이빗 IP>'`로 바꾼다.
4. 접속 허용 대상 등록: 같은 폴더의 `pg_hba.conf`에 한 줄 추가한다.
   ```
   host  parking  app  <GPU EC2 프라이빗 IP>/32  scram-sha-256
   ```
5. 적용: `sudo systemctl restart postgresql`
6. 보안 그룹: 백엔드 EC2 보안 그룹에 "5432 포트, 출발지 = GPU EC2 보안 그룹" 규칙을 추가한다.

**자주 하는 실수**

| 실수 | 결과 |
|---|---|
| `listen_addresses`를 바꾸지 않음 | 기본값이 localhost라 GPU 워커가 접속하지 못한다 |
| `pg_hba.conf`에 등록하지 않음 | `no pg_hba.conf entry` 오류로 접속이 거부된다 |
| 5432 포트를 인터넷 전체(`0.0.0.0/0`)에 열기 | 누구나 DB 접속을 시도할 수 있다. **절대 금지.** GPU EC2 보안 그룹만 허용한다 |
| DB 비밀번호를 코드나 설정 파일에 커밋 | 금지. 환경변수나 서버의 별도 파일로 둔다 |
| 백엔드 EC2를 삭제하고 새로 만듦 | DB 데이터가 함께 사라진다. 중지·시작은 괜찮다(디스크가 유지된다). 필요하면 `pg_dump` 결과를 S3에 백업한다(선택) |

- 백엔드와 GPU EC2의 프라이빗 IP는 인스턴스를 삭제하지 않는 한 바뀌지 않는다. 그래서 설정 파일을 매번 고칠 필요가 없다. (D-12)

**적용 위치**: 02장 2.2, 2.3, 2.7, 2.9, 2.11 / 03장 3.1 / 04장 / 10장

## D-18. 원본 영상은 presigned URL로 S3에 직접 업로드한다

- **날짜**: 2026-09-15
- **결정**
  - 관리자의 브라우저가 백엔드에서 업로드용 presigned URL을 받아, 원본 영상을 S3 원본 영역에 **직접** 올린다.
  - 백엔드는 URL 발급과 업로드 완료 기록만 한다. 업로드가 끝나면 브라우저가 백엔드에 완료를 알리고, 백엔드가 1단계 작업을 SQS에 넣는다.
  - 업로드 URL 발급이 GPU 켜기 신호다. (D-15)
- U-04를 해결한다.

**이유**

- 24시간 CCTV 영상은 수 GB다. 백엔드를 거치면 업로드하는 동안 백엔드의 네트워크·디스크·메모리를 차지해 다른 요청이 밀린다. (D-19)
- 재생도 presigned URL로 S3에서 직접 받으므로(D-09), 영상 트래픽이 백엔드를 전혀 거치지 않는다.

**필요한 것과 주의점**

- **S3 버킷 CORS 설정** 🔐: 브라우저가 백엔드 주소의 페이지에서 S3 주소로 파일을 보내므로 출처가 다르다. 버킷에 CORS를 설정해야 브라우저가 막지 않는다.
  - ⚠️ 백엔드 퍼블릭 IP가 켤 때마다 바뀐다(D-12). CORS 허용 출처를 IP로 적으면 켤 때마다 고쳐야 한다. 허용 출처를 `*`로 두는 방법이 있다. presigned URL 자체가 서명과 만료 시간으로 보호되므로 데모에서는 받아들일 만하다. → 데모는 `*`로 정했다 (D-22)
- **5GB 한도** ⚠️: presigned URL 한 번(단일 PUT)으로 올릴 수 있는 파일은 최대 5GB다. 이보다 큰 영상은 **멀티파트 업로드**(파일을 여러 조각으로 나눠 올리고 조각마다 URL을 발급)가 필요하다. → 데모는 단일 PUT, 실제 운영은 멀티파트로 정했다 (D-22)

**버린 대안**

| 대안 | 버린 이유 |
|---|---|
| API 서버를 거쳐 업로드 | 백엔드가 수 GB 파일을 받아야 해 다른 요청이 밀린다 |
| S3 이벤트 알림으로 업로드 완료 감지 | 추가 설정·권한이 필요하다. 브라우저가 완료를 알리는 것으로 충분하다 |

**적용 위치**: 02장 2.3, 2.5, 2.9 / 05장

## D-19. 부하 대응은 최소 조치만 하고, 확장은 방향만 적는다

- **날짜**: 2026-09-15
- **결정**
  - 사용자가 몰려도 **서버가 멈추지 않도록** 하는 최소 조치만 지금 구현한다.
  - 처리 속도를 늘리는 확장(GPU 여러 대, 백엔드 여러 대 등)은 02장 2.10에 방향만 적고 구현하지 않는다.
  - 나중에 확장할 수 있도록 **무상태 API 규칙**을 지킨다.

**배경**

- 팀장: "지금 데모 서비스라 실질적으로 필요하진 않지만, 발표를 해야 해서 사용자가 많아졌을 때도 당장 서버가 터지지 않을 최소한의 조치는 하고, 실질적으로 필요한 부분은 확장 가능성으로 열어둬야 한다."
- 두 가지를 구분한다.
  - **서버가 멈추지 않음** (지금 구현): 요청이 몰려도 API가 응답하고, 작업을 잃어버리지 않는다.
  - **빨리 처리함** (확장 방향): 분석 대기 시간을 줄인다. GPU를 늘려야 한다.
- 지금 구조에서 사용자가 몰리면 **분석 대기가 길어질 뿐, 서버는 멈추지 않는다.**

**최소 조치**

| # | 조치 | 막는 문제 | 추가 비용 |
|---|---|---|---|
| 1 | API는 무거운 일을 하지 않는다. 분석은 모두 GPU 워커가 한다 (D-14) | 분석 때문에 다른 사용자의 요청이 밀림 | 없음 |
| 2 | 작업은 SQS에 쌓고, 워커가 자기 속도로 처리한다 (D-16) | 작업이 몰릴 때 작업 유실, 워커 과부하 | 무료 범위 |
| 3 | 영상 트래픽은 백엔드를 거치지 않는다. 업로드(D-18)와 재생(D-09) 모두 presigned URL로 S3에 직접 | 백엔드 네트워크 포화 | 없음 |
| 4 | 동시 실행 수를 제한한다. GPU 워커 프로세스 수(D-02), Bedrock 동시 호출 수(D-06). Bedrock 한도를 넘으면 재시도하되 기다리는 시간을 점점 늘린다(백오프) | GPU 메모리 부족, Bedrock 한도 초과로 인한 실패 | 없음 |
| 5 | 화면의 상태 조회 주기를 5~10초로 둔다 (🚧 U-18) | 화면이 너무 자주 물어 API·DB 부하 | 없음 |
| 6 | 대기 순서를 보여준다: "대기 중 (앞에 N건)". N은 DB에서 계산한다 | 사용자가 멈춘 줄 알고 재업로드·새로고침을 반복 | 없음 |

**무상태 API 규칙** (확장을 위해 지금부터 지킨다)

- 파일은 서버 디스크가 아니라 S3에 둔다.
- 로그인 세션을 서버 메모리에 두지 않는다. DB나 토큰에 둔다. (08장)
- 작업 상태는 DB에만 둔다. 서버 메모리에 두지 않는다.
- DB 접속 주소는 환경변수로 받는다. DB를 백엔드 EC2 밖(RDS)으로 옮길 수 있다. (D-17)
- 이 규칙을 지키면 백엔드 EC2를 여러 대로 늘려도 코드를 고칠 필요가 없다. 어느 서버가 요청을 받아도 같은 결과를 돌려주기 때문이다.

**점검: 사용자가 몰릴 때 생기는 문제별 대응**

| 문제 | 지금 막는 방법 | 확장 방법 (02장 2.10) |
|---|---|---|
| API 응답이 느려짐 | 1, 5 | 백엔드 여러 대 + ALB |
| 업로드·재생 트래픽으로 네트워크 포화 | 3 | 재생에 CloudFront |
| 분석 요청이 한꺼번에 몰림 | 2 (쌓아 둠), 6 (순서 표시) | GPU 여러 대 + 대기 작업 수 기반 Auto Scaling |
| Bedrock 한도 초과 | 4 | 한도 증가 요청 |
| DB 부하 | 5 | RDS, 읽기 전용 복제본 |
| 분석 대기 시간이 길어짐 | **해결하지 않는다.** 한계로 명시한다 (02장 2.11) | GPU 여러 대, 항상 켜 둔 GPU |

**버린 대안**

| 대안 | 버린 이유 |
|---|---|

## D-21. GPU EC2 AMI는 AWS Deep Learning Base AMI를 쓴다

- **날짜**: 2026-09-15
- **결정**
  - GPU EC2는 AWS Deep Learning Base AMI(DLAMI)로 만든다. 이름: `Deep Learning Base OSS Nvidia Driver GPU AMI (Ubuntu 22.04)`. NVIDIA 드라이버와 CUDA가 미리 설치되어 있다.
  - 루트 볼륨은 AMI 기본 크기 그대로 쓰고 늘리지 않는다.
  - 원본 영상·청크 같은 임시 파일은 로컬 NVMe(`/opt/dlami/nvme`)에 두는 것을 기본으로 한다. 확정은 🚧 06장.
- U-16을 해결한다.

**배경**

- 팀장 질문 1: "추천안(Deep Learning AMI)은 무조건 필요한 부분이 아니라서 학교에서 비용까지 지불하면서 해주지 않을 것 같은데, 기본 우분투에 직접 설치해야 하나?"
- 팀장 질문 2: "DLAMI를 사용하면 기본 우분투보다 얼마나 차이가 나는지, 기본 우분투와 달리 따로 권한을 받아야 하는지"
- 조사 결과를 듣고 팀장이 DLAMI로 결정했다.

**이유**

- **AMI 사용료가 없다.** AWS 문서: "there is no additional charge for the Deep Learning AMIs – you only pay for the AWS resources needed to store and run your applications." 어느 AMI를 쓰든 EC2 시간 요금과 EBS(디스크) 요금만 낸다.
- **비용 차이는 루트 볼륨 크기뿐이다.**
  - gp3는 GB당 월 $0.08이다. us-east-1 기준이고, 다른 리전은 조금 다르다 ⚠️ (C-05).
  - 차이 10GB당 월 약 $0.8이다.
  - EBS는 GPU를 꺼 둬도 요금이 나간다.
- **설치·관리 부담이 줄어든다.** 드라이버 설치, NVMe 마운트 스크립트, 커널 업데이트 뒤 드라이버 점검이 필요 없다. 경험이 적은 팀이라 설치 문제로 쓰는 시간이 월 몇 달러보다 비싸다.
- **추가 권한이 없다.** (아래)

**비교**

| 항목 | DLAMI (채택) | 기본 Ubuntu + NVIDIA 드라이버 직접 설치 |
|---|---|---|
| AMI 사용료 | 없음 | 없음 |
| GPU 시간 요금 | 같음 | 같음 |
| 미리 설치된 것 | NVIDIA 드라이버, CUDA, 컨테이너용 NVIDIA 도구 등 | OS만 |
| 우리가 할 일 | Python 패키지 설치 | 드라이버 설치(`sudo ubuntu-drivers install` 등) → 재부팅 → `nvidia-smi`로 GPU 확인 → Python 패키지 설치. PyTorch pip 패키지에 CUDA 런타임이 들어 있어 CUDA Toolkit은 따로 설치하지 않아도 된다 |
| 루트 디스크 | 기본 크기가 크다. CUDA 4개 버전(12.6, 12.8, 12.9, 13.0), NCCL·EFA 등 우리가 쓰지 않는 도구까지 들어 있다. AMI 기본 크기보다 작게 줄여서 시작할 수는 없다 | Ubuntu 공식 AMI 기본값은 8GB라 늘려야 한다. OS + 드라이버 + PyTorch + 모델이면 30GB 정도로 충분할 것으로 본다 ⚠️ |
| 영상 작업 공간 | g4dn.xlarge에 요금이 포함된 로컬 NVMe 디스크(125GB, 인스턴스 스토어)를 `/opt/dlami/nvme`에 자동으로 붙여 준다 | NVMe를 직접 포맷·마운트해야 한다. 중지하면 NVMe 내용이 지워지므로 켤 때마다 다시 붙이는 부팅 스크립트가 필요하다 |
| g4dn 지원 | 릴리스 노트에 명시되어 있다 (`supported_ec2_instances: G4dn, G5, G6, ...`, 2026-01-20 판) | 드라이버 버전을 직접 골라야 한다 |
| 위험 | 적다. AWS가 드라이버 호환을 확인해 둔 상태다 | 커널 업데이트 뒤 드라이버가 깨질 수 있다 |

**권한**

- 따로 받지 않아도 된다. DLAMI는 AWS(`amazon`)가 공개한 AMI이고, AWS Marketplace 구독 상품이 아니다. 기본 Ubuntu(Canonical이 공개한 AMI)와 똑같이 `ec2:RunInstances` 권한으로 시작한다.
- 예외는 멘토가 계정에서 쓸 수 있는 AMI를 제한해 둔 경우다. IAM 정책 조건으로 특정 AMI만 허용했거나, 계정에 "Allowed AMIs" 설정을 켰을 수 있다. 이때는 기본 Ubuntu도 똑같이 막힐 수 있다. 멘토에게 "AMI 제한이 있는지"를 확인한다. ⚠️ ([C-07](#확인-방법), 02장 2.9 멘토 승인 요청 목록 2번)

**주의점**

- ⚠️ **루트 볼륨 기본 크기를 확인한다.** 콘솔 "인스턴스 시작" 화면에서 이 AMI를 고르면 스토리지 칸에 표시된다. 확인하면 02장 2.9에 크기와 월 요금을 적는다. ([C-06](#확인-방법))
- **Terraform에서 AMI ID를 고정한다.** (팀원 2)
  - `aws_ami` 데이터 소스에 `most_recent = true`를 쓰면, AWS가 새 DLAMI를 낼 때마다 `terraform apply`가 GPU EC2를 지우고 새로 만들려 한다.
  - 처음 찾은 AMI ID를 변수에 적어 고정한다. `aws_ami` 데이터 소스는 `ec2:DescribeImages`만 쓰므로 추가 권한이 없다.
- **로컬 NVMe는 중지하면 비워진다.** 켤 때마다 비어 있다고 가정한다. 남겨야 하는 데이터는 S3와 DB에 둔다.
- **AMI를 바꾸면 GPU EC2를 새로 만든다.** 이때 루트 볼륨에 설치한 내용이 사라지므로, GPU EC2 설치 과정을 스크립트로 남긴다 (10장).

**버린 대안**

| 대안 | 버린 이유 |
|---|---|
| 기본 Ubuntu + NVIDIA 드라이버 직접 설치 | 비용 차이는 월 몇 달러 수준이다. 반면 드라이버 설치, NVMe 마운트 스크립트, 커널 업데이트 관리가 늘어난다 |

**적용 위치**: 02장 2.9 / 03장 3.1 / 06장 / 10장

## D-22. 업로드는 단일 PUT으로 구현하고, 실제 운영에서는 멀티파트로 바꾼다

- **날짜**: 2026-09-15
- **결정**
  - **데모(이번 구현)**
    - presigned URL 1개로 파일 전체를 한 번에 올린다(단일 PUT).
    - 5GB를 넘는 파일은 프론트가 업로드 전에 막고 안내한다.
    - S3 버킷 CORS는 허용 출처 `*`, 메서드 `PUT`만, 헤더는 필요한 것만(`Content-Type` ⚠️) 허용한다.
  - **실제 운영**
    - 멀티파트 업로드로 바꾼다. (아래 "바꿀 때 할 일")
    - 고정 도메인이 생기면(02장 2.10 "상시 접속") CORS 허용 출처를 그 도메인으로 좁힌다.
- U-19를 해결한다.

**배경**

- presigned URL 한 번(단일 PUT)으로 올릴 수 있는 파일은 최대 5GB다. 24시간 CCTV 영상은 화질·코덱에 따라 5GB를 넘을 수 있다 ⚠️.
- 백엔드 퍼블릭 IP가 켤 때마다 바뀐다(D-12). 그래서 CORS 허용 출처를 IP로 적으면 켤 때마다 고쳐야 한다.
- 팀장: "시연할 때 짧은 영상들로만 할 거라 상관없어" → 시연에서는 5GB 한도에 걸리지 않는다.
- 팀장: "일단 데모 프로그램이니까 A안으로 구현 진행하고, 실제 운영 시 B안으로 수정하도록 설계문서에 남겨줘"

**5GB 한도 대안**

| 대안 | 방법 | 장점 | 단점 |
|---|---|---|---|
| **A. 단일 PUT (데모 채택)** | presigned URL 1개로 파일 전체를 한 번에 올린다 | 가장 단순하다. 백엔드 API 1개, 프론트 요청 1번 | 최대 5GB. 업로드 중 끊기면 처음부터 다시 올린다 |
| **B. 멀티파트 업로드 (실제 운영)** | ① 백엔드가 `CreateMultipartUpload`로 업로드 ID를 받고, 조각마다 presigned URL을 발급한다 ② 브라우저가 파일을 조각내 각각 올리고 조각별 `ETag`를 모은다 ③ 백엔드가 `CompleteMultipartUpload`로 합친다 | 최대 5TB. 끊긴 조각만 다시 올린다. 여러 조각을 동시에 올려 빨라질 수 있다 | 프론트·백엔드 구현이 늘어난다. 추가 설정·권한이 필요하다 (아래) |
| C. 관리자가 영상을 나눠 올림 | 5GB 이하 파일 여러 개로 | 서버 변경이 적다 | 관리자가 번거롭다. 여러 파일을 이어 원본 시간을 계산해야 해 복잡해진다 |
| D. 백엔드를 거쳐 업로드 | | | D-18에서 버렸다 (백엔드 부하) |
| E. S3 Transfer Acceleration | 가까운 AWS 엣지로 올려 전송을 빠르게 한다 | 먼 거리 업로드가 빨라진다 | 추가 요금이 든다. 5GB 한도는 그대로다 |

**CORS 허용 출처 대안**

| 대안 | 방법 | 장점 | 단점 |
|---|---|---|---|
| **A. 허용 출처 `*` (데모 채택)** | 버킷 CORS를 한 번만 설정한다. 메서드는 `PUT`만, 헤더는 필요한 것만 허용한다 | 한 번 설정하면 끝난다. 추가 권한·작업이 없다 | 어느 사이트든 브라우저에서 이 버킷으로 요청을 보낼 수는 있다. 하지만 유효한 presigned URL(서명·만료 시간)이 없으면 S3가 거부한다. CORS는 접근 제어가 아니라 브라우저가 지키는 규칙이고, 실제 보호는 presigned URL이 한다 |
| B. 켤 때마다 CORS를 새 IP로 수정 | 배포 워크플로 또는 수동으로 `PutBucketCors` 실행 | 출처를 정확히 제한한다 | 켤 때마다 할 일이 늘고, 잊으면 업로드가 막힌다. 워크플로로 하면 GitHub Actions에 AWS 권한이 필요해져 D-13과 어긋난다 |
| **C. 고정 주소 (실제 운영)** | 고정 도메인을 허용 출처로 적는다 | 출처가 고정된다 | 데모에서는 EIP·도메인을 쓰지 않는다 (D-12) |

**실제 운영에서 멀티파트로 바꿀 때 할 일**

| # | 할 일 | 담당 영역 |
|---|---|---|
| 1 | 업로드 시작(`CreateMultipartUpload` → 업로드 ID), 조각별 presigned URL 발급(`UploadPart`), 업로드 취소(`AbortMultipartUpload`) API를 추가한다 | 백엔드 |
| 2 | 업로드 완료 알림 API가 `CompleteMultipartUpload`까지 호출하도록 늘린다. 완료 뒤 1단계 작업을 SQS에 넣는 부분은 그대로 둔다 | 백엔드 |
| 3 | 파일을 조각내 올리고, 조각별 `ETag`를 모아 완료 API에 보낸다. 조각 크기는 5MB~5GB(마지막 조각은 5MB보다 작아도 된다), 조각 수는 최대 10,000개다. 실패한 조각만 다시 올린다 | 프론트 |
| 4 | S3 CORS의 `ExposeHeaders`에 `ETag`를 추가한다. 이게 없으면 브라우저가 `ETag`를 읽지 못해 완료를 요청할 수 없다 | 인프라 |
| 5 | S3 수명 주기 규칙 `AbortIncompleteMultipartUpload`(예: 시작 후 7일)를 건다. 끝나지 않은 업로드의 조각은 목록에 보이지 않지만 저장 요금이 나간다 | 인프라 |
| 6 | 백엔드 역할에 `s3:AbortMultipartUpload` 권한을 추가한다 🔐. 조각 업로드와 완료는 `s3:PutObject` 권한으로 된다 | 인프라 |

- 추가 비용: 새 리소스가 없다. 조각 수만큼 S3 요청 수가 늘어나는 정도다 ⚠️.

**지금 지키는 것** (나중에 바꾸기 쉽게)

- 업로드 URL 발급이 GPU 켜기 신호라는 점(D-15)과, 업로드 완료 알림 뒤 1단계 작업을 넣는 흐름(D-18)은 멀티파트에서도 그대로다. 바뀌는 것은 URL 발급 방식과 완료 처리뿐이다.

**버린 대안**

| 대안 | 버린 이유 |
|---|---|

### 확인 방법

**C-06. DLAMI 루트 볼륨 기본 크기** (AWS 콘솔, 인스턴스를 만들지 않고 확인)

1. AWS 콘솔에서 사용할 리전을 고른다 (U-10). AMI는 리전마다 따로 있다.
2. EC2 → **인스턴스 시작**을 누른다.
3. "애플리케이션 및 OS 이미지" 검색창에 `Deep Learning Base OSS Nvidia Driver GPU AMI (Ubuntu 22.04)`를 입력한다. 검색 결과의 "빠른 시작 AMI" 또는 "AWS Marketplace AMI"가 아니라 AWS가 제공한 AMI(소유자 `amazon`)를 고른다.
4. 아래 **스토리지 구성** 칸에 표시된 기본 크기(GiB)와 볼륨 유형(gp3)을 적는다.
5. **인스턴스를 시작하지 않고** 취소한다.
6. 결과를 D-21과 02장 2.9 멘토 승인 요청 목록 2번에 적는다. 예: 크기가 75GiB면 월 약 75 × $0.08 = $6 (us-east-1 기준).

- 다른 방법: EC2 → 이미지 → **AMI** → 필터를 "퍼블릭 이미지"로 바꾸고 같은 이름으로 검색 → AMI를 누르면 상세 정보의 "블록 디바이스"에 루트 볼륨 크기가 나온다.

**C-07. 계정의 AMI 사용 제한** (멘토에게 질문)

- 제한은 두 곳에 걸 수 있다. 우리 권한으로는 둘 다 직접 보지 못할 수 있으므로 멘토에게 묻는다.
  - **IAM 정책**: `ec2:RunInstances`에 특정 AMI ID나 소유자만 허용하는 조건이 있는지.
  - **EC2 "Allowed AMIs" 설정**: 계정(리전별)에서 허용한 AMI 제공자만 쓸 수 있게 하는 설정. DLAMI는 `amazon` 제공자에 속한다. ⚠️ 콘솔에서는 EC2 대시보드의 계정 속성에서 볼 수 있다. 메뉴 위치는 콘솔 버전에 따라 다를 수 있다.
- 멘토에게 보낼 질문 예시:
  > GPU EC2에 AWS가 제공하는 Deep Learning Base AMI(`Deep Learning Base OSS Nvidia Driver GPU AMI (Ubuntu 22.04)`, 소유자 amazon)를 쓰려고 합니다. AMI 사용료는 없고 Marketplace 구독 상품도 아닙니다. 계정에 IAM 조건이나 Allowed AMIs 설정으로 쓸 수 있는 AMI가 제한되어 있는지 확인 부탁드립니다.
- 제한이 있고 DLAMI가 막혀 있으면: 허용을 요청한다. 허용이 안 되면 기본 Ubuntu + 드라이버 직접 설치(D-21의 버린 대안)로 돌아간다. 이때 Canonical 제공 Ubuntu AMI도 허용되어 있는지 함께 확인한다.
