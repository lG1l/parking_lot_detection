# 06. 비전·VLM 파이프라인

> 마지막 수정: 2026-10-06
> 표시: 🚧 미정 · ⚠️ 확인 필요 · 🔐 멘토 승인 필요
> 이 장의 구조는 D-67~D-75(모두 상태 "확정 필요")를 따른다. 모델·수치는 대부분 🚧이고, 무엇을 어떻게 정할지는 [6.10](#610-추후-결정-항목)에 모았다.

## 6.1 전체 흐름

**사용자가 기다리는 시간보다 탐지 성능과 처리 속도를 우선한다.** 그래서 영상 전체 분석은 사용자 입력을 받은 **뒤에** 한다. 입력(본인 차량·파손 부위·탐지 상황)을 알아야 근접 영역만 조밀하게 보고, 클래스 없는 물체를 잡고, 작은 물체를 크롭해 볼 수 있기 때문이다. (D-67)

```
[업로드] 최소 수 분
  업로드 남은 예상 시간 <= 임계(1.6)가 되면 GPU 켜기 요청 (D-62)

[1단계: 정지 장면] 업로드 완료 직후. 수십 초 (추정)
  코덱 검사 → 첫 프레임 1장 → 차량 탐지 → 타일 방식 비식별화 → 저장

[사용자 입력] 아무 때나
  본인 차량 고르기 + 탐지 상황 [보임/안 보임] + 파손 위치 사각형(보임·안 보임 모두 드래그)
  + 내 차 바닥 네 모서리 + 파손 변 (D-98)
  + 사진(선택) + 텍스트 설명(선택) → 확인창 → 저장 (D-66, D-72)
  GPU가 꺼져 있으면 다시 켠다 (부팅 2~3분, D-15)

[2단계: 전체 분석] 입력 저장 후. 24시간 영상 약 30분 (추정, 실측 필요)
  ① 후보 탐지: 분석 크롭 위에서 채널 B(움직임 감지, 영상 전체) + 채널 A(YOLO+ByteTrack, 근접 영역 움직임 구간만)
     → 바닥점 필터(0단계) → 후보 (D-95, D-97)
  ② VLM: 1차(싼 모델, 탈락만) → 2차(점수 0~100) → 점수순 정렬. 2차 형식 실패 → 파싱 실패 목록 (D-93)
  ③ 후보군 목록·파싱 실패 목록 각각 상위 20개(묶음 2개) 후보 클립: 보여줄 크롭 → 비식별화 → "확인 가능"

[확인]
  [다음] → 이미 준비된 다음 묶음을 바로 보여줌
         → 동시에 GPU를 켜고 그다음 묶음을 비식별화 (한 묶음 앞서 준비, D-68)
```

| 단계 | 시작 조건 | GPU | 사용자가 기다리나 |
|---|---|---|---|
| 1단계 | 업로드 완료 알림 | 필요 (탐지·비식별화) | 업로드 직후 바로 입력하려면 수십 초 |
| 2단계 | 입력 저장 | 필요 | **기다린다.** 24시간 영상 약 30분 (추정). GPU가 꺼져 있었으면 부팅이 더해진다 |
| 다음 묶음 | [다음] | 필요 (비식별화) | 기다리지 않는다. 이미 준비된 묶음을 보여준다 |

- 1단계는 이제 정지 장면만 만든다. 영상 전체 객체탐지·추적은 2단계로 옮겼다 (D-67이 D-05를 바꿈).
- **입력은 항상 1단계가 끝난 뒤에 들어온다.** 정지 장면이 1단계의 마지막 산출물이기 때문이다. 그래서 "1단계 중 입력 → 1단계가 끝나면 2단계 자동 시작" 경로(D-15 결정 3, `stage1_input_done`)가 필요 없다. 상태 정리는 04장 4.3에 반영했다 (D-81).

## 6.2 GPU 워커 운영

(D-14, D-15, D-16, D-62)

- SQS 긴 폴링(20초)으로 작업 꺼내기
- 처리 중 가시성 제한 시간 주기적 연장 (`ChangeMessageVisibility`, 연장 주기 U-18). **이제 오래 걸리는 쪽은 2단계다** (약 30분, 추정)
- 처리 전 DB 상태로 중복 확인 (이미 끝났거나 처리 중이면 건너뜀)
- 처리 후 메시지 삭제 (`DeleteMessage`). 조건부 UPDATE가 0행이면 지운다. `analysis_jobs` 행이 없는 경우도 마찬가지다 (D-56, 04장 4.4). **단, 받은 메시지의 작업이 `*_running`이면 지우지 않고 이어서 한다(아래, D-94).**
- **죽은 작업 이어서 하기** (D-94): 가시성 제한 시간은 살아 있는 워커만 연장하므로, `*_running` 작업의 메시지가 다시 왔다는 것은 처리하던 워커가 죽었다는 뜻이다. 워커는 그 작업을 이어서 한다.
  - `stills_running`: 1단계를 처음부터 다시 한다(정지 장면 1장이라 짧다).
  - `stage2_running`: `processed_sec`부터 탐지·추적을 이어 간다(D-76). VLM 단계에서는 점수가 이미 있는 후보를 건너뛴다.
  - `batch_running`: `pending` 클립부터 다시 만든다.
  - **상한**: 메시지의 `ApproximateReceiveCount`가 4 이상이면(= 3번 죽었으면) 이어서 하지 않고 `failed`로 바꾸고 메시지를 지운다. 메모리 부족처럼 같은 원인으로 되풀이해 죽는 경우를 끊기 위해서다. DB 칼럼은 더하지 않는다.
  - 복구까지 걸리는 시간은 가시성 제한 시간만큼이다(연장 주기와 함께 🚧 U-18). GPU가 꺼져 있으면 백엔드 5초 점검이 켠다(D-42).
- 실패 처리: 재시도 상한과 DLQ는 없다(위 이어서 하기 3회 상한은 예외). **입력 자체가 잘못된 경우만 `failed`로 바꾼다**: 코덱 불량·읽기 불가, 영상 길이 0, 원본 S3 객체 없음. 그 밖의 예외(네트워크, 일시 오류 등)는 메시지를 지우지 않고 SQS 재전달에 맡긴다. VLM 파싱 실패율·장애 지속은 6.6을 따른다 (D-43, D-56, D-93, D-94)
- **켜기**: 업로드 남은 시간이 임계 이하일 때(D-62), 그리고 GPU가 필요한 작업을 SQS에 넣을 때마다(1단계, 2단계, 다음 묶음). 사용자가 1단계 뒤 15분 넘게 입력하지 않으면 GPU가 꺼져 있으므로 입력 저장 시 다시 켠다(부팅 2~3분).
- 15분 동안 할 일이 없으면 SQS·DB를 한 번 더 확인한 뒤 OS 종료. 워커가 OS 종료 명령을 실행할 권한을 얻는 방법 🚧
  - 확인과 종료 사이에 들어온 작업은 워커가 챙기지 않아도 된다. 백엔드의 5초 주기 점검이 완전히 꺼진 뒤 다시 켠다 (D-42)
- 자동 꺼짐 켜고 끄기 설정 (시연 날에는 끔, [02장 2.8](02-architecture.md#시연-날-설정))
- 가짜 워커 모드: GPU·Bedrock 없이 정해진 시간 기다린 뒤 가짜 결과를 DB·S3에 쓴다 (D-20)
- 임시 파일 위치: 원본 영상은 로컬 NVMe(`/opt/dlami/nvme`)에 두는 것을 기본으로 한다. 중지하면 비워지므로 켤 때마다 비어 있다고 가정한다 (D-21)

## 6.3 1단계: 정지 장면

- 시작 직후 `ffprobe`로 코덱을 확인한다. H.264·H.265가 아니거나 읽을 수 없으면 재시도 없이 `failed`로 바꾸고 `error_message`에 이유를 적는다 (D-43, ⚠️ 팀장 확인)
- 원본을 열어 **첫 프레임 1장**만 뽑는다. `t_sec = 0.0`. 시크가 없다 (D-48)
- **비식별화 전 프레임에서 차량을 탐지해** `still_frames.detections`에 저장한다 (D-65). 사용자가 이 중에서 본인 차를 고른다
  - 모자이크가 씌워진 뒤에 탐지하면 차량 경계가 흐려진다. 좌표는 원본 해상도 기준이라 두 결과가 같은 좌표계다
  - 누끼(다각형)는 만들지 않는다.
  - 탐지가 0건이어도 `[]`로 저장한다. 화면은 재업로드 안내로 간다 (D-65)
  - 2단계 채널 A와 **같은 탐지 모델·클래스를 쓴다** (U-09). 기준이 갈리면 "탐지된 차량을 골랐는데 2단계에서는 다른 모양으로 잡히는" 경우가 생긴다
- 비식별화는 **타일 방식**이다. 프레임 전체를 겹치는 타일로 나눠 각각 탐지하고 합친다(SAHI 방식). 이 시점에는 본인 차량을 모르므로 크롭할 기준이 없고, 프레임이 1장이라 타일 수만큼 느려져도 괜찮다 (D-69, 6.8)
- 1단계는 여기서 끝난다. 청크 분할·객체탐지·추적은 하지 않는다 (D-67)

## 6.4 사용자 입력 (워커가 받는 값)

PRD 3.2가 정한 입력을 워커가 이렇게 읽는다. 저장 형식은 04장 `vehicle_selections`·`damage_inputs`이고, 바뀌어야 할 점은 04장 머리에 적었다.

| 입력 | 필수 | 쓰는 곳 |
|---|---|---|
| 본인 차량 (`det_id` → `bbox`) | 필수 | 근접 영역, 바닥선, 크롭 기준 |
| 탐지 상황: 파손이 CCTV에 **보임 / 안 보임** | 필수 | 룰 분기 (6.5) |
| 파손 부위 드래그 (보임일 때) | 보임이면 필수 | 근접 판정 기준, VLM 안내 프레임 |
| 파손 위치 사각형 (안 보임일 때) | 필수, 원본 화면 좌표 (D-92) | 인접 영역 계산, VLM 안내 프레임 |
| 내 차 바닥 네 모서리, 파손 변 (D-98) | 필수 (반영 필요: 04·05·07장) | 시야·거리 파악, ROI·크롭 크기, 바닥점 필터 (6.5) |
| 파손 사진 | 선택 | VLM 입력 |
| 텍스트 설명 | 선택 | VLM 입력 (데이터로만 취급) |

**파손이 안 보일 때의 입력 방식** (D-92, U-25 해결)

사용자가 CCTV 화면에서 파손 위치에 해당한다고 보는 곳에 작은 사각형을 드래그한다. 원본 프레임 절대 픽셀 좌표 `damage_bbox`로 저장하며 차량 박스 내부로 제한하지 않는다. `visible=false`와 함께 전달해 실제 보이는 파손 부위와 구분한다. 해당 위치를 기준으로 인접 영역을 계산하고 VLM 안내 프레임에 표시한다. 크롭할 때는 크롭 원점과 배율을 반영해 좌표를 변환한다. 구체적인 인접 영역 폭·근접 임계값은 U-13에서 정한다.

**통로 쪽 / 옆면 구분** (U-26 → D-98로 대체)

- 파손 부위가 차의 통로 쪽(앞·뒤 범퍼 쪽)인지 옆면(옆 칸 쪽)인지에 따라 근접하는 물체와 빈도가 크게 다르다(6.5 페르미 추정).
- 사용자가 바닥 네 모서리 사각형에서 파손 변을 직접 고르므로 따로 고르거나 계산하지 않는다 (6.5 "내 차 바닥 네 모서리로 시야 판단과 ROI 정하기"). D-34처럼 bbox로 계산하면 카메라 각도에 따라 "bbox의 어느 변"이 "차의 어느 면"인지가 어긋날 수 있어서다.

**사진·텍스트 전처리**

- 둘 다 선택이다. 없으면 VLM 프롬프트에서 그 항목을 통째로 뺀다 (빈 칸으로 두지 않는다).
- 사진: EXIF 제거(GPS 포함), HEIC는 JPEG로 변환, 긴 변 768~1024px로 줄인다. 사진에는 **사용자 본인 차 번호판**이 찍혀 있을 수 있다. 사용자 자신의 정보이고 VLM에만 보내며 화면에 다시 보여주지 않으므로 비식별화하지 않는다. 파기 대상에는 넣는다 (04장 4.9, D-83).

## 6.5 2단계-① 후보 탐지

**목표**: 사고 클립 후보 검출 누락률 1% 이하 (PRD 2장 KPI). CCTV에 가려져 사람도 판단할 수 없는 경우를 빼고 모두 잡는다. **재현율이 우선이지만, 확실히 관계없는 것은 여기서 뺀다.** (D-71)

### 대상 장면

| 장면 | 주로 잡는 채널 | 보이는 파손의 신호 | 안 보이는 파손의 신호 |
|---|---|---|---|
| 문콕 (옆 차 문 열림) | A(사람·차) + B(문 움직임) | 옆 차 쪽 덩어리가 파손 부위에 닿음 | 옆 칸 사람 승하차, 옆 차 문 쪽 움직임 |
| 주행 차량 접촉 | A | 차량 바닥점이 띠 안으로 들어옴 | 차량이 차 너머로 가려졌다 나타남, 느린 통과 |
| 물체·구조물 쓰러짐 | B | 밑동(바닥점) 근처에서 위쪽 덩어리가 차 쪽으로 기움 | 차 너머에서 큰 움직임 |
| 바퀴 달린 물체가 혼자 굴러옴 (카트·유모차) | B (+ A가 잡으면 A) | 덩어리 바닥점이 띠 안으로 이동 | 인접 영역 진입·체류 |
| 물체가 날아옴 | B | 짧고 빠른 덩어리가 차 쪽으로 | 바닥점 신뢰 불가 → 남김 |
| 사람 접촉 (고의·과실) | A | 사람 바닥점이 띠 안, 체류 | 차 너머 체류, 가려짐·재등장 |
| 동물 | A(COCO 동물 클래스) + B | 바닥점이 띠 안 | 인접 영역 체류 |

### 탐지 채널

- **채널 A: 객체탐지 + 추적.** COCO 사전학습 YOLO + ByteTrack. 프레임 전체가 아니라 **분석 크롭** 위에서 본다 (D-95). 쓸 클래스 목록과 모델 크기는 🚧 (U-09). Ultralytics `model.track()`의 기본 추적기는 BoT-SORT이므로 ByteTrack을 지정한다
  - **채널 A는 영상 전체에 돌지 않는다.** 채널 B가 ROI 움직임을 감지했을 때만 켠다. 규칙은 아래 "채널 A 켜고 끄기" (D-97).
- **채널 B: 근접 영역의 움직임.** 본인 차량 bbox를 넓힌 **근접 영역(ROI)** 에 닿은 움직임 덩어리를 찾는다. 배경 차분(MOG2, `detectShadows=True`로 그림자 제거) 또는 광학 흐름(Farneback)을 쓴다. ROI는 "이 구역에서 움직임이 생기면 그 물체를 보기 시작하는 곳"이고, 물체를 따라가는 것은 ByteTrack이다. 덩어리는 물체 전체로 넓혀서 bbox를 만든다 (D-96).
  - (a) **채널 A 트랙에 붙이기**: 덩어리가 채널 A의 bbox와 겹치거나 맞닿으면 그 물체의 일부(손, 열리는 문 등)로 본다. 채널 B 트랙을 따로 만들지 않고, 바닥점은 채널 A bbox의 것을 쓴다.
  - (b) **움직임 영역 확장**: 붙일 채널 A 트랙이 없으면, 움직임 감지를 ROI가 아니라 분석 크롭 전체에 돌려 둔 전경 마스크에서 **ROI에 닿은 덩어리와 이어진 전경 픽셀 전체(연결 요소)** 의 bbox를 쓴다. 이 bbox를 ByteTrack에 넣어 클래스 없는 트랙으로 만든다. 후보의 시작은 ROI에 닿은 덩어리로만 한다.
  - 가만히 서서 손만 움직이는 사람은 몸이 배경으로 흡수되어 (b)로는 손만 남는다. 이 경우는 (a)가 맡는다.
  - 채널 B는 **클래스가 없는 물체**(카트, 라바콘, 떨어지는 물건)를 잡고, 채널 A를 켜는 신호도 된다(아래). MOG2와 광학 흐름 중 무엇을 쓸지, ROI 크기는 🚧 (U-09, U-30)
- **분석 크롭**: 본인 차량 bbox에 여백을 더한 고정 사각형이다. 영상 하나에 하나이고 끝까지 바뀌지 않는다(본인 차량은 움직이지 않는다, D-29). 사용자에게 보여줄 크롭(6.7)보다 **크게** 잡는다. 근접 영역(ROI)은 이 안에 있고, 비식별화 탐지도 이 영역에서 한다(6.8) (D-95).
  - 이유: 프레임 전체를 모델 입력 크기로 줄이면 사람·카트처럼 작은 물체가 작아진다. 분석 크롭은 줄어드는 정도가 작거나 없다.
  - 크롭 밖에서 들어오는 물체는 크롭 가장자리에서 트랙이 시작된다. 크롭은 고정이라 트랙이 크롭 때문에 끊기지는 않는다. 가장자리에 걸려 잘린 bbox는 바닥점을 믿을 수 없는 트랙으로 보고 남긴다(아래 바닥점 필터).
  - 큰 차량이 일부만 크롭에 걸리면 YOLO가 놓칠 수 있다. 그래서 보여줄 크롭보다 여백을 더 둔다. 크기는 🚧 (U-30). 초기 가설: 한 변이 모델 입력 크기를 넘지 않게(줄어들지 않게) 잡고, 그보다 커야 하면 모델 입력 크기(`imgsz`)를 키운다. 채널 A에는 타일을 쓰지 않는다. 타일 결과를 합친 뒤 추적하면 트랙이 끊기지는 않지만, 24시간 영상 전체에 타일 수만큼 시간이 곱해지고, 차처럼 큰 물체가 타일 경계에서 조각나 합치기가 어려워진다. 사람·차는 줄어들지만 않으면 충분히 크다.
- 채널 B는 D-04에서 "사전 필터"로만 검토하던 움직임 감지를 **후보를 만드는 채널**로 올린 것이다 (D-71이 D-04·U-07을 바꿈). 전체 프레임이 아니라 ROI만 보므로 조명·비의 오탐이 줄고 비용도 작다.
- 두 채널이 같은 물체를 잡으면 채널 B 덩어리를 채널 A 트랙에 붙여 하나로 친다(위 (a), D-96). 겹침 기준 수치는 🚧 (U-09). 후보 병합은 🚧 (U-13)
- 청크는 디코딩에만 쓴다. 탐지·추적(채널 A·B)은 프로세스 1개가 영상 처음부터 끝까지 한 줄로 한다 (D-76, [02장 2.6](02-architecture.md#26-청크-분할과-병렬-처리)). 청크 경계에서 프레임이 빠지거나 겹치지 않게 자른다(시크 후 청크 시작 전 프레임 버리기). 샘플링 fps, 디코딩 청크 길이, 디코딩 프로세스 수는 🚧 (U-06). 날아오는 물체는 낮은 fps에서 한두 프레임에만 걸리므로, **ROI 안은 fps를 높이는 안**도 함께 잰다.
- 중간 저장: 구간마다 트랙 파일과 추적기 상태를 저장한다. 저장 순서는 구간 파일 → 추적기 상태 → `processed_sec` (D-76, 04장 4.8·4.9). 간격은 🚧 (U-06). 도중에 죽은 작업은 재전달된 메시지를 받은 워커가 이어서 한다 (6.2, D-94). 추적기 상태 형식과 이어서 할 때의 순서는 아래 "채널 A 켜고 끄기"의 "추적기 상태 파일 내용"과 "이어서 하기" (D-97)
- 본인 차량은 추적하지 않는다. 입력한 bbox를 고정 영역으로 쓴다 (D-29). 본인 차량과 옆 차에 걸리는 채널 A 트랙(주차된 차 자체)은 "움직이지 않는 트랙"으로 뺀다.

### 채널 A 켜고 끄기 (D-97)

**요약**: 채널 B(움직임 감지)는 영상 전체에 돈다. 채널 A(YOLO + ByteTrack)는 **ROI 움직임을 처음 감지한 때부터 15초 전 ~ 마지막으로 감지한 때부터 20초 후** 구간에만 돈다.

**이유**: 차에 접촉하려면 무언가가 ROI 안에서 움직여야 한다. 움직임이 없는 시간에 YOLO를 돌려도 후보가 나오지 않는다. 24시간 영상은 대부분 차 옆에 움직임이 없어 YOLO 연산이 크게 준다. 하루 종일 움직임이 있는 최악의 경우에도 영상 전체에 돌리는 것과 같다.

**수치** (초기값이며 실측으로 조정한다, 🚧 U-06)

- **켤 때 거슬러 올라가는 시간 15초**: 사용자 클립 앞부분(−10초, 1.6)에 ByteTrack 워밍업 5초를 더한 값이다. 새 트랙은 몇 프레임 연속으로 잡혀야 확정되고, 처음 몇 프레임은 박스가 불안정하다. 클립 첫 프레임에서 사람 트랙이 이미 안정돼 있어야 비식별화 폴백(6.8)에 빈틈이 없다.
- **끌 때 여유 20초**: 사용자 클립 뒷부분(+20초, 1.6)과 같다.

**ROI 움직임의 정의**: 한 프레임에서 채널 B의 전경 덩어리 중 하나라도 ROI와 겹치면 그 프레임에 ROI 움직임이 있다. 노이즈 크기 이하의 덩어리는 뺀다. 노이즈 기준과 전경 임계값은 🚧 (U-09)이다. **임계값은 낮게** 잡는다. 움직임을 놓치면 YOLO가 켜지지 않아 후보를 잃는다. 반대로 잘못 켜지면 YOLO를 조금 더 돌릴 뿐이다.

**동작 규칙**

1. **켜기**: YOLO가 꺼진 상태에서 ROI 움직임이 감지되면 YOLO를 켠다. 이때 감지 시각 15초 전부터 감지 시각 직전까지의 프레임에 먼저 YOLO를 돌리고, 그다음 감지 프레임부터 정상적으로 이어 간다. 15초 전 프레임은 **링 버퍼**에서 가져온다. 링 버퍼는 최근 15초의 분석 크롭 프레임(샘플링 fps)을 항상 메모리에 들고 있다. 영상 시작이 15초보다 가까우면 영상 시작부터 돌린다.
2. **연장**: YOLO가 켜진 동안 ROI 움직임이 감지될 때마다, 끌 시각을 "그 감지 시각 + 20초"로 다시 정한다.
3. **끄기**: 끌 시각에 도달하면 YOLO를 끈다. 이후에는 채널 B만 돈다.
4. **다시 켤 때 겹침 처리**: 꺼진 지 15초가 안 돼 다시 켜지면, 거슬러 올라갈 범위의 앞부분이 이미 YOLO를 돌린 구간이다. 이미 돌린 프레임은 다시 돌리지 않고, 마지막으로 돌린 프레임의 다음 프레임부터 돌린다. 이 경우 YOLO가 돈 구간은 끊기지 않으므로 앞 구간에 이어 붙여 하나의 구간으로 기록한다. 같은 프레임을 두 번 돌리면 같은 시각에 트랙 줄이 두 번 생기고 ByteTrack 상태가 꼬인다.
5. **ByteTrack은 영상 하나에 한 인스턴스**: 껐다 켜도 새로 만들지 않고 끝까지 같은 인스턴스를 쓴다. 그래서 `track_id`가 영상 안에서 겹치지 않는다(04장 4.8). 꺼진 동안 사라진 물체의 트랙은 ByteTrack이 시간이 지나 스스로 정리한다.
6. **채널 B 연결 순서**: 한 프레임에서 YOLO 결과를 먼저 내고, 그다음 채널 B 덩어리를 채널 A 트랙에 붙인다(D-96 (a)). 거슬러 돌린 덕분에 움직임이 처음 감지된 프레임에도 채널 A 트랙이 이미 있다.
7. **영상 끝**: 영상이 끝날 때 YOLO가 켜져 있으면 마지막 프레임 시각에 구간을 닫는다.

**예시**

| 원본 시간 | 일어난 일 | YOLO |
|---|---|---|
| 0~99초 | ROI 움직임 없음 | 꺼짐. 채널 B만 돈다 |
| 100초 | 사람이 ROI에 들어옴 (첫 움직임) | 버퍼의 85~100초를 먼저 돌리고 켠다. 끌 시각 120초 |
| 100~112초 | 계속 움직임 | 켜짐. 끌 시각이 계속 밀려 132초 |
| 112~132초 | 움직임 없음 | 켜짐 유지 |
| 132초 | 끌 시각 도달 | 끈다. YOLO 구간 [85, 132] |
| 140초 | 다른 사람이 ROI에 들어옴 | 15초 전은 125초지만 132초까지는 이미 돌렸다. 132초 다음 프레임부터 돌리고 켠다. 구간은 [85, …]로 이어진다 |

**메모리**: 링 버퍼는 640×640 RGB, 10fps 기준 약 180MB다. 워커는 작업을 하나씩 처리하므로(D-94) 동시 사용자가 늘어도 버퍼는 작업 하나 분량이다.

**YOLO 구간 기록**

- YOLO가 돈 구간 목록(원본 시간의 [시작, 끝] 목록, 처음부터 누적)을 **추적기 상태 파일**(`videos/{video_id}/tracks/tracker_state`, 04장 4.9)에 함께 저장한다.
- 트랙 파일만으로는 이 정보를 알 수 없어서 따로 기록한다. 트랙 줄이 없는 시각은 "YOLO가 꺼져 있었다"일 수도 있고 "켜져 있었는데 아무것도 없었다"일 수도 있다.
- 쓰이는 곳: 다시 켤 때 겹침 처리(규칙 4), 이어서 하기(아래), 클립을 만들 때 YOLO가 돌지 않은 부분 보충(6.7).

**추적기 상태 파일 내용**: JSON 하나이며, 구간 파일을 저장할 때마다 덮어쓴다. 형식은 06장에서 정한다는 04장 4.9를 따른다.

- `processed_sec`, 다음에 쓸 `track_id` 번호
- 채널 A·B ByteTrack 상태(직렬화 가능한 형태)
- YOLO가 지금 켜져 있는지, 켜져 있다면 끌 시각, 마지막으로 YOLO를 돌린 프레임 시각
- YOLO 구간 목록 전체

**이어서 하기** (D-94): 작업이 중간에 죽어 다른 워커가 이어받을 때의 절차다.

1. 추적기 상태 파일을 읽어 위 상태와 두 ByteTrack을 복원한다.
2. `processed_sec` 15초 전부터 `processed_sec`까지 디코딩한다. 이 구간은 **링 버퍼와 MOG2 배경 모델을 다시 채우는 용도로만** 쓴다. 움직임 판정, YOLO 실행, 트랙 쓰기는 하지 않는다. 링 버퍼와 MOG2 배경 모델은 메모리에만 있고 저장하지 않기 때문이다. 15초로 배경이 충분히 안정되는지는 ⚠️ 확인이 필요하다.
3. `processed_sec` 다음 프레임부터 위 동작 규칙대로 이어 간다. 저장 시점에 YOLO가 켜져 있었으면 켜진 상태로 시작한다.

### 내 차 바닥 네 모서리로 시야 판단과 ROI 정하기 (D-98)

**요약**: 사용자에게 **내 차가 바닥에 닿는 네 모서리**를 화면에서 찍게 한다. 이 사각형 하나로 세 가지를 한다. ① 바닥점이 차의 어느 면 쪽에 있는지 판단하는 기준(바닥점 필터), ② 사각형이 찌그러진 정도로 **CCTV 시야(내려다보는 각도)** 파악, ③ 사각형의 크기로 **내 차가 카메라에서 얼마나 먼지** 파악. ②와 ③으로 ROI 크기를 정한다. 구체적인 수치와 계산 방법은 추후 정한다 🚧 (U-30).

**왜 필요한가**

- ROI를 내 차 bbox에 고정 배율로 더하는 방식은 카메라 높이를 반영하지 못한다. 같은 차라도 카메라 구도에 따라 가려지는 영역이 크게 다르다.
- **카메라가 높아 차를 위에서 내려다볼수록** 차 너머 바닥까지 보인다. 가려지는 영역이 작으므로 ROI를 작게 잡아도 된다. 불필요한 움직임이 줄어 후보도 줄어든다.
- **카메라가 낮아 차를 옆에서 볼수록** 내 차가 차 너머를 많이 가린다. 안 보이는 파손 쪽에서 일어나는 움직임은 지붕 위로 나온 머리나 상체로만 보이므로 ROI를 크게 잡아야 한다.
- 차가 카메라에서 멀면 화면에서 작게 보이고 가까우면 크게 보인다. 고정 픽셀로는 거리를 반영하지 못한다.
- 주차칸 흰 선은 쓰지 않는다. 내 차가 접근하는 쪽의 선을 가리는 경우가 많기 때문이다. 내 차의 바닥 모서리는 바퀴 위치로 대략 짐작할 수 있다.

**입력**

1. 내 차가 바닥에 닿는 네 모서리. 화면에 보이지 않는 모서리(차 너머)는 사용자가 짐작해서 찍는다.
2. 파손이 있는 변. 한 변, 또는 모서리 파손이면 이웃한 두 변을 고른다. 6.4의 통로 쪽 / 옆면 구분 입력을 이것이 대신한다 (U-26 → D-98).

**네 모서리에서 읽는 것**

| 사각형에서 보는 것 | 알 수 있는 것 | 쓰는 곳 |
|---|---|---|
| 찌그러진 정도 (실제 차 바닥은 폭 약 1.8m × 길이 약 4.7m인데 화면에서 얼마나 납작한가, 차 bbox 높이 대비 사각형 세로 높이 등) | 카메라가 내려다보는 각도. 납작할수록 낮은 카메라 | ROI를 위쪽(차 너머 가려짐)으로 얼마나 넓힐지 |
| 크기 (변의 화면상 길이) | 내 차까지의 거리. 작을수록 멀다 | ROI·크롭 크기를 화면 픽셀로 환산하는 자 |
| 각 변의 위치 | 차의 앞·뒤·좌·우 면이 화면 어디에 있는지 | 바닥점이 어느 면 쪽에 있는지 판단 (바닥점 필터) |

**ROI를 정하는 방향**

- **파손이 보이는 경우**: ROI는 사용자가 드래그한 파손 영역이 기준이다. 넓히는 양은 🚧.
- **파손이 안 보이는 경우**: 파손 변 바로 바깥에 선 물체(사람 등)가 화면에 나타나는 자리를 ROI로 잡는다. 카메라가 낮을수록 그 자리는 내 차 몸체와 지붕 위쪽으로 넓게 퍼지므로 ROI가 커지고, 높을수록 파손 변 주변의 얇은 띠로 줄어든다. 위·아래·가로로 넓히는 양은 🚧.
- 보여줄 크롭과 분석 크롭도 같은 자(네 모서리에서 구한 거리)로 정한다. ROI ⊂ 보여줄 크롭 ⊂ 분석 크롭이다 (D-95).

**정하지 않은 것** 🚧 (U-30)

- 찌그러진 정도와 크기를 어떤 값으로 계산할지.
- 그 값에서 ROI·보여줄 크롭·분석 크롭을 얼마나 넓힐지(상한·하한 포함).
- 사용자가 모서리를 잘못 찍었을 때(사각형이 꼬였거나 차 bbox와 크게 어긋남) 어떻게 할지.
- 실제 영상(높은 카메라, 낮은 카메라, 가까운 차, 먼 차)으로 확인한 뒤 정한다.

**한계**

- 차보다 낮은 물체가 차 너머에서 움직이면 ROI를 키워도 보이지 않는다. 이때 남는 단서는 내 차 흔들림, 가려졌다 다시 나타남, 그림자다.
- 보이지 않는 모서리는 사용자의 짐작이라 오차가 있다. 그래서 이 사각형으로는 **확실히 아닌 것만** 뺀다 (D-91).

### 바닥점 필터 (근접 판정)

> 이 절은 D-98(네 모서리 입력)에 맞춰 다시 쓸 예정이다. 바닥선·띠를 차 bbox 아래 변 대신 네 모서리 사각형으로 바꾸고, 파손 변 쪽이 아닌 구역에서만 움직인 것이 확실한 트랙을 뺀다. 구체 규칙은 🚧.

2D에서 bbox가 겹친다는 것만으로는 부족하다. 카메라와 내 차 사이를 지나가는 모든 것이 겹쳐 보인다. 그래서 **바닥 위의 위치**를 명백하게 무관한 통행만 제외하는 보조 정보로 쓴다. **근접을 증명해야 통과하는 조건이 아니다.** 바닥점을 신뢰할 수 있고 관찰된 움직임까지 고려했을 때 접촉 가능한 영역에 접근하지 않았음이 명확한 경우에만 제외한다 (D-91).

| 용어 | 뜻 |
|---|---|
| 바닥점 | 트랙 bbox 아래 변의 가운데. 물체가 바닥에 닿는 자리로 본다 |
| 바닥선 | 본인 차량이 바닥에 닿는 경계. 처음에는 **차량 bbox 아래 변**으로 두었다. D-98로 바닥 네 모서리 사각형으로 바꾼다 🚧 |
| 띠 | 바닥선 바로 아래(카메라 쪽)의 좁은 영역. 폭은 **차량 bbox 높이에 비례**한다(비율 🚧 U-30). 원근 때문에 멀리 있는 차는 작게 보이므로 고정 픽셀 폭을 쓰지 않는다 |

- **보이는 파손**: 트랙의 바닥점이 파손 부위의 가로 범위 근처에서 **띠 안**에 들어오면 근접 후보로 남긴다. 띠 밖이라는 사실만으로 제외하지 않는다.
- **안 보이는 파손**: 트랙의 바닥점이 바닥선 **위쪽**(차 너머)에 있거나, 차에 가려 사라졌다 다시 나타나거나, 인접 영역에 머무르면 근접 후보로 남긴다. 가려진 동안의 위치를 알 수 없으면 비접촉으로 단정하지 않는다.
- **전제**: 바닥이 평평하다. 바닥점의 y는 카메라 구도와 가림에 따라 신뢰도가 달라지는 대략적인 단서다. bbox 아래 변의 가운데를 계산할 수 있다는 것만으로 실제 바닥 접촉점이 확인된 것은 아니다.
- **확장**: 주차 칸 선의 네 점으로 바닥 호모그래피를 구하면 미터 단위 거리로 판정할 수 있다. 칸 규격(2.5×5.0m ⚠️)을 기준으로 쓴다. 지금은 하지 않는다.
- **바닥점을 믿을 수 없는 트랙은 거르지 않는다.** 채널 B 덩어리가 불안정하거나, 발이 가려졌거나, 화면 가장자리에서 잘렸거나, 공중에 떠 있는 물체(날아옴)가 그렇다. 이런 트랙은 후보로 남기고 VLM이 본다 (6.6의 1차 필터 (b)안).

### 0단계 필터 원칙

**"확실히 관계없는 것만 빼고, 판단이 안 되면 남긴다."** 트랙 단위로, 트랙이 파손 부위에 가장 가까웠던 순간을 기준으로 판정한다.

| 뺀다 | 남긴다 |
|---|---|
| 바닥점을 신뢰할 수 있고, 관찰된 움직임상 접촉 가능한 영역에 접근하지 않았음이 명확하며 다른 접촉 가능성 단서도 없음 | 띠 안이거나, 띠 밖이어도 접촉 가능성을 배제할 수 없음 |
| 너무 짧거나 너무 작은 트랙 (노이즈). 기준 🚧 | 바닥점을 믿을 수 없음 |
| 화면 전체가 동시에 바뀜 (조명 변화, 카메라 흔들림) | 날아옴·떨어짐처럼 공중 물체 |
| 움직이지 않는 트랙 (주차된 차) | 안 보이는 면의 신호 (차 너머, 가려짐·재등장, 체류) |

- **바닥점이 구해져도 손·문·소지품·쓰러지는 물체 끝부분이 닿을 가능성이 있으면 남긴다.** 밑동이나 발이 띠 밖이라는 이유만으로 제외하지 않는다. 객체탐지 또는 움직임 감지의 다른 단서가 접촉 가능성을 보여주는 경우에도 바닥점 필터로 제외하지 않는다 (D-91).
- 바닥점을 구하지 못하거나 신뢰할 수 없는 후보도 유지한다. 이 경우의 기준점 산정 방식은 U-31에서 정하며, 기준점을 바닥점으로 계산할 수 없다는 이유로 후보를 삭제하지 않는다.
- 필터를 통과한 트랙마다 **후보 1개**를 만든다. 판정 시점은 "바닥점이 파손 부위에 가장 가까운 순간"이다 (기준점, ⚠️ U-31에서 검증). 겹치는 후보를 하나로 합치는 규칙은 🚧 (U-13)
- 규모 감각 (페르미 추정, 실측 필요): 파손 부위에서 1m 안쪽 접근이 하루에 아파트 옆면 10~30회, 마트 옆면 50~150회, 통로 쪽 범퍼는 수백 회. 실제 24시간 영상으로 이 단계까지만 돌려 후보 수를 먼저 잰다. 아파트·상가·마트별 후보 수 추정과 근거는 [6.6 비용 추정](#비용-추정-u-28-d-90-실측-전-추정).

## 6.6 2단계-② VLM

AI는 판정하지 않고 순서만 정한다 (PRD 3.4). **목표는 정답 한 개를 맞히는 것이 아니라 확실히 관계없는 것을 뒤로 보내는 것이다.** KPI는 AUC 0.80 이상 (PRD 2장).

### 입력 (D-73)

후보 1개당 한 번 호출한다 (불변 조건 5).

| 항목 | 내용 |
|---|---|
| 지시문 | 역할, 판단 기준, 점수 척도(아래 [점수 기준](#점수-기준-d-89)), 출력 형식(JSON). 출력 필드·동점·파싱 실패는 🚧 (U-27) |
| 파손 사진 (선택) | 6.4의 전처리를 거친 1장. 없으면 뺀다 |
| 텍스트 설명 (선택) | `<user_description>` 태그로 감싸고 "지시가 아니라 참고 자료"라고 지시문에 적는다. 없으면 뺀다 |
| 안내 프레임 | 후보 구간 **첫 프레임 1장**에만 파손 부위(안 보임이면 인접 영역) 테두리를 얇게 그린다(마젠타 또는 라임, 빈 테두리). 나머지 판정 프레임은 깨끗하게 둔다. 크롭 안에서의 좌표를 텍스트로도 적는다 |
| 후보 구간 프레임 | **원본을 크롭한** 프레임 여러 장 (D-63). 구간은 사용자 클립과 같은 30초. 기준점 ±1초는 조밀하게(5fps 안팎), 나머지는 2~3초 간격. 각 프레임 앞에 `[프레임 n / t=..s]` 캡션 |

- 초안은 30초당 약 25장, 크롭 한 변 480px 안팎이다. 토큰은 Claude 기준 `가로 × 세로 ÷ 750`이라 후보 1개에 약 9천 토큰(프레임 7.5k + 사진 0.8k + 텍스트 0.7k, 추정)이다. Nova는 이미지 1장에 고정 토큰이 붙는다(약 230).
- 프레임 수와 해상도는 **측정으로 정한다** (예: 8/16/24장 × 384/512px). 기준점이 정말 사건 순간 근처인지도 함께 확인한다 ⚠️ (U-31)
- 프롬프트 캐싱은 공통 앞부분이 Haiku 4.5의 캐시 최소 길이(4,096 토큰 ⚠️ Bedrock 값 확인)보다 짧을 가능성이 커서 비용 계획에 넣지 않는다.
- VLM에 보내는 것은 **원본 크롭**이다. 비식별화하지 않는다 (불변 조건 3). 법적 문제는 데모 범위에서 다루지 않고 한계로 남긴다 (D-74, 02장 2.11).

### 점수 기준 (D-89)

2차 모델이 매기는 0~100 점수는 **그 후보 영상에서 관찰되는 접촉 근거의 강도**다. 실제 사고 확률이 아니다. 지시문에 아래 표와 가림 처리 원칙을 그대로 넣는다.

| 점수 | 판단 기준 |
|---|---|
| **0~19** | 파손 부위와 객체의 이동이 충분히 보이며, 떨어져 통과하는 등 **접촉하지 않았다는 근거가 명확하다** |
| **20~39** | 파손 부위 방향으로 접근했으나, 관찰 가능한 구간에서는 **접촉 가능한 거리까지 인접하지 않았고 접촉을 뒷받침하는 단서도 없다** |
| **40~59** | 파손 부위 또는 가려진 부위의 인접 공간까지 접근했으나, **접촉 여부를 판단할 근거가 부족하다** |
| **60~79** | 접촉 가능한 위치까지 접근했고, 그 시점의 움직임 변화 등 **접촉을 뒷받침하는 간접 단서가 있으나 확실하지 않다** |
| **80~100** | **직접 접촉 장면이 명확하게 보이거나**, 접촉 순간이 가려져도 위치·시간이 일치하는 복수의 간접 단서가 접촉을 강하게 뒷받침한다 |

**가림 처리 원칙**

- 가려져 보이지 않는다는 사실만으로 점수를 낮추거나 높이지 않는다.
- 객체가 가려진 동안 더 가까이 접근했는지 알 수 없다면 "인접하지 않았다"고 단정하지 않는다.
- 간접 단서는 영상에서 실제로 관찰된 내용만 쓰며, 보이지 않는 접촉을 추정 사실처럼 서술하지 않는다.

**판정 방식**

- 구간 경계는 근거의 종류로 나눈다: 불접촉 근거 명확(0~19) → 접근했지만 인접하지 않음(20~39) → 인접했지만 근거 부족(40~59) → 간접 단서 있음(60~79) → 직접 장면 또는 복수 단서(80~100). 구간 안의 세부 점수는 근거의 양과 선명도로 정한다.
- 이 점수는 정렬에만 쓴다 (6.7). 점수 구간으로 자동 판정하거나 사용자에게 "사고 확률"로 보여주지 않는다 (PRD 3.4).
- **1차 탈락 기준은 0~19 구간이다.** 1차 모델은 점수를 매기지 않고 "0~19에 확실히 해당하는가"만 묻는다. 확실하면 탈락, 조금이라도 애매하면 통과다. 물체 없이 빛·그림자만 바뀐 장면(노이즈)도 접촉 근거가 없으므로 여기에 든다. 이 기준은 1차 탈락률과 A 클립 탈락 여부를 실측한 뒤 바꿀 수 있다 (U-32).
- 1차에서 탈락한 후보의 0점은 2차 모델이 매긴 점수가 아니라 "1차 탈락" 표시다. 정렬과 AUC에서는 0점으로 같이 다룬다.
- 출력은 점수와 짧은 근거다(비용 추정의 출력 약 150토큰). 출력 필드, 동점 처리, 파싱 실패 처리는 🚧 (U-27).

### 1차·2차 구조 (D-74)

| | 1차 | 2차 |
|---|---|---|
| 목적 | **확실히 아닌 것**(점수 기준 0~19에 확실히 해당)만 탈락 | 남은 후보에 점수 |
| 출력 | 통과 / 탈락 | 0~100 점수 |
| 모델 | **Nova Lite** (잠정. 측정 후 바꿀 수 있다). 비교 후보: Nova 2 Lite | **Claude Haiku 4.5**. 품질이 모자라면 Sonnet 5 |
| 입력 | 위 표와 같다. 우리가 샘플링한 이미지를 넣는다 | 같음 |

- **점수는 2차 모델 하나에서만 나온다.** 1차에서 탈락한 후보는 **0점**을 받아 정렬 맨 아래에 남는다. 후보 수는 줄지 않는다 (불변 조건 4, PRD 3.4 AC). AUC 계산에서도 0점으로 넣는다.
- **1차에 보낼 후보** — 두 안을 모두 적고, (a)부터 해 본다.
  - (a) **모든 후보**를 1차에 보낸다.
  - (b) **바닥점을 믿을 수 없는 후보만** 1차에 보낸다. 바닥점이 띠 안인 후보는 1차를 건너뛰고 바로 2차로 간다.
  - (a)로 실제 영상에서 1차가 얼마나 걸러내는지 잰 뒤, 걸러내는 양과 A 클립 탈락 여부를 보고 (a)와 (b) 중 하나로 정한다 🚧 (U-32).
- 1차 통과 기준: 조정용 A 클립이 1차에서 하나도 탈락하지 않을 것.
- Nova 2 Lite는 영상을 직접 받아 스스로 샘플링하지만 1fps로 고정되고, 공식 문서상 공간 추론에 한계가 있다. 그래서 영상 직접 입력이 아니라 우리 샘플 이미지를 넣어 비교하고, 최종 점수용(2차)으로는 쓰지 않는다.
- temperature 0 (1.6). **점수는 도구 강제 호출로 받는다** (D-93). Converse API에 점수 제출 도구 하나를 정의하고(입력 스키마: D-89 구간 값만 허용하는 정수 `score` + 짧은 근거) `toolChoice`로 그 도구를 반드시 부르게 한다. 자유 문장 응답을 파싱하지 않는다. ⚠️ 1차 Nova Lite의 `toolChoice` 지정 지원은 구현 전 문서로 확인한다.
- **파싱 실패**: 도구 호출이 없거나, 스키마에 어긋나거나(범위 밖 값 등), 응답이 잘린 경우다. 시스템 오류(스로틀링·5xx·타임아웃)는 파싱 실패가 아니라 장애로 다룬다(바로 아래). 파싱 실패하면 오류 내용을 붙여 다시 부른다. **최초 호출 포함 최대 3회**다. (D-93)
  - **1차**에서 끝내 실패한 후보는 탈락시키지 않고 **통과로 보고 2차로 보낸다.** 재현율 우선이다.
  - **2차**에서 끝내 실패한 후보는 0점을 주지 않고 **파싱 실패 목록**으로 보낸다(6.7).
  - **실패율 상한**: 1차·2차 각각, 재시도를 포함한 전체 호출 시도 중 파싱 실패 시도가 **30%를 넘으면** 작업을 `failed`로 바꾸고 `error_message`에 "VLM 파싱 실패율 초과"를 적는다. 프롬프트·도구 정의가 잘못됐다는 신호이므로 개발자가 프롬프트를 고친다. VLM 단계를 마친 뒤 판정한다.
- **장애**(스로틀링·5xx·타임아웃 등)는 대기 시간을 늘려 가며 재시도하고, 그래도 일정 시간(예: 총 10분)을 넘기면 작업을 `failed`로 바꾼다. 룰 점수만으로 조용히 끝내지 않는다 (6.12, D-93).

### 비용 추정 (U-28, D-90, 실측 전 추정)

비용은 **후보 수 × 후보 1개당 비용**이다. 후보 수는 6.5의 산출 방식에 가정을 넣어 추정했고, 1개당 비용은 위 입력 구성으로 토큰을 계산했다. 모두 실측으로 바꿀 값이다.

**① 하루치(24시간) 영상의 후보 수 추정**

산출 방식(6.5): 채널 A(차·사람·동물)와 채널 B(근접 영역 움직임)의 트랙 → 바닥점 필터 → 확실히 관계없는 것만 제거 → **트랙 1개 = 후보 1개**. VLM 1차에서 탈락해도 0점으로 남으므로 후보 수는 줄지 않는다. 그래서 후보 수는 유동인구보다 **파손 쪽(옆면/통로 쪽), 보임 여부, 병합 규칙(U-13)**에 크게 좌우된다.

## 6.7 2단계-③ 정렬과 후보 클립

- 점수 내림차순으로 정렬해 `rank`를 매긴다. 동점 처리 규칙 🚧 (U-27)
- **목록은 두 개다** (D-93): 점수가 나온 **후보군 목록**과, 2차 파싱에 끝내 실패한 **파싱 실패 목록**. 파싱 실패 후보는 후보군 목록의 순위에 넣지 않는다.
  - 파싱 실패 목록도 10개 단위 묶음으로 보여주고, 클립 만들기·비식별화는 후보군 목록과 **같은 방식**이다(처음에 상위 20개를 만들고 이후 한 묶음 앞서 준비). 목록 안의 순서는 🚧.
  - 04·05·07 반영(파싱 실패 표시 칼럼, 목록 API, 화면)은 해당 담당자가 정한다 🚧.
- **처음에 상위 20개(묶음 2개)의 클립을 만든 뒤 "확인 가능"으로 바꾼다.** (D-68)
- 사용자가 [다음]을 누르면 이미 준비된 다음 묶음을 **바로** 보여준다. 동시에 백엔드가 다음 묶음 작업을 넣어 GPU를 켜고, 그다음 묶음(예: 21~30번)을 비식별화한다. 항상 **한 묶음 앞서** 준비한다.
  - 사용자가 준비 속도보다 빨리 [다음]을 누르면 기다린다. 한 묶음을 확인하는 데 최대 5분이 걸리므로 드물다.
- 클립 구간: 판정 시점 −10초 ~ +20초, 영상 경계에서 자른다 (1.6).
- **클립 구간에 YOLO가 돌지 않은 부분이 있으면 클립을 만들 때 그 부분만 YOLO를 돌린다** (D-97).
  - 왜 생기나: YOLO 구간은 ROI **움직임** 시각으로 정해지고, 클립 구간은 **판정 시점**(바닥점이 파손 부위에 가장 가까운 순간)으로 정해진다. 둘은 다를 수 있다. 예: 사람이 100초에 ROI에 들어와 112초에 차 옆에 멈춰 선다. 멈춘 몸은 MOG2 배경으로 흡수되어 마지막 움직임은 112초, YOLO는 132초에 꺼진다. 그런데 바닥점이 가장 가까운 순간이 125초라면 클립은 115~145초다. 132~145초에는 YOLO 결과가 없어 사람 트랙이 없고, 비식별화 폴백(사람 전체 가리기, 6.8)을 그 구간에 적용할 수 없다.
  - 방법: 클립 구간에서 YOLO 구간 목록(6.5 "YOLO 구간 기록")에 들어가지 않는 빈 구간마다, 빈 구간 시작 5초 전부터(워밍업, 영상 시작 전이면 영상 시작부터) 빈 구간 끝까지 YOLO + ByteTrack을 새 인스턴스로 돌린다. 결과는 **그 클립의 비식별화에만** 쓰고 트랙 파일·후보에는 넣지 않는다(후보 탐지 결과를 바꾸지 않기 위해서다).
  - 상위 20개와 다음 묶음 클립에만 하므로 비용이 작다.
- **클립은 본인 차량 주변으로 크롭한다** (D-70). 크롭 크기는 🚧 (U-30). 보여주는 범위가 줄어 비식별화를 놓쳐도 노출이 작아진다. 이 **보여줄 크롭**은 분석 크롭(6.5)보다 작고, 비식별화 탐지는 분석 크롭에서 한다(6.8, D-95).
- 인코딩: H.264 코덱 MP4 (Flutter Web 재생 조건, D-08).
- 클립 생성 실패는 D-51을 따른다.

## 6.8 비식별화

(D-69)

**대상**: 사람 **얼굴**과 차량 **번호판**. 사람 몸 전체를 기본으로 가리지 않는다.

- **폴백**: 사람으로 탐지됐는데 그 bbox 안에서 얼굴을 찾지 못하면 **그 사람 전체를 가린다.** 판단은 프레임이 아니라 **트랙 단위**다. 한 트랙에서 얼굴이 안정적으로 잡히지 않으면 그 트랙의 모든 프레임을 사람 전체로 가린다. 프레임마다 판단하면 모자이크가 깜빡이며 얼굴이 드러나는 프레임이 생긴다.
- 사람 트랙은 채널 A의 COCO `person` 트랙을 그대로 쓴다.

| 정지 장면 (1단계) | 프레임 전체 **타일** 탐지 | 본인 차량을 아직 모른다. 1장이라 느려도 된다 |
| 후보 클립 (2단계, 다음 묶음) | **분석 크롭**(보여줄 크롭보다 큼)에서 탐지·추적하고, 모자이크는 보여줄 크롭에만 적용 (D-95) | 작은 얼굴·번호판이 상대적으로 커진다. 크롭 경계에 걸쳐 들어오는 얼굴·번호판도 경계 밖에서부터 온전히 잡혀 트랙이 이어진다 |

**누락을 줄이는 방법** — 재현율(놓치지 않기)이 정밀도보다 중요하다. 위에서부터 차례로 적용하고, 앞의 것으로 부족할 때만 다음으로 간다.

1. 탐지 임계값을 낮춘다. 오탐(엉뚱한 곳 모자이크)은 받아들인다.
2. 추적으로 빈 프레임을 채운다 (D-88). 별도 추적 모델은 두지 않는다.
   - 얼굴·번호판 탐지 결과를 **ByteTrack**으로 묶는다. 채널 A와 같은 코드를 쓰되, 입력은 보여줄 클립의 **모든 프레임**이다. ByteTrack은 점수가 낮은 탐지도 기존 트랙에 이어 붙이므로 낮은 임계값과 잘 맞는다.
   - ByteTrack은 앞으로만 진행하고, 놓친 프레임에는 박스를 내지 않는다. 저장된 영상이라 뒤 프레임도 볼 수 있으므로 **양방향 후처리**를 붙인다.
     - 구간 보간: 한 트랙에서 탐지가 끊긴 구간은 앞뒤 bbox를 선형으로 이어 채운다.
     - 앞뒤 연장: 트랙의 첫 bbox는 앞으로, 마지막 bbox는 뒤로 몇 프레임 늘린다. 프레임 수 🚧 (U-09)
     - 박스 확대: 보간·연장한 bbox는 오차를 감안해 크게 친다. 비율 🚧 (U-09)
   - 후처리는 CPU 계산이라 처리 속도에 거의 영향이 없다.
   - ⚠️ Ultralytics에 들어 있는 ByteTrack은 AGPL이다. 원본 ByteTrack(MIT) 또는 MIT 구현체를 쓴다. 구현체를 고를 때 라이선스를 확인한다.
3. 작은 대상은 크롭해 키워서 탐지한다. 크롭은 사용자 입력(본인 차량) 주변이다.
   - 모델은 어떤 크기가 들어와도 자기 입력 크기로 바꿔 탐지한다. 그래서 탐지 성능을 정하는 것은 크롭 크기 자체가 아니라 **입력 크기로 바꾼 뒤 얼굴·번호판이 몇 px가 되느냐**다.
   - 크롭이 입력보다 크면 줄어들어 작은 대상이 사라진다. 입력보다 작으면 키워져 대체로 좋아지지만, 지나치게 작으면 흐려져 오히려 성능이 떨어진다.
   - 모델은 입력을 **레터박스**로 바꾼다. 가로세로 비율을 유지한 채 긴 변을 입력 크기에 맞춰 같은 배율로 줄이거나 키우고, 남는 쪽은 회색으로 채운다. 그래서 내용이 찌그러지지 않고, 성능을 정하는 것은 **배율 = 모델 입력 크기 ÷ 타일 긴 변** 하나다.
   - **확정 규칙: 타일 긴 변 ≤ 모델 입력 크기** (배율 ≥ 1, D-95). 어떤 영상이든 원본보다 줄어드는 일이 없다. 영상 속 얼굴·번호판이 몇 px인지 미리 알 수 없으므로, 영상과 관계없이 안전한 규칙을 둔다.
   - 더 키울지(예: 타일 긴 변 = 입력의 1/2, 2배 확대)는 실측으로 정한다 (U-30). 원본에서 이미 10px 안팎인 얼굴은 줄이지 않아도 놓치므로 키워야 잡힌다. 대신 타일 수가 약 4배가 되어 속도 기준(아래)과 부딪친다.
   - 탐지는 보여줄 크롭이 아니라 그보다 큰 **분석 크롭**(6.5)에서 한다 (D-95). 보여줄 크롭 경계에 반쯤 걸린 얼굴·번호판은 잘린 채로는 잘 안 잡힌다. 여백에서 미리 잡아 두면 경계를 넘어 들어올 때 트랙이 이미 이어져 있다.
   - 분석 크롭의 긴 변이 모델 입력 크기보다 크면 타일로 나눠 탐지한다. 타일은 겹치게 자르고, 타일 결과를 크롭 좌표로 합친 뒤 추적(위 2)하므로 타일 경계에서 트랙이 끊기지 않는다. 얼굴·번호판은 작아서 타일 경계에 걸려 조각날 일도 드물다. 30초 클립에만 하므로 타일 수만큼 느려지는 것은 받아들인다. 5분 안에 한 묶음(아래 처리 속도)을 못 맞추면 그때 영역을 줄인다.
   - 가로세로 비율을 유지한다. 정사각형 입력에 넣을 때 찌그러뜨리지 않는다.
4. 사람 bbox 안에서 얼굴을 못 찾으면 사람 전체를 가린다 (위 폴백, 트랙 단위).
5. 파인튜닝. 마지막 수단이다.

### 모델 후보 (D-88)

두 모델을 실측으로 비교한 뒤 정한다. 확정은 🚧 (U-09).

| | UrbanAnonymizer | EgoBlur Gen2 (Meta) |
|---|---|---|
| 구조 | D-FINE-X, 모델 1개(얼굴·번호판 2클래스), 입력 1408px | Faster R-CNN + ResNeXt, **얼굴·번호판 모델 2개**, 각 약 1억 400만 파라미터 |
| 공개 성능 | 저자 비교에서 얼굴·번호판 AP50이 EgoBlur Gen2보다 높다 (저자 보고). 추적 후처리를 붙이면 저자 영상에서 머리가 가려진 프레임이 87.4% → 95.8% | 모델 하나당 2MP 이미지 약 21ms (GPU 종류 미공개). 두 모델이면 프레임당 두 번 실행 |
| 실측에서 볼 것 | CCTV 구도, 한국 번호판 | CCTV 구도(1인칭 영상으로 학습), 두 모델 합산 속도 |

- 95.8%는 탐지 모델의 탐지율이 아니다. 저자 영상에서 **추적 후처리까지 붙였을 때** 머리가 가려진 프레임 비율이다. 우리 목표값과 바로 비교하지 않는다.
- **대안 경로 (증류)**: 속도 기준을 못 맞출 때 쓴다.
  - EgoBlur Gen2를 선생 모델로 우리 데이터에 의사 라벨을 붙인다.
  - 사람이 검수해 틀린 박스를 지우고 놓친 박스를 추가한다.
  - 더 가벼운 모델(예: D-FINE-S/M)을 얼굴·번호판 2클래스로 파인튜닝한다.
- 두 클래스를 모델 1개로 할지 2개로 할지는 실측에서 **얼굴·번호판 재현율을 따로** 재서 정한다. 한쪽만 떨어지면 그 클래스만 떼어 별도 모델로 만든다.
- 번호판은 번호를 읽지 않고(OCR 아님) 위치만 탐지하면 된다. 한국 번호판에서 탐지가 떨어지면 AI Hub 한국 번호판 데이터로 파인튜닝한다 (5번).
- 참고 (라이선스): 이번 범위는 시연이다. UrbanAnonymizer 가중치는 CC BY-NC 4.0(비상업), EgoBlur Gen2는 코드·가중치 Apache 2.0이다(내려받을 때 약관 동의). 실운영으로 넘어가면 EgoBlur Gen2 또는 이를 선생으로 증류한 모델을 쓴다.

### 속도 기준 (D-88)

- **다음 묶음 10개(30초 클립 × 10, 30fps 기준 약 9천 프레임)를 5분 안에** 비식별화한다. 얼굴·번호판을 합쳐 **약 30fps**가 필요하다. 사용자가 한 묶음을 보는 동안 다음 묶음을 준비하기 위해서다 (D-68).
- 보여줄 모든 프레임을 빠짐없이 처리한다 (샘플링하지 않음). 속도가 모자라면 먼저 입력 크기·모델 크기를 줄이고, 그래도 모자라면 증류 경로로 간다.
- 동시 사용자가 늘면 GPU 워커를 늘려 대응한다 ([02장 2.10](02-architecture.md#210-확장-방향-이번-범위-밖)의 GPU ASG). 이번 범위는 동시 사용자 1명 기준이다.

### 목표 (D-88)

- **제출 목표: 누락률 5% 이하 (재현율 95% 이상)**. 얼굴(사람)과 번호판 결과를 합산한다. 공공 데이터셋 기준이다 (PRD 2장 KPI).
- **추진 목표: 재현율 99%**. 실제 주차장은 차량이 서행하고, 본인 차량 주변만 크롭하고, 추적으로 빈 프레임을 채우므로 공공 데이터셋보다 유리하다. 검증 데이터셋은 조사 후 정한다 🚧 (U-34).
- 누락 판정: 정답 박스의 중심이 마스크로 가려졌으면 탐지, 가려지지 않았으면 누락이다. 크기와 관계없이 모든 정답 박스를 넣는다.
- 보고는 합산 수치로 하고, 내부적으로는 얼굴(사람)·번호판 수치를 따로 기록해 모델 선택과 개선에 쓴다.
- 측정 데이터셋은 🚧 (U-29).
- 번호판은 위치만 탐지하면 되므로 사람 전체 가리기 같은 대비책을 따로 두지 않는다.
- 차 안 운전자도 같은 얼굴·사람 탐지로 가린다. 별도 대책(앞유리 영역 가림 등)은 두지 않고, 탐지가 부족하면 파인튜닝한다 (U-35 해결).

## 6.9 원본 시간 규칙

- 후보의 판정 시점 = 청크 offset + 청크 내부 시간 (디코딩 단계에서 프레임마다 붙인다) (불변 조건 7)
- 후보 클립 구간 = 판정 시점 −10초 ~ +20초, 영상 경계에서 자른다
- VLM 입력 구간은 사용자 클립 구간과 같다 (D-73)

## 6.12 필수 VLM 정렬 (D-92)

VLM 정렬은 필수 처리 단계다. 1차 평가에서 낮은 후보를 0점으로 유지하는 기존 2단계 방식은 유지하며, 점수를 이유로 후보를 제거하지 않는다. 사진·설명은 선택 입력이므로 없어도 영상과 위치 정보로 VLM을 수행한다. 장애 시 조용히 룰 정렬만으로 완료 처리하지 않는다. 재호출·실패 처리는 6.6(D-93)을 따른다: 점수는 도구 강제 호출로 받고, 파싱 실패는 최초 포함 최대 3회 호출, 파싱 실패율 30% 초과나 장애 지속이면 `failed`.
