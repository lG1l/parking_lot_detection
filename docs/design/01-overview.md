## 1.4 작성 규칙

사람과 에이전트 모두 이 규칙을 따른다.

- 결정은 [11장](11-decisions.md)에 `D-01` 형식의 ID로 기록한다. 본문에는 결과만 적고 `(D-05)`처럼 근거를 링크한다.
- **새로 기록하는 결정은 상태를 "확정 필요"로 적는다.** 팀이 함께 검토한 뒤에만 "확정"으로 바꾼다. 한 사람과의 논의로 정한 것을 "확정"으로 적으면 다른 팀원이 검토 없이 구현한다. ([11장 상태 표기](11-decisions.md#목차))
- 결정을 바꿀 때는 기존 기록을 지우지 않는다. 새 결정을 추가하고 기존 결정에 "D-xx로 대체됨"을 표시한다.
- 미정 항목은 🚧로 표시하고 11장 미결정 목록에 `U-01` 형식의 ID로 올린다.
- 수치 상수는 [1.6](#16-주요-상수)에만 적고 다른 곳에서는 이름으로 참조한다.
- API·파일 형식 같은 인터페이스는 설명보다 예시 JSON으로 적는다.
- 반드시 지켜야 하는 규칙(불변 조건)은 [02장 2.4](02-architecture.md#24-이중-경로와-불변-조건)에 모아 둔다. 코드와 테스트는 이 조건을 기준으로 작성한다.

## 1.5 용어집

문서와 코드에서 아래 용어를 이 뜻으로만 쓴다.

**사람·역할**

| 용어 | 뜻 |
|---|---|
| 사용자 (피해자) | 차량이 파손되어 CCTV를 확인하려는 사람. 서비스 계정의 주인이다. |
| 관리자 | 주차장 관리자. 사용자의 계정으로 CCTV 영상을 업로드한다. |

**영상·시간**

| 용어 | 뜻 |
|---|---|
| 원본 영상 | 관리자가 업로드한 파일 그대로의 영상. 분석에만 쓰고 사용자에게는 절대 보여주지 않는다. |
| 원본 시간 | 원본 영상 시작부터의 경과 시간(초). 모든 시간 정보의 기준이다. |
| 청크 | 분석을 위해 원본 영상을 시간 단위로 나눈 구간. 원본 시간 기준 시작·끝을 가진다. |
| 샘플링 fps | 분석할 때 초당 몇 장의 프레임을 뽑아 탐지할지 정한 값. |
| 정지 장면 | 차량 선택용 프레임. 원본 영상 **시작 장면(첫 프레임) 1장**이다. 1단계에서 가장 먼저 만든다. 다른 시점으로 넘겨 보는 기능은 없다. (PRD 3.2, D-48) |
| 비식별화 | 번호판과 사람을 모자이크 처리하는 작업. "마스킹"·"모자이크"와 같은 뜻이며, 문서에서는 "비식별화"로 통일한다. |
| 마스킹본 | 비식별화가 끝난 영상·이미지. 사용자에게는 마스킹본만 보여준다. |
| 이중 경로 | 분석은 원본 영상으로, 열람은 마스킹본으로 하는 원칙. (PRD 3.1) |

**분석**

| 용어 | 뜻 |
|---|---|
| 객체탐지 | 프레임에서 차·사람의 위치(bbox)를 찾는 작업. YOLO 계열 모델을 쓴다. |
| 추적 (트래킹) | 프레임마다 탐지된 bbox를 이어 붙여 같은 객체에 같은 ID를 주는 작업. ByteTrack을 쓴다. |
| 트랙 | 추적 결과로 만들어진 객체 하나의 시간별 bbox 목록(궤적). |
| 차량 영역 | 사용자가 정지 장면에서 드래그해 지정한 본인 차량의 사각형. 2단계 룰이 쓴다. (D-29, D-36) |
| 누끼 | 탐지 결과로 딴 차량 외곽. 우선 쓰지 않고, 나중에 차량 영역을 보정하거나 화면에 표시할 때 더할 수 있다. (D-36) |
| 본인 차량 | 사용자가 정지 장면에서 드래그로 지정한 자신의 차량. |
| 파손 부위 | 사용자가 입력한 본인 차량의 파손 위치. 입력 방식은 🚧 (U-13) |
| 인접 영역 | 파손 부위가 CCTV에 보이지 않을 때 대신 감시하는 파손 부위 쪽 공간(옆 주차면, 통로). (PRD 3.3) |
| 룰 | 트랙과 파손 부위·인접 영역의 위치 관계로 근접을 판정하는 규칙. 상황 목록과 판정 방식은 🚧 (U-13) |
| 판정 시점 | 룰이 후보로 판정한 원본 시간. |
| 후보 | 룰이 판정한 근접 순간 하나. 판정 시점을 가진다. 연속된 판정을 하나로 합치는 규칙은 🚧 (U-13) |
| VLM 점수 | Bedrock VLM이 후보마다 따로 매긴 접촉 가능성 점수(0~100). 정렬에만 쓴다. |
| 1단계 분석 | 업로드 직후 자동 실행하는 분석. 사용자 입력이 필요 없는 무거운 작업이다. 정지 장면 비식별화를 먼저 하고, 그다음 청크별 객체탐지·추적을 해 트랙을 저장한다. GPU 워커가 실행한다. (D-05, D-14, D-15) |
| 2단계 분석 | 1단계가 끝났고 사용자 입력이 있으면 자동 실행하는 분석. 저장된 트랙에 룰 적용(다시 탐지하지 않음), 후보별 VLM 점수, 정렬, 상위 후보 클립 비식별화. GPU 워커가 실행한다. (D-05, D-14) |

**확인·결과**

| 용어 | 뜻 |
|---|---|
| 사건 지점 | 판정 시점 + 5초. 후보 클립의 가운데 시점이다. (PRD 3.5) |
| 후보 클립 | 사건 지점 전후 15초(판정 시점 −10초 ~ +20초), 총 30초 길이의 마스킹본 영상. 영상 경계를 넘는 부분은 잘라낸다. |
| 후보 묶음 | 한 번에 제공하는 후보 클립 최대 10개. |
| 사건 지점 고정 | 사용자가 "찾음"을 고른 후보 클립을 클라우드에 저장하고, 원본 시간 기준 시작~끝을 표시하는 것. (PRD 3.6) |
| 후보 전부 확인 완료 | 모든 후보를 "못 찾음"으로 확인한 상태. 사건이 없다는 뜻이 아니다. (PRD 3.6) |

**인프라**

| 용어 | 뜻 |
|---|---|
| 백엔드 EC2 | 웹 정적 파일, FastAPI API 서버, PostgreSQL을 실행하는 CPU 인스턴스. 통신과 관리만 하고 영상 분석은 하지 않는다. (D-10, D-14, D-17) |
| GPU EC2 (GPU 워커) | 1단계·2단계 분석을 모두 실행하는 GPU 인스턴스. 관리자가 업로드를 시작할 때 켜지고, 15분 동안 할 일이 없으면 스스로 꺼진다. (D-10, D-14, D-15) |
| SQS 작업 대기열 | 백엔드가 분석 작업을 넣고 GPU 워커가 꺼내 가는 AWS 대기열. 메시지에는 작업 ID만 넣는다. (D-16) |
| 작업 상태 | 작업이 지금 어느 단계인지(대기 중, 1단계 분석 중, 확인 가능, 실패 등). SQS가 아니라 DB에 기록한다. (D-16) |
| presigned URL | 서명이 들어간, 일정 시간만 유효한 S3 임시 주소. 원본 업로드와 마스킹본 재생에 쓴다. (D-09, D-18) |
| 가짜 워커 | GPU·Bedrock 없이 정해진 시간 기다린 뒤 가짜 결과를 쓰는 워커 실행 방식. 부하 테스트와 로컬 개발에 쓴다. (D-20) |
| 무상태 API | 서버 메모리에 사용자·작업 정보를 두지 않는 API. 어느 서버가 요청을 받아도 같은 결과를 돌려주므로 서버를 여러 대로 늘릴 수 있다. (D-19) |
