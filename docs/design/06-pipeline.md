# 06. 비전·VLM 파이프라인

> 🚧 미작성. 작성할 항목과 이미 정해진 관련 결정만 적어 둔다.

## 작성할 항목

**PRD가 설계 문서로 미룬 항목**

- 파손 부위 입력 방식: **정지 장면 위에서 두 번 드래그한다 (D-29, 확정).** 우선 누끼 없이 드래그한 차량 사각형을 그대로 쓴다 (D-36, 상태 "확정 필요"). 남은 것은 룰에 넘길 입력 항목과, 드래그 사각형에 걸리는 본인 차량·옆 차 트랙을 룰에서 빼는 방법이다 (PRD 3.2, U-13)
  - 확장: 드래그 오차가 문제가 되면 2단계 시작 때 워커가 드래그 사각형을 1단계 트랙과 맞춰 보정한다 (D-36 확장 방법 1). 이때 맞추는 기준(겹침 비율 등)을 여기서 정한다
- 룰로 나눌 상황 목록, 근접 판정 방식, 인접 영역 정의 (PRD 3.3, U-13)

**GPU 워커 운영** (D-14, D-15, D-16)

- SQS 긴 폴링(20초)으로 작업 꺼내기
- 처리 중 가시성 제한 시간 주기적 연장 (`ChangeMessageVisibility`, 연장 주기 U-18)
- 처리 전 DB 상태로 중복 확인 (이미 끝났거나 처리 중이면 건너뜀)
- 처리 후 메시지 삭제 (`DeleteMessage`). 조건부 UPDATE가 0행이면 이유를 가리지 않고 지운다. `analysis_jobs` 행이 없는 경우도 마찬가지다 (D-56, 04장 4.4 ⚠️ 팀장 확인)
- 실패 처리: 재시도 상한과 DLQ는 없다. 워커가 되풀이해도 소용없는 오류를 만났을 때만 `failed`로 바꾼다. 어떤 오류를 그렇게 볼지 정하는 것이 남았다 (D-43, D-56)
- 1단계가 끝나면 DB에서 입력이 있는지 확인하고, 있으면 이어서 2단계 실행
- 15분 동안 할 일이 없으면 SQS·DB를 한 번 더 확인한 뒤 OS 종료. 워커가 OS 종료 명령을 실행할 권한을 얻는 방법 🚧
  - 확인과 종료 사이에 들어온 작업은 워커가 챙기지 않아도 된다. 백엔드의 5초 주기 점검이 완전히 꺼진 뒤 다시 켠다 (D-42)
- 자동 꺼짐 켜고 끄기 설정 (시연 날에는 끔, [02장 2.8](02-architecture.md#시연-날-설정))
- 가짜 워커 모드: GPU·Bedrock 없이 정해진 시간 기다린 뒤 가짜 결과를 DB·S3에 쓴다 (D-20)
- 임시 파일 위치: 원본 영상은 로컬 NVMe(`/opt/dlami/nvme`)에 두는 것을 기본으로 한다. 중지하면 비워지므로 켤 때마다 비어 있다고 가정한다 (D-21)
- **로컬 원본 사본 삭제 (D-68)**: 워커가 **15분 동안 할 일이 없으면 로컬에 받아 둔 원본 사본을 모두 지운다.** 자동 꺼짐이 켜져 있으면 지운 뒤 OS를 종료하고, 꺼져 있으면(시연 날) 지우기만 하고 계속 기다린다. 작업이 이어지는 동안에는 지우지 않고 2단계 묶음마다 다시 쓴다 (D-37)
  - "중지하면 비워진다"에만 기대면 자동 꺼짐을 끈 날 S3 원본을 파기(D-52)한 뒤에도 사본이 남는다
  - 작업을 시작할 때 로컬 사본이 있어도 **S3 원본이 아직 있는지 먼저 확인한다**(`HeadObject`, `s3:GetObject` 권한으로 된다). 없으면 파기된 것이므로 사본을 바로 지우고 D-52의 처리를 따른다. 파기된 원본을 사본으로 계속 분석하는 일을 막는다
  - 로컬 사본이 없으면 S3에서 다시 받는다

**1단계 분석**

- 1단계 시작 직후 `ffprobe`로 코덱을 확인한다. H.264·H.265가 아니거나 읽을 수 없으면 재시도 없이 `failed`로 바꾸고 `error_message`에 이유를 적는다 (D-43, ⚠️ 팀장 확인)
- 정지 장면을 가장 먼저 처리: 원본을 열어 **첫 프레임 1장**만 뽑아 비식별화하고 `t_sec = 0.0`으로 저장 (D-15, D-48). 시크가 없다. 다른 시점 장면은 만들지 않는다. 차량 탐지·누끼 생성도 하지 않는다 (D-36)
- 청크는 디코딩에만 쓴다. 탐지·추적은 프로세스 1개가 영상 처음부터 끝까지 한 줄로 한다 (D-63, [02장 2.6](02-architecture.md#26-청크-분할과-병렬-처리))
  - 디코딩 청크 길이, 디코딩 프로세스 수, 샘플링 fps (U-06)
  - 청크 경계에서 프레임이 빠지거나 겹치지 않게 자르는 방법 (시크 후 청크 시작 전 프레임 버리기)
- 중간 저장: 간격(U-06), 추적기 상태 파일 형식, 저장 순서(구간 파일 → 추적기 상태 → `processed_sec`) (D-63, 04장 4.8·4.9)
- 1단계 도중 죽은 작업을 누가 다시 시작시키나 🚧 (D-63 한계, D-56 한계)
- 객체탐지 모델과 클래스, ByteTrack 설정 (U-09). Ultralytics `model.track()`의 기본 추적기는 BoT-SORT이므로 ByteTrack을 지정한다
- 트랙 저장 형식 (2단계가 다시 탐지하지 않고 이 파일만 읽는다)
- 움직임 감지 사전 필터 도입 여부 (U-07)
- 영상 디코딩이 병목일 때 GPU 하드웨어 디코딩 검토

**2단계 분석**

- 저장된 트랙을 읽어 룰 적용 (다시 탐지하지 않는다. 좌표 계산만 한다)
- 후보 병합 규칙 (연속 프레임이 각각 후보가 되지 않도록)
- VLM: 모델, 입력 형식(영상 또는 프레임), 프롬프트, 점수 파싱, 동시 호출 수 (U-08, U-18)
- Bedrock 한도 초과(`ThrottlingException`) 시 대기 시간을 늘려 가며 재시도 (D-19)
- 원본 시간 계산 공식: 청크 offset + 청크 내부 시간(디코딩 단계), 후보 클립 구간, 영상 경계 잘라내기
- 다음 후보 묶음을 미리 비식별화해 둘지 여부 ("못 찾음" 뒤 대기와 GPU 켜진 시간의 맞바꿈, D-15)

**비식별화**

- 사람·번호판 탐지 모델, 모자이크 방식 (U-09)
- 적용 시점 2곳: 정지 장면, 후보 클립 (PRD 3.1)
- 보여줄 모든 프레임을 빠짐없이 처리 (샘플링하지 않음)
- 후보 클립 인코딩: H.264 코덱 MP4 (Flutter Web 재생 조건, D-08)

## 관련 결정·조건

- 청크는 디코딩만 나누고 탐지·추적은 한 줄로, 중간 저장: D-63 (D-02를 대체, D-03 일부 변경)
- 후보 선별 = 객체탐지 + 추적 + 룰: D-04
- 두 단계 분석: D-05 / VLM 호출 방식: D-06
- 분석은 모두 GPU 워커: D-14 / GPU 켜고 끄기: D-15, 꺼짐 중 켜기 실패 대비 점검: D-42 / 정지 장면은 시작 장면 1장, 1단계에서 가장 먼저 생성: D-48 / 허용 코덱 검사: D-43 / SQS 규칙: D-16 / 조건부 UPDATE가 0행이면 이유를 가리지 않고 메시지를 지움: D-56
- 부하 대응: D-19 / 가짜 워커: D-20
- 로컬 원본 사본은 15분 쉬면 지우고, 쓰기 전에 S3 원본이 남아 있는지 확인한다: D-68
- 차량·파손 부위 입력은 두 번 드래그, 본인 차량은 추적하지 않는다: D-29
- 우선 누끼 없이 드래그한 차량 사각형을 그대로 씀: D-36
- 불변 조건 2~5, 7: [02장 2.4](02-architecture.md#24-이중-경로와-불변-조건)
