# 06. 비전·VLM 파이프라인

> **D-112 반영: 사용자 재시도는 완료 결과를 보존하고 실패 단계의 미완료 작업부터 처리한다. 단계별 체크포인트·실행 식별·오래된 메시지 차단·실행별 자동 재시도 집계를 보완한다. 개별 클립 열람 불가(D-109)의 일괄 재생성으로 확대하지 않는다. 사용자 재시도는 최초 분석·자동 재시도를 제외하고 작업당 누적 최대 3회다. 서버가 유효하게 접수한 재시도만 원자적으로 차감하며 중복·거절 요청은 차감하지 않는다. 3회 소진 후 다시 실패하면 재시도 버튼 대신 운영 담당자 문의를 안내한다.**

> **D-111: 사용자가 확인을 보류해도 대기·실행 중 분석은 계속 진행한다. 데모 GPU 1대의 다중 영상 처리 대기는 허용하며 대기 단축·ASG는 구현 범위 밖이다. 다중 워커 운영 전 필요한 변경은 02장 2.10.1을 따른다.**

> **D-221(2026-11-03, 팀장): 1단계 차량 탐지는 YOLO11m-seg로 하고, 조각을 이은 `polygon`과 중복 합치기를 더한다 (6.3).**

> **D-245(2026-11-10, 팀장): 후보는 트랙 단위가 아니라 "ROI 안에서 움직임이 있는 구간"으로 잡고 30초 이하 클립으로 나눈다. 클립 1개가 후보 1개다. 클립마다 유력 시점(파손 위치에 가장 가까운 프레임, 최솟값 +1% 이내는 모두)을 골라 VLM 프레임 밀도를 세 단계로 나눈다. 차 흔들림은 유력 시점에 쓰지 않는다 (6.5 후보 구간과 유력 시점, 6.6 입력). 클립 구간 규칙(6.5)은 2026-11-12에 채널 A 켜고 끄기, 6.7 클립 구간, 6.9 클립 구간에 반영했다. ⚠️ 아직 옛 내용인 곳: 6.6 비용 추정("30초당 약 25장", 트랙 1개 = 후보 1개, U-28에서 다시 추정한다). 구현 전에 D-245의 "아직 정하지 않은 것"을 확인한다.**

> **D-246·D-247·D-248(2026-11-12, 팀장): "판정 시점 + 5초"라는 사건 지점 정의를 없앴다. 후보 클립은 후보 구간 앞뒤 여유 5초, 30초 이하다 (D-246). 채널 A는 ROI 움직임 첫 감지 10초 전 ~ 마지막 감지 5초 후에만 돌고, 링 버퍼는 10초다 (D-247). 이어서 하기 때는 `processed_sec` 1분 전부터 다시 읽어 MOG2 배경을 다시 만든다 (D-248) (6.5 채널 A 켜고 끄기, 6.7, 6.9).**

> **D-249·D-250(2026-11-12, 팀장): 후보에는 든 트랙 번호 전부, 합친 후보 구간 목록, 트랙별 유력 시점 목록을 남긴다. 채널과 룰 이름은 남기지 않는다. 후보는 영상 전체 탐지가 끝난 뒤 한 번에 계산한다 (6.5 후보 구간과 유력 시점). 칸 형식은 👤 팀원 2가 정한 뒤 04장에 반영한다.**

> **D-251(2026-11-12, 팀장): 트럭·버스의 유력 시점은 승용차와 같은 계산(bbox 아래 변 → 파손 지점의 바닥 지도 거리)으로 잡는다. 빼는 조건은 그대로다 (6.5 후보 구간과 유력 시점).**

> **D-272(2026-11-14, 팀장): VLM 비용 추정(6.6)은 지금 다시 계산하지 않는다. 구현이 끝난 뒤 마지막에 다시 추정한다 (U-28). 그때까지 6.6의 비용 숫자는 D-245 전 방식으로 계산한 옛 값이다.**

> **D-273(2026-11-14, 팀장): 일반 구간의 VLM 프레임은 0.5fps(2초에 1장)로 확정한다. 일반 구간마다 첫 프레임을 넣고 거기서부터 2초마다 1장을 넣는다. 다른 두 밀도는 시작값 그대로다 (6.6 프레임 밀도).**

> **D-274(2026-11-14, 팀장): VLM 모델은 학교 대체 LLM API의 허용 모델 중 `bedrock-haiku`, `bedrock-sonnet`, `bedrock-gpt-5.6-terra`, `bedrock-gpt-5.6-luna`를 시험해 보고 정한다. 아래 1차·2차 구조 표의 Nova Lite·Haiku 4.5는 이 API에서 쓸 수 없다. 1차·2차 구조는 그대로다 (6.6 1차·2차 구조).**

> **D-275(2026-11-14, 팀장): VLM 호출의 처리 리전은 한정하지 않는다. 학교 대체 LLM API가 미국 추론 프로파일 등 어느 리전에서 처리해도 된다. 아래 "교차 리전 추론 프로파일"을 모델별로 고르는 내용은 Bedrock 직접 호출 기준이라 쓰지 않는다.**

> **D-276(2026-11-14, 팀장): VLM은 boto3가 아니라 학교 대체 LLM API(OpenAI 호환)로 부른다. 429·5xx는 재시도, 422(한도 소진)·401·400은 재시도하지 않고 작업 `failed` (6.6 파싱 실패와 장애, 03장 3.2).**

> **D-278(2026-11-14, 팀장): 1차 VLM에는 처음에 모든 후보를 보내고, 일부만 보낼지는 팀장이 돌려 보고 정한다. 미리 정한 기준은 두지 않는다. 파손 사각형은 차량 사각형 밖도 받고(D-231), 채널 B 덩어리 붙이기는 D-256 기준으로, 모델·도구 호출은 D-274·D-276으로, 안내 프레임은 클립 첫 프레임으로 맞췄다 (6.2, 6.5, 6.6, 6.7).**

> **D-269(2026-11-14, 팀장): YOLO가 한 트랙의 클래스를 프레임마다 다르게 내면, 그 트랙의 클래스는 가장 많은 프레임에 나온 클래스로 본다. 같은 수이고 트럭·버스가 끼어 있으면 트럭·버스로 본다. 빼는 조건과 유력 시점 계산에 쓴다 (6.5 "물체 종류별 기준 거리").**

> **D-268(2026-11-14, 팀장): 분석 크롭의 30% 이상인 채널 B 덩어리(덩어리 크기 상한, D-195)가 있는 프레임에서는 채널 A 트랙의 움직임을 덩어리가 아니라 bbox로 묶어 직전 분석 프레임과의 차이만으로 잰다 (D-265와 같은 방법). 조명이 크게 바뀐 뒤 MOG2가 다시 배우는 약 1분과 전조등이 화면을 넓게 비추는 동안에도 사람·차의 접촉이 후보가 된다 (6.5 "후보 구간의 규칙").**

> **D-267(2026-11-14, 팀장): 고른 차량 사각형(`bbox`)과 어긋나게 찍은 네 모서리는 따로 처리하지 않는다. 꼬인 사각형만 지금처럼 화면과 서버가 막는다 (6.5 "정하지 않은 것").**

> **D-266(2026-11-14, 팀장): 차 너머 트랙 빼기에 "발이 앞 차에 가려진 사람"을 가르는 조건을 더하지 않는다. 내 차가 일부만 가려진 구간에서 앞 차와 내 차 사이에 선 사람이 머리만 보이면 빠질 수 있고, 이것은 한계로 둔다 (6.5 "차 너머 트랙 빼기").**

> **D-265(2026-11-14, 팀장): 영상 시작에서 MOG2가 안정되기 전(약 1분)의 움직임은 MOG2 전경 없이 직전 분석 프레임과의 차이만으로 잰다. 채널 A 트랙의 bbox와 ROI가 겹친 곳에서 세고, 기준값(밝기 차이 25, 분석 크롭의 0.01%)은 그대로다. 이 구간의 `moved_px`는 `null`이 아니라 숫자다. 전경을 쓰는 차 영역 키는 지금처럼 측정 불가다 (6.5 "후보 구간의 규칙", 채널 A 켜고 끄기 규칙 8, 구현 주의사항).**

> **D-264(2026-11-14, 팀장): 내 차는 "고른 차량 사각형과 가장 많이 겹치는 마스크 하나"가 아니라, 네 모서리로 만든 "내 차 자리"에 서 있는 차량 마스크를 모두 합쳐 찾는다. 내 차 자리는 내 차 영역이 아니라 마스크를 고르는 틀이다. 기둥·옆 차에 가려 조각이 나뉘어도 모두 합치고, 내 차 앞에 선 차는 바닥에 닿는 위치로 걸러낸다. 시작값은 안쪽 80%, 아래 여유 10%, 좌우 여유 10%다. 넓이 50% 실패 기준(D-256 5번)은 없앤다 (6.5 "내 차 찾기", "0단계 필터의 시작값" 표).**

> **D-263(2026-11-14, 팀장): 구간마다의 기준 영역은 추적기 상태 파일의 YOLO 구간 목록에 다각형 목록으로 적는다. 조각마다 다각형 하나이고 줄인 분석 프레임 좌표다. 기준 영역으로 쓰는 모양은 다각형으로 바꾼 뒤 다시 그린 모양이다 (6.5 YOLO 구간 기록).**

## 6.1 전체 흐름

**사용자가 기다리는 시간보다 탐지 성능과 처리 속도를 우선한다.** 그래서 영상 전체 분석은 사용자 입력을 받은 **뒤에** 한다. 입력(본인 차량·파손 부위·탐지 상황)을 알아야 근접 영역만 조밀하게 보고, 클래스 없는 물체를 잡고, 작은 물체를 크롭해 볼 수 있기 때문이다. (D-67)

```
[업로드] 최소 수 분
  업로드 남은 예상 시간 <= 임계(1.6)가 되면 GPU 켜기 요청 (D-62)

[1단계: 정지 장면] 업로드 완료 직후. 수십 초 (추정)
  코덱 검사 → 첫 프레임 1장 → 차량 탐지 → 타일 방식 비식별화 → 저장

[사용자 입력] 아무 때나
  본인 차량 고르기 + 탐지 상황 [보임/안 보임] + 파손 위치 사각형(보임·안 보임 모두 드래그)
  + 내 차 바닥 네 모서리 + 파손 변 (D-98)
  + 사진(선택) + 텍스트 설명(선택) → 확인창 → 저장 (D-66, D-72)
  GPU가 꺼져 있으면 다시 켠다 (부팅 2~3분, D-15)

[2단계: 전체 분석] 입력 저장 후. 24시간 영상 약 20분 (추정, 실측 필요)
  ① 후보 탐지: 분석 크롭 위에서 채널 B(MOG2를 분석 크롭 전체에 영상 처음부터 끝까지, 움직임 판정은 ROI 안 픽셀 변화로, D-192) + 채널 A(YOLO+ByteTrack, 근접 영역 움직임 구간만)
     → 바닥점 필터(0단계) → 후보 (D-95, D-97)
  ② VLM: 1차(싼 모델, 탈락만) → 2차(점수 0~100) → 점수순 정렬. 2차 형식 실패 → 파싱 실패 목록 (D-93)
  ③ 후보군 목록·파싱 실패 목록 각각 상위 20개(묶음 2개) 후보 클립: 보여줄 크롭 → 비식별화 → "확인 가능"

[확인]
  [다음] → 이미 준비된 다음 묶음을 바로 보여줌
         → 동시에 GPU를 켜고 그다음 묶음을 비식별화 (한 묶음 앞서 준비, D-68)
```

| 단계 | 시작 조건 | GPU | 사용자가 기다리나 |
|---|---|---|---|
| 1단계 | 업로드 완료 알림 | 필요 (탐지·비식별화) | 업로드 직후 바로 입력하려면 수십 초 |
| 2단계 | 입력 저장 | 필요 | **기다린다.** 24시간 영상 약 20분 (추정). GPU가 꺼져 있었으면 부팅이 더해진다 |
| 다음 묶음 | [다음] | 필요 (비식별화) | 기다리지 않는다. 이미 준비된 묶음을 보여준다 |

- 1단계는 이제 정지 장면만 만든다. 영상 전체 객체탐지·추적은 2단계로 옮겼다 (D-67이 D-5를 바꿈).
- **입력은 항상 1단계가 끝난 뒤에 들어온다.** 정지 장면이 1단계의 마지막 산출물이기 때문이다. 그래서 "1단계 중 입력 → 1단계가 끝나면 2단계 자동 시작" 경로(D-15 결정 3, `stage1_input_done`)가 필요 없다. 상태 정리는 04장 4.3에 반영했다 (D-81).

## 6.2 GPU 워커 운영

(D-14, D-15, D-16, D-62)

- SQS 긴 폴링(20초)으로 작업 꺼내기
- 처리 중 가시성 제한 시간 주기적 연장 (`ChangeMessageVisibility`). 대기열 기본값 2분, 작업을 받으면 별도 스레드가 1분마다 다시 2분으로 늘린다. 작업 종류와 상관없이 같다 (D-141). **이제 오래 걸리는 쪽은 2단계다** (약 20분, 추정)
- 처리 전 DB 상태로 중복 확인 (이미 끝났거나 처리 중이면 건너뜀)
- 처리 후 메시지 삭제 (`DeleteMessage`). 조건부 UPDATE가 0행이면 지운다. `analysis_jobs` 행이 없는 경우도 마찬가지다 (D-56, 04장 4.4). **단, 받은 메시지의 작업이 `*_running`이면 지우지 않고 이어서 한다(아래, D-94).**
- **죽은 작업 이어서 하기** (D-94): 가시성 제한 시간은 살아 있는 워커만 연장하므로, `*_running` 작업의 메시지가 다시 왔다는 것은 처리하던 워커가 죽었다는 뜻이다. 워커는 그 작업을 이어서 한다.
  - `stills_running`: 1단계를 처음부터 다시 한다(정지 장면 1장이라 짧다).
  - `stage2_running`: `processed_sec`부터 탐지·추적을 이어 간다(D-76). VLM 단계에서는 점수가 이미 있는 후보를 건너뛴다.
  - `batch_running`: `pending` 클립부터 다시 만든다.
  - **상한**: 메시지의 `ApproximateReceiveCount`가 4 이상이면(= 3번 죽었으면) 이어서 하지 않고 `failed`로 바꾸고 메시지를 지운다. 메모리 부족처럼 같은 원인으로 되풀이해 죽는 경우를 끊기 위해서다. DB 칼럼은 더하지 않는다.
  - 복구까지 걸리는 시간은 가시성 제한 시간만큼이다(최대 2분, D-141). GPU가 꺼져 있으면 백엔드 5초 점검이 켠다(D-42).
- 실패 처리: 재시도 상한과 DLQ는 없다(위 이어서 하기 3회 상한은 예외). **입력 자체가 잘못된 경우만 `failed`로 바꾼다**: 코덱 불량·읽기 불가, 영상 길이 0, 원본 S3 객체 없음. 그 밖의 예외(네트워크, 일시 오류 등)는 메시지를 지우지 않고 SQS 재전달에 맡긴다. VLM 파싱 실패율·장애 지속은 6.6을 따른다 (D-43, D-56, D-93, D-94)
- **켜기**: 업로드 남은 시간이 임계 이하일 때(D-62), 그리고 GPU가 필요한 작업을 SQS에 넣을 때마다(1단계, 2단계, 다음 묶음). 사용자가 1단계 뒤 15분 넘게 입력하지 않으면 GPU가 꺼져 있으므로 입력 저장 시 다시 켠다(부팅 2~3분).
- 15분 동안 할 일이 없으면 SQS·DB를 한 번 더 확인한 뒤 OS 종료. 워커가 OS 종료 명령을 실행할 권한을 얻는 방법 🚧
  - 확인과 종료 사이에 들어온 작업은 워커가 챙기지 않아도 된다. 백엔드의 5초 주기 점검이 완전히 꺼진 뒤 다시 켠다 (D-42)
- 자동 꺼짐 켜고 끄기 설정: `.env`의 대기 시간 값(분, 0이면 끔)을 워커 시작 때 읽는다. 시연 날에는 0으로 바꾼다 (D-131, [02장 2.8](02-architecture.md#시연-날-설정))
- 가짜 워커 모드: GPU·VLM 호출 없이 정해진 시간 기다린 뒤 가짜 결과를 DB·S3에 쓴다 (D-20)
- 임시 파일 위치: 원본 영상은 로컬 NVMe(`/opt/dlami/nvme`)에 두는 것을 기본으로 한다. 중지하면 비워지므로 켤 때마다 비어 있다고 가정한다 (D-21)

## 6.3 1단계: 정지 장면

- 시작 직후 `ffprobe`로 코덱을 확인한다. H.264·H.265가 아니거나 읽을 수 없으면 재시도 없이 `failed`로 바꾸고 `error_message`에 이유를 적는다 (D-43, ⚠️ 팀장 확인)
- 원본을 열어 **첫 프레임 1장**만 뽑는다. `t_sec = 0.0`. 시크가 없다 (D-48)
- **비식별화 전 프레임에서 차량을 탐지해** `still_frames.detections`에 저장한다 (D-65). 사용자가 이 중에서 본인 차를 고른다
  - 모자이크가 씌워진 뒤에 탐지하면 차량 경계가 흐려진다. 좌표는 원본 해상도 기준이라 두 결과가 같은 좌표계다
  - **YOLO11m-seg**로 car·motorcycle·bus·truck을 탐지한다. 시작값은 `conf` 0.25다 (D-221, U-06)
  - **조각 잇기**: 차 하나의 마스크 조각을 모두 모아 볼록 껍질 하나로 만든다. 이것이 `polygon`이다. 기둥에 끊겨도 한 영역이 된다. `masks.xy`는 가장 큰 조각만 주므로 `masks.data`를 쓴다
  - **중복 합치기**: 신뢰도가 높은 탐지부터 보며 마스크 IoU가 0.3(시작값) 이상이면 한 대로 합친다. 종류와 `conf`는 신뢰도가 높은 쪽, `bbox`는 합집합을 쓰고 `det_id`는 합친 뒤에 매긴다. 박스 IoU는 쓰지 않는다. 박스만 겹친 옆 차가 합쳐지기 때문이다
  - `polygon`은 화면 표시와 고르기에만 쓴다. 2단계는 `bbox`를 쓰고(분석 크롭·ROI·파손 드래그 제한·내 차 자리, D-264), 2단계 차 영역(D-193)과는 별개다. 차 영역은 "내 차 픽셀을 가렸는가"를 보는 세 곳(차 너머 트랙 빼기, 차 앞 트랙 빼기, 바닥점이 보임 판정)에만 쓰고, 2단계에서 YOLO 구간마다 segmentation 마스크로 새로 만든다 (D-259). `bbox`나 볼록 껍질인 `polygon`으로 대신하지 않는다. 차가 아닌 바닥·배경이 섞여 차를 가리지 않은 물체도 "앞"으로 판단되기 때문이다 (6.5)
  - 탐지가 0건이어도 `[]`로 저장한다. 화면은 재업로드 안내로 간다 (D-65)
  - 채널 A도 같은 모델(YOLO11m-seg, D-260)이지만 같은 차의 `bbox`가 조금 다를 수 있다. 1단계는 첫 프레임 전체를 보고 중복 합치기를 하고, 채널 A는 분석 크롭을 보기 때문이다. 1단계 `bbox`는 2단계에서 내 차를 고르는 틀(내 차 자리, D-264)을 만드는 데만 쓰고 트랙과 맞추지 않으므로 받아들인다 (D-221, D-259)
- 비식별화는 **타일 방식**이다. 프레임 전체를 겹치는 타일로 나눠 각각 탐지하고 합친다(SAHI 방식). 이 시점에는 본인 차량을 모르므로 크롭할 기준이 없고, 프레임이 1장이라 타일 수만큼 느려져도 괜찮다 (D-69, 6.8)
- 1단계는 여기서 끝난다. 청크 분할·객체탐지·추적은 하지 않는다 (D-67)

## 6.4 사용자 입력 (워커가 받는 값)

PRD 3.2가 정한 입력을 워커가 이렇게 읽는다. 저장 형식은 04장 `vehicle_selections`·`damage_inputs`이고, 바뀌어야 할 점은 04장 머리에 적었다.

| 입력 | 필수 | 쓰는 곳 |
|---|---|---|
| 본인 차량 (`det_id` → `bbox`) | 필수 | 근접 영역, 크롭 기준 |
| 탐지 상황: 파손이 CCTV에 **보임 / 안 보임** | 필수 | 룰 분기 (6.5) |
| 파손 부위 드래그 (보임일 때) | 보임이면 필수 | 근접 판정 기준, VLM 안내 프레임 |
| 파손 위치 사각형 (안 보임일 때) | 필수, 원본 화면 좌표, 차량 `bbox` 밖도 허용 (D-92, D-231) | 인접 영역 계산, VLM 안내 프레임 |
| 내 차 바닥 네 모서리, 파손 변 (D-98) | 필수 (반영 필요: 04·05·07장) | 시야·거리 파악, ROI·크롭 크기, 바닥점 필터 (6.5) |
| 파손 사진 | 선택 | VLM 입력 |
| 텍스트 설명 | 선택 | VLM 입력 (데이터로만 취급) |

**파손이 안 보일 때의 입력 방식** (D-92, U-25 해결)

사용자가 CCTV 화면에서 파손 위치에 해당한다고 보는 곳에 작은 사각형을 드래그한다. 원본 프레임 절대 픽셀 좌표 `damage_bbox`로 저장하며 **고른 차량 사각형 밖으로 나가도 받는다** (D-231이 차량 안으로 제한하던 D-165를 바꿨다). 영상 화면 밖과 빈 사각형만 거절한다. `visible=false`와 함께 전달해 실제 보이는 파손 부위와 구분한다. 해당 위치를 기준으로 인접 영역을 계산하고 VLM 안내 프레임에 표시한다. 크롭할 때는 크롭 원점과 배율을 반영해 좌표를 변환한다. 구체적인 인접 영역 폭·근접 임계값은 U-30에서 정한다.

**통로 쪽 / 옆면 구분** (U-26 → D-98로 대체)

- 파손 부위가 차의 통로 쪽(앞·뒤 범퍼 쪽)인지 옆면(옆 칸 쪽)인지에 따라 근접하는 물체와 빈도가 크게 다르다(6.5 페르미 추정).
- 사용자가 바닥 네 모서리 사각형에서 파손 변을 직접 고르므로 따로 고르거나 계산하지 않는다 (6.5 "내 차 바닥 네 모서리로 시야 판단과 ROI 정하기"). D-34처럼 bbox로 계산하면 카메라 각도에 따라 "bbox의 어느 변"이 "차의 어느 면"인지가 어긋날 수 있어서다.

**사진·텍스트 전처리**

- 둘 다 선택이다. 없으면 VLM 프롬프트에서 그 항목을 통째로 뺀다 (빈 칸으로 두지 않는다).
- 사진: EXIF 제거(GPS 포함), HEIC는 JPEG로 변환, 긴 변 768~1024px로 줄인다. 사진에는 **사용자 본인 차 번호판**이 찍혀 있을 수 있다. 사용자 자신의 정보이고 VLM에만 보내며 화면에 다시 보여주지 않으므로 비식별화하지 않는다. 파기 대상에는 넣는다 (04장 4.9, D-83).

## 6.5 2단계-① 후보 탐지

**목표**: 사고 클립 후보 검출 누락률 1% 이하 (PRD 2장 KPI). CCTV에 가려져 사람도 판단할 수 없는 경우를 빼고 모두 잡는다. **재현율이 우선이지만, 확실히 관계없는 것은 여기서 뺀다.** (D-71)

### 대상 장면

| 장면 | 주로 잡는 채널 | 보이는 파손의 신호 | 안 보이는 파손의 신호 |
|---|---|---|---|
| 문콕 (옆 차 문 열림) | A(사람·차) + B(문 움직임) | 옆 차 쪽 덩어리가 파손 부위에 닿음 | 옆 칸 사람 승하차, 옆 차 문 쪽 움직임 |
| 주행 차량 접촉 | A | 차량 바닥점이 손이 닿는 구역으로 들어옴 | 차량이 차 너머로 가려졌다 나타남, 느린 통과 |
| 물체·구조물 쓰러짐 | B | 밑동(바닥점) 근처에서 위쪽 덩어리가 차 쪽으로 기움 | 차 너머에서 큰 움직임 |
| 바퀴 달린 물체가 혼자 굴러옴 (카트·유모차) | B (+ A가 잡으면 A) | 덩어리가 ROI로 이동 | 인접 영역 진입·체류 |
| 물체가 날아옴 | B | 짧고 빠른 덩어리가 차 쪽으로 | 바닥점 신뢰 불가 → 남김 |
| 사람 접촉 (고의·과실) | A | 사람 바닥점이 손이 닿는 구역 안, 체류 | 차 너머 체류, 가려짐·재등장 |
| 동물 | A(COCO 동물 클래스) + B | 바닥점이 손이 닿는 구역 안 | 인접 영역 체류 |

### 탐지 채널

- **채널 A: 객체탐지 + 추적.** COCO 사전학습 **YOLO11m-seg**로 찾고, `trackers` 2.6.1의 ByteTrack(`ByteTrackTracker`)으로 잇는다 (D-196, D-200, D-260, 모델 크기는 시작값). 한 번 실행해 사각형과 영역(마스크)을 함께 얻는다. 사각형·클래스·신뢰도는 ByteTrack에 넣고, 마스크는 내 차의 것만 차 영역(기준 영역, 영역 줄어듦)에 쓴다 (D-259). 다른 차량의 마스크는 어느 것이 내 차인지 가리는 데만 본다 (D-264). Ultralytics `model.track()`은 쓰지 않는다. 내장 추적기에는 채널 B 덩어리를 넣을 수 없고 상태를 파일로 저장·복원하기 어렵기 때문이다. 프레임 전체가 아니라 **분석 크롭** 위에서 본다 (D-95). 클래스는 사람·승용차·오토바이·자전거·트럭·버스·COCO 동물 클래스 전체다 (D-196)
  - **채널 A는 영상 전체에 돌지 않는다.** 채널 B가 ROI 움직임을 감지했을 때만 켠다. 단, 영상 시작부터 MOG2가 안정될 때까지는 켜 둔다 (D-199). 규칙은 아래 "채널 A 켜고 끄기" (D-97).
- **채널 B: 근접 영역의 움직임.** 본인 차량 bbox를 넓힌 **근접 영역(ROI)** 에 닿은 움직임 덩어리를 찾는다. 배경 차분(MOG2, `detectShadows=True`로 그림자 제거)을 쓴다. 광학 흐름은 쓰지 않는다. 필요한 것은 "파손 근처에서 무언가 움직였나"뿐이고 방향·속도는 필요 없으며, 광학 흐름은 더 무겁고 멈춘 물체를 놓치는 약점도 같다 (D-192). ROI는 "이 구역에서 움직임이 생기면 그 물체를 보기 시작하는 곳"이고, 물체를 따라가는 것은 ByteTrack이다. 덩어리는 물체 전체로 넓혀서 bbox를 만든다 (D-96).
  - (a) **채널 A 트랙에 붙이기**: 덩어리 넓이의 50% 이상이 채널 A 트랙의 bbox 안에 있으면 그 물체의 일부(손 등)로 본다 (D-256이 D-197의 "bbox를 사방으로 10% 넓힌 범위에 겹침"을 바꿨다). 여러 트랙에 걸치면 가장 많이 겹치는 트랙에 붙인다. **멈춘 차에는 붙이지 않고 (b)로 넘긴다.** 멈춘 차는 최근 1초 동안 bbox 중심 이동이 bbox 폭의 5% 미만인 차 트랙이다. 사람·동물은 멈춰도 붙인다 (D-197, D-256, 시작값). 채널 B 트랙을 따로 만들지 않고, 바닥점은 채널 A bbox의 것을 쓴다.
  - (b) **움직임 영역 확장**: 붙일 채널 A 트랙이 없으면, 움직임 감지를 ROI가 아니라 분석 크롭 전체에 돌려 둔 전경 마스크에서 **ROI에 닿은 덩어리와 이어진 전경 픽셀 전체(연결 요소)** 의 bbox를 쓴다. 분석 크롭 짧은 변의 1% 안쪽 간격이면 이어진 것으로 본다 (D-197, 시작값). 이 bbox를 ByteTrack에 넣어 클래스 없는 트랙으로 만든다. 후보의 시작은 ROI에 닿은 덩어리로만 한다. **ByteTrack에는 ROI에 닿은 덩어리만 넣는다.** 덩어리 전체가 ROI를 벗어나면 그 트랙은 더 이어 붙지 않고 ByteTrack이 정리한다. 클래스 없는 트랙의 추적은 "ROI 근처에 있는 동안 같은 물체로 묶고, 한두 프레임 놓쳐도 이어 붙이는" 용도이며 ROI 밖 경로는 따라가지 않는다 (D-192).
  - 가만히 서서 손만 움직이는 사람은 몸이 배경으로 흡수되어 (b)로는 손만 남는다. 이 경우는 (a)가 맡는다.
  - 채널 B는 **클래스가 없는 물체**(카트, 라바콘, 떨어지는 물건)를 잡고, 채널 A를 켜는 신호도 된다(아래). 시작값은 D-195(전경 임계값 16, 배경 학습 약 1분, 노이즈는 분석 크롭의 0.01% 미만, 덩어리 크기 상한 30%)이고 실측으로 조정한다(U-09). 상한 이상인 덩어리로는 클래스 없는 트랙을 만들지 않지만 채널 A는 켠다. 상한 이상인 덩어리가 있는 프레임에서는 채널 A 트랙의 움직임을 덩어리 대신 bbox로 묶어 잰다 (6.5 "후보 구간의 규칙", D-268). 비율은 줄인 프레임(D-201) 기준이다. 배경 학습 시간은 샘플링 fps로 프레임 수를 환산한다. ROI 크기는 🚧 (U-30)
  - **MOG2 계산 범위 (D-192)**: MOG2는 영상 처음부터 끝까지 **분석 크롭 전체**에 돈다. ROI 마스크는 움직임 판정(채널 A를 켤지, 후보를 시작할지)에만 쓴다. 크롭 전체의 전경 마스크가 늘 있어야 (b) 확장에서 ROI 밖으로 이어진 부분을 바로 찾을 수 있다. ROI 밖 배경을 채널 A가 켜질 때에야 학습하면 켜진 직후 몇 초는 배경 기준이 없어 (b)가 망가진다.
  - 바꾸는 조건: 처리 속도 실측(U-06)에서 MOG2가 병목으로 나오고 GPU 전환(D-198)으로도 부족하면 "평소에는 ROI의 외접 사각형에만 MOG2를 돌리고, 채널 A를 켤 때 링 버퍼의 10초로 크롭 전체용 MOG2를 따로 학습시키는 안"으로 바꾼다. MOG2는 640×360에서 프레임당 약 3.7ms다(Mac 간이 시험, D-201). 서버에서 다시 잰다 (D-198).
- **분석 크롭**: 본인 차량 bbox에 여백을 더한 고정 사각형이다. **가로세로 비율은 보여줄 크롭과 같은 16:9이고, 넓이만 더 크다**(D-176). 영상 하나에 하나이고 끝까지 바뀌지 않는다(본인 차량은 움직이지 않는다, D-29). 사용자에게 보여줄 크롭(6.7)보다 **크게** 잡는다. 근접 영역(ROI)은 이 안에 있고, 비식별화 탐지도 이 영역에서 한다(6.8) (D-95).
  - **크기 (D-201, D-244, 시작값)**: 폭은 본인 차량 bbox 폭의 약 2배, 높이는 폭의 9/16이고 원본 픽셀로 계산한다. 위치는 bbox 중심에 맞추고, 원본 밖으로 나가면 크기를 유지한 채 안쪽으로 민다(D-175). ROI나 보여줄 크롭을 담지 못하면 16:9를 지키며 담을 때까지 넓힌다.
  - **채널 A·B 프레임 (D-201, 시작값)**: 긴 변이 640보다 크면 640×360으로 줄이고(`INTER_AREA`), 640 이하면 그대로 쓴다. 한 영상 안에서는 끝까지 같은 크기다. YOLO 입력(`imgsz`)은 640이고, 작은 물체를 놓치면 1280으로 올린다. MOG2·ROI 마스크·차 영역 마스크도 줄인 프레임 크기를 쓴다. 비식별화는 줄이지 않는다(6.8).
  - **좌표**: 트랙 파일의 `bbox`는 원본 해상도 픽셀이다(04장 4.8). 줄인 프레임의 좌표를 분석 크롭 위치와 축소 배율로 되돌려 저장한다. 구현 주의는 D-201에 있다.
  - 이유: 프레임 전체를 모델 입력 크기로 줄이면 사람·카트처럼 작은 물체가 작아진다. 내 차 크기에 맞춰 자르면 입력 640에서 내 차 폭이 크롭 크기와 상관없이 약 213px로 보여, 차 주변 물체가 보이는 크기가 일정하다.
  - 크롭 밖에서 들어오는 물체는 크롭 가장자리에서 트랙이 시작된다. 크롭은 고정이라 트랙이 크롭 때문에 끊기지는 않는다. 가장자리에 걸려 잘린 bbox는 바닥점을 믿을 수 없는 트랙으로 보고 남긴다(아래 바닥점 필터).
  - 큰 차량이 일부만 크롭에 걸리면 YOLO가 놓칠 수 있다. 그래서 보여줄 크롭보다 여백을 더 둔다. 채널 A에는 타일을 쓰지 않는다. 타일 결과를 합친 뒤 추적하면 트랙이 끊기지는 않지만, 24시간 영상 전체에 타일 수만큼 시간이 곱해지고, 차처럼 큰 물체가 타일 경계에서 조각나 합치기가 어려워진다.
- 채널 B는 D-4에서 "사전 필터"로만 검토하던 움직임 감지를 **후보를 만드는 채널**로 올린 것이다 (D-71이 D-4·U-07을 바꿈). 움직임 판정을 ROI 안의 변화로만 하므로 화면 전체의 조명·비 변화로 생기는 오탐이 준다.
- 두 채널이 같은 물체를 잡으면 채널 B 덩어리를 채널 A 트랙에 붙여 하나로 친다(위 (a), D-96). 겹침 기준은 덩어리 넓이의 50% 이상이 트랙 bbox 안에 있는 것이다 (시작값, D-256). 후보 단위는 트랙이 아니라 ROI 안 움직임 구간이다 (D-245)
- 청크는 디코딩에만 쓴다. 탐지·추적(채널 A·B)은 프로세스 1개가 영상 처음부터 끝까지 한 줄로 한다 (D-76, [02장 2.6](02-architecture.md#26-청크-분할과-병렬-처리)). 청크 경계에서 프레임이 빠지거나 겹치지 않게 자른다(시크 후 청크 시작 전 프레임 버리기). 시작값은 샘플링 10fps, 디코딩 청크 30초, 디코딩 프로세스 3개다 (D-198, 실측으로 조정). **ROI만 fps를 높이지 않고** 영상 전체를 같은 fps로 본다. 날아오는 물체는 한두 프레임에만 걸릴 수 있어 평가에서 확인한다.
- 처리 시간은 고정 목표로 두지 않는다. 느리면 NVDEC → MOG2 GPU 전환(OpenCV 직접 빌드) → MOG2 범위 축소 → fps 낮추기 순서로 줄인다. 빌드 주의사항은 D-198에 있다.
- 중간 저장: 구간마다 트랙 파일과 추적기 상태를 저장한다. 저장 순서는 구간 파일 → 추적기 상태 → `processed_sec` (D-76, 04장 4.8·4.9). 간격은 원본 시간 10분이다 (D-198, 시작값). 도중에 죽은 작업은 재전달된 메시지를 받은 워커가 이어서 한다 (6.2, D-94). 추적기 상태 형식과 이어서 할 때의 순서는 아래 "채널 A 켜고 끄기"의 "추적기 상태 파일 내용"과 "이어서 하기" (D-97)
- 본인 차량은 추적하지 않는다. 입력한 bbox를 고정 영역으로 쓴다 (D-29). 본인 차량과 옆 차에 걸리는 채널 A 트랙(주차된 차 자체)은 움직임이 없으므로 후보 구간을 만들지 않는다 (D-245, D-278).

### 채널 A 켜고 끄기 (D-97, D-247)

**요약**: 채널 B(MOG2)는 영상 처음부터 끝까지 분석 크롭 전체에 돌고, 움직임 판정은 **ROI 안의 픽셀 변화로만** 한다 (D-192). 채널 A(YOLO + ByteTrack)는 **ROI 움직임을 처음 감지한 때부터 10초 전 ~ 마지막으로 감지한 때부터 5초 후** 구간에만 돈다 (D-247).

**10초·5초의 근거 (D-247가 D-192의 35초를 바꿨다)**: 감지 시각 10초 전 ~ 마지막 감지 5초 후는 후보 클립(후보 구간 앞뒤 여유 5초, 아래 "후보 구간과 유력 시점")을 빠짐없이 덮는 길이다. 이 구간의 분석 결과는 후보 선정뿐 아니라 0단계 필터와 사람 비식별화(6.8)의 자료로도 쓰인다. 그래서 클립 전체가 채널 A로 분석돼 있어야 한다.

**이유**: 차에 접촉하려면 무언가가 ROI 안에서 움직여야 한다. 움직임이 없는 시간에 YOLO를 돌려도 후보가 나오지 않는다. 24시간 영상은 대부분 차 옆에 움직임이 없어 YOLO 연산이 크게 준다. 하루 종일 움직임이 있는 최악의 경우에도 영상 전체에 돌리는 것과 같다.

**수치** (초기값이며 실측으로 조정한다, 🚧 U-06)

- **켤 때 거슬러 올라가는 시간 10초**: 클립 앞 여유 5초에 ByteTrack 워밍업 5초를 더한 값이다. 새 트랙은 몇 프레임 연속으로 잡혀야 확정되고, 처음 몇 프레임은 박스가 불안정하다. 클립 첫 프레임에서 사람 트랙이 이미 안정돼 있어야 비식별화 폴백(6.8)에 빈틈이 없다.
- **끌 때 여유 5초**: 클립 뒤 여유 5초와 같다. 더 길게 두지 않는 이유는 세 가지다. ① 꺼진 지 10초 안에 다시 움직이면 이미 돌린 곳 다음부터 이어 붙이므로(규칙 4), 10초 이하로 끊긴 후보 구간을 한 클립으로 합쳐도 클립 전체가 덮인다. ② 멈춘 물체는 MOG2에서 한동안 전경으로 남아, 마지막 감지가 보통 후보 구간의 끝보다 늦다. ③ 그래도 빈틈이 생기면 클립을 만들 때 그 부분만 YOLO를 돌린다(6.7).

**ROI 움직임의 정의**: 한 프레임에서 채널 B의 전경 덩어리 중 하나라도 ROI와 겹치면 그 프레임에 ROI 움직임이 있다. 노이즈 크기 이하의 덩어리는 뺀다. 노이즈 기준과 전경 임계값의 시작값은 D-195이다. **임계값은 낮게** 잡는다. 움직임을 놓치면 YOLO가 켜지지 않아 후보를 잃는다. 반대로 잘못 켜지면 YOLO를 조금 더 돌릴 뿐이다.

**동작 규칙**

1. **켜기**: YOLO가 꺼진 상태에서 ROI 움직임이 감지되면 YOLO를 켠다. 이때 감지 시각 10초 전부터 감지 시각 직전까지의 프레임에 먼저 YOLO를 돌리고, 그다음 감지 프레임부터 정상적으로 이어 간다. 10초 전 프레임은 **링 버퍼**에서 가져온다. 링 버퍼는 최근 10초의 분석 크롭 프레임(샘플링 fps)을 항상 메모리에 들고 있다. 영상 시작이 10초보다 가까우면 영상 시작부터 돌린다.
   - 거슬러 돌리는 프레임에는 **YOLO + ByteTrack만** 돌린다. MOG2는 그 프레임들을 이미 처리했으므로 다시 돌리지 않는다. MOG2는 지난 프레임으로 배경을 계속 학습하는 상태라서, 같은 프레임을 다시 넣으면 배경이 두 번 학습되고 시간 순서가 꼬인다 (D-192).
   - 거슬러 돌린 결과(트랙 줄)는 정상 구간과 똑같이 트랙 파일에 쓰고(정렬하지 않고 만든 순서대로 쓴다. 그래서 파일 안의 줄 순서는 시간순이 아닐 수 있다. 04장 4.8, D-258), 이어서 감지 프레임부터 정상적으로 진행한다. 클래스 없는 트랙((b))은 지금처럼 ROI에 닿은 프레임부터 만든다.
2. **연장**: YOLO가 켜진 동안 ROI 움직임이 감지될 때마다, 끌 시각을 "그 감지 시각 + 5초"로 다시 정한다.
3. **끄기**: 끌 시각에 도달하면 YOLO를 끈다. 이후에는 채널 B만 돈다.
4. **다시 켤 때 겹침 처리**: 꺼진 지 10초가 안 돼 다시 켜지면, 거슬러 올라갈 범위의 앞부분이 이미 YOLO를 돌린 구간이다. 이미 돌린 프레임은 다시 돌리지 않고, 마지막으로 돌린 프레임의 다음 프레임부터 돌린다. 이 경우 YOLO가 돈 구간은 끊기지 않으므로 앞 구간에 이어 붙여 하나의 구간으로 기록한다. 같은 프레임을 두 번 돌리면 같은 시각에 트랙 줄이 두 번 생기고 ByteTrack 상태가 꼬인다.
5. **ByteTrack은 영상 하나에 채널마다 한 인스턴스, 모두 둘** (D-257): 채널 A 추적기에는 YOLO 탐지만, 채널 B 추적기에는 움직임 덩어리만 넣는다. 추적기 하나가 그 채널의 물체 전부를 따라가며, 물체마다 추적기를 만들지 않는다. 껐다 켜도 새로 만들지 않고 끝까지 같은 인스턴스를 쓴다. `track_id`는 채널 A가 1번부터, 채널 B가 1,000,001번부터 매겨 영상 안에서 겹치지 않는다(04장 4.8). 꺼진 동안 사라진 물체의 트랙은 ByteTrack이 시간이 지나 스스로 정리한다. 움직임 덩어리에는 신뢰도가 없으므로 채널 B 추적기에는 모든 덩어리의 신뢰도를 1.0으로 넣는다. 새 트랙 시작 기준(0.5, D-200)을 항상 넘어 신뢰도 때문에 버려지는 덩어리가 없다. 이 값은 트랙 파일에 쓰지 않는다(04장 4.8, D-258).
6. **채널 B 연결 순서**: 한 프레임에서 YOLO 결과를 먼저 내고, 그다음 채널 B 덩어리를 채널 A 트랙에 붙인다(D-96 (a)). 거슬러 돌린 덕분에 움직임이 처음 감지된 프레임에도 채널 A 트랙이 이미 있다.
7. **영상 끝**: 영상이 끝날 때 YOLO가 켜져 있으면 마지막 프레임 시각에 구간을 닫는다.
8. **영상 시작**: MOG2가 안정될 때까지는 ROI 움직임과 상관없이 YOLO를 켜 둔다 (D-199). 안정 전 전경은 믿을 수 없어 이 구간을 ROI 움직임에 맡기면 3초 영상처럼 짧은 영상에서 후보가 0개가 될 수 있다. 이 구간의 움직임은 MOG2 없이 직전 분석 프레임과의 차이만으로 잰다 (아래 "후보 구간의 규칙", D-265). 안정되는 시각에 끌 시각이 지나 있으면 그때 끄고, 그 전에 ROI 움직임이 있었으면 규칙 2의 끌 시각까지 이어 간다. 구간은 영상 시작부터 하나로 기록한다. 안정 시간은 **약 1분**이고, 배경 학습 시간(D-195)과 같은 값을 쓴다. 배경 학습 시간을 바꾸면 안정 시간도 같이 바뀐다 (D-199). 이어서 하기 때는 이 규칙을 쓰지 않는다. 1분 전부터 다시 읽어 배경을 만든 뒤 이어 가기 때문이다 (아래 "이어서 하기", D-248).

**예시**

| 원본 시간 | 일어난 일 | YOLO |
|---|---|---|
| 0~99초 | ROI 움직임 없음 | 꺼짐. 채널 B만 돈다 |
| 100초 | 사람이 ROI에 들어옴 (첫 움직임) | 버퍼의 90~100초를 먼저 돌리고 켠다. 끌 시각 105초 |
| 100~112초 | 계속 움직임 | 켜짐. 끌 시각이 계속 밀려 117초 |
| 112~117초 | 움직임 없음 | 켜짐 유지 |
| 117초 | 끌 시각 도달 | 끈다. YOLO 구간 [90, 117] |
| 122초 | 다른 사람이 ROI에 들어옴 | 10초 전은 112초지만 117초까지는 이미 돌렸다. 117초 다음 프레임부터 돌리고 켠다. 구간은 [90, …]로 이어진다 |

**메모리**: 링 버퍼에는 줄인 프레임을 담는다. 640×360 RGB, 10fps, 10초 기준 약 70MB다 (D-201, D-247). 워커는 작업을 하나씩 처리하므로(D-94) 동시 사용자가 늘어도 버퍼는 작업 하나 분량이다.

**YOLO 구간 기록**

- YOLO가 돈 구간 목록(원본 시간의 [시작, 끝] 목록, 처음부터 누적)을 **추적기 상태 파일**(`videos/{video_id}/tracks/tracker_state`, 04장 4.9)에 함께 저장한다.
- 트랙 파일만으로는 이 정보를 알 수 없어서 따로 기록한다. 트랙 줄이 없는 시각은 "YOLO가 꺼져 있었다"일 수도 있고 "켜져 있었는데 아무것도 없었다"일 수도 있다.
- 구간마다 **기준 영역**(그 구간의 첫 프레임에서 만든 내 차 영역, 아래 "차 너머 트랙 빼기")을 하나씩 함께 적는다 (D-259). 내 차를 찾지 못한 구간은 기준 영역이 없다고 적는다. 규칙 4로 앞 구간에 이어 붙은 경우는 한 구간이므로 다시 만들지 않는다.
- 기준 영역은 **다각형 목록**으로 적는다 (D-263). 다각형 하나는 영역 한 조각의 바깥 윤곽이고, 꼭짓점은 줄인 분석 프레임 좌표의 정수 `[x, y]`다. 기둥 등에 끊겨 조각이 여럿이면 다각형도 여럿이다. 1단계 `polygon`(6.3)처럼 볼록 껍질 하나로 잇지 않는다. 이으면 가려진 부분까지 내 차 영역이 된다. 영역 안의 구멍은 적지 않아 채워진다. 내 차를 찾지 못한 구간은 빈 목록이다.

  | 구간 (원본 시간, 초) | 상황 | 기준 영역 |
  |---|---|---|
  | 712.0 ~ 745.5 | 내 차 전체가 보인다 | 다각형 1개 |
  | 1310.2 ~ 1342.0 | 기둥이 가운데를 가려 두 조각으로 보인다 | 다각형 2개 |
  | 2001.0 ~ 2019.4 | 내 차를 찾지 못했다 | 빈 목록 |

- **기준 영역으로 쓰는 모양은 "다각형으로 바꾼 뒤 다시 그린 모양"이다** (D-263). segmentation 마스크를 그대로 쓰지 않는다. 이어서 하기로 추적기 상태 파일에서 읽어 다시 그려도 한 픽셀도 달라지지 않게 하기 위해서다.
- 쓰이는 곳: 다시 켤 때 겹침 처리(규칙 4), 이어서 하기(아래), 클립을 만들 때 YOLO가 돌지 않은 부분 보충(6.7), 차 너머·차 앞 트랙 빼기와 바닥점 보임 판정(기준 영역).

**추적기 상태 파일 내용**: JSON 하나이며, 구간 파일을 저장할 때마다 덮어쓴다. 형식은 06장에서 정한다는 04장 4.9를 따른다.

- `processed_sec`, 채널 A·B 각각의 다음에 쓸 `track_id` 번호 (D-257)
- 채널 A·B ByteTrack 상태(직렬화 가능한 형태)
- YOLO가 지금 켜져 있는지, 켜져 있다면 끌 시각, 마지막으로 YOLO를 돌린 프레임 시각
- YOLO 구간 목록 전체 (구간마다의 기준 영역 포함, D-259)

**이어서 하기** (D-94): 작업이 중간에 죽어 다른 워커가 이어받을 때의 절차다.

1. 추적기 상태 파일을 읽어 위 상태와 두 ByteTrack을 복원한다.
2. `processed_sec` **1분 전**부터 `processed_sec`까지 다시 디코딩한다 (D-248). 이 구간에는 **MOG2만** 돌려 배경 모델을 다시 만들고, 마지막 10초의 프레임은 링 버퍼에도 담는다. 움직임 판정, YOLO 실행, 트랙 쓰기는 하지 않는다. 링 버퍼와 MOG2 배경 모델은 메모리에만 있고 저장하지 않기 때문이다. 링 버퍼만 채우려면 10초로 충분하지만, 배경은 약 1분을 학습해야 안정된다. 1분은 배경 학습 시간(D-195)과 같은 값이다. 중간 저장 간격이 10분(D-198)이라 1분 전이 영상 시작보다 앞서는 일은 없다.
3. `processed_sec` 다음 프레임부터 위 동작 규칙대로 이어 간다. 저장 시점에 YOLO가 켜져 있었으면 켜진 상태로 시작한다. 이어받은 지점에서 배경이 이미 안정돼 있으므로, 측정 불가로 기록하는 구간이나 YOLO를 강제로 켜 두는 구간은 없다.

예시 (`processed_sec`이 30:00인 작업을 이어받는 경우)

| 다시 읽는 구간 | 하는 일 |
|---|---|
| 29:00~29:50 | MOG2만 돌린다 (배경 학습) |
| 29:50~30:00 | MOG2를 돌리고, 프레임을 링 버퍼에 담는다 |
| 30:00 다음 프레임부터 | 평소대로 처리한다 |

한계: 다시 만든 배경은 죽기 전의 배경과 완전히 같지는 않아, 이어받은 지점 근처의 결과가 끊김 없이 처리했을 때와 조금 다를 수 있다 (D-248).

### 내 차 바닥 네 모서리로 시야 판단과 ROI 정하기 (D-98)

**요약**: 사용자에게 **내 차가 바닥에 닿는 네 모서리**를 화면에서 찍게 한다. 이 사각형 하나로 세 가지를 한다. ① 바닥점이 차의 어느 면 쪽에 있는지 판단하는 기준(바닥점 필터), ② 사각형이 찌그러진 정도로 **CCTV 시야(내려다보는 각도)** 파악, ③ 사각형의 크기로 **내 차가 카메라에서 얼마나 먼지** 파악. ②와 ③으로 ROI 크기를 정한다. 구체적인 수치와 계산 방법은 추후 정한다 🚧 (U-30).

**왜 필요한가**

- ROI를 내 차 bbox에 고정 배율로 더하는 방식은 카메라 높이를 반영하지 못한다. 같은 차라도 카메라 구도에 따라 가려지는 영역이 크게 다르다.
- **카메라가 높아 차를 위에서 내려다볼수록** 차 너머 바닥까지 보인다. 가려지는 영역이 작으므로 ROI를 작게 잡아도 된다. 불필요한 움직임이 줄어 후보도 줄어든다.
- **카메라가 낮아 차를 옆에서 볼수록** 내 차가 차 너머를 많이 가린다. 안 보이는 파손 쪽에서 일어나는 움직임은 지붕 위로 나온 머리나 상체로만 보이므로 ROI를 크게 잡아야 한다.
- 차가 카메라에서 멀면 화면에서 작게 보이고 가까우면 크게 보인다. 고정 픽셀로는 거리를 반영하지 못한다.
- 주차칸 흰 선은 쓰지 않는다. 내 차가 접근하는 쪽의 선을 가리는 경우가 많기 때문이다. 내 차의 바닥 모서리는 바퀴 위치로 대략 짐작할 수 있다.

**입력**

1. 내 차가 바닥에 닿는 네 모서리. 화면에 보이지 않는 모서리(차 너머)는 사용자가 짐작해서 찍는다.
2. 파손이 있는 변. 한 변, 또는 모서리 파손이면 이웃한 두 변을 고른다. 6.4의 통로 쪽 / 옆면 구분 입력을 이것이 대신한다 (U-26 → D-98).

**네 모서리에서 읽는 것**

| 사각형에서 보는 것 | 알 수 있는 것 | 쓰는 곳 |
|---|---|---|
| 찌그러진 정도 (실제 차 바닥은 폭 약 1.8m × 길이 약 4.7m인데 화면에서 얼마나 납작한가, 차 bbox 높이 대비 사각형 세로 높이 등) | 카메라가 내려다보는 각도. 납작할수록 낮은 카메라 | ROI를 위쪽(차 너머 가려짐)으로 얼마나 넓힐지 |
| 크기 (변의 화면상 길이) | 내 차까지의 거리. 작을수록 멀다 | ROI·크롭 크기를 화면 픽셀로 환산하는 자 |
| 각 변의 위치 | 차의 앞·뒤·좌·우 면이 화면 어디에 있는지 | 바닥점이 어느 면 쪽에 있는지 판단 (바닥점 필터) |

**ROI를 정하는 방향**

- **파손이 보이든 안 보이든 ROI 구성은 같다 (D-192이 D-191의 보이는 파손 규칙을 바꿈)**: 파손 변 바로 바깥에 선 물체(사람 등)가 화면에 나타나는 자리를 ROI로 잡는다. ROI는 **내 차 차체, 파손 변 양 끝의 좁은 출입 띠, 지붕 위 여유**를 포함한다.
  - 안 보이는 파손: 차가 사람보다 높으면 반대편 사람은 양 끝에서 나타나고 사라지는 순간과 차체 흔들림으로만 보인다 (D-191).
  - 보이는 파손: 앞에 차를 세우거나 사람이 몸으로 가린 채 그 뒤에서 파손 부위를 건드리면, 파손 부위 자체에는 변화가 거의 안 보인다. 그래서 파손 부위 근처만 잡으면 놓친다.
  - 접근 경로 전체는 넣지 않는다. 그것은 분석 크롭 전체를 보는 채널 A가 본다.
- **파손 변이 모두 카메라 쪽 변이면 ROI를 좁게 잡는다 (D-244, 시작값)**: 파손 앞 사람이 내 차에 가려지지 않으므로 지붕 위 여유와 차체 전체는 넣지 않는다. ROI는 아래 셋의 합집합이다. 건너편·앞뒤 끝 변이 섞이거나 바닥 지도를 믿을 수 없으면 위 구성을 쓴다.
  - 파손 변 바깥 띠: 바닥 지도에서 바깥 1m, 양 끝 0.5m씩 늘린 사각형을 화면으로 옮기고, 각 열을 차량 bbox 위 변까지 위로 채운다.
  - 파손 변 양 끝점을 중심으로 bbox 폭·높이의 ±0.12배 상자.
  - 파손 박스를 bbox 폭·높이의 0.15배씩 넓힌 사각형.
  - 카메라 높이에 따라 줄일지(구도 추정)와 위·아래·가로로 넓히는 양은 🚧.
- 보여줄 크롭도 같은 자(네 모서리에서 구한 거리)로 정한다. 분석 크롭은 내 차 bbox 폭으로 시작한다 (D-201, D-244). ROI ⊂ 보여줄 크롭 ⊂ 분석 크롭이다 (D-95).

| | 안 A: 코드 규칙 | 안 B: VLM 제안 + 코드 검증 |
|---|---|---|
| 만드는 방법 | 바닥 네 모서리·파손 변·차 bbox·파손 사각형으로 코드가 다각형을 계산한다. 차 방향의 바닥 띠, 위로 쓸어올리기, 양 끝 출입 영역을 차 크기 비율로 만든다. 세부는 `docs/영역설계.md`(검토용 초안) | 분석 시작 전 영상마다 한 번, 정지 장면과 사용자 입력을 VLM에 주고 다각형을 받는다 |
| 검증 | 변환이 뒤집히거나 결과가 너무 크면 대체 규칙 | 아래 검증을 통과하면 쓰고, 실패하거나 호출이 실패하면 안 A의 ROI를 쓴다 |
| 장점 | 같은 입력이면 항상 같은 결과, 추가 비용 없음, 단위 테스트 가능 | 장면을 보고 파손 근처를 타이트하게 잡는다(사진 비교에서 확인) |
| 약점 | 계수에 따라 넓고 기계적인 모양이 나온다 | 호출마다 결과가 다를 수 있고, 검증을 통과해도 틀릴 수 있다. 영상당 VLM 호출 1회 추가 |

안 B의 검증 조건(기준값은 U-30):

- 다각형이 꼬이지 않았다(자기교차 없음, 꼭짓점 3개 이상).
- 분석 크롭 안에 있다.
- 파손 사각형을 포함한다.
- 면적이 상한·하한 안이다.
- 차체·파손 변 양 끝 출입 띠·지붕 위를 포함한다(보임·안 보임 공통, D-192). 파손 변이 모두 카메라 쪽이면 D-244 구성(바깥 띠·양 끝 상자·넓힌 파손 박스)을 포함하는지로 본다.

**두 안의 공통 처리 (D-191)**

- ROI는 다각형이다. 영상마다 처음 한 번 분석 크롭 크기의 마스크(안쪽 1, 바깥 0)로 바꾸고, 채널 B의 전경 결과에 씌워 ROI 안의 변화만 센다. 움직임 판정은 두 안 모두 코드가 한다.
- ROI 좌표는 분석 크롭 기준 비율 좌표(0~1)로 다룬다. 한 번 만든 ROI는 그 영상의 분석 끝까지 바꾸지 않는다.
- 움직임 판정 기준은 ROI 마스크 안에서 달라진 픽셀 수가 **분석 크롭 넓이의 0.01%** 이상인 것이다 (시작값, D-254). 분모는 ROI 넓이가 아니라 분석 크롭 넓이다. 같은 움직임이 바꾸는 픽셀 수는 ROI 크기와 상관없고, 분석 크롭은 내 차 크기에 맞춰 잡기 때문이다 (D-244).
- 16:9 맞춤용 패딩 영역은 마스크에서 뺀다.

**정하지 않은 것** 🚧 (U-30)

- 찌그러진 정도와 크기를 어떤 값으로 계산할지.
- 그 값에서 ROI·보여줄 크롭을 얼마나 넓힐지(상한·하한 포함). 분석 크롭과 카메라 쪽 파손 ROI의 시작값은 D-244다.
- ~~사용자가 모서리를 잘못 찍었을 때(사각형이 꼬였거나 차 bbox와 크게 어긋남) 어떻게 할지.~~ **정함 → D-267**: 꼬인 사각형은 화면과 서버가 막는다 (05장 5.7 검증 11·12). 차 `bbox`와 어긋난 모서리는 따로 처리하지 않는다.
- 실제 영상(높은 카메라, 낮은 카메라, 가까운 차, 먼 차)으로 확인한 뒤 정한다.

**한계**

- 차보다 낮은 물체가 차 너머에서 움직이면 ROI를 키워도 보이지 않는다. 이때 남는 단서는 내 차 흔들림, 가려졌다 다시 나타남, 그림자다.
- 보이지 않는 모서리는 사용자의 짐작이라 오차가 있다. 그래서 이 사각형으로는 **확실히 아닌 것만** 뺀다 (D-91).

### 바닥점 필터 (근접 판정) (D-193)

**요약**: 화면에서 내 차와 겹쳐 보인다는 것은 근거가 되지 않는다. 카메라와 내 차 사이를 지나가기만 해도 겹쳐 보인다. 그래서 물체가 **바닥 어디를 밟았는지**를 본다. 이 필터는 접촉을 증명하지 않고, **멀리 지나간 것이 확실한 트랙만** 뺀다 (D-91). 판단은 프레임이 아니라 트랙 단위로 한다.

| 용어 | 뜻 |
|---|---|
| 바닥 지도 | 내 차 바닥 네 모서리를 실제 차 바닥 직사각형(폭 약 1.8m × 길이 약 4.7m)에 맞춰 만든 좌표. 사용자가 고른 앞쪽 변과 그 맞은편 변을 폭 약 1.8m, 나머지 두 변을 길이 약 4.7m에 맞춘다. 화면에 보이는 변 길이로 긴 변을 추정하지 않는다 (D-194). 화면 위 점을 "내 차에서 몇 m 떨어진 바닥 위치"로 바꾼다. 원근 때문에 멀리 있는 물체가 작게 보여도 같은 기준으로 잰다 |
| 바닥점 | 사람은 bbox 아래 변의 가운데(두 발 사이), 승용차·오토바이는 bbox 아래 변 전체(선분). 물체가 바닥에 닿는 부분 중 카메라에 가장 가까운 쪽이다 |
| 손이 닿는 구역 | 바닥 지도 위 파손 변에서 아래 표의 기준 거리 안쪽. 물체 종류별로 영역을 따로 저장하지 않고, 파손 변까지의 거리를 기준 거리와 비교한다. 화면 위의 ROI와 다르다. ROI는 채널 A를 켤지 정하고, 이 구역은 트랙을 뺄지 정한다 |
| 차 영역 | 내 차의 픽셀 모양 마스크. **YOLO 구간마다 한 번**, 그 구간의 첫 프레임에서 만든다(기준 영역, D-259). 내 차는 자리를 옮기지 않지만 옆 차가 오가면 보이는 부분이 바뀌기 때문이다. 구간 안에서는 충돌로 살짝 밀리거나 흔들려도 다시 만들지 않는다. 이때의 변화는 아래 "충돌로 내 차가 흔들림" 행처럼 후보를 남기는 근거가 된다 |
| 차 영역 변화 | 트랙 bbox와 차 영역이 겹치는 곳의 MOG2 전경(픽셀 변화). 차 영역 전체의 전경과 구분한다 |
| 영역 줄어듦 | 기준 영역 가운데 트랙 bbox 안에 있으면서, 지금 프레임의 내 차 영역에서는 빠진 픽셀 수. 물체가 내 차를 가리면 그만큼 내 차 영역이 줄어든다. 차 너머 트랙 빼기에만 쓴다 (D-259) |
| 내 차 자리 | 네 모서리 사각형이 걸친 세로줄마다 사각형의 아래 경계에서 고른 차량 `bbox`의 위 변까지를 채우고, 좌우로 `bbox` 폭의 10%씩 넓힌 화면 위 영역. 영상마다 한 번 만들고 영상 내내 고정이다. **차 영역이 아니다.** 채널 A가 낸 차량 마스크 가운데 어느 것이 내 차인지 가리는 틀로만 쓴다 (D-264) |

**물체 종류별 기준 거리** (값은 🚧 U-30)

| 물체 | 재는 거리 | 기준 거리 | 이유 |
|---|---|---|---|
| 사람 | 바닥점 → 파손 변 | 팔 길이 + 여유. 파손 변 바깥쪽만 0.8m, 양 끝 0.3m (시작값, D-244) | 발이 멀어도 손·가방·문이 닿을 수 있다 |
| 승용차·오토바이 | bbox 아래 변 → 파손 변의 가장 짧은 거리 | **차 길이 (약 5m)**. 나란히 지나가면 **차 폭 + 여유 (약 2.5m)** | 아래 변은 그 차의 카메라 쪽 면이고, 내 차 쪽 면은 차의 깊이만큼 더 가깝다. 차 방향은 bbox 모양으로 추정하지 않고 가장 긴 경우로 잡되, 움직인 방향으로 확인되면 줄인다 |
| 내 차 너머의 사람·승용차·오토바이 (바닥점이 내 차보다 먼 쪽에 보임) | 바닥점 → 파손 변 | **약 2m** | 보이는 면이 곧 내 차 쪽 면이라 차 길이를 더하지 않는다. 건너편 모서리는 사용자의 짐작이라 1m보다 넉넉히 잡는다 |
| 트럭·버스 | 재지 않음. 차 앞 트랙 빼기로만 뺀다 | – | 높고 길어서 바닥점으로 거리를 믿을 수 없다 |
| 클래스 없는 물체, 새 | 재지 않음. 차 앞 트랙 빼기로만 뺀다 | – | 덩어리 모양이 불안정하다. 새는 날아다녀 바닥점이 바닥에 닿지 않는다 (D-245) |

자전거는 위 표의 오토바이와, 새를 뺀 동물은 사람과 같은 기준을 쓴다 (D-196). 동물의 바닥점은 사람처럼 bbox 아래 변의 가운데다. 내 차 위에 올라간 고양이는 바닥에 닿지 않아 위치가 틀릴 수 있다. 그래서 동물의 유력 시점은 바닥점을 쓰지 않고 화면 거리로 잡는다 (D-252). 새는 클래스 없는 물체와 같은 빼는 조건과 유력 시점 계산을 쓴다 (D-245). 0단계 공통 필터(너무 짧거나 작음, 화면 전체가 동시에 바뀜, 움직이지 않음)는 새와 클래스 없는 물체에도 적용한다.

**클래스가 바뀌는 트랙 (D-269)**: YOLO는 같은 물체의 클래스를 프레임마다 다르게 낼 수 있다. SUV·픽업·밴은 `car`와 `truck`을 오간다 (D-251). 빼는 조건은 클래스마다 달라서 한 트랙에 두 클래스가 섞이면 어느 규칙을 쓸지 정해야 한다.

- **트랙의 클래스는 그 트랙에서 가장 많은 프레임에 나온 클래스다.** 판정은 탐지가 끝난 뒤 트랙 파일로 하므로(D-250) 프레임 수를 세면 된다.
- 프레임 수가 같으면 남기는 쪽으로 본다. 트럭·버스가 끼어 있으면 트럭·버스다. 그 밖의 동률은 트랙에서 먼저 나온 클래스다.
- 위 표의 기준 거리, 빼는 조건, 차 너머 트랙 빼기, 유력 시점 계산은 이 클래스로 고른다.
- 프레임을 처리하면서 하는 판단(멈춘 차인지, 차 영역 마스크의 대상인지)은 그 프레임의 클래스를 쓴다. 트랙이 끝나기 전이라 전체를 셀 수 없다. 차량 클래스끼리 바뀌는 것은 "차량"이라는 점이 같아 결과가 같다.
- 트랙 파일의 `cls`는 프레임마다 YOLO가 낸 값을 그대로 쓴다 (04장 4.8).

| 한 트랙의 프레임 | 트랙의 클래스 | 쓰는 규칙 |
|---|---|---|
| `car` 80, `truck` 20 (SUV) | 승용차 | 승용차 기준 거리, 차 너머 트랙 빼기 |
| `truck` 70, `car` 30 | 트럭 | 거리를 재지 않는다. 차 앞 트랙 빼기로만 뺀다 |
| `car` 50, `truck` 50 | 트럭 (동률은 남기는 쪽) | 거리를 재지 않는다. 차 앞 트랙 빼기로만 뺀다 |
| `motorcycle` 60, `bicycle` 40 | 오토바이 | 둘은 같은 기준을 써서 결과가 같다 |

**나란히 지나가는 차**: 차는 앞이나 뒤로만 가므로, 바닥 지도에서 움직인 방향이 곧 차가 향한 방향이다. 파손 변과 나란히 움직인 차는 파손 변 쪽 깊이가 차 폭이므로 차 길이 대신 차 폭 + 여유를 기준으로 쓴다. 트랙 내내 방향이 일정할 때만 줄이고, 멈춤·아주 느림·방향 바뀜이 있으면 차 길이를 유지한다. 파손 변이 여러 개이면 변마다 따로 판단한다. 나란함과 느림의 기준은 🚧 (U-30).

**빼는 조건**: 트랙이 끝나면 트랙 전체에서 파손 변에 가장 가까웠던 순간을 찾는다. 아래 다섯 조건을 **모두** 만족할 때만 뺀다. 하나라도 아니거나 판단이 안 되면 남긴다.

1. 가장 가까운 순간과 그 앞뒤로 바닥점이 보였다. 발·바퀴가 가려지지 않았고 bbox가 분석 크롭 가장자리에서 잘리지 않았다. 판정 방법은 아래 구현 주의사항을 따른다.
2. 처음부터 끝까지 한 물체로 봤다. 트랙이 중간에 끊기거나 ID가 바뀌지 않았다.
3. 가장 가까운 순간에도 손이 닿는 구역 밖이었다.
4. 내 차에 가려진 적이 없다. 차에 가려졌다 다시 나타나면 남긴다. 바닥점이 보이는 채로 내 차 너머를 지나간 것은 괜찮다. 파손 쪽 바닥이 내 차에 가려져 있으면, 그곳을 밟은 물체는 발이 가려지므로 이 조건에서 자동으로 남는다.
5. 바닥 지도를 믿을 수 있다. 네 모서리가 꼬였거나 너무 납작해 변환을 믿을 수 없으면, 그 영상은 이 필터를 끄고 아무것도 빼지 않는다.

**차 너머 트랙 빼기**: 내 차에 가려지는 것은 항상 내 차보다 카메라에서 먼 쪽에 있다. 내 차 앞에서 움직이면 차를 가리므로 차 영역의 픽셀이 변하고, 차 너머에서 움직이면 차 영역은 그대로이고 지붕 위나 차 끝 바깥만 변한다. 그래서 위 다섯 조건과 별도로, 사람·승용차·오토바이 트랙이 아래 셋을 모두 만족하면 뺀다. 새와 클래스 없는 트랙에는 쓰지 않는다 (D-245).

- 파손 변이 **모두 카메라 쪽 변**이다. 네 모서리 사각형에서 바깥쪽이 화면 아래를 향한 변이 카메라 쪽 변이다. 대각선 구도에서는 두 변이 카메라 쪽일 수 있다. 앞·뒤 끝 변이 섞이면 이 규칙을 쓰지 않는다. 차 너머에서 끝으로 손을 뻗을 수 있기 때문이다.
- 트랙이 사는 동안 바닥점이 한 번도 보이지 않았다. 차 끝을 돌아 나와 발이 보이면 위 다섯 조건으로 판단한다.
- 트랙이 사는 동안 트랙 위치에서 차 영역의 픽셀 변화가 없었다. 트랙 bbox와 겹친 차 영역에서 변한 픽셀이 분석 크롭 넓이의 1% 이상인 프레임이 하나라도 있으면 변화가 있는 것이다 (시작값, D-256). **영역 줄어듦도 없었다** (D-259). 트랙 bbox 안에서 줄어든 픽셀이 분석 크롭 넓이의 1% 이상인 프레임이 하나라도 있으면 영역 줄어듦이 있는 것이다 (시작값, D-261). 픽셀 변화나 영역 줄어듦 중 하나라도 있으면 빼지 않는다.

**차 너머 트랙 빼기의 한계: 앞 차에 발이 가려진 사람 (D-266)**: 이 규칙은 발이 **내 차에** 가려졌다고 보고 건너편으로 판단한다. 발이 내 차가 아니라 내 차 앞에 선 차에 가려진 경우는 따로 가르지 않는다. 내 차가 일부만 가려져 "찾음"인 구간에서, 앞 차와 내 차 사이에 선 사람이 내 차가 보이지 않는 자리에서 머리만 보이면 세 조건을 모두 만족해 빠진다. 조건을 더하지 않고 한계로 둔다.

| 장면 | 결과 |
|---|---|
| 앞 차가 내 차를 전부 가린다 | 내 차를 "찾지 못함"이다. 차 너머 트랙 빼기를 쓰지 않아 남는다 |
| 앞 차와 내 차 사이에 선 사람의 상반신이 보이는 내 차를 가린다 | 픽셀 변화나 영역 줄어듦이 기준(분석 크롭의 1%)을 넘으면 남는다 |
| 앞 차가 내 차의 일부를 가리고, 사람이 그 가려진 자리에 서서 머리만 보인다 | 바닥점이 보이지 않고 차 영역의 변화도 줄어듦도 없다. **빠진다** (한계) |

시연 4번(09장 9.9)을 찍을 때는 사이에 선 사람의 상반신이 보이는 내 차를 가려야 후보로 남는다.

차 영역은 **YOLO 구간마다 다시 만든다** (D-259). YOLO가 켜질 때마다 그 구간의 첫 프레임에서 내 차 영역을 만들어 그 구간의 **기준 영역**으로 쓴다. 첫 프레임은 거슬러 돌린 10초의 첫 프레임이라 ROI에 움직임이 없던 순간이다. 내 차는 네 모서리로 만든 "내 차 자리"로 찾는다 (아래 "내 차 찾기", D-264). 픽셀 변화, 영역 줄어듦, 바닥점이 차 영역에 닿았는지는 모두 그 프레임이 속한 구간의 기준 영역으로 잰다. 내 차를 찾지 못한 구간의 트랙에는 차 영역을 쓰는 두 규칙만 쓰지 않고 전부 남긴다.

| 상황 | 기준 영역 | 결과 |
|---|---|---|
| 시작 장면에서 내 차가 옆 차에 대부분 가려져 있다 | 보이는 부분만 기준 영역이 된다 | 보이는 부분 앞의 움직임은 잰다. 가려진 부분은 옆 차가 가리고 있어 어차피 보이지 않는다 |
| 가리던 옆 차가 떠난다 | 떠나는 동안은 이전 기준 영역. 다음 YOLO 구간부터 넓어진 영역 | 새로 드러난 부분 앞의 움직임도 다음 구간부터 잰다 |
| 옆 차가 와서 내 차를 가린다 | 오는 동안은 이전 기준 영역. 다음 구간부터 줄어든 영역 | 오는 차는 내 차 영역을 바꾸므로 남는다 |
| 거슬러 돌린 10초 | 그 구간의 기준 영역 | 픽셀 변화는 못 재고(MOG2 없음) 영역 줄어듦은 잰다 |

**내 차 찾기: "내 차 자리" (D-264)**: 채널 A(YOLO11m-seg)는 프레임마다 차량 마스크를 여러 개 낸다. 그 가운데 어느 것이 내 차인지는 사용자가 찍은 네 모서리로 만든 **내 차 자리**로 가린다. 내 차 자리는 내 차 영역이 아니다. 내 차 영역은 언제나 segmentation이 낸 실제 차체 픽셀이고, 내 차 자리는 "이 마스크가 내 차의 것인가"를 가리는 틀이다. 내 차가 기둥이나 옆 차에 가려 마스크가 여러 조각으로 나와도, 조건을 만족하는 조각을 전부 합쳐 내 차 영역으로 쓴다.

- **원리**
  - 차체의 모든 부분은 차가 바닥에 닿는 사각형(네 모서리)의 바로 위에 있다. 실제로 수직인 선은 화면에서도 거의 세로로 보인다. 그래서 내 차의 차체는 화면에서 네 모서리 사각형의 위쪽 세로줄 안에만 나타난다.
  - 내 차를 가리는 차는 내 차보다 카메라에 가깝다. 바닥에서는 카메라에 가까운 것일수록 화면에서 더 아래에 닿는다. 그래서 내 차 앞에 선 차의 마스크는 내 차의 네 모서리 사각형보다 아래로 내려간다. 얼마나 겹쳤는지가 아니라 **바닥에 닿는 위치**로 가른다.
- **내 차 자리 만들기** (영상마다 한 번, 영상 내내 고정)
  1. 네 모서리 사각형을 화면에 놓는다.
  2. 사각형이 걸친 세로줄마다, 사각형의 아래 경계에서 고른 차량 `bbox`(6.3)의 위 변까지를 채운다. ROI의 파손 변 바깥 띠(D-244)와 같은 방식이다. `bbox`의 위 변은 지붕의 높이다.
  3. 채운 모양을 왼쪽과 오른쪽으로 `bbox` 폭의 10%씩 넓힌다 (**좌우 여유**). 안내 문구가 "차가 바닥에 닿는 네 모서리"라 사용자가 바퀴 자리를 찍기 쉽고, 그러면 바퀴보다 밖으로 나온 범퍼가 사각형 밖에 놓이기 때문이다.
- **마스크 고르기** (구간의 첫 프레임과 YOLO가 도는 모든 프레임에서 같은 규칙을 쓴다)
  - 대상은 채널 A가 낸 차량 클래스(승용차·오토바이·버스·트럭)의 마스크다. 내 차가 다른 차량 클래스로 잡혀도 된다.
  - 아래 둘을 **모두** 만족하는 마스크를 전부 합친 것이 그 프레임의 내 차 영역이다.
    - **안쪽 80%**: 마스크 픽셀의 80% 이상이 내 차 자리 안에 있다.
    - **아래 여유 10%**: 마스크가 내 차 자리의 아래 경계보다 `bbox` 높이의 10% 넘게 아래로 내려가지 않는다. 내 차 자리가 걸친 세로줄에서만 본다.
  - 둘을 만족하는 마스크가 하나도 없으면 그 프레임은 **"찾지 못함"**이다. 구간의 첫 프레임이 "찾지 못함"이면 기준 영역은 빈 목록이고(D-263), 그 구간의 트랙에는 차 영역을 쓰는 두 규칙을 쓰지 않고 전부 남긴다 (D-259).
  - 넓이로 실패를 가리던 기준(영역 넓이가 고른 차량 사각형의 50% 미만, D-256 5번)은 없앤다. 가려져 작게 보이는 것은 실패가 아니다.
  - 프레임마다 처음부터 다시 고른다. 앞 프레임의 결과를 이어받지 않으므로 이어서 하기를 위해 더 저장할 것이 없다.
- **내 차 자리를 만들 수 없는 영상**: 네 모서리를 믿을 수 없어 0단계 필터를 끄는 영상(위 조건 5)이거나 `bbox`의 위 변이 네 모서리 사각형보다 아래에 있으면 내 차 자리를 만들지 않는다. 모든 구간이 "찾지 못함"이다.

내 차 자리의 예시 (숫자는 설명용이다):

| 무엇 | 값 |
|---|---|
| 네 모서리 | (200, 250), (420, 270), (460, 230), (250, 215) |
| 고른 차량 `bbox` | 위 변 y = 120, 폭 280, 높이 150 |
| 위로 채운 모양 | 사각형의 아래 경계 (200, 250) → (420, 270) → (460, 230)에서 y = 120까지. 가로 200 ~ 460 |
| 좌우 여유 | 280의 10% = 28픽셀. 내 차 자리는 가로 172 ~ 488 |
| 아래 여유 | 150의 10% = 15픽셀 |

마스크 고르기의 예시 (비율과 픽셀은 추정이다):

| 마스크 | 내 차 자리 안에 든 비율 | 아래 경계보다 내려간 정도 | 결과 |
|---|---|---|---|
| 내 차의 왼쪽 조각 (기둥 왼쪽) | 약 97% | 5픽셀 | 내 차 |
| 내 차의 오른쪽 조각 (기둥 오른쪽) | 약 95% | 내려가지 않음 | 내 차. 왼쪽 조각과 합친다 |
| 내 차 앞에 선 차 | 약 55% | 40픽셀 | 내 차가 아니다 (둘 다 넘지 못함) |
| 옆 칸의 차 | 약 15% | 내려가지 않음 | 내 차가 아니다 (안쪽 80%를 넘지 못함) |

| 상황 | 결과 |
|---|---|
| 기둥·옆 차에 가려 내 차가 두 조각으로 보인다 | 두 조각 모두 내 차 영역이 된다 |
| 내 차 앞에 선 차가 내 차를 대부분 가린다 (시연 4번, 09장 9.9) | 앞 차는 빠지고 보이는 내 차 조각만 내 차 영역이 된다. 보이는 조각이 없으면 "찾지 못함" |
| 내 차가 완전히 가려졌다가 다시 드러난다 | 드러난 프레임부터 다시 찾는다 |
| 시작 장면에서 가려져 있다가 나중에 드러난다 | 찾는다. 내 차 자리는 시작 장면의 마스크가 아니라 네 모서리로 만들기 때문이다 |

**내 차 찾기의 한계 (D-264)**: 방향은 대체로 안전하다. 내 차를 "찾지 못함"으로 잘못 보면 두 규칙을 쓰지 않아 후보만 는다. 위험한 쪽은 **다른 차를 내 차로 잘못 뽑는 경우**다.

- 네 모서리를 잘못 찍으면 틀린다. 카메라 쪽 모서리를 실제보다 위에 찍으면 내 차도 아래 여유를 넘어 "찾지 못함"이 된다(후보만 는다). 실제보다 아래에 찍으면 내 차 앞에 선 차가 통과할 수 있다.
- 멀리서 낮게 찍으면 내 차와 앞 차의 바닥 위치 차이가 아래 여유보다 작아져 앞 차가 통과할 수 있다. 카메라 높이 1.5m면 약 25m부터다 (어림 계산, 측정하지 않음 ⚠️).
- 내 차 너머의 차가 내 차 위로 조금만 보이면, 보이는 부분이 내 차 자리 안에 들어와 내 차 영역에 섞일 수 있다.
- 옆에서 본 구도에서 사용자가 바퀴 자리를 정확히 찍으면, 좌우 여유를 더해도 내 차 마스크의 안쪽 비율이 80% 근처가 된다 (어림 계산 ⚠️). 넘지 못하면 "찾지 못함"이 되어 후보만 는다.
- 카메라가 많이 기울었거나 광각 왜곡이 크면 차체가 내 차 자리 밖으로 기울어 보인다 ⚠️.
- 세 값(80%, 10%, 10%)은 측정하지 않은 시작값이다. 시연 영상으로 조정한다.

영역 줄어듦을 차 너머 트랙 빼기에만 쓰는 이유는 방향이 다르기 때문이다. 차 너머 트랙 빼기는 변화가 있으면 **남기므로**, 영역 줄어듦이 잘못 잡혀도 후보만 는다. 차 앞 트랙 빼기는 변화가 있으면 **빼므로**, segmentation 테두리가 프레임마다 조금 흔들려 가리지 않았는데 줄어든 것으로 나오면 건너편 물체를 잘못 뺀다 (D-259). 바닥점 다섯 조건은 그대로 쓴다. 반사·그림자로 차 영역이 변하면 "앞"으로 판단되어 남으므로 후보만 조금 늘고 사건을 놓치지는 않는다. 파손이 건너편이면 이 규칙은 쓰지 않는다. 건너편 물체는 파손과 같은 쪽에 있어서 범인일 수 있다.

**차 앞 트랙 빼기**: 파손 변이 **모두 건너편 변**(네 모서리 사각형에서 화면 위쪽을 향한 변)이면, 내 차를 가린 트랙은 카메라 쪽에 있으므로 파손에 닿을 수 없다. 트랙이 아래 셋을 모두 만족하면 물체 종류와 바닥점 여부에 상관없이 뺀다. 앞·뒤 끝 변이 섞이면 이 규칙을 쓰지 않는다.

- 트랙 위치에서 **차 영역 아래쪽 1/2**의 픽셀 변화가 여러 프레임 이어졌다. 화면 세로줄마다 차 영역의 위 끝과 아래 끝의 가운데보다 아래쪽을 본다. 물체는 바닥에서부터 차를 가리고, 이 부분은 대체로 유리 아래라 뒤가 비치지 않는다. 유리 위치를 따로 계산하지 않는다 (D-219).
- 그 순간 차 영역 전체가 함께 변하지 않았다. 충돌로 차가 흔들리는 경우를 가린 것으로 착각하지 않기 위해서다.
- 차 끝을 돌아 건너편으로 넘어가지 않았다.

기준은 시작값이며 시연 영상으로 조정한다 (D-256). "여러 프레임 이어졌다"는 트랙 bbox와 겹친 아래쪽 1/2의 10% 이상이 0.5초(5프레임) 연속으로 변한 것이다. "전체가 함께 변했다"는 트랙 bbox 바깥의 차 영역 가운데 5% 이상이 변한 것이다. 차가 흔들리면 가린 물체에서 먼 쪽의 윤곽도 변하기 때문이다. 차 영역을 만들지 못했거나 애매하면 남긴다. 차 앞 트랙 빼기에는 영역 줄어듦을 쓰지 않는다 (D-259).

**0단계 필터의 시작값 (D-256)**: 줄인 프레임(640×360) 기준이고 실측값이 아니다. 시연 영상으로 조정한다.

| 쓰는 곳 | 시작값 | 틀렸을 때 |
|---|---|---|
| 바닥점 "닿음" 여유 | 분석 크롭 짧은 변의 1% (약 4픽셀) | 클수록 "바닥점 안 보임"이 늘어 남는 트랙이 는다 |
| 채널 B 덩어리를 채널 A 트랙에 붙이는 겹침 | 덩어리 넓이의 50% 이상이 트랙 bbox 안 | 못 붙으면 클래스 없는 트랙이 하나 더 남는다 |
| 차 너머 트랙 빼기의 "차 영역 변화" | 트랙 bbox와 겹친 차 영역에서 변한 픽셀이 분석 크롭의 1%(약 2,300픽셀) 이상인 프레임이 하나라도 있으면 변화 있음 | 발이 화면 밖이고 팔만 내 차 앞으로 뻗은 사람(약 300픽셀, 추정)이 빠질 수 있다 ⚠️. 시연 영상에서 못 잡으면 0.1%로 낮춘다 |
| 차 앞 트랙 빼기의 "여러 프레임" | 트랙 bbox와 겹친 아래쪽 1/2의 10% 이상이 0.5초(5프레임) 연속 변함 | 못 미치면 빼지 못하고 남는다 |
| 차 앞 트랙 빼기의 "전체가 함께" | 트랙 bbox 바깥의 차 영역 가운데 5% 이상이 변함 | 약한 흔들림은 못 알아채지만 그때는 위 10% 조건도 넘지 못해 빼지 않는다 |
| 차 너머 트랙 빼기의 "영역 줄어듦" (D-259, D-261) | 트랙 bbox 안에서 줄어든 픽셀이 분석 크롭의 1%(약 2,300픽셀) 이상인 프레임이 하나라도 있으면 줄어듦 있음. 위 "차 영역 변화"와 값은 같지만 상수는 따로 둔다 | 낮추면 영역 테두리 흔들림만으로 "가림"이 되어 건너편 트랙이 남는다(후보만 는다). 팔만 뻗은 가림(약 300픽셀, 추정)은 못 잡는다. 테두리 흔들림 크기는 측정하지 않았다 ⚠️ |
| 내 차 고르기의 "안쪽" (D-264) | 마스크 픽셀의 80% 이상이 내 차 자리 안 | 높이면 내 차 조각도 떨어져 "찾지 못함"이 늘고 후보만 는다. 낮추면 옆 칸 차나 내 차 너머 차가 내 차 영역에 섞인다 |
| 내 차 고르기의 "아래 여유" (D-264) | 내 차 자리의 아래 경계에서 고른 차량 `bbox` 높이의 10%까지 | 줄이면 모서리를 조금 위에 찍었을 때 내 차도 떨어진다(후보만 는다). 늘리면 내 차 앞에 선 차가 내 차로 뽑히고, 그 사이를 걸은 사람이 차 너머 트랙 빼기로 빠질 수 있다 ⚠️ (시연 4번) |
| 내 차 자리의 "좌우 여유" (D-264) | 고른 차량 `bbox` 폭의 10%씩 | 줄이면 범퍼 쪽이 자리 밖에 놓여 내 차가 안쪽 80%를 넘지 못한다(후보만 는다). 늘리면 옆 칸 차가 섞인다 |
| 내 차를 찾지 못함 (D-264) | 위 조건을 만족하는 마스크가 하나도 없다. 옛 기준(영역 넓이가 고른 차량 사각형의 50% 미만, D-256)은 없앴다 | 그 구간에서 차 영역을 쓰는 두 규칙을 쓰지 않고 전부 남긴다 |

**아래쪽 1/2의 한계 (D-219)**: 내 차 아랫부분이 다른 차에 가려지면 카메라 쪽 물체도 이 영역을 바꾸지 못해 남는다. 후보만 늘고 사건을 놓치지는 않는다. 반대로 카메라가 높거나 차를 비스듬히 보면 아래쪽 1/2에 유리가 섞일 수 있고, 그때는 유리 너머 건너편 물체가 빠질 수 있다.

**구현 주의사항 (D-193)**: 아래는 빠뜨리면 사건을 놓치거나 판단이 틀어지는 부분이다. 모든 항목의 방향은 같다. 측정할 수 없거나 애매하면 **빼지 않는다.**

| 주제 | 지켜야 할 내용 | 이유 |
|---|---|---|
| 판단 시점과 자료 | 빼기 판단은 트랙이 끝난 뒤 트랙 파일로 한다. 전경 마스크는 저장하지 않으므로, 차 영역 변화는 **프레임을 처리할 때 재서** 트랙 줄에 함께 쓴다 (04장 4.8) | 트랙이 끝난 뒤에는 마스크가 없어서 다시 잴 수 없다 |
| 좌표 | 트랙 bbox, 네 모서리, 파손 변, 차 영역은 모두 원본 해상도 좌표로 맞춘 뒤 비교한다. 크롭 안에서 처리했으면 원본 좌표로 되돌린다 | 좌표계가 다르면 오류 없이 틀린 결과가 나온다 |
| 바닥 지도 바깥 | 지평선 위쪽 점은 변환값이 튀거나 뒤집힌다. 변환 결과가 카메라 뒤쪽이거나 비정상이면 그 순간의 바닥점은 안 보인 것으로 친다. 이런 프레임이 가장 가까운 순간을 대신하게 두지 않는다 | 먼 물체가 엉뚱하게 멀거나 가깝게 계산된다 |
| 바닥점이 보임의 판정 | 다음 중 하나면 그 프레임의 바닥점은 안 보인 것이다: bbox 아래 변이 차 영역(그 프레임이 속한 구간의 기준 영역, D-259)에 닿음, 다른 트랙 bbox에 닿음, 분석 크롭 가장자리에 닿음. 거리가 분석 크롭 짧은 변의 1% 이하(640×360에서 약 4픽셀)면 닿은 것이다 (시작값, D-256) | 가려지면 bbox 아래 변이 가린 물체 위에 걸려 실제보다 가깝게 찍힌다 |
| 조건 2의 판정 | 탐지가 몇 프레임 빠져 ByteTrack이 이어 붙인 경우는 끊김이 아니다. 트랙이 분석 크롭 가장자리나 YOLO 구간 경계가 아닌 화면 가운데에서 갑자기 시작하거나 끝나면 끊긴 것으로 본다. YOLO 구간 경계는 끊김이 아니다. YOLO가 꺼진 동안은 ROI 움직임이 없었기 때문이다 | ID 바뀜은 직접 알 수 없어 시작·끝 위치로 추정한다 |
| 거슬러 돈 프레임 | MOG2를 돌리지 않으므로 전경 마스크가 없다. 이 프레임은 ROI 움직임이 없던 구간이고 ROI는 차체를 포함하므로 픽셀 변화는 **변화 없음**으로 기록한다. 영역 줄어듦은 YOLO가 도는 프레임이라 이 프레임에서도 잰다 (D-259) | 측정값 없음과 구분해야 한다 |
| MOG2가 안정되기 전 | 영상 시작에서 배경이 안정되기 전 프레임은 전경을 쓰는 차 영역 키(`car_fg_px`, `car_front_fg`, `car_out_fg`)를 **측정 불가**로 기록한다. 움직인 픽셀 수(`moved_px`)는 측정 불가가 아니다. 직전 분석 프레임과의 차이만으로 재어 적는다 (D-265). 이 구간은 YOLO를 켜 둔다 (D-199). 이어서 하기 때는 1분 전부터 다시 읽어 배경을 만든 뒤 이어 가므로 이런 프레임이 없다 (D-248). 측정 불가 프레임이 있는 트랙에는 차 너머·차 앞 트랙 빼기를 쓰지 않는다. 안정 시간은 약 1분으로 배경 학습 시간과 같다 (D-199) | 안정 전 전경은 믿을 수 없다 |
| 멈춘 트랙 | "변화 없음"은 움직인 프레임에서만 근거가 된다. 멈춘 물체는 배경으로 흡수되어 앞에 있어도 변화가 없다. 움직인 프레임이 없는 트랙에는 차 너머 트랙 빼기를 쓰지 않는다. 움직임이 없으므로 후보 구간을 만들지 않는다 (D-245, D-278) | 앞에 서 있는 물체를 건너편으로 오판할 수 있다 |
| 그림자 | MOG2의 그림자 픽셀은 규칙마다 다르게 센다. 차 너머 트랙 빼기는 **변화로 센다.** 차 앞 트랙 빼기는 **세지 않는다** | 둘 다 빼기 어려운 쪽으로 움직여 사건을 놓치지 않게 한다 |
| 변화 기준의 방향 | 차 너머는 조금만 변해도 변화 있음으로, 차 앞은 충분히 변해야 변화 있음으로 본다 | 위와 같다 |
| 차 영역 만들기 | YOLO가 켜질 때마다 그 구간의 첫 프레임에서 만들어 YOLO 구간 목록에 다각형 목록으로 적는다 (D-259, D-263). 다각형으로 바꾼 뒤 다시 그린 모양을 쓴다. 이어서 할 때는 추적기 상태 파일에서 읽는다. 앞 구간에 이어 붙은 경우(규칙 4)는 다시 만들지 않는다. 영상 시작 구간(규칙 8)은 영상 첫 프레임에서 만든다. 내 차는 "내 차 자리"로 찾고, 조건을 만족하는 마스크가 없으면 "찾지 못함"으로 빈 목록을 적는다 (D-264) | 옆 차가 오가면 내 차의 보이는 부분이 바뀐다. 시작 장면의 영역을 끝까지 쓰면 새로 드러난 부분 앞의 움직임을 놓친다 |
| 영역 줄어듦 재기 | YOLO가 도는 프레임마다 그 프레임의 내 차 영역을 얻어 기준 영역과 비교하고, 트랙 bbox 안에서 줄어든 픽셀 수만 트랙 줄에 쓴다. 영역 모양은 프레임마다 기록하지 않는다. 그 프레임에서 내 차를 찾지 못하면 빼지 않는 쪽으로 처리한다. 그 프레임의 내 차 영역은 채널 A(YOLO11m-seg)의 결과에서 얻는다 (D-260). 구간의 첫 프레임과 같은 규칙(내 차 자리)으로 고른다 (D-264) | 판정에 필요한 것은 숫자다. 모양이 필요한 판정(바닥점이 차 영역에 닿았는가)은 구간의 기준 영역으로 충분하다 |
| 내 차 자리 | 영상마다 한 번 만들고 저장하지 않는다. 네 모서리와 `bbox`에서 언제든 같은 모양으로 다시 만들 수 있다. 마스크와 견줄 때는 같은 좌표계로 맞춘다. 다른 차량의 마스크는 내 차인지 가리는 데만 보고 기록하지 않는다. 구간의 첫 프레임과 그 뒤 프레임에 같은 규칙을 쓴다 (D-264) | 첫 프레임과 뒤 프레임의 규칙이 다르면 고른 조각이 달라져, 가리지 않았는데도 영역 줄어듦이 생긴다 |
| 고정 가정 | 네 모서리는 영상 내내 고정이다. 차 영역은 YOLO 구간 안에서 고정이고 구간마다 다시 만든다 (D-259). 카메라가 움직이면 어긋나지만 그때는 전경이 넓게 잡혀 "전체가 함께 변함"이 되어 남는다 | 네 모서리는 영상 도중 다시 계산하지 않는다 |
| 나란함 계산 | 바닥점이 보인 프레임의 궤적만 쓴다. bbox 떨림을 피하려고 몇 초 단위의 이동으로 본다. 앞으로 가든 뒤로 가든 나란하면 같다 | 프레임 단위 방향은 떨림으로 흔들린다 |
| 제외 기록 | 뺀 트랙마다 `track_id`와 적용한 규칙 이름을 로그로 남긴다. 저장 위치는 🚧 (U-13) | 놓친 사건이 어느 규칙 때문인지 평가할 때 찾아야 한다 |

| 파손이 건너편인데 충돌로 내 차가 흔들림 | 남김 | 차 영역 전체가 함께 변함 |

**한계**: 바닥이 평평하다고 가정하므로 경사로에서는 거리가 틀어질 수 있다. 안 보이는 모서리는 사용자의 짐작이다. 그래서 기준 거리를 넉넉히 잡고 애매하면 남긴다.

- **확장**: 주차 칸 선의 네 점으로 바닥 지도를 만드는 방법은 칸 규격(2.5×5.0m ⚠️)이 필요해 지금은 하지 않는다.
- **바닥점을 믿을 수 없는 트랙은 거르지 않는다.** 채널 B 덩어리가 불안정하거나, 발이 가려졌거나, 화면 가장자리에서 잘렸거나, 공중에 떠 있는 물체(날아옴)가 그렇다. 이런 트랙은 후보로 남기고 VLM이 본다. 위 "차 너머 트랙 빼기"와 "차 앞 트랙 빼기"만 예외다.

### 0단계 필터 원칙

**ROI에 닿은 트랙만 후보 자격이 있다 (D-202).** 트랙이 살아 있는 동안 한 프레임이라도 bbox가 ROI와 겹치면 자격이 있고, 자격이 있는 트랙에만 아래 필터를 적용한다. 자격이 없는 트랙은 후보만 만들지 않고 트랙 파일에는 남긴다. 비식별화 폴백(6.8)이 쓰기 때문이다. 판단은 트랙이 끝난 뒤 하고, 거슬러 돈 프레임의 bbox도 포함한다.

**"확실히 관계없는 것만 빼고, 판단이 안 되면 남긴다."** 트랙 단위로, 트랙이 파손 부위에 가장 가까웠던 순간을 기준으로 판정한다.

| 뺀다 | 남긴다 |
|---|---|
| 바닥점을 신뢰할 수 있고, 관찰된 움직임상 접촉 가능한 영역에 접근하지 않았음이 명확하며 다른 접촉 가능성 단서도 없음 | 손이 닿는 구역 안이거나, 구역 밖이어도 접촉 가능성을 배제할 수 없음 |
| 너무 짧거나 너무 작은 것 (노이즈). 따로 기준을 두지 않고 채널 B 노이즈 기준(D-195)과 ByteTrack의 트랙 확정 조건(시작값 3프레임 = 0.3초 ⚠️)이 트랙이 되기 전에 거른다 (D-255) | 바닥점을 믿을 수 없음 |
| 화면 전체가 동시에 바뀜 (조명 변화, 카메라 흔들림). 채널 B 덩어리가 분석 크롭 넓이의 30% 이상이면 이것으로 보고 클래스 없는 트랙을 만들지 않는다 (덩어리 크기 상한, D-195) | 날아옴·떨어짐처럼 공중 물체 |
| — (움직이지 않는 것은 따로 빼지 않는다. 움직임이 없으면 후보 구간이 생기지 않는다, D-245, D-278) | 안 보이는 면의 신호 (차 너머, 가려짐·재등장, 체류). 단 파손이 카메라 쪽이면 "차 너머 트랙 빼기"를 따른다 (D-193) |

- **바닥점이 구해져도 손·문·소지품·쓰러지는 물체 끝부분이 닿을 가능성이 있으면 남긴다.** 밑동이나 발이 손이 닿는 구역 밖이라는 이유만으로 제외하지 않는다. 객체탐지 또는 움직임 감지의 다른 단서가 접촉 가능성을 보여주는 경우에도 바닥점 필터로 제외하지 않는다 (D-91).
- 바닥점을 구하지 못하거나 신뢰할 수 없는 트랙도 유지한다. 이런 트랙의 유력 시점은 아래 "후보 구간과 유력 시점"의 규칙(발이 있을 수 있는 범위, 화면 거리)으로 구하며, 거리를 바닥점으로 계산할 수 없다는 이유로 빼지 않는다 (D-245).
- 필터를 통과한 트랙으로 후보를 만드는 방법은 아래 "후보 구간과 유력 시점"을 따른다. 트랙 1개가 후보 1개가 아니다 (D-245가 D-202를 바꿨다).
- 규모 감각 (페르미 추정, 실측 필요): 파손 부위에서 1m 안쪽 접근이 하루에 아파트 옆면 10~30회, 마트 옆면 50~150회, 통로 쪽 범퍼는 수백 회. 실제 24시간 영상으로 이 단계까지만 돌려 후보 수를 먼저 잰다. 아파트·상가·마트별 후보 수 추정과 근거는 [6.6 비용 추정](#비용-추정-u-28-d-90-실측-전-추정).

### 후보 구간과 유력 시점 (D-245)

수치는 모두 시작값이고 실측하면서 바꾼다. 계산 방식은 시험하지 않았다 ⚠️ (U-31).

**후보를 만드는 순서**

| 순서 | 내용 |
|---|---|
| ① 트랙 판정 | 위 ROI 자격과 0단계 필터를 적용한다 |
| ② 후보 구간 | 남은 트랙이 **ROI 안에서 움직임을 보이는 시간대**다. 움직임이 없는 시간은 후보 구간이 아니다. 나갔다가 다시 들어오거나 멈췄다가 다시 움직이면 그 시간이 새 후보 구간이 된다 |
| ③ 클립 | 후보 구간을 30초 이하의 클립으로 나눈다. 같은 시간대의 트랙 여러 개는 한 클립에 함께 들어간다. **클립 1개가 후보 1개**이고 VLM 호출·점수·정렬의 단위다 |
| ④ 유력 시점 | 클립마다, 그 클립에 든 트랙마다 따로 잡는다 |
| ⑤ VLM 프레임 | 유력 시점, 후보 구간, 그 밖의 세 단계로 밀도를 나눈다 (6.6 입력) |

**계산하는 때와 남기는 값 (D-249, D-250)**

- 탐지 중에는 프레임마다 트랙 줄(bbox, 움직인 픽셀 수 `moved_px`, 차 영역 키. 04장 4.8, D-262)만 트랙 파일에 쓴다. 위 ①~④는 **영상 전체의 탐지·추적이 끝난 뒤** 트랙 파일만 읽어 한 번에 계산한다. 영상을 다시 디코딩하지 않는다. 계산한 후보를 DB에 넣은 다음 VLM(⑤)을 시작한다.
- 후보 1개(= 클립 1개)마다 아래 값을 남긴다. 시간은 모두 원본 영상 기준 초다(6.9). 칸 형식은 👤 담당자 결정 필요(팀원 2)이고 04장에 반영한다.

  | 남기는 값 | 내용 | 예 |
  |---|---|---|
  | 클립 구간 | 시작·끝 | 100~122초 |
  | 트랙 번호 | 그 클립 안에 후보 구간이 있는 트랙 전부 | 31, 47 |
  | 후보 구간 목록 | 트랙을 나누지 않고 합친 시작·끝 쌍. 클립 구간 안에 들어오는 부분만 | 105~112초, 115~117초 |
  | 유력 시점 목록 | 트랙 번호와 시각. 한 트랙에 여러 개일 수 있다 | 트랙 31: 108.4초 / 트랙 47: 116.0초, 116.1초 |

- 합치는 예: 트랙 31의 후보 구간이 105~112초, 트랙 47의 후보 구간이 110~112초와 115~117초이면 후보 구간 목록은 105~112초, 115~117초다.
- 일반 구간(클립 구간에서 후보 구간을 뺀 나머지)과 조밀 구간(유력 시점 앞뒤 1초)은 남기지 않고 위 값에서 계산한다.
- 채널(A·B)과 룰 이름은 후보에 남기지 않는다. 탐지 뒤 단계에서 갈리는 기준은 채널이 아니라 클래스가 있는 트랙인지이고, 트랙 파일의 `cls` 키로 안다 (D-249).
- 탐지는 끝났는데 후보가 DB에 없는 상태로 워커가 죽으면, 이어받은 워커가 트랙 파일에서 다시 계산한다. 한 작업의 후보는 한꺼번에 넣는다.

**후보 구간의 규칙**

- 움직임은 bbox가 이동했는지가 아니라 **ROI 안의 픽셀 변화**로 정의한다 (D-245). 서서 긁는 사람은 bbox가 움직이지 않고 팔만 움직인다.
- **움직인 픽셀 = MOG2 전경이면서 직전 분석 프레임(0.1초 전)과 실제로 값이 달라진 픽셀.** MOG2 전경에는 움직이는 물체와 아직 배경으로 흡수되지 않은 멈춘 물체가 함께 들어 있다. 멈춘 물체는 직전 프레임과 같으므로 빠지고, 멈춘 순간 후보 구간이 끝난다. 그림자로 표시된 픽셀은 세지 않는다. **기준값 (D-254, 시작값)**: 밝기(0~255) 차이가 25 이상이면 달라진 픽셀로 본다. 한 트랙의 달라진 픽셀이 ROI 안에 분석 크롭 넓이의 0.01% 이상이면 그 프레임에 그 트랙이 움직인 것이다. 640×360에서는 약 23픽셀이고, 채널 B 노이즈 기준(D-195)과 같은 비율이다. 달라진 픽셀은 채널 B 노이즈 기준을 통과한 덩어리 안에서만 센다. 실측값이 아니며 시연 영상으로 조정한다 (D-253, U-09).
- 움직인 픽셀은 트랙에 묶어 센다. 남은 트랙에 붙은 변화((a)로 붙은 덩어리, 클래스 없는 트랙은 그 덩어리 자체) 가운데 ROI 안에서 움직인 픽셀만 그 트랙의 움직임이다. 프레임을 처리할 때 세어 트랙 줄의 `moved_px`에 쓴다 (D-262). 0.01% 기준은 판정할 때 견준다. 전경 마스크와 직전 프레임은 저장하지 않아 나중에 다시 셀 수 없다.
- **MOG2가 안정되기 전의 움직임 (D-265)**: 영상 시작에서 MOG2가 안정되기 전(약 1분, 채널 A 켜고 끄기 규칙 8)에는 전경을 믿을 수 없어 위 정의를 쓸 수 없다. 이 구간에서는 "MOG2 전경이면서"를 빼고 **직전 분석 프레임과 밝기 차이가 25 이상인 픽셀**만으로 센다.
  - 채널 A 트랙마다 센다. 세는 곳은 그 트랙의 bbox를 사방으로 10% 넓힌 범위((a)와 같은 범위)와 ROI가 겹친 곳이다. 채널 B 덩어리를 믿을 수 없어 덩어리 대신 bbox로 묶는다.
  - **멈춘 차 트랙에는 세지 않는다.** 멈춘 차의 정의는 (a)와 같다(최근 1초 동안 bbox 중심 이동이 bbox 폭의 5% 미만). 내 차와 옆 칸 차의 bbox 안에서 일어난 변화가 그 차의 움직임으로 세어지는 것을 막는다. 사람·동물은 멈춰도 센다.
  - 기준은 같다. 그 트랙의 달라진 픽셀이 분석 크롭 넓이의 0.01% 이상이면 그 프레임에 그 트랙이 움직인 것이다. 값은 같은 `moved_px` 키에 쓴다.
  - 영상의 맨 첫 프레임은 견줄 직전 프레임이 없어 `moved_px`가 `null`이다. `null`인 프레임은 후보 구간으로 보지 않는다.
  - 0단계 필터는 이 구간의 트랙에도 그대로 쓴다. 차 너머·차 앞 트랙 빼기만 쓰지 않는다 (구현 주의사항 "MOG2가 안정되기 전").
  - 이어서 하기 때는 1분 전부터 다시 읽어 배경을 만들므로 이 규칙을 쓰는 프레임이 없다 (D-248).

  | 처음 1분의 상황 | 결과 |
  |---|---|
  | 사람이 내 차 옆에 서서 긁는다 | 사람 트랙의 bbox 안에서 팔이 움직인다. 후보 구간이 된다 |
  | 차가 내 차 옆을 지나간다 | 차 트랙이 움직인다. 후보 구간이 되고 0단계 필터가 지금처럼 가른다 |
  | 내 차와 옆 칸 차만 서 있다 | 멈춘 차라 세지 않는다. 후보가 없다 |
  | YOLO가 못 잡는 물체가 날아와 맞는다 | 트랙이 없어 세지 못한다. 후보가 되지 않는다 (한계) |
  | 움직이는 사람·차의 bbox 안에서 그림자나 전조등 빛이 바뀐다 | 그림자 제거가 없어 변화로 센다. 후보 구간이 조금 길어진다 |
  | 3초짜리 영상에서 차가 내 차를 긁는다 | 0.1초 프레임부터 잰다. 후보 구간이 된다 |
- **화면 전체가 전경이 된 프레임의 움직임 (D-268)**: 가로등이 켜지거나 카메라가 야간 모드로 바뀌면 MOG2가 다시 배우는 약 1분 동안 화면 전체가 하나의 큰 전경 덩어리가 된다. 전조등이 화면을 넓게 비출 때도 같다. 큰 덩어리는 넓이의 50% 이상이 트랙 bbox 안에 들 수 없어 어느 트랙에도 붙지 않고((a)의 겹침 기준, D-256), 상한에 걸려 클래스 없는 트랙도 되지 않는다(D-195). 위 정의대로면 그 프레임에서 사람·차 트랙의 움직인 픽셀이 0이 되어 접촉을 놓친다. 그래서 이런 프레임은 따로 잰다.
  - **쓰는 프레임**: 분석 크롭 넓이의 30% 이상인 채널 B 덩어리(덩어리 크기 상한, D-195)가 하나라도 있는 프레임이다. 프레임마다 본다. 타이머나 새 키는 없다. 그런 덩어리가 없어지면 다음 프레임부터 위 정의로 돌아간다.
  - **재는 방법**: D-265와 같다. 채널 A 트랙마다, 그 트랙의 bbox를 사방으로 10% 넓힌 범위와 ROI가 겹친 곳에서 직전 분석 프레임과 밝기 차이가 25 이상인 픽셀을 센다. 멈춘 차 트랙에는 세지 않고, 사람·동물은 멈춰도 센다. 기준(분석 크롭 넓이의 0.01%)과 쓰는 키(`moved_px`)도 같다.
  - **바뀌지 않는 것**: 상한보다 작은 덩어리의 처리((a) 붙이기, (b) 클래스 없는 트랙)와 클래스 없는 트랙의 움직임은 지금과 같다. 차 영역 키도 지금처럼 잰다. 0단계 필터도 그대로 쓴다.
  - 큰 덩어리가 차 영역을 덮은 프레임에서는 차 영역 전체가 변한 것으로 나온다. 그 프레임을 거친 트랙은 차 너머 트랙 빼기와 차 앞 트랙 빼기에 걸리지 않고 남는다.

  | 30% 이상인 덩어리가 있는 프레임의 상황 | 결과 |
  |---|---|
  | 가로등이 켜진 뒤 1분 안에 사람이 와서 긁는다 | 사람 트랙의 bbox 안에서 센다. 후보 구간이 된다 |
  | 밤에 전조등이 화면을 넓게 비추며 차가 다가와 긁는다 | 차 트랙이 움직인다. 후보 구간이 된다 |
  | 큰 차가 가까이 지나가 그 차의 덩어리만으로 30%를 넘는다 | 차 트랙의 bbox 안에서 센다. 후보 구간이 되고 0단계 필터가 지금처럼 가른다 |
  | 조명만 바뀌고 내 차와 옆 칸 차만 서 있다 | 멈춘 차라 세지 않는다. 후보가 없다 |
  | 조명이 바뀌는 순간 사람이 ROI에 닿은 채 서 있다 | 그 프레임에 bbox 안 전체가 달라져 센다. 짧은 후보 구간이 생긴다 (잘못 잡는 쪽) |
  | 건너편을 지나는 사람의 트랙이 ROI에 닿는다 | 차 영역 전체가 변한 것으로 나와 차 너머 트랙 빼기가 빼지 못한다. 후보로 남는다 |
  | 카트나 던진 물체가 그동안 내 차에 닿는다 | 그 물체의 변화가 큰 덩어리에 묻히면 트랙이 없어 세지 못한다. 후보가 되지 않는다 (D-195의 한계) |
- **채널 A를 켜는 신호는 바꾸지 않는다.** 지금처럼 MOG2 전경이 ROI에 닿으면 켠다. 이 기준이 후보 구간의 기준보다 넓으므로 후보 구간이 되는 순간에는 YOLO가 항상 켜져 있다. 빼기 규칙에 걸린 트랙의 변화는 후보 구간을 만들지 않는다.
- **차 흔들림을 따로 감지하지 않는다.** 차가 흔들리면 ROI 안에 픽셀 변화가 생기므로 그 시간은 위 규칙만으로 후보 구간이 된다.
- 못 잡는 것: 가려져서 화면에 변화가 없는 움직임, 노이즈 기준보다 작은 움직임, 어두워서 배경과 구분되지 않는 움직임.
- **던지기 (한계)**: 던지는 주체가 보이지 않으면 날아온 물체만으로는 후보가 되지 않는다. 던지는 주체가 ROI에 들어오거나, 물체가 맞은 뒤 천천히 움직이면 후보가 될 수 있다.
- 잘못 잡는 것: 카메라 흔들림·전체 조명 변화는 "화면 전체가 동시에 바뀜"으로, 그림자는 MOG2 그림자 제거로, 비·눈·벌레는 노이즈 기준과 ByteTrack의 트랙 확정 조건으로 줄인다 (D-255). 카메라 가까이 지나가 0.3초를 넘긴 벌레·빗방울은 후보가 되고 VLM이 본다. 전조등 빛이나 반사가 ROI에 비치는 것은 줄이지 못하고 VLM이 본다.
- 옆 칸에 주차한 차는 멈춘 뒤로 움직임이 없어 후보 구간이 끝난다. 나중에 문이 열리면 그때 다시 후보 구간이 된다.
- **끊김 간격 1초** (시작값): 한 트랙의 움직임이 1초 이하로 끊겼다가 다시 이어지면 같은 후보 구간으로 보고, 끊긴 시간도 후보 구간에 넣는다(프레임 밀도·유력 시점 모두). 1초보다 길게 끊기면 다른 후보 구간이다. 트랙마다 따로 본다. 후보 구간이 나뉘어도 유력 시점은 클립·트랙마다 구하므로 늘지 않는다.
- **클립 앞뒤 여유 5초** (시작값): 클립은 후보 구간의 시작 5초 전부터 끝 5초 뒤까지다. 여유는 일반 구간이다. 후보 구간이 20초보다 길면 여유를 앞뒤 똑같이 줄여 30초에 맞춘다. 후보 구간이 짧아도 30초로 늘리지 않는다(후보 구간 3초면 클립 13초). 영상의 처음·끝을 넘는 여유는 잘라 낸다.
- **가까운 후보 구간 합치기** (시작값): 앞 후보 구간의 끝과 다음 후보 구간의 시작 사이가 10초 이하이면(겹치면 0초) 한 클립으로 합친다. 합친 구간은 가장 이른 시작부터 가장 늦은 끝까지이고, 앞뒤 여유는 위 규칙을 따른다. 시간순으로 앞에서부터, 더 합칠 수 없을 때까지 이어서 합친다. 트랙이 달라도 합친다. 끊김 간격(1초)은 한 트랙의 후보 구간을 이을 때, 합치기 간격(10초)은 후보 구간끼리 한 클립으로 묶을 때 쓴다.

  | 경우 | 처리 | 예 |
  |---|---|---|
  | 후보 구간 하나, 20초 이하 | 앞뒤 여유 5초씩 | 3초 → 클립 13초 |
  | 후보 구간 하나, 20초 초과 30초 이하 | 여유를 앞뒤 똑같이 줄여 클립 30초 (30초면 여유 0) | 26초 → 여유 2초씩 |
  | 후보 구간 하나, 30초 초과 | 5초씩 겹치는 30초 이하 클립 여러 개로 나눈다 (아래) | 45초 → −5~25초, 20~50초 |
  | 두 구간, 사이 10초 초과 | 합치지 않고 각자 클립 | A 0~5초, B 20~25초 |
  | 두 구간, 사이 10초 이하, 합친 길이 30초 이하 | 합친다 | A 0~8초, B 14~22초 → 0~22초, 여유 4초씩 |
  | 두 구간, 겹치지 않고 사이 10초 이하, 합친 길이 30초 초과 | 합치지 않고, 30초를 넘게 만드는 구간부터 새 클립을 시작한다 | A 0~10초, B 19~22초, C 24~40초 → [A+B] 0~22초, [C] 24~40초 |
  | 두 구간이 겹치고, 합친 길이 30초 초과 | 먼저 하나로 이은 뒤 나눈다 (아래) | A 0~15초, B 12~40초 → 0~40초 → −5~22.5초, 17.5~45초 |
  | 세 구간 이상 (연쇄) | 합친 결과를 다음 구간과 같은 조건으로 다시 비교한다 | A 0~4초, B 10~15초, C 22~27초 → 0~27초, 여유 1.5초씩 |

- **합친 구간이 30초를 넘을 때** (구간이 겹치지 않는 경우): 30초를 넘게 만드는 구간은 합치지 않고, 그 구간부터 새 클립을 시작한다. 빈 시간에서 자르므로 움직임 중간이 잘리지 않는다. 새로 시작한 구간이 혼자 30초를 넘으면 아래 나누기 규칙을 쓴다. 이미 30초를 넘는 구간 다음에 오는 구간도 새 클립을 시작한다.
- **겹치는 구간이 30초를 넘을 때**: 서로 겹치는 후보 구간은 먼저 하나로 잇는다. 이은 구간이 30초를 넘으면 아래 나누기 규칙으로 나눈다. 구간 하나가 30초를 넘을 때와 같은 계산이라 이웃 클립의 겹침이 항상 5초다. 겹치는 구간을 모두 이은 다음에 10초 간격 합치기를 한다(A 0~10초, B 15~22초, C 20~40초 → B와 C를 먼저 이어 15~40초. A와 합치면 40초라 합치지 않는다 → [A] 0~10초, [B+C] 15~40초). 유력 시점은 나눈 클립마다, 그 클립에 든 트랙마다 구한다.
- **30초를 넘는 후보 구간 나누기** (시작값): 30초 이하 클립 여러 개로 나눈다. 이웃한 클립은 5초 겹친다. 일반 구간 여유는 첫 클립 앞과 마지막 클립 뒤에만 붙는다.
  - 클립 수는 가장 적게 잡는다. 후보 구간에서 5초를 뺀 길이를 25초로 나눠 올림한 값이다(최소 1개).
  - 여유 5초씩을 붙여도 클립이 30초를 다 채우지 못하면 모든 클립 길이를 똑같이 줄인다.
  - 여유 5초씩을 붙이면 30초를 넘으면 양끝 여유를 똑같이 줄인다.
  - 이 규칙에 30초 이하 후보 구간을 넣으면 위의 한 클립 규칙과 같은 결과가 나온다.

  | 후보 구간 | 클립 수 | 처리 | 클립 (후보 구간 시작 = 0초) |
  |---|---|---|---|
  | 35초 | 2 | 여유 5초, 클립을 똑같이 줄임 (25초) | −5~20, 15~40 |
  | 45초 | 2 | 딱 맞음 (클립 30초, 여유 5초) | −5~25, 20~50 |
  | 50초 | 2 | 클립 30초, 양끝 여유를 줄임 (2.5초) | −2.5~27.5, 22.5~52.5 |
  | 60초 | 3 | 여유 5초, 클립을 똑같이 줄임 (약 26.7초) | −5~21.7, 16.7~43.3, 38.3~65 |
  | 95초 | 4 | 딱 맞음 | −5~25, 20~50, 45~75, 70~100 |

  - 클립이 가장 짧은 때는 후보 구간이 30초를 조금 넘을 때로, 약 22.5초다.
  - 겹친 5초는 두 클립에 모두 들어가 VLM에 두 번 간다. 자른 곳에 걸린 순간은 어느 한 클립 안에서 앞뒤가 2.5초 이상 보이므로, 유력 시점 앞뒤 1초 조밀 구간이 한 클립에 통째로 들어간다.
  - 클립 시각은 분석 프레임 단위로 맞춘다. 영상의 처음·끝을 넘는 여유는 한 클립 규칙처럼 잘라 낸다.

- 움직임 판정 기준값은 시작값이다 (D-254). 서서 천천히 긁는 손은 달라진 픽셀이 기준 근처라 놓치는 프레임이 생길 수 있다. 멈춘 물체가 배경이 되기 전 약 1분 동안 영상 압축 때문에 픽셀이 깜빡이면 후보 구간이 끝나지 않을 수 있다. 둘 다 측정하지 않았다 ⚠️.

**유력 시점: 파손 위치에 가장 가까웠던 프레임**

거리는 그 물체가 화면에 보이는 프레임에서만, 후보 구간 안의 프레임에서만 잰다.

| 물체 | 재는 곳 | 재는 거리 |
|---|---|---|
| 사람, 발이 보임 | 바닥 지도 | 바닥점 → 파손 지점 |
| 승용차·오토바이·자전거·트럭·버스, 바퀴가 보임 | 바닥 지도 | bbox 아래 변(선분) → 파손 지점의 가장 짧은 거리 |
| 위 물체인데 발·바퀴가 가려짐 | 바닥 지도 | "발이 있을 수 있는 범위"(선분) → 파손 지점의 가장 짧은 거리 |
| 클래스 없는 물체 (던진 물체 포함), **동물 전부 (새 포함)** | 화면 (픽셀) | 덩어리 bbox(동물은 채널 A bbox) ↔ 파손 사각형의 가장 짧은 거리. 겹치면 0. 바닥 지도를 쓰지 않는다 |

- 트럭·버스도 승용차와 같은 계산을 쓴다 (D-251). 빼는 조건에서는 거리를 믿지 않아 재지 않지만, 유력 시점은 가장 짧은 프레임만 고르므로 거리 값 자체가 커도 고르는 프레임이 같다. YOLO가 같은 차를 car와 truck으로 번갈아 내도 한 트랙 안의 거리를 같은 단위로 비교할 수 있다. 트럭이 방향을 틀거나 다가오면 유력 시점이 조금 어긋날 수 있다.
- 새는 클래스가 있지만 날아다녀 바닥에 붙어 있다고 볼 수 없으므로 클래스 없는 물체의 계산법을 쓴다. 빼는 조건도 클래스 없는 물체와 같다(위 기준 거리 표).
- 개·고양이 등 나머지 동물도 유력 시점은 화면 거리로 잡는다 (D-252). 내 차 위에 올라간 고양이는 바닥 지도에서 실제보다 훨씬 멀게 계산되어, 차 위에 있는 시간이 유력 시점이 되지 않기 때문이다. 차 위인지는 따로 판정하지 않는다. 빼는 조건은 사람과 같은 기준 그대로다 (D-196).
- **파손 지점**: 파손 사각형의 가운데 세로줄이 파손 변과 만나는 점을 바닥 지도로 옮긴 점이다. 파손 변 전체까지의 거리는 차 옆을 따라 걷는 내내 같아서 쓰지 않는다. 정확한 정의는 시험에서 확인한다 ⚠️.
- **발이 있을 수 있는 범위**: 화면에서 "몸이 보이는 아래 끝"부터 "발을 가린 물체의 바닥 쪽 끝"까지의 세로줄 구간이다. 두 끝점을 바닥 지도로 옮기면 선분이 된다. 실제 발이 이 범위 안에 있으면 거리가 실제보다 크게 나오지 않는다.

  | 발을 가린 것 | 가린 물체의 바닥 쪽 끝 |
  |---|---|
  | 내 차 | 바닥 네 모서리 사각형의 건너편 변 (차에 붙어 서 있다고 본다) |
  | 다른 차·다른 트랙 | 그 bbox의 아래 변 |
  | 분석 크롭 가장자리 | 가장자리 점 |

- **클래스 없는 물체에 바닥 지도를 쓰지 않는 이유**: 사람·차·동물은 바닥에 붙어 있다고 볼 수 있지만, 던진 물체나 클래스 없는 덩어리는 공중에 있을 수 있어 바닥 위 위치로 바꾸면 틀린다. 원근을 따지지 않고 화면에서 파손 사각형에 가장 가까운 프레임을 쓴다. 가려지면 사라지기 직전의 보이는 프레임이 된다.
- **거리가 같으면 모두 잡는다**: 클립 안에서 그 트랙의 최솟값을 구하고, 거리가 **최솟값 이상, 최솟값 × 1.01 이하**인 프레임을 모두 유력 시점으로 한다. 최솟값이 0이면 0인 프레임만 해당한다.
- **차 흔들림은 쓰지 않는다**: `car_out_fg`(옛 이름 `car_all_fg`, D-262)로 유력 시점을 고르거나 더하지 않는다. 약한 접촉은 흔들림이 없고, 전조등·반사를 흔들림으로 잘못 잡을 수 있다. `car_out_fg`는 "차 앞 트랙 빼기"의 "차 영역 전체가 함께 변하지 않았다" 조건에서만 쓴다. 이 조건을 없애면 건너편에서 부딪혀 내 차를 흔든 차가 "내 차 앞을 지나간 차"로 잘못 빠져 후보 구간이 되지 않는다.

**구현 주의**

- 유력 시점은 트랙마다, 클립마다 따로 구한다. 한 트랙이 두 클립에 걸치면 클립마다 그 안의 최솟값을 다시 구한다.
- 이 거리(발 범위, 화면 거리)는 유력 시점에만 쓴다. 트랙을 빼는 조건(다섯 조건, 차 너머·차 앞 트랙 빼기)에는 쓰지 않는다.
- 거리를 잴 프레임이 하나도 없는 트랙은 유력 시점을 만들지 않는다. 유력 시점이 없다는 이유로 클립을 빼지 않는다.
- 파손 위치에 겹친 채 **멈춰 있는** 시간은 움직임이 없어 후보 구간이 아니므로 유력 시점에 들어가지 않는다. 겹친 채 **계속 움직이면**(최솟값 0이 이어짐) 그 시간 전체가 유력 시점이 된다. 상한은 두지 않았고 실측에서 장수를 보고 조정한다.

**한계**

- 건너편에서 차에 가려진 채 머무는 동안은 화면에 변화가 없어 후보 구간이 아니다. 들어갈 때와 나올 때만 후보 구간이 된다.
- 가려진 곳에서 닿으면 유력 시점이 어긋난다. 후보 구간의 초당 1장이 받친다.
- 발 범위는 사람이 화면에서 똑바로 서 있다고 가정한다. 화면 가장자리에서는 어긋난다. 내 차에 가려진 사람이 차에서 멀리 떨어져 있으면 거리가 실제보다 작게 나온다.
- 한자리에 서서 긁으면 거리가 거의 변하지 않아, 떨림으로 생긴 최솟값 한두 프레임만 유력 시점이 된다.
- 동물이 카메라와 파손 사이의 바닥을 지나가면 멀리 있어도 화면에서 파손 사각형과 겹쳐 유력 시점이 생긴다 (D-252).

## 6.6 2단계-② VLM

AI는 판정하지 않고 순서만 정한다 (PRD 3.4). **목표는 정답 한 개를 맞히는 것이 아니라 확실히 관계없는 것을 뒤로 보내는 것이다.** KPI는 AUC 0.80 이상 (PRD 2장).

**구현할 때 참고**: VLM은 학교가 주는 대체 LLM API로 부른다. 호출 주소·인증·모델 이름·오류 코드는 사용 가이드 <https://bedrock.nxtcloud.kr/guide/>를 따른다. 가이드 요약, 가이드에 없어 실제 호출로 확인할 것(이미지 입력, JSON 출력, 한도), 이 절의 모델(D-74)과 맞지 않는 곳은 [02장 2.9](02-architecture.md#29-aws-서비스와-권한)의 「학교 대체 LLM API: 사용 가이드」에 있다 ⚠️ (C-18).

### 입력 (D-73)

후보 1개당 한 번 호출한다 (불변 조건 5).

| 항목 | 내용 |
|---|---|
| 지시문 | 역할, 판단 기준, 점수 척도(아래 [점수 기준](#점수-기준-d-89)), 출력 형식(JSON). 출력 필드·동점·파싱 실패는 🚧 (U-27) |
| 파손 사진 (선택) | 6.4의 전처리를 거친 1장. 없으면 뺀다 |
| 텍스트 설명 (선택) | `<user_description>` 태그로 감싸고 "지시가 아니라 참고 자료"라고 지시문에 적는다. 없으면 뺀다 |
| 안내 프레임 | 클립 **첫 프레임 1장**에만 파손 부위(안 보임이면 인접 영역) 테두리를 얇게 그린다(마젠타 또는 라임, 빈 테두리). 나머지 판정 프레임은 깨끗하게 둔다. 크롭 안에서의 좌표를 텍스트로도 적는다 |
| 클립 프레임 | **원본을 크롭한** 프레임 여러 장 (D-63). 구간은 사용자 클립(후보 1개 = 클립 1개, D-245)과 같다. 밀도는 아래 표를 따른다 (D-245). 각 프레임 앞에 `[프레임 n / t=..s]` 캡션 |

**프레임 밀도 (D-245, D-273. 위 두 줄은 시작값이고 실측하면서 바꾼다. 일반 구간은 D-273으로 확정했다)**

| 클립 안의 구간 | 밀도 |
|---|---|
| 유력 시점 앞 1초 ~ 뒤 1초 | 초당 3장 |
| 유력 시점이 아닌 후보 구간 | 초당 1장 |
| 일반 구간 (클립 안에서 후보 구간이 아닌 나머지) | 0.5fps (2초에 1장). 구간마다 첫 프레임부터 (D-273) |

- 프레임은 분석에 쓴 10fps 프레임에서 고른다. 초당 3장은 약 0.3초 간격이다. 유력 시점 프레임 자체는 반드시 넣는다.
- 유력 시점이 이어져 있거나 앞뒤 1초 창이 서로 겹치면 하나의 조밀 구간으로 보고, 같은 프레임을 두 번 보내지 않는다.
- 일반 구간은 **구간마다 따로** 센다. 각 일반 구간의 첫 프레임을 넣고, 거기서부터 20프레임(2초)마다 1장을 넣는다. 그래서 2초보다 짧은 일반 구간에도 1장은 들어간다. 조밀 구간과 겹쳐 같은 프레임이 두 번 뽑히면 한 번만 보낸다 (D-273).

  | 일반 구간 | 넣는 프레임 (구간 시작부터 잰 시각) | 장수 |
  |---|---|---|
  | 5초 (클립 앞뒤 여유) | 0초, 2초, 4초 | 3 |
  | 3초 (후보 구간 사이) | 0초, 2초 | 2 |
  | 2.5초 (나눈 클립의 줄인 여유) | 0초, 2초 | 2 |
  | 1.5초 (후보 구간 사이) | 0초 | 1 |

- 장수는 클립마다 다르다. 예:

  | 클립 | 조밀 | 후보 구간 | 그 밖 | 합계 |
  |---|---|---|---|---|
  | 후보 구간 12초 + 앞뒤 여유 5초씩 (클립 22초), 유력 시점 1개 | 2초 × 3 = 6 | 10초 × 1 = 10 | 여유 5초 2개 × 3장 = 6 | 약 22장 |
  | 후보 구간 30초, 유력 시점 2개 (떨어져 있음) | 4초 × 3 = 12 | 26초 × 1 = 26 | 0 | 약 38장 |
  | 후보 구간 30초, 파손 위치에 겹친 채 10초 동안 계속 움직임 (거리 0) | 12초 × 3 = 36 | 18초 × 1 = 18 | 0 | 약 54장 |

- 크롭 한 변은 480px 안팎이다. 토큰은 Claude 기준 `가로 × 세로 ÷ 750`이라 프레임 1장에 약 307 토큰이다. Nova는 이미지 1장에 고정 토큰이 붙는다(약 230). ⚠️ 아래 비용 추정은 "후보 1개 약 25장, 약 9천 토큰"으로 계산한 옛 값이다 (U-28에서 다시 추정. 시점은 구현이 끝난 뒤 마지막, D-272).
- 밀도와 해상도는 **측정으로 정한다**. 유력 시점이 정말 사건 순간 근처인지도 함께 확인한다 ⚠️ (U-31)
- 프롬프트 캐싱은 공통 앞부분이 Haiku 4.5의 캐시 최소 길이(4,096 토큰 ⚠️ Bedrock 값 확인)보다 짧을 가능성이 커서 비용 계획에 넣지 않는다.
- VLM에 보내는 것은 **원본 크롭**이다. 비식별화하지 않는다 (불변 조건 3). 법적 문제는 데모 범위에서 다루지 않고 한계로 남긴다 (D-74, 02장 2.11).

### 점수 기준 (D-89)

2차 모델이 매기는 0~100 점수는 **그 후보 영상에서 관찰되는 접촉 근거의 강도**다. 실제 사고 확률이 아니다. 지시문에 아래 표와 가림 처리 원칙을 그대로 넣는다.

| 점수 | 판단 기준 |
|---|---|
| **0~19** | 파손 부위와 객체의 이동이 충분히 보이며, 떨어져 통과하는 등 **접촉하지 않았다는 근거가 명확하다** |
| **20~39** | 파손 부위 방향으로 접근했으나, 관찰 가능한 구간에서는 **접촉 가능한 거리까지 인접하지 않았고 접촉을 뒷받침하는 단서도 없다** |
| **40~59** | 파손 부위 또는 가려진 부위의 인접 공간까지 접근했으나, **접촉 여부를 판단할 근거가 부족하다** |
| **60~79** | 접촉 가능한 위치까지 접근했고, 그 시점의 움직임 변화 등 **접촉을 뒷받침하는 간접 단서가 있으나 확실하지 않다** |
| **80~100** | **직접 접촉 장면이 명확하게 보이거나**, 접촉 순간이 가려져도 위치·시간이 일치하는 복수의 간접 단서가 접촉을 강하게 뒷받침한다 |

**가림 처리 원칙**

- 가려져 보이지 않는다는 사실만으로 점수를 낮추거나 높이지 않는다.
- 객체가 가려진 동안 더 가까이 접근했는지 알 수 없다면 "인접하지 않았다"고 단정하지 않는다.
- 간접 단서는 영상에서 실제로 관찰된 내용만 쓰며, 보이지 않는 접촉을 추정 사실처럼 서술하지 않는다.

**판정 방식**

- 구간 경계는 근거의 종류로 나눈다: 불접촉 근거 명확(0~19) → 접근했지만 인접하지 않음(20~39) → 인접했지만 근거 부족(40~59) → 간접 단서 있음(60~79) → 직접 장면 또는 복수 단서(80~100). 구간 안의 세부 점수는 근거의 양과 선명도로 정한다.
- 이 점수는 정렬에만 쓴다 (6.7). 점수 구간으로 자동 판정하지 않는다. 점수는 후보마다 사용자에게 보이지만 "사고 확률"로 보여주지 않는다 (PRD 3.4).
- **1차 탈락 기준은 0~19 구간이다.** 1차 모델은 점수를 매기지 않고 "0~19에 확실히 해당하는가"만 묻는다. 확실하면 탈락, 조금이라도 애매하면 통과다. 물체 없이 빛·그림자만 바뀐 장면(노이즈)도 접촉 근거가 없으므로 여기에 든다. 이 기준은 1차 탈락률과 A 클립 탈락 여부를 실측한 뒤 바꿀 수 있다 (U-32).
- 1차에서 탈락한 후보의 0점은 2차 모델이 매긴 점수가 아니라 "1차 탈락" 표시다. 정렬과 AUC에서는 0점으로 같이 다룬다.
- 출력은 점수와 짧은 근거다(비용 추정의 출력 약 150토큰). 출력 필드, 동점 처리, 파싱 실패 처리는 🚧 (U-27).

### 1차·2차 구조 (D-74)

> **모델은 D-274로 정한다.** 학교 대체 LLM API의 `bedrock-haiku`, `bedrock-sonnet`, `bedrock-gpt-5.6-terra`, `bedrock-gpt-5.6-luna`를 시험해 보고 1차·2차에 쓸 모델을 정한다. 이 절의 비용 계산(Nova Lite·Claude Haiku 4.5 기준)은 옛 값이며 구현이 끝난 뒤 다시 추정한다 (D-272).

| | 1차 | 2차 |
|---|---|---|
| 목적 | **확실히 아닌 것**(점수 기준 0~19에 확실히 해당)만 탈락 | 남은 후보에 점수 |
| 출력 | 통과 / 탈락 | 0~100 점수 |
| 모델 | D-274의 네 모델(`bedrock-haiku`, `bedrock-sonnet`, `bedrock-gpt-5.6-terra`, `bedrock-gpt-5.6-luna`) 중 시험해 보고 정한다 | 같음 |
| 입력 | 위 표와 같다. 우리가 샘플링한 이미지를 넣는다 | 같음 |

- **점수는 2차 모델 하나에서만 나온다.** 1차에서 탈락한 후보는 **0점**을 받아 정렬 맨 아래에 남는다. 후보 수는 줄지 않는다 (불변 조건 4, PRD 3.4 AC). AUC 계산에서도 0점으로 넣는다.
- **1차에 보낼 후보**: 처음에는 **모든 후보**를 1차에 보낸다. 일부 후보만 1차에 보낼지는 팀장이 실제로 돌려 결과를 본 뒤 정한다. 미리 정한 기준(예: 바닥점을 믿을 수 없는 후보만)은 두지 않는다 (D-278, U-32).
- 1차 통과 기준: 조정용 A 클립이 1차에서 하나도 탈락하지 않을 것.
- 영상을 직접 넣지 않고 우리가 샘플링한 이미지를 넣는다.
- temperature 0 (1.6). **점수는 도구 강제 호출로 받는다** (D-93). 학교 대체 LLM API(OpenAI 호환, D-276)의 `tools`에 점수 제출 도구 하나를 정의하고(입력 스키마: D-89 구간 값만 허용하는 정수 `score` + 짧은 근거) `tool_choice`로 그 도구를 반드시 부르게 한다. 자유 문장 응답을 파싱하지 않는다. ⚠️ 고른 모델이 `tool_choice` 지정을 지원하는지는 시험할 때 확인한다.
- **파싱 실패**: 도구 호출이 없거나, 스키마에 어긋나거나(범위 밖 값 등), 응답이 잘린 경우다. 시스템 오류(스로틀링·5xx·타임아웃)는 파싱 실패가 아니라 장애로 다룬다(바로 아래). 파싱 실패하면 오류 내용을 붙여 다시 부른다. **최초 호출 포함 최대 3회**다. (D-93)
  - **1차**에서 끝내 실패한 후보는 탈락시키지 않고 **통과로 보고 2차로 보낸다.** 재현율 우선이다.
  - **2차**에서 끝내 실패한 후보는 0점을 주지 않고 **파싱 실패 목록**으로 보낸다(6.7).
  - **실패율 상한**: 1차·2차 각각, 재시도를 포함한 전체 호출 시도 중 파싱 실패 시도가 **30%를 넘으면** 작업을 `failed`로 바꾸고 `error_message`에 "VLM 파싱 실패율 초과"를 적는다. 프롬프트·도구 정의가 잘못됐다는 신호이므로 개발자가 프롬프트를 고친다. VLM 단계를 마친 뒤 판정한다.
- **장애**(스로틀링·5xx·타임아웃 등)는 대기 시간을 늘려 가며 재시도하고, 그래도 일정 시간(예: 총 10분)을 넘기면 작업을 `failed`로 바꾼다. 룰 점수만으로 조용히 끝내지 않는다 (6.12, D-93).
- 학교 대체 LLM API의 429(너무 빨리 보냄)·500·502·504는 장애로 보고 위처럼 재시도한다. 422 `budget_exceeded`(한도 소진)·401·400은 다시 보내도 안 되므로 재시도하지 않고 작업을 `failed`로 바꾼다 (D-19, D-276, 03장 3.2). 동시 호출 수는 계정 한도(C-03)가 허용하는 최대로 연다 (D-138)

**리전** (D-74가 D-54를 바꿈)

> **이 절은 쓰지 않는다.** VLM을 Bedrock 직접 호출이 아니라 학교 대체 LLM API로 부르게 되어(D-276), 처리 리전을 고르지 않는다(D-275). 아래 교차 리전 추론 프로파일과 가격표는 옛 Bedrock 직접 호출 기준으로 남겨 둔 것이다. S3·GPU·DB를 서울 `ap-northeast-2`에 두는 것만 그대로 유효하다.

- 저장(S3)·GPU·DB는 서울 `ap-northeast-2`에 그대로 둔다.
- Bedrock은 서울에서 **교차 리전 추론 프로파일**로 부른다. 서울에서 In-Region으로 쓸 수 있는 VLM은 이미지 입력이 없는 모델뿐이라서다(2026-09-26 확인).

| 모델 | 서울에서 부르는 방법 | 입력/출력 1M 토큰당 (USD) |
|---|---|---|
| Nova Lite | APAC Geo 프로파일 | 0.06 / 0.24 |
| Nova 2 Lite | Global 프로파일 | 0.30 / 2.50 |
| Claude Haiku 4.5 | Global 프로파일 | 1 / 5 |
| Claude Sonnet 5 | Global 프로파일 | 약 2 / 10 ⚠️ |

- 가격은 참고값이다. 아래 추정을 실측(후보 수, 1차 탈락률) 뒤 갱신한다 🚧 (U-28). 갱신은 구현이 끝난 뒤 마지막에 한다 (D-272)

### 비용 추정 (U-28, D-90, 실측 전 추정)

비용은 **후보 수 × 후보 1개당 비용**이다. 후보 수는 6.5의 산출 방식에 가정을 넣어 추정했고, 1개당 비용은 위 입력 구성으로 토큰을 계산했다. 모두 실측으로 바꿀 값이다.

**① 하루치(24시간) 영상의 후보 수 추정**

⚠️ 아래 ①은 D-245 전의 옛 산출 방식(트랙 1개 = 후보 1개)으로 계산했다. 지금은 30초 이하 클립 1개가 후보 1개라 후보 수가 줄어든다. U-28에서 다시 추정한다. 다시 추정하는 시점은 구현이 끝난 뒤 마지막이다 (D-272).

## 6.7 2단계-③ 정렬과 후보 클립

- 점수 내림차순으로 정렬해 `rank`를 매긴다. 동점 처리 규칙 🚧 (U-27)
- **목록은 두 개다** (D-93): 점수가 나온 **후보군 목록**과, 2차 파싱에 끝내 실패한 **파싱 실패 목록**. 파싱 실패 후보는 후보군 목록의 순위에 넣지 않는다.
  - 파싱 실패 목록은 점수가 없으므로 **영상에서 먼저 일어난 순**(`start_sec` 오름차순)으로 `rank`를 매긴다(D-177).
  - 파싱 실패 목록도 10개 단위 묶음으로 보여주고, 클립 만들기·비식별화는 후보군 목록과 **같은 방식**이다(처음에 상위 20개를 만들고 이후 한 묶음 앞서 준비).
  - 04·05·07 반영(파싱 실패 표시 칼럼, 목록 API, 화면)은 해당 담당자가 정한다 🚧.
- **처음에 상위 20개(묶음 2개)의 클립을 만든 뒤 "확인 가능"으로 바꾼다.** (D-68)
- 사용자가 [다음]을 누르면 이미 준비된 다음 묶음을 **바로** 보여준다. 동시에 백엔드가 다음 묶음 작업을 넣어 GPU를 켜고, 그다음 묶음(예: 21~30번)을 비식별화한다. 항상 **한 묶음 앞서** 준비한다.
  - 사용자가 준비 속도보다 빨리 [다음]을 누르면 기다린다. 한 묶음을 확인하는 데 최대 5분이 걸리므로 드물다.
- 클립 구간: 6.5 "후보 구간과 유력 시점"의 규칙으로 정한다(후보 구간 앞뒤 여유 5초, 30초 이하). 영상 경계에서 자른다 (D-245, D-246).
- **클립 구간에 YOLO가 돌지 않은 부분이 있으면 클립을 만들 때 그 부분만 YOLO를 돌린다** (D-97).
  - 왜 생기나: 보통은 생기지 않는다. YOLO 구간은 채널 B가 ROI 움직임을 감지한 시간대의 앞 10초·뒤 5초이고, 클립은 후보 구간의 앞뒤 5초라서 클립이 YOLO 구간 안에 들어간다 (D-247). 후보 구간의 달라진 픽셀은 채널 B 노이즈 기준을 통과한 덩어리 안에서만 세므로(D-254) 기준값 때문에 어긋나지는 않는다. 이 규칙을 지키지 않으면 생기는 일은 다음과 같다. 예: 채널 B의 마지막 감지가 112초라 YOLO는 117초에 꺼진다. 그런데 후보 구간이 더 작은 움직임까지 세어 115초에 끝나면 클립은 120초까지다. 117~120초에는 YOLO 결과가 없어 사람 트랙이 없고, 비식별화 폴백(사람 전체 가리기, 6.8)을 그 구간에 적용할 수 없다.
  - 방법: 클립 구간에서 YOLO 구간 목록(6.5 "YOLO 구간 기록")에 들어가지 않는 빈 구간마다, 빈 구간 시작 5초 전부터(워밍업, 영상 시작 전이면 영상 시작부터) 빈 구간 끝까지 YOLO + ByteTrack을 새 인스턴스로 돌린다. 결과는 **그 클립의 비식별화에만** 쓰고 트랙 파일·후보에는 넣지 않는다(후보 탐지 결과를 바꾸지 않기 위해서다).
  - 상위 20개와 다음 묶음 클립에만 하므로 비용이 작다.
- **클립은 본인 차량 주변으로 크롭한다** (D-70). **가로세로 비율은 16:9로 고정**하고, 차가 비율에 안 맞으면 노출이 더 늘어도 영역을 넓혀 비율을 맞춘다(D-175). 크기(픽셀)는 🚧 (U-30). 보여주는 범위가 줄어 비식별화를 놓쳐도 노출이 작아진다. 이 **보여줄 크롭**은 분석 크롭(6.5)보다 작고, 비식별화 탐지는 분석 크롭에서 한다(6.8, D-95).
- 인코딩: H.264 코덱 MP4 (Flutter Web 재생 조건, D-8).
- 클립 생성 실패는 **D-109**를 따른다(D-51 대체). 재시도 가능한 오류만 최초 포함 총 3회 시도한다. 복구 불가능한 오류나 재시도 소진은 열람 불가로 구분하고 정상 클립은 계속 제공한다. 실패 후보를 `not_found`로 기록하지 않는다. 오류 분류·대기 간격·재시작에도 유지되는 횟수 기록은 담당자 상세 반영이 필요하다. 비식별화 품질 누락과 처리 오류를 구분한다.

## 6.8 비식별화

(D-69)

**대상**: 사람 **얼굴**과 차량 **번호판**. 사람 몸 전체를 기본으로 가리지 않는다.

- **폴백**: 사람으로 탐지됐는데 그 bbox 안에서 얼굴을 찾지 못하면 **그 사람 전체를 가린다.** 판단은 프레임이 아니라 **트랙 단위**다. 한 트랙에서 얼굴이 안정적으로 잡히지 않으면 그 트랙의 모든 프레임을 사람 전체로 가린다. 프레임마다 판단하면 모자이크가 깜빡이며 얼굴이 드러나는 프레임이 생긴다.
- 사람 트랙은 채널 A의 COCO `person` 트랙을 그대로 쓴다.

**적용 위치**

| 위치 | 탐지 방식 | 이유 |
|---|---|---|
| 정지 장면 (1단계) | 프레임 전체 **타일** 탐지 | 본인 차량을 아직 모른다. 1장이라 느려도 된다 |
| 후보 클립 (2단계, 다음 묶음) | **분석 크롭**(보여줄 크롭보다 큼)에서 탐지·추적하고, 모자이크는 보여줄 크롭에만 적용 (D-95) | 작은 얼굴·번호판이 상대적으로 커진다. 크롭 경계에 걸쳐 들어오는 얼굴·번호판도 경계 밖에서부터 온전히 잡혀 트랙이 이어진다 |

**누락을 줄이는 방법** — 재현율(놓치지 않기)이 정밀도보다 중요하다. 위에서부터 차례로 적용하고, 앞의 것으로 부족할 때만 다음으로 간다.

1. 탐지 임계값을 낮춘다. 오탐(엉뚱한 곳 모자이크)은 받아들인다.
2. 추적으로 빈 프레임을 채운다 (D-88). 별도 추적 모델은 두지 않는다.
   - 얼굴·번호판 탐지 결과를 **ByteTrack**으로 묶는다. 채널 A와 같은 코드를 쓰되, 입력은 보여줄 클립의 **모든 프레임**이다. ByteTrack은 점수가 낮은 탐지도 기존 트랙에 이어 붙이므로 낮은 임계값과 잘 맞는다.
   - ByteTrack은 앞으로만 진행하고, 놓친 프레임에는 박스를 내지 않는다. 저장된 영상이라 뒤 프레임도 볼 수 있으므로 **양방향 후처리**를 붙인다.
     - 구간 보간: 한 트랙에서 탐지가 끊긴 구간은 앞뒤 bbox를 선형으로 이어 채운다.
     - 앞뒤 연장: 트랙의 첫 bbox는 앞으로, 마지막 bbox는 뒤로 몇 프레임 늘린다. 프레임 수 🚧 (U-09)
     - 박스 확대: 보간·연장한 bbox는 오차를 감안해 크게 친다. 비율 🚧 (U-09)
   - 후처리는 CPU 계산이라 처리 속도에 거의 영향이 없다.
   - 채널 A와 같은 `trackers` 패키지를 쓴다 (D-200). 라이선스는 이번 프로젝트의 선택 조건이 아니다.
3. 작은 대상은 크롭해 키워서 탐지한다. 크롭은 사용자 입력(본인 차량) 주변이다.
   - 모델은 어떤 크기가 들어와도 자기 입력 크기로 바꿔 탐지한다. 그래서 탐지 성능을 정하는 것은 크롭 크기 자체가 아니라 **입력 크기로 바꾼 뒤 얼굴·번호판이 몇 px가 되느냐**다.
   - 크롭이 입력보다 크면 줄어들어 작은 대상이 사라진다. 입력보다 작으면 키워져 대체로 좋아지지만, 지나치게 작으면 흐려져 오히려 성능이 떨어진다.
   - 모델은 입력을 **레터박스**로 바꾼다. 가로세로 비율을 유지한 채 긴 변을 입력 크기에 맞춰 같은 배율로 줄이거나 키우고, 남는 쪽은 회색으로 채운다. 그래서 내용이 찌그러지지 않고, 성능을 정하는 것은 **배율 = 모델 입력 크기 ÷ 타일 긴 변** 하나다.
   - **확정 규칙: 타일 긴 변 ≤ 모델 입력 크기** (배율 ≥ 1, D-95). 어떤 영상이든 원본보다 줄어드는 일이 없다. 영상 속 얼굴·번호판이 몇 px인지 미리 알 수 없으므로, 영상과 관계없이 안전한 규칙을 둔다.
   - 더 키울지(예: 타일 긴 변 = 입력의 1/2, 2배 확대)는 실측으로 정한다 (U-30). 원본에서 이미 10px 안팎인 얼굴은 줄이지 않아도 놓치므로 키워야 잡힌다. 대신 타일 수가 약 4배가 되어 속도 기준(아래)과 부딪친다.
   - 탐지는 보여줄 크롭이 아니라 그보다 큰 **분석 크롭**(6.5)에서 한다 (D-95). 보여줄 크롭 경계에 반쯤 걸린 얼굴·번호판은 잘린 채로는 잘 안 잡힌다. 여백에서 미리 잡아 두면 경계를 넘어 들어올 때 트랙이 이미 이어져 있다.
   - 분석 크롭의 긴 변이 모델 입력 크기보다 크면 타일로 나눠 탐지한다. 타일은 겹치게 자르고, 타일 결과를 크롭 좌표로 합친 뒤 추적(위 2)하므로 타일 경계에서 트랙이 끊기지 않는다. 얼굴·번호판은 작아서 타일 경계에 걸려 조각날 일도 드물다. 30초 클립에만 하므로 타일 수만큼 느려지는 것은 받아들인다. 5분 안에 한 묶음(아래 처리 속도)을 못 맞추면 그때 영역을 줄인다.
   - 가로세로 비율을 유지한다. 정사각형 입력에 넣을 때 찌그러뜨리지 않는다.
4. 사람 bbox 안에서 얼굴을 못 찾으면 사람 전체를 가린다 (위 폴백, 트랙 단위).
5. 파인튜닝. 마지막 수단이다.

### 모델 후보 (D-88)

두 모델을 실측으로 비교한 뒤 정한다. 확정은 🚧 (U-09).

| | UrbanAnonymizer | EgoBlur Gen2 (Meta) |
|---|---|---|
| 구조 | D-FINE-X, 모델 1개(얼굴·번호판 2클래스), 입력 1408px | Faster R-CNN + ResNeXt, **얼굴·번호판 모델 2개**, 각 약 1억 400만 파라미터 |
| 공개 성능 | 저자 비교에서 얼굴·번호판 AP50이 EgoBlur Gen2보다 높다 (저자 보고). 추적 후처리를 붙이면 저자 영상에서 머리가 가려진 프레임이 87.4% → 95.8% | 모델 하나당 2MP 이미지 약 21ms (GPU 종류 미공개). 두 모델이면 프레임당 두 번 실행 |
| 실측에서 볼 것 | CCTV 구도, 한국 번호판 | CCTV 구도(1인칭 영상으로 학습), 두 모델 합산 속도 |

- 95.8%는 탐지 모델의 탐지율이 아니다. 저자 영상에서 **추적 후처리까지 붙였을 때** 머리가 가려진 프레임 비율이다. 우리 목표값과 바로 비교하지 않는다.
- **대안 경로 (증류)**: 속도 기준을 못 맞출 때 쓴다.
  - EgoBlur Gen2를 선생 모델로 우리 데이터에 의사 라벨을 붙인다.
  - 사람이 검수해 틀린 박스를 지우고 놓친 박스를 추가한다.
  - 더 가벼운 모델(예: D-FINE-S/M)을 얼굴·번호판 2클래스로 파인튜닝한다.
- 두 클래스를 모델 1개로 할지 2개로 할지는 실측에서 **얼굴·번호판 재현율을 따로** 재서 정한다. 한쪽만 떨어지면 그 클래스만 떼어 별도 모델로 만든다.
- 번호판은 번호를 읽지 않고(OCR 아님) 위치만 탐지하면 된다. 한국 번호판에서 탐지가 떨어지면 AI Hub 한국 번호판 데이터로 파인튜닝한다 (5번).
- 참고 (라이선스): 이번 범위는 시연이다. UrbanAnonymizer 가중치는 CC BY-NC 4.0(비상업), EgoBlur Gen2는 코드·가중치 Apache 2.0이다(내려받을 때 약관 동의). 실운영으로 넘어가면 EgoBlur Gen2 또는 이를 선생으로 증류한 모델을 쓴다.

### 속도 기준 (D-88)

- **다음 묶음 10개(30초 이하 클립 × 10, 최대 30초 기준 30fps 약 9천 프레임)를 5분 안에** 비식별화한다. 얼굴·번호판을 합쳐 **약 30fps**가 필요하다. 사용자가 한 묶음을 보는 동안 다음 묶음을 준비하기 위해서다 (D-68).
- 보여줄 모든 프레임을 빠짐없이 처리한다 (샘플링하지 않음). 속도가 모자라면 먼저 입력 크기·모델 크기를 줄이고, 그래도 모자라면 증류 경로로 간다.
- 동시 사용자가 늘면 GPU 워커를 늘려 대응한다 ([02장 2.10](02-architecture.md#210-확장-방향-이번-범위-밖)의 GPU ASG). 이번 범위는 동시 사용자 1명 기준이다.

### 목표 (D-88)

- **제출 목표: 누락률 5% 이하 (재현율 95% 이상)**. 얼굴(사람)과 번호판 결과를 합산한다. 공공 데이터셋 기준이다 (PRD 2장 KPI).
- **추진 목표: 재현율 99%**. 실제 주차장은 차량이 서행하고, 본인 차량 주변만 크롭하고, 추적으로 빈 프레임을 채우므로 공공 데이터셋보다 유리하다. 검증 데이터셋은 조사 후 정한다 🚧 (U-34).
- 누락 판정: 정답 박스의 중심이 마스크로 가려졌으면 탐지, 가려지지 않았으면 누락이다. 크기와 관계없이 모든 정답 박스를 넣는다.
- 보고는 합산 수치로 하고, 내부적으로는 얼굴(사람)·번호판 수치를 따로 기록해 모델 선택과 개선에 쓴다.
- 측정 데이터셋은 🚧 (U-29).
- 번호판은 위치만 탐지하면 되므로 사람 전체 가리기 같은 대비책을 따로 두지 않는다.
- 차 안 운전자도 같은 얼굴·사람 탐지로 가린다. 별도 대책(앞유리 영역 가림 등)은 두지 않고, 탐지가 부족하면 파인튜닝한다 (U-35 해결).

## 6.9 원본 시간 규칙

- 트랙 줄·후보 구간·유력 시점의 시각 = 청크 offset + 청크 내부 시간 (디코딩 단계에서 프레임마다 붙인다) (불변 조건 7, D-246, D-250)

- VLM 입력 구간은 사용자 클립 구간과 같다 (D-73)

## 6.12 필수 VLM 정렬 (D-92)

VLM 정렬은 필수 처리 단계다. 1차 평가에서 낮은 후보를 0점으로 유지하는 기존 2단계 방식은 유지하며, 점수를 이유로 후보를 제거하지 않는다. 사진·설명은 선택 입력이므로 없어도 영상과 위치 정보로 VLM을 수행한다. 장애 시 조용히 룰 정렬만으로 완료 처리하지 않는다. 재호출·실패 처리는 6.6(D-93)을 따른다: 점수는 도구 강제 호출로 받고, 파싱 실패는 최초 포함 최대 3회 호출, 파싱 실패율 30% 초과나 장애 지속이면 `failed`.
