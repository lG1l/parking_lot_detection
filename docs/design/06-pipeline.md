# 06. 비전·VLM 파이프라인

> 마지막 수정: 2026-09-27
> 표시: 🚧 미정 · ⚠️ 확인 필요 · 🔐 멘토 승인 필요
> 이 장의 구조는 D-67~D-75(모두 상태 "확정 필요")를 따른다. 모델·수치는 대부분 🚧이고, 무엇을 어떻게 정할지는 [6.10](#610-추후-결정-항목)에 모았다.

## 6.1 전체 흐름

**사용자가 기다리는 시간보다 탐지 성능과 처리 속도를 우선한다.** 그래서 영상 전체 분석은 사용자 입력을 받은 **뒤에** 한다. 입력(본인 차량·파손 부위·탐지 상황)을 알아야 근접 영역만 조밀하게 보고, 클래스 없는 물체를 잡고, 작은 물체를 크롭해 볼 수 있기 때문이다. (D-67)

```
[업로드] 최소 수 분
  업로드 남은 예상 시간 <= 임계(1.6)가 되면 GPU 켜기 요청 (D-62)

[1단계: 정지 장면] 업로드 완료 직후. 수십 초 (추정)
  코덱 검사 → 첫 프레임 1장 → 차량 탐지 → 타일 방식 비식별화 → 저장

[사용자 입력] 아무 때나
  본인 차량 고르기 + 탐지 상황 [보임/안 보임] + 파손 부위(보임일 때 드래그)
  + 사진(선택) + 텍스트 설명(선택) → 확인창 → 저장 (D-66, D-72)
  GPU가 꺼져 있으면 다시 켠다 (부팅 2~3분, D-15)

[2단계: 전체 분석] 입력 저장 후. 24시간 영상 약 30분 (추정, 실측 필요)
  ① 후보 탐지: 청크별 채널 A(YOLO+ByteTrack) + 채널 B(근접 영역 움직임) → 바닥점 필터(0단계) → 후보
  ② VLM: 1차(싼 모델, 탈락만) → 2차(점수 0~100) → 점수순 정렬
  ③ 상위 20개(묶음 2개) 후보 클립: 본인 차량 주변 크롭 → 비식별화 → "확인 가능"

[확인]
  [다음] → 이미 준비된 다음 묶음을 바로 보여줌
         → 동시에 GPU를 켜고 그다음 묶음을 비식별화 (한 묶음 앞서 준비, D-68)
```

| 단계 | 시작 조건 | GPU | 사용자가 기다리나 |
|---|---|---|---|
| 1단계 | 업로드 완료 알림 | 필요 (탐지·비식별화) | 업로드 직후 바로 입력하려면 수십 초 |
| 2단계 | 입력 저장 | 필요 | **기다린다.** 24시간 영상 약 30분 (추정). GPU가 꺼져 있었으면 부팅이 더해진다 |
| 다음 묶음 | [다음] | 필요 (비식별화) | 기다리지 않는다. 이미 준비된 묶음을 보여준다 |

- 1단계는 이제 정지 장면만 만든다. 영상 전체 객체탐지·추적은 2단계로 옮겼다 (D-67이 D-05를 바꿈).
- **입력은 항상 1단계가 끝난 뒤에 들어온다.** 정지 장면이 1단계의 마지막 산출물이기 때문이다. 그래서 "1단계 중 입력 → 1단계가 끝나면 2단계 자동 시작" 경로(D-15 결정 3, `stage1_input_done`)가 필요 없다. 상태 정리는 04장 담당(팀원 2)과 맞춘다 ⚠️ (04장 머리 참고).

## 6.2 GPU 워커 운영

(D-14, D-15, D-16, D-62)

- SQS 긴 폴링(20초)으로 작업 꺼내기
- 처리 중 가시성 제한 시간 주기적 연장 (`ChangeMessageVisibility`, 연장 주기 U-18). **이제 오래 걸리는 쪽은 2단계다** (약 30분, 추정)
- 처리 전 DB 상태로 중복 확인 (이미 끝났거나 처리 중이면 건너뜀)
- 처리 후 메시지 삭제 (`DeleteMessage`). 조건부 UPDATE가 0행이면 이유를 가리지 않고 지운다. `analysis_jobs` 행이 없는 경우도 마찬가지다 (D-56, 04장 4.4 ⚠️ 팀장 확인)
- 실패 처리: 재시도 상한과 DLQ는 없다. 워커가 되풀이해도 소용없는 오류를 만났을 때만 `failed`로 바꾼다. 어떤 오류를 그렇게 볼지 정하는 것이 남았다 🚧 (D-43, D-56)
- **켜기**: 업로드 남은 시간이 임계 이하일 때(D-62), 그리고 GPU가 필요한 작업을 SQS에 넣을 때마다(1단계, 2단계, 다음 묶음). 사용자가 1단계 뒤 15분 넘게 입력하지 않으면 GPU가 꺼져 있으므로 입력 저장 시 다시 켠다(부팅 2~3분).
- 15분 동안 할 일이 없으면 SQS·DB를 한 번 더 확인한 뒤 OS 종료. 워커가 OS 종료 명령을 실행할 권한을 얻는 방법 🚧
  - 확인과 종료 사이에 들어온 작업은 워커가 챙기지 않아도 된다. 백엔드의 5초 주기 점검이 완전히 꺼진 뒤 다시 켠다 (D-42)
- 자동 꺼짐 켜고 끄기 설정 (시연 날에는 끔, [02장 2.8](02-architecture.md#시연-날-설정))
- 가짜 워커 모드: GPU·Bedrock 없이 정해진 시간 기다린 뒤 가짜 결과를 DB·S3에 쓴다 (D-20)
- 임시 파일 위치: 원본 영상·청크는 로컬 NVMe(`/opt/dlami/nvme`)에 두는 것을 기본으로 한다. 중지하면 비워지므로 켤 때마다 비어 있다고 가정한다 (D-21)

## 6.3 1단계: 정지 장면

- 시작 직후 `ffprobe`로 코덱을 확인한다. H.264·H.265가 아니거나 읽을 수 없으면 재시도 없이 `failed`로 바꾸고 `error_message`에 이유를 적는다 (D-43, ⚠️ 팀장 확인)
- 원본을 열어 **첫 프레임 1장**만 뽑는다. `t_sec = 0.0`. 시크가 없다 (D-48)
- **비식별화 전 프레임에서 차량을 탐지해** `still_frames.detections`에 저장한다 (D-65). 사용자가 이 중에서 본인 차를 고른다
  - 모자이크가 씌워진 뒤에 탐지하면 차량 경계가 흐려진다. 좌표는 원본 해상도 기준이라 두 결과가 같은 좌표계다
  - 누끼(다각형)는 만들지 않는다. 바닥선 개선(6.5)에 segmentation을 쓰게 되면 그때 함께 검토한다 🚧 (U-09)
  - 탐지가 0건이어도 `[]`로 저장한다. 화면은 재업로드 안내로 간다 (D-65)
  - 2단계 채널 A와 **같은 탐지 모델·클래스를 쓴다** (U-09). 기준이 갈리면 "탐지된 차량을 골랐는데 2단계에서는 다른 모양으로 잡히는" 경우가 생긴다
- 비식별화는 **타일 방식**이다. 프레임 전체를 겹치는 타일로 나눠 각각 탐지하고 합친다(SAHI 방식). 이 시점에는 본인 차량을 모르므로 크롭할 기준이 없고, 프레임이 1장이라 타일 수만큼 느려져도 괜찮다 (D-69, 6.8)
- 1단계는 여기서 끝난다. 청크 분할·객체탐지·추적은 하지 않는다 (D-67)

## 6.4 사용자 입력 (워커가 받는 값)

PRD 3.2가 정한 입력을 워커가 이렇게 읽는다. 저장 형식은 04장 `vehicle_selections`·`damage_inputs`이고, 바뀌어야 할 점은 04장 머리에 적었다.

| 입력 | 필수 | 쓰는 곳 |
|---|---|---|
| 본인 차량 (`det_id` → `bbox`) | 필수 | 근접 영역, 바닥선, 크롭 기준 |
| 탐지 상황: 파손이 CCTV에 **보임 / 안 보임** | 필수 | 룰 분기 (6.5) |
| 파손 부위 드래그 (보임일 때) | 보임이면 필수 | 근접 판정 기준, VLM 안내 프레임 |
| 파손 부위 위치 (안 보임일 때) | 🚧 U-25 | 인접 영역 계산, VLM 안내 프레임 |
| 파손 사진 | 선택 | VLM 입력 |
| 텍스트 설명 | 선택 | VLM 입력 (데이터로만 취급) |

**파손이 안 보일 때의 입력 방식** 🚧 (U-25, 팀장이 나중에 정한다)

| 안 | 방식 | 장점 | 단점 |
|---|---|---|---|
| (a) 대략 드래그 | 차량 bbox 안에서 파손이 있을 법한 **가장자리**를 대충 드래그 | 보임일 때와 화면·저장 형식이 같다 | 보이지 않는 면을 2D 화면에 그리는 것이라 사용자가 헷갈린다. 드래그한 자리의 뜻이 "보이는 부위"와 달라 룰이 두 뜻을 구분해야 한다 |
| **(b) 방향 버튼 (권장)** | [카메라 반대편] / [화면 왼쪽 끝] / [화면 오른쪽 끝] 중 하나를 고름 | 화면 기준이라 사용자가 차의 앞뒤를 몰라도 고를 수 있다. 룰이 받을 값이 셋뿐이라 인접 영역 계산이 단순하다 | 버튼 문구를 이해시켜야 한다(07장). 대각선 방향은 표현하지 못한다 |

- 어느 안이든 VLM 안내 프레임에는 **파손 부위 대신 그 쪽 인접 영역**을 표시한다 (6.6).
- 버린 안: **차량 정면 방향 자동 추정.** 주차 칸 모양만으로는 앞뒤를 구분할 수 없고, 후면 주차가 흔하다. 3D 박스 모델은 CCTV 화각과 학습 데이터의 차이가 크고, 틀려도 사용자에게 드러나지 않는다.

**통로 쪽 / 옆면 구분** 🚧 (U-26)

- 파손 부위가 차의 통로 쪽(앞·뒤 범퍼 쪽)인지 옆면(옆 칸 쪽)인지에 따라 근접하는 물체와 빈도가 크게 다르다(6.5 페르미 추정).
- 사용자가 고르게 할지, D-34처럼 파손 부위와 차량 bbox를 비교해 계산할지 아직 정하지 않았다. 계산은 입력이 줄지만 카메라 각도에 따라 "bbox의 어느 변"이 "차의 어느 면"인지가 어긋날 수 있다.

**사진·텍스트 전처리**

- 둘 다 선택이다. 없으면 VLM 프롬프트에서 그 항목을 통째로 뺀다 (빈 칸으로 두지 않는다).
- 사진: EXIF 제거(GPS 포함), HEIC는 JPEG로 변환, 긴 변 768~1024px로 줄인다. 사진에는 **사용자 본인 차 번호판**이 찍혀 있을 수 있다. 사용자 자신의 정보이고 VLM에만 보내며 화면에 다시 보여주지 않으므로 비식별화하지 않는다. 파기 대상에는 넣는다 (04장 머리) ⚠️.

## 6.5 2단계-① 후보 탐지

**목표**: 사고 클립 후보 검출 누락률 1% 이하 (PRD 2장 KPI). CCTV에 가려져 사람도 판단할 수 없는 경우를 빼고 모두 잡는다. **재현율이 우선이지만, 확실히 관계없는 것은 여기서 뺀다.** (D-71)

### 대상 장면

| 장면 | 주로 잡는 채널 | 보이는 파손의 신호 | 안 보이는 파손의 신호 |
|---|---|---|---|
| 문콕 (옆 차 문 열림) | A(사람·차) + B(문 움직임) | 옆 차 쪽 덩어리가 파손 부위에 닿음 | 옆 칸 사람 승하차, 옆 차 문 쪽 움직임 |
| 주행 차량 접촉 | A | 차량 바닥점이 띠 안으로 들어옴 | 차량이 차 너머로 가려졌다 나타남, 느린 통과 |
| 물체·구조물 쓰러짐 | B | 밑동(바닥점) 근처에서 위쪽 덩어리가 차 쪽으로 기움 | 차 너머에서 큰 움직임 |
| 바퀴 달린 물체가 혼자 굴러옴 (카트·유모차) | B (+ A가 잡으면 A) | 덩어리 바닥점이 띠 안으로 이동 | 인접 영역 진입·체류 |
| 물체가 날아옴 | B | 짧고 빠른 덩어리가 차 쪽으로 | 바닥점 신뢰 불가 → 남김 |
| 사람 접촉 (고의·과실) | A | 사람 바닥점이 띠 안, 체류 | 차 너머 체류, 가려짐·재등장 |
| 동물 | A(COCO 동물 클래스) + B | 바닥점이 띠 안 | 인접 영역 체류 |

### 탐지 채널

- **채널 A: 객체탐지 + 추적.** COCO 사전학습 YOLO + ByteTrack. 프레임 전체를 본다. 쓸 클래스 목록과 모델 크기는 🚧 (U-09)
- **채널 B: 근접 영역의 움직임.** 본인 차량 bbox를 넓힌 **근접 영역(ROI)** 안에서만 배경 차분(MOG2, `detectShadows=True`로 그림자 제거) 또는 광학 흐름(Farneback)으로 움직이는 덩어리를 찾고, 덩어리의 bbox를 ByteTrack에 넣어 트랙으로 만든다. **클래스가 없는 물체**(카트, 라바콘, 떨어지는 물건)를 잡기 위한 것이다. MOG2와 광학 흐름 중 무엇을 쓸지, ROI 크기는 🚧 (U-09, U-30)
- 채널 B는 D-04에서 "사전 필터"로만 검토하던 움직임 감지를 **후보를 만드는 채널**로 올린 것이다 (D-71이 D-04·U-07을 바꿈). 전체 프레임이 아니라 ROI만 보므로 조명·비의 오탐이 줄고 비용도 작다.
- 두 채널이 같은 물체를 잡으면 겹침으로 하나로 친다. 규칙은 후보 병합과 함께 🚧 (U-13)
- 청크 분할·병렬 처리는 02장 2.6을 따른다. 샘플링 fps와 청크 길이는 🚧 (U-06). 날아오는 물체는 낮은 fps에서 한두 프레임에만 걸리므로, **ROI 안은 fps를 높이는 안**도 함께 잰다.
- 본인 차량은 추적하지 않는다. 입력한 bbox를 고정 영역으로 쓴다 (D-29). 본인 차량과 옆 차에 걸리는 채널 A 트랙(주차된 차 자체)은 "움직이지 않는 트랙"으로 뺀다.

### 바닥점 필터 (근접 판정)

2D에서 bbox가 겹친다는 것만으로는 부족하다. 카메라와 내 차 사이를 지나가는 모든 것이 겹쳐 보인다. 그래서 **바닥 위의 위치**로 깊이를 대략 가른다.

| 용어 | 뜻 |
|---|---|
| 바닥점 | 트랙 bbox 아래 변의 가운데. 물체가 바닥에 닿는 자리로 본다 |
| 바닥선 | 본인 차량이 바닥에 닿는 경계. 처음에는 **차량 bbox 아래 변**으로 두고, 개선안은 YOLO-seg 마스크의 아래 윤곽 🚧 (U-09) |
| 띠 | 바닥선 바로 아래(카메라 쪽)의 좁은 영역. 폭은 **차량 bbox 높이에 비례**한다(비율 🚧 U-30). 원근 때문에 멀리 있는 차는 작게 보이므로 고정 픽셀 폭을 쓰지 않는다 |

- **보이는 파손**: 트랙의 바닥점이 파손 부위의 가로 범위 근처에서 **띠 안**에 들어오면 근접이다.
- **안 보이는 파손**: 트랙의 바닥점이 바닥선 **위쪽**(차 너머)에 있거나, 차에 가려 사라졌다 다시 나타나거나, 인접 영역에 머무르면 근접이다.
- **전제**: 바닥이 평평하다. 천장에 달린 CCTV는 내려다보는 각도라 바닥점의 y가 거리를 잘 나타낸다(유리한 조건).
- **확장**: 주차 칸 선의 네 점으로 바닥 호모그래피를 구하면 미터 단위 거리로 판정할 수 있다. 칸 규격(2.5×5.0m ⚠️)을 기준으로 쓴다. 지금은 하지 않는다.
- **바닥점을 믿을 수 없는 트랙은 거르지 않는다.** 채널 B 덩어리가 불안정하거나, 발이 가려졌거나, 화면 가장자리에서 잘렸거나, 공중에 떠 있는 물체(날아옴)가 그렇다. 이런 트랙은 후보로 남기고 VLM이 본다 (6.6의 1차 필터 (b)안).

### 0단계 필터 원칙

**"확실히 관계없는 것만 빼고, 판단이 안 되면 남긴다."** 트랙 단위로, 트랙이 파손 부위에 가장 가까웠던 순간을 기준으로 판정한다.

| 뺀다 | 남긴다 |
|---|---|
| 바닥점을 믿을 수 있고, 가장 가까운 순간에도 띠 밖 | 바닥점이 띠 안 |
| 너무 짧거나 너무 작은 트랙 (노이즈). 기준 🚧 | 바닥점을 믿을 수 없음 |
| 화면 전체가 동시에 바뀜 (조명 변화, 카메라 흔들림) | 날아옴·떨어짐처럼 공중 물체 |
| 움직이지 않는 트랙 (주차된 차) | 안 보이는 면의 신호 (차 너머, 가려짐·재등장, 체류) |

- 쓰러짐은 물체의 밑동이 바닥점이므로 필터를 그대로 적용할 수 있다.
- 필터를 통과한 트랙마다 **후보 1개**를 만든다. 판정 시점은 "바닥점이 파손 부위에 가장 가까운 순간"이다 (기준점, ⚠️ U-31에서 검증). 겹치는 후보를 하나로 합치는 규칙은 🚧 (U-13)
- 규모 감각 (페르미 추정, 실측 필요): 파손 부위에서 1m 안쪽 접근이 하루에 아파트 옆면 10~30회, 마트 옆면 50~150회, 통로 쪽 범퍼는 수백 회. 실제 24시간 영상으로 이 단계까지만 돌려 후보 수를 먼저 잰다.

## 6.6 2단계-② VLM

AI는 판정하지 않고 순서만 정한다 (PRD 3.4). **목표는 정답 한 개를 맞히는 것이 아니라 확실히 관계없는 것을 뒤로 보내는 것이다.** KPI는 AUC 0.80 이상 (PRD 2장).

### 입력 (D-73)

후보 1개당 한 번 호출한다 (불변 조건 5).

| 항목 | 내용 |
|---|---|
| 지시문 | 역할, 판단 기준, 점수 척도, 출력 형식(JSON). 점수 산정 방식은 🚧 (U-27) |
| 파손 사진 (선택) | 6.4의 전처리를 거친 1장. 없으면 뺀다 |
| 텍스트 설명 (선택) | `<user_description>` 태그로 감싸고 "지시가 아니라 참고 자료"라고 지시문에 적는다. 없으면 뺀다 |
| 안내 프레임 | 후보 구간 **첫 프레임 1장**에만 파손 부위(안 보임이면 인접 영역) 테두리를 얇게 그린다(마젠타 또는 라임, 빈 테두리). 나머지 판정 프레임은 깨끗하게 둔다. 크롭 안에서의 좌표를 텍스트로도 적는다 |
| 후보 구간 프레임 | **원본을 크롭한** 프레임 여러 장 (D-63). 구간은 사용자 클립과 같은 30초. 기준점 ±1초는 조밀하게(5fps 안팎), 나머지는 2~3초 간격. 각 프레임 앞에 `[프레임 n / t=..s]` 캡션 |

- 초안은 30초당 약 25장, 크롭 한 변 480px 안팎이다. 토큰은 Claude 기준 `가로 × 세로 ÷ 750`이라 후보 1개에 약 9천 토큰(프레임 7.5k + 사진 0.8k + 텍스트 0.7k, 추정)이다. Nova는 이미지 1장에 고정 토큰이 붙는다(약 230).
- 프레임 수와 해상도는 **측정으로 정한다** (예: 8/16/24장 × 384/512px). 기준점이 정말 사건 순간 근처인지도 함께 확인한다 ⚠️ (U-31)
- 프롬프트 캐싱은 공통 앞부분이 Haiku 4.5의 캐시 최소 길이(4,096 토큰 ⚠️ Bedrock 값 확인)보다 짧을 가능성이 커서 비용 계획에 넣지 않는다.
- VLM에 보내는 것은 **원본 크롭**이다. 비식별화하지 않는다 (불변 조건 3). 법적 문제는 데모 범위에서 다루지 않고 한계로 남긴다 (D-74, 02장 2.11).

### 1차·2차 구조 (D-74)

| | 1차 | 2차 |
|---|---|---|
| 목적 | **확실히 아닌 것**만 탈락 | 남은 후보에 점수 |
| 출력 | 통과 / 탈락 | 0~100 점수 |
| 모델 | **Nova Lite** (잠정. 측정 후 바꿀 수 있다). 비교 후보: Nova 2 Lite | **Claude Haiku 4.5**. 품질이 모자라면 Sonnet 5 |
| 입력 | 위 표와 같다. 우리가 샘플링한 이미지를 넣는다 | 같음 |

- **점수는 2차 모델 하나에서만 나온다.** 1차에서 탈락한 후보는 **0점**을 받아 정렬 맨 아래에 남는다. 후보 수는 줄지 않는다 (불변 조건 4, PRD 3.4 AC). AUC 계산에서도 0점으로 넣는다.
- **1차에 보낼 후보** — 두 안을 모두 적고, (a)부터 해 본다.
  - (a) **모든 후보**를 1차에 보낸다.
  - (b) **바닥점을 믿을 수 없는 후보만** 1차에 보낸다. 바닥점이 띠 안인 후보는 1차를 건너뛰고 바로 2차로 간다.
  - (a)로 실제 영상에서 1차가 얼마나 걸러내는지 잰 뒤, 걸러내는 양과 A 클립 탈락 여부를 보고 (a)와 (b) 중 하나로 정한다 🚧 (U-32).
- 1차 통과 기준: 조정용 A 클립이 1차에서 하나도 탈락하지 않을 것.
- Nova 2 Lite는 영상을 직접 받아 스스로 샘플링하지만 1fps로 고정되고, 공식 문서상 공간 추론에 한계가 있다. 그래서 영상 직접 입력이 아니라 우리 샘플 이미지를 넣어 비교하고, 최종 점수용(2차)으로는 쓰지 않는다.
- temperature 0 (1.6). 점수 파싱에 실패하면 1회 다시 부르고, 그래도 실패하면 🚧 (U-27).
- Bedrock 한도 초과(`ThrottlingException`) 시 대기 시간을 늘려 가며 재시도한다 (D-19). 동시 호출 수는 🚧 (U-18)

**리전** (D-74가 D-54를 바꿈)

- 저장(S3)·GPU·DB는 서울 `ap-northeast-2`에 그대로 둔다.
- Bedrock은 서울에서 **교차 리전 추론 프로파일**로 부른다. 서울에서 In-Region으로 쓸 수 있는 VLM은 이미지 입력이 없는 모델뿐이라서다(2026-09-26 확인).

| 모델 | 서울에서 부르는 방법 | 입력/출력 1M 토큰당 (USD) |
|---|---|---|
| Nova Lite | APAC Geo 프로파일 | 0.06 / 0.24 |
| Nova 2 Lite | Global 프로파일 | 0.30 / 2.50 |
| Claude Haiku 4.5 | Global 프로파일 | 1 / 5 |
| Claude Sonnet 5 | Global 프로파일 | 약 2 / 10 ⚠️ |

- 가격은 참고값이다. 비용 예측은 후보 수 실측 뒤에 한다 🚧 (U-28)

## 6.7 2단계-③ 정렬과 후보 클립

- 점수 내림차순으로 정렬해 `rank`를 매긴다. 동점 처리 규칙 🚧 (U-27)
- **처음에 상위 20개(묶음 2개)의 클립을 만든 뒤 "확인 가능"으로 바꾼다.** (D-68)
- 사용자가 [다음]을 누르면 이미 준비된 다음 묶음을 **바로** 보여준다. 동시에 백엔드가 다음 묶음 작업을 넣어 GPU를 켜고, 그다음 묶음(예: 21~30번)을 비식별화한다. 항상 **한 묶음 앞서** 준비한다.
  - 사용자가 준비 속도보다 빨리 [다음]을 누르면 기다린다. 한 묶음을 확인하는 데 최대 5분이 걸리므로 드물다.
- 클립 구간: 판정 시점 −10초 ~ +20초, 영상 경계에서 자른다 (1.6).
- **클립은 본인 차량 주변으로 크롭한다** (D-70). 크롭 크기는 🚧 (U-30). 보여주는 범위가 줄어 비식별화를 놓쳐도 노출이 작아지고, 비식별화 탐지도 이 크롭 위에서 한다(6.8).
- 인코딩: H.264 코덱 MP4 (Flutter Web 재생 조건, D-08).
- 클립 생성 실패는 D-51을 따른다.

## 6.8 비식별화

(D-69)

**대상**: 사람 **얼굴**과 차량 **번호판**. 사람 몸 전체를 기본으로 가리지 않는다.

- **폴백**: 사람으로 탐지됐는데 그 bbox 안에서 얼굴을 찾지 못하면 **그 사람 전체를 가린다.** 판단은 프레임이 아니라 **트랙 단위**다. 한 트랙에서 얼굴이 안정적으로 잡히지 않으면 그 트랙의 모든 프레임을 사람 전체로 가린다. 프레임마다 판단하면 모자이크가 깜빡이며 얼굴이 드러나는 프레임이 생긴다.
- 사람 트랙은 채널 A의 COCO `person` 트랙을 그대로 쓴다.

**적용 위치**

| 위치 | 탐지 방식 | 이유 |
|---|---|---|
| 정지 장면 (1단계) | 프레임 전체 **타일** 탐지 | 본인 차량을 아직 모른다. 1장이라 느려도 된다 |
| 후보 클립 (2단계, 다음 묶음) | 본인 차량 주변 **크롭** 위에서 탐지 | 클립이 크롭이므로 보여줄 영역만 보면 된다. 작은 얼굴·번호판이 상대적으로 커진다 |

**누락을 줄이는 방법** — 재현율(놓치지 않기)이 정밀도보다 중요하다. 위에서부터 차례로 적용하고, 앞의 것으로 부족할 때만 다음으로 간다.

1. 탐지 임계값을 낮춘다. 오탐(엉뚱한 곳 모자이크)은 받아들인다.
2. 추적으로 빈 프레임을 채운다. 트랙 중간에 탐지가 빠진 프레임은 앞뒤 bbox로 보간해 가린다.
3. 작은 대상은 크롭해 키워서 탐지한다. 크롭은 사용자 입력(본인 차량) 주변이다. 세부(크롭 크기·배율)는 🚧 (U-30)
4. 사람 bbox 안에서 얼굴을 못 찾으면 사람 전체를 가린다 (위 폴백, 트랙 단위).
5. 파인튜닝. 마지막 수단이다.

- 모델 후보: 얼굴 RetinaFace, SCRFD, YuNet, YOLOv8-face (EgoBlur는 라이선스 ⚠️). 번호판은 AI Hub 한국 번호판 데이터로 학습한 모델. 확정은 🚧 (U-09)
- 보여줄 모든 프레임을 빠짐없이 처리한다 (샘플링하지 않음).
- 목표 수치와 측정 데이터셋은 🚧 (U-29, PRD 2장 KPI).

- 후보의 판정 시점 = 청크 offset + 청크 내부 시간 (불변 조건 7)
- 후보 클립 구간 = 판정 시점 −10초 ~ +20초, 영상 경계에서 자른다
- VLM 입력 구간은 사용자 클립 구간과 같다 (D-73)
