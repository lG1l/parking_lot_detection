# 차량 주변 ROI·보여줄 크롭·분석 크롭 설계안

> 작성일: 2026-10-26
> 상태: **검토용 제안. 구현 명세로 확정되지 않았다.**
> 목적: 사용자가 입력한 바닥 네 모서리로 차량의 방향·화면상 크기·눌려 보이는 정도를 읽고, 차량 bbox로 차체가 차지하는 범위를 보완하여 영역을 자동 계산한다.
> 이 문서만 작성한다. PRD·SRS·설계 01~11장·API·DB·화면·코드는 변경하지 않는다. 문서 작성 요청을 아래 제안에 대한 승인으로 취급하지 않는다.

## 1. 무엇을 해결하려는가

같은 차량 주변을 보더라도 촬영 구도에 따라 감지해야 할 화면 위치가 달라진다.

- 낮게 바라보면 차량 뒤쪽 바닥이 가려진다. 파손 변 바깥의 바닥만 검사하면, 지붕 위에 드러나는 사람의 머리나 차량 앞뒤로 출입하는 움직임을 놓칠 수 있다.
- 위에서 내려다보면 주변 바닥이 더 잘 보인다. 이때도 낮은 시점과 똑같이 넓은 영역을 검사하면 관계없는 움직임이 많이 들어온다.
- 화면에서 작게 보이는 차량과 크게 보이는 차량에 같은 픽셀 여유를 주면 실제 관심 범위가 크게 달라진다.
- 차량이 화면에서 회전해 있으면 화면의 좌우·상하와 차량의 앞뒤·좌우가 일치하지 않는다.

필요한 결과는 CCTV의 설치 높이와 거리를 미터로 복원하는 것이 아니다. **차량 주변에서 사건의 단서가 화면에 나타날 범위를 정하는 것**이다.

카메라 내부 정보, 실제 차량 치수, 실제 거리, 실측 주차면 크기는 입력받지 않는다. 차량의 화면상 크기를 자로 쓰고, 촬영 구도는 상대적인 참고값으로 다룬다.

## 2. 추천하는 전체 방식

**바닥 네 점으로 방향별 바닥 영역을 만들고, 차량 bbox로 높이 방향의 감지 여유를 보완한다. 촬영 구도 추정이 불확실하거나 파손이 안 보이면 좁은 ROI로 전환하지 않는다. ROI를 먼저 만들고 두 크롭을 그 바깥에 만든다.**

각 정보의 역할을 분리한다.

| 정보 | 맡기는 역할 | 맡기면 안 되는 역할 |
|---|---|---|
| 바닥 네 모서리 | 차량의 바닥 경계, 주변 영역의 방향, 원근의 대략적인 반영 | 정확한 지붕·사람 머리 위치 복원 |
| 정면 변 | 차량 길이 방향과 폭 방향 구분 | CCTV가 어느 쪽에 있는지 단독 판정 |
| 차량 bbox | 화면상 차량 크기, 차체가 들어갈 크롭의 최소 범위, 높이 방향 여유의 기준 | 실제 차체 높이·정확한 외곽선·가림 경계 측정 |
| 파손 변 | 어느 면 주변의 움직임을 우선 볼지 결정 | 파손 면이 실제로 보인다고 추정 |
| 보임/안 보임 | 직접 관측 중심과 가려진 쪽 접근 중심의 분기 | 주변 바닥까지 전부 보인다는 보장 |
| 파손 사각형 | 보임에서는 직접 접촉 위치, 안 보임에서는 사용자가 지목한 위치 참고 | 안 보임 입력을 실제 관측한 표면 좌표로 사용 |

이 설계는 규칙 기반 자동 계산이다. 런타임에 사람이 사진을 보고 매번 ROI를 그리는 방식이나 VLM에 영역 생성을 맡기는 방식은 기본안에 포함하지 않는다.

## 3. 입력과 전제

### 3.1 이미 받는 정보

1. 원본 영상 해상도와 탐지된 본인 차량 bbox.
2. 사용자가 찍은 바닥 네 모서리.
3. 파손이 있는 변 한 개 또는 이웃한 두 개.
4. 파손 보임/안 보임과 차량 내부의 파손 위치 사각형.

사진·텍스트 설명은 영역 계산의 필수 입력으로 사용하지 않는다. 별도의 의미 해석이 개입하면 동일한 기하 입력에서도 결과가 달라질 수 있기 때문이다.

### 3.2 추가를 추천하는 정보: 정면 변 하나

**기존 바닥 사각형의 네 변 중 앞범퍼 쪽 변 하나를 선택받는 것을 추천한다.** 새 점 두 개를 추가로 찍게 하지 않는다.

- 정면과 그 반대편이 차량의 폭 방향 변이다.
- 나머지 두 변이 차량 길이 방향 변이다.
- 원근 때문에 화면에서 가장 짧은 변이 정면일 것이라고 추정하지 않는다.
- 정면을 구분하기 어려운 경우를 허용하는 안을 권장한다. 이때는 길이·폭을 가정하는 구도 계산을 생략하고 넓은 대체 영역을 사용한다.

정면 정보의 효과는 **차량 좌표 방향의 확정**이다. 이것을 추가했다고 촬영 각도를 정확하게 얻는 것은 아니다.

### 3.3 바닥 네 점의 뜻을 먼저 통일해야 한다

제안하는 의미는 **차체의 앞·뒤·좌·우 외곽을 바닥으로 내려다 놓았다고 생각했을 때의 네 모서리**다. 바퀴 중심이나 바퀴 접지점 네 개와 섞어 쓰지 않는다.

차체 외곽과 바퀴 접지점은 간격이 다르다. 입력 의미가 섞이면 주변 띠의 시작점과 차량의 길이·폭 비율이 달라진다. 바퀴는 위치를 짐작하는 단서로만 사용한다. 이 해석은 기존 문서의 모호한 표현을 구체화하는 **제안**이므로 입력 안내를 확정하기 전에 팀장이 검토해야 한다.

점은 차량 둘레를 따라 순서대로 찍는다. 시계·반시계 방향은 계산에서 처리할 수 있지만, 순서를 정리할 때 정면 변과 파손 변의 대응도 함께 보존해야 한다.

### 3.4 기본 적용 전제

- 고정 CCTV이며 분석 중 본인 차량은 같은 위치에 있다.
- 차량 주변 바닥은 국소적으로 평평하다고 근사한다.
- 영상의 위쪽이 대략 실제 위쪽이다. 심한 화면 회전·어안 구도에는 높이 방향 확장 규칙을 그대로 적용하지 않는다.
- 차체 일부와 접근 흔적을 볼 수 있다. 전부 가려져 아무 신호도 남지 않는 장면은 ROI를 넓혀도 해결되지 않는다.

## 4. 높낮이와 크기를 어떻게 계산할 것인가

### 4.1 화면상 크기는 직접 측정한다

차량 bbox의 가로·세로, 바닥 사각형 면적, 각 변의 길이, 원본 영상에서 차량 bbox가 차지하는 면적 비율을 구한다.

이 값은 실제 거리를 의미하지 않는다. **주변 여유를 원본 픽셀로 바꿀 때 사용하는 크기 기준**이다. 크롭 계산 전에 640픽셀 등으로 줄인 영상의 좌표를 사용하지 않는다.

예를 들어 차체 위에 bbox 세로의 0.5배 여유를 준다는 규칙이면, bbox 높이가 200픽셀인 차량에는 100픽셀을, 80픽셀인 차량에는 40픽셀을 준다. 이 수치는 설명용이며 성능이 검증된 여유가 아니다.

### 4.2 단순한 바닥 박스의 세로÷가로만 사용하지 않는다

차량이 화면에서 회전하면 카메라가 그대로여도 바닥 박스의 가로·세로가 달라진다. 따라서 그 비율만으로 높은 시점과 낮은 시점을 구분하면 안 된다.

또한 바닥 사각형 면적÷bbox 면적은 입력 오차와 차량 종류의 영향을 받고, bbox 상단과 바닥점 사이 간격에는 원근에 따른 차량 길이도 섞인다. 세 값 모두 실제 각도의 측정값은 아니다.

### 4.3 구도 추정의 구체적인 실험안

정면 정보가 있으면 다음 절차를 비교 실험할 수 있다.

1. 정면·후면 변의 같은 방향 벡터를 평균내어 화면상 폭 방향을 구한다.
2. 양쪽 측면 변의 같은 방향 벡터를 평균내어 화면상 길이 방향을 구한다.
3. 실제 길이가 폭보다 길다는 점을 보정하기 위해, 길이 방향 벡터를 **가정한 차량 길이÷폭 비율**로 나눈다. 미터 치수는 사용하지 않는다.
4. 두 벡터로 만든 2차원 변환의 큰 축과 작은 축 길이를 구한다. 수학적으로는 2×2 행렬의 특이값 분해(SVD)로 계산할 수 있다.
5. 작은 축 길이÷큰 축 길이를 **바닥 눌림 지표**로 사용한다. 0에 가까우면 한 방향이 강하게 눌렸고, 1에 가까우면 두 방향의 축소 정도가 비슷하다는 뜻이다.

이 방식은 단순한 화면 가로·세로 비율보다 차량의 화면상 회전 영향을 줄이는 목적이다. **바닥이 직사각형이고, 종횡비 가정이 맞으며, 차량 내부의 원근 차이가 작다는 조건에서만** 내려다보는 정도와 연결된다. 강한 원근·광각 왜곡·잘못된 모서리에는 정확한 각도로 해석할 수 없다. 도 단위 각도나 CCTV 위치를 출력하지 않는다.

처음 비교할 종횡비 후보는 2.0, 2.5, 3.0으로 제안한다. 이는 실차나 RC카 전체를 대표한다고 확인한 범위가 아니다. 후보 비율에 따라 결과가 크게 바뀌면 구도를 불확실로 처리한다. RC카의 형태가 이 가정과 맞지 않으면 해당 구도 추정법 자체가 적합하지 않을 수 있다.

### 4.4 bbox 단서와 입력 민감도를 함께 본다

바닥 눌림 지표에 다음을 보조적으로 붙인다.

- 바닥 사각형 면적÷차량 bbox 면적.
- 바닥 사각형의 가장 위쪽과 bbox 상단의 간격을 bbox 높이로 나눈 값.
- 마주 보는 변들의 길이 차이. 차이가 크면 강한 원근 또는 입력 오류 가능성을 검토한다.
- 각 모서리를 조금 옮겼을 때 구도 판정과 ROI 경계가 얼마나 바뀌는지.

민감도 시험의 시작안은 원본에서 각 점을 좌우·상하로 각각 **2픽셀과 bbox 대각선의 1% 중 큰 값**만큼 한 점씩 이동시켜 다시 계산하는 것이다. 이것은 실제 사용자 오차의 통계적 추정이 아니라 불안정한 입력을 찾기 위한 시험 조건이다. 가려진 점의 실제 오차는 더 클 수 있으므로 별도의 큰 오차 시험도 필요하다.

원래 입력에서만 높게 보는 것으로 나오고 작은 좌표 변화에서 낮게 보이는 것으로 바뀌면, 작은 ROI를 선택하지 않는다.

### 4.5 최종 구도는 세 가지로 둔다

| 구도 결과 | 의미 | 영역 처리 |
|---|---|---|
| 내려다봄 | 여러 단서와 민감도 시험에서 일관되게 위에서 보는 형태 | 보이는 파손에 한해 좁은 확장량 적용을 검토 |
| 낮게 봄 | 바닥이 강하게 눌리고 차체 세로 범위가 두드러짐 | 높이 방향과 출입 경로 여유 확대 |
| 불확실 | 단서 충돌, 정면 미상, 강한 원근, 작은 차량, 불안정한 입력 | 넓은 대체 영역 사용 |

**분류 경계값과 단서 결합 규칙은 아직 검증되지 않았다. 초기 기준 구현은 구도에 의한 자동 축소를 끈 상태로 시작하고, 조정용 영상에서 검증한 뒤 활성화하는 안을 추천한다.** 임의 가중합을 곧바로 신뢰도나 확률이라고 부르지 않는다.

이는 자동화를 포기하는 것이 아니다. 넓은 기준 영역도 자동 생성하고, 구도에 따른 축소 기능만 별도로 검증한다. 새로운 구도 계산이 누락을 늘리는지 기준안과 직접 비교할 수 있다.

## 5. 바닥 주변 영역 만들기

### 5.1 차량 방향에 맞는 상대 좌표

차량 바닥을 위에서 본 가상의 직사각형으로 놓고 폭과 길이를 각각 0~1로 표현한다. 정면 변을 기준으로 대응점을 정한다.

네 모서리가 정상이라면 이 직사각형과 입력 사각형 사이의 평면 변환, 즉 호모그래피를 구할 수 있다. **이때의 상대 좌표는 미터 단위가 아니며, 카메라 내부 정보 없이도 점 대응으로 계산할 수 있다.**

파손 변 바깥에 띠를 만든 뒤 그 띠를 원본 영상으로 옮긴다.

- 옆면 파손: 바깥 여유는 차량 폭의 비율, 양 끝 여유는 차량 길이의 비율로 정한다.
- 앞·뒤 범퍼 파손: 바깥 여유는 차량 길이의 비율, 양 끝 여유는 차량 폭의 비율로 정한다.
- 모서리 파손: 선택한 두 변의 띠를 각각 만들고 합친다. 두 변의 평균 방향으로 하나의 띠를 만들지 않는다.

폭과 길이를 각각 1로 두었으므로 두 축의 단위는 서로 다르다. 이 공간에서 두 점의 거리를 계산해 실제 거리처럼 비교하지 않는다.

### 5.2 변환을 신뢰하지 못할 때

호모그래피는 네 점 안에서는 그럴듯해 보여도 바깥으로 확장하면 급격히 벌어질 수 있다. 다음 경우에는 해당 바닥 띠를 신뢰하지 않는다.

1. 사각형이 거의 일직선이거나 면적이 지나치게 작다.
2. 확장한 띠가 뒤집히거나 교차하거나, 투영의 분모가 0에 접근해 경계가 발산한다.
3. 작은 클릭 변화로 띠가 화면 반대편까지 이동한다.
4. 결과가 차량 크기에 비해 비정상적으로 크다. 판정 배수는 조정용 영상에서 정한다.

이때는 실패한 띠를 작은 사각형으로 강제 잘라 쓰지 않는다. **파손 변을 포함하는 화면상 범위를 bbox 크기에 비례해 넓히는 대체 규칙**을 쓴다. 파손 변 자체도 불안정하면 차량 bbox 전체 주변을 감시한다.

## 6. 움직임 ROI 만들기

### 6.1 ROI의 의미

ROI는 **그 안의 움직임을 단서로 후보 탐지를 시작하는 영역**이다. 물체의 모든 픽셀이나 모든 트랙이 계속 ROI 안에 있어야 한다는 뜻은 아니다.

ROI는 사각형 하나로 제한하지 않고, 다음 부분들의 합집합 마스크로 만든다. 실제 분석 프레임을 자르는 크롭은 사각형으로 유지한다.

| 부분 | 목적 | 생성 기준 |
|---|---|---|
| 파손 위치 주변 | 직접 접촉·문·손·물체 끝부분의 움직임 | 파손 사각형에 여유 추가 |
| 파손 변 바깥 바닥 띠 | 접근·머무름·바퀴와 발의 움직임 | 5장의 상대 좌표 띠 |
| 높이 방향 확장 | 발은 가려져도 나타나는 상체·물체 윗부분 | 바닥 띠와 bbox 세로 크기 |
| 양 끝 출입 영역 | 차 너머 진입·이탈·재등장 | 파손 변 양 끝과 주변 여유 |

### 6.2 파손이 보이는 경우

1. 파손 사각형을 확장하여 직접 접촉 영역을 만든다.
2. 선택한 파손 변의 바닥 띠를 더한다. 파손 사각형만 보면 접근 과정이 빠질 수 있기 때문이다.
3. 바닥 띠를 화면 위쪽으로 일정 길이만큼 쓸어 올린 영역을 더한다. 쓸어 올린다는 것은 원래 띠부터 위로 이동한 띠까지 사이를 모두 포함한다는 뜻이다.
4. 변 양 끝의 출입 여유를 더한다.
5. 검증된 내려다봄 구도에서는 높이 확장량을 줄인다. 낮게 봄·불확실에서는 더 큰 값을 사용한다.

직접 보이는 손·문·공중 물체의 움직임을 바닥 띠 밖이라는 이유로 제거하지 않는다.

### 6.3 파손이 안 보이는 경우 — 가장 중요한 분기

안 보임의 이유는 본인 차의 반대편, 옆 차량, 기둥 등일 수 있다. 현재 입력만으로 이 이유를 구분할 수 없다. **따라서 안 보임이면 높은 구도로 추정돼도 바로 좁은 ROI를 선택하지 않는다.**

기본 처리 순서는 다음과 같다.

1. 선택한 파손 변의 바닥 띠와 양 끝 출입 영역을 만든다. 파손 위치 사각형이 작더라도 파손 변의 일부만 남기도록 축소하지 않는다.
2. 바닥 띠와 출입 영역을 화면 위쪽으로 확장한다. 시작안에서는 각 영역의 가로 범위 안에서 기존 영역부터 **차량 bbox 상단보다 추가 여유만큼 위인 선**까지 연결한다.
3. 확장한 영역은 실제 사람의 키를 복원한 결과가 아니다. 차 너머로 나타날 수 있는 신호를 넉넉하게 포함하려는 근사다.
4. 사용자가 지정한 파손 사각형과 그 주변도 합친다. 다만 그 좌표를 가려진 표면의 정확한 위치로 간주하지 않는다.
5. 입력이나 변환이 불안정하면 차량 bbox 전체와 그 주변을 포함하는 넓은 대체 ROI로 바꾼다.

이 방법은 본인 차 몸체에 겹치는 화면 영역도 감시한다. 그 때문에 반사나 조명 변화가 들어올 수 있다. 정확한 차체 외곽·가림 경계 없이 차 내부를 모두 빼면 문·손·차량 흔들림 같은 단서까지 사라질 수 있어, 기본안에서는 빼지 않는다.

### 6.4 높은 시점에서 안 보이는 파손도 줄이고 싶다면

현 입력만으로는 “높게 보지만 주변은 다른 차에 가려진 상황”과 “높게 보이고 접근 공간은 잘 보이는 상황”을 안정적으로 구분할 수 없다.

추가 입력이 필요하다면 카메라 높이를 묻기보다 **‘파손된 쪽 바로 옆 바닥과 사람이 드나드는 공간이 보이나요?’**를 묻는 것이 목적에 더 직접적이다. 답은 보임·가림·모르겠음으로 두는 안이다.

- 주변 보임 + 검증된 내려다봄: 바닥 띠와 짧은 높이 확장으로 줄이는 안을 시험할 수 있다.
- 주변 가림·모르겠음: 넓은 안 보임 ROI를 유지한다.

이 입력은 **선택적 대안**이며 기본안에 몰래 추가하지 않는다. 정면 선택 외에 입력을 늘리지 않는다면 높은 시점의 안 보임도 넓게 처리하는 비용을 받아들여야 한다.

### 6.5 검증을 시작하기 위한 확장량 초안

아래 숫자는 **실험 시작값 제안**이다. 범용 성능이나 누락률 목표를 보장하지 않으며, 팀장 승인·조정용 영상 검증 없이 확정값으로 사용하지 않는다.

| 항목 | 시작값 제안 | 이유와 위험 |
|---|---|---|
| 옆면 바깥 바닥 여유 | 차량 폭의 0.5배 | 옆 공간 접근 포함. 긴 문이나 큰 물체에는 부족할 수 있음 |
| 범퍼 바깥 바닥 여유 | 차량 길이의 0.25배 | 앞뒤 접근 포함. 급한 접근·큰 차량은 별도 확인 |
| 바닥 띠 양 끝 여유 | 해당 변 길이의 각 0.2배 | 모서리 접근 포함. 원근이 강하면 변환 불안정 |
| 파손 사각형 확장 | 좌우 각각 bbox 폭의 0.15배, 상하 각각 높이의 0.15배 | 작은 입력에 따른 누락 완화. 배경 반사 유입 |
| 보임·내려다봄의 높이 확장 | bbox 높이의 0.25배 | 바닥 밖 손·물체를 위한 최소 실험 여유 |
| 보임·낮게 봄 또는 불확실의 높이 확장 | bbox 높이의 0.75배 | 더 넓은 세로 범위 확보 |
| 안 보임의 상단 여유 | bbox 상단에서 bbox 높이의 0.5배 더 위까지 | 지붕 위 움직임 확보. 높은 차량·원근에 따라 부족하거나 과대 가능 |
| 양 끝 출입 영역 | 각 끝점을 좌우 bbox 폭의 0.25배, 상하 높이의 0.25배로 둘러쌈 | 가려짐 전후 움직임 포함 |
| 기하 계산 실패 시 대체 ROI | 차량 bbox를 좌우 각 폭의 0.5배, 위 높이의 0.75배, 아래 높이의 0.25배 확장 | 방향을 못 믿을 때 넓게 탐색. 후보·처리량 증가 |

출입 영역에도 보임/안 보임의 높이 확장을 적용한다. 화면 밖 부분은 버리되, 잘렸다는 사실을 검증 기록에 남긴다.

수치 조정은 누락 원인을 보고 한다. 머리를 놓치면 위쪽 여유를, 출입을 놓치면 끝점 여유를, 문 끝을 놓치면 바깥 띠·파손 주변 여유를 조정한다. 모든 배수를 동시에 키워 원인을 숨기지 않는다.

## 7. 보여줄 크롭과 분석 크롭

### 7.1 계산 순서

**ROI 생성 → 차량 bbox와 ROI를 모두 포함하는 보여줄 크롭 → 접근 맥락 여유를 더한 분석 크롭** 순서다.

낮은 시점에서 ROI가 위로 커지면 두 크롭도 함께 커진다. 높은 시점에서 검증된 조건으로 ROI를 줄이면 크롭도 줄어들 여지가 생긴다. 다만 차량 전체와 16:9 조건 때문에 ROI만큼 크롭이 작아지지 않을 수 있다.

### 7.2 보여줄 크롭

1. 차량 bbox 전체와 화면 안의 ROI 전체를 감싸는 최소 사각형을 구한다.
2. 보기 여유의 시작안으로 좌우 각각 차량 bbox 폭의 0.1배, 상하 각각 높이의 0.1배를 더한다.
3. 필요한 영역을 깎지 않고 모자란 축을 늘려 16:9로 맞춘다.
4. 가능한 경우 원본 안으로 평행 이동한다. 이동 후에도 차량 bbox와 ROI가 포함되는지 다시 검사한다.

### 7.3 분석 크롭

> **D-201로 바뀜**: 분석 크롭은 내 차 bbox 폭의 약 3배로 시작하고, ROI·보여줄 크롭을 못 담으면 넓힌다. 아래 내용은 비교한 초안이다.

1. 완성된 보여줄 크롭에 좌우 각각 차량 bbox 폭의 0.5배, 상하 각각 높이의 0.5배를 더하는 안부터 시험한다.
2. 16:9로 맞추고 원본 안에서 위치를 조정한다.
3. 물체가 ROI에 닿기 전부터 객체 일부와 이동 경로가 보이는지 검사한다. 위 배수만으로 추적 워밍업이나 큰 차량 전체 포함을 보장하지 않는다.
4. 영상 하나에서는 같은 크롭을 유지한다. ROI 움직임마다 크롭 중심을 따라 움직이지 않는다.

### 7.4 화면 경계와 16:9가 충돌할 때

원본이 세로 영상이거나 4:3이고 필요한 영역이 크면, 원본 안의 16:9 사각형으로 모든 관심 영역을 담는 것이 불가능할 수 있다.

**추천 예외안은 필요한 원본 영역을 보존하고 남는 부분에 패딩을 추가해 최종 입력·출력을 16:9로 만드는 것**이다. 원본 안에서 실제로 가져오는 사각형과 패딩 후 캔버스를 구분한다. 패딩은 원본 픽셀이 아니므로 움직임 감지·후보 판정에서 제외한다.

이는 기존 D-175의 원본 비율 예외에 대한 새 제안이다. 기존 크롭 좌표 기록만으로 패딩 배치를 표현할 수 있는지 담당자 검토가 필요하다. 승인 전에는 ‘원본 전체를 쓰면 항상 16:9 조건도 만족한다’고 가정하지 않는다.

원본 한계로 보여줄 크롭과 분석 크롭이 같아질 수 있다. 이때는 화면 내부의 포함 관계를 유지하고 외부 여유가 없음을 기록한다. 엄격하게 분석 크롭이 더 커야 한다는 기존 표현의 경계 예외로 검토해야 한다.

### 7.5 크롭을 넓히면 탐지 성능도 확인해야 한다

같은 모델 입력 해상도로 줄인다면 큰 크롭일수록 사람·작은 물체가 더 작아진다. 넓히는 것이 무료이거나 항상 유리한 것은 아니다.

- 필요한 ROI를 모델 입력 크기에 맞추려고 잘라내지 않는다.
- 원본→크롭→모델 입력의 축소율과 작은 물체의 픽셀 크기를 확인한다.
- 작아져 누락되면 모델 입력 해상도 상향과 처리 시간을 비교한다. 640을 이 문서의 확정값으로 두지 않는다.
- 채널 B를 축소 영상에서 실행한다면 같은 문제가 생기므로, 움직임 감지용 해상도도 함께 검증한다.

## 8. 상황별 동작

| 상황 | 추천 처리 | 남는 한계 |
|---|---|---|
| 거의 수직으로 내려다봄 + 파손 보임 | 검증된 경우 좁은 바닥 띠·짧은 높이 확장 | 문·손·공중 물체를 위한 최소 여유 필요 |
| 낮게 옆에서 봄 + 파손 보임 | 직접 접촉 영역 + 넓은 높이·출입 여유 | 가까운 무관한 통행도 들어올 수 있음 |
| 낮게 봄 + 반대편 파손 안 보임 | 바닥 띠 + bbox 상단 위까지 확장 + 양 끝 출입 | 차보다 낮고 완전히 숨은 물체는 직접 관측 불가 |
| 높게 봄 + 파손 안 보임 | 구도만으로 축소하지 않고 넓은 안 보임 규칙 | 옆 차량·기둥 가림 이유를 입력만으로 알 수 없음 |
| 중간 높이 또는 단서 충돌 | 불확실로 분류하여 넓게 처리 | 처리량·오탐 증가 |
| 정면·후면에서 촬영 | 정면 선택으로 길이·폭 대응을 유지 | 화면상 짧은 변만으로 구도 판정 금지 |
| 차량이 대각선으로 주차 | 차량 상대 좌표에서 띠를 만들어 영상으로 변환 | 화면 수평 띠만 쓰는 오류 방지 |
| 모서리 파손으로 두 변 선택 | 두 변의 ROI 합집합 | 합친 범위가 넓어질 수 있음 |
| 작고 먼 차량 | bbox 비례 계산 후 원본·모델 입력에서 해상도 검사; 불안정하면 넓은 규칙 | 원본에 없는 세부는 확대해도 복구 안 됨 |
| 크고 가까운 차량 | 필요한 영역을 보존하며 화면 경계 처리 | 화면 밖 접근 단서는 얻을 수 없음 |
| 일부가 원본 밖으로 잘린 차량 | 정상 기하 추정으로 취급하지 않음; 보이는 범위의 대체 ROI | 가상 바닥 전체를 짐작해도 실제 관측 범위는 늘지 않음 |
| 옆 차량·기둥에 가림 | 안 보임의 넓은 규칙으로 출입 흔적 확보 | 높게 찍혔다는 이유로 가림 해결 불가 |
| 트럭·특수차·형태가 다른 RC카 | 종횡비 가정을 신뢰하지 않고 구도 축소 중단 | 승용차 가정에 의한 오판 방지, 넓은 ROI 비용 |
| 네 점이 꼬이거나 중복됨 | 저장 전 입력 오류로 재지정; 저장된 비정상 자료는 계약 오류로 처리 | 잘못된 형식을 정상 입력처럼 조용히 통과시키지 않음 |
| 네 점은 유효하지만 매우 납작함 | 낮은 시점일 수 있으므로 거절하지 않고 기하 확장 대신 대체 ROI | 낮은 시점과 부정확한 입력을 완전히 구분 못 함 |
| 심한 어안·화면 회전·경사 바닥 | 기본 기하 가정의 검증 범위 밖으로 표시; 시험 시 사방 여유의 넓은 대체 ROI | 정확한 방향별 축소를 지원한다고 주장하지 않음 |
| 그림자·반사·전조등·비 | ROI 안에서도 생김. 움직임 노이즈 처리는 별도 검증 | ROI 크기만으로 해결 안 됨 |
| 영상 도중 카메라 이동·줌·본인 차량 이동 | 최초 고정 영역의 전제가 깨짐. 재설정·처리 정책 별도 결정 | 본 설계가 자동 추종한다고 가정하지 않음 |
| 접근·접촉·이탈 모두 완전히 안 보임 | 관측 불가로 한계 기록 | ROI 확대나 VLM으로 보이지 않는 사건 복원 불가 |

## 9. 영역 계산과 후보 탐지의 연결

1. ROI에 들어온 움직임은 분석을 시작할 단서다. ROI에 닿았다는 사실만으로 접촉 후보를 확정하지 않는다.
2. 객체탐지·추적은 분석 크롭에서 수행한다. ROI 밖으로 나갔다는 이유만으로 트랙을 삭제하지 않는다.
3. 물체 바닥점이 불안정하거나 가려졌다면 ROI·바닥 띠 밖이라는 이유로 접촉 가능성을 배제하지 않는다. 기존 D-91 원칙을 따른다.
4. ROI를 놓치면 채널 A가 켜지지 않을 수 있다. ROI 포함 여부와 객체탐지 성능을 따로 확인해야 한다.
5. 움직임이 전혀 보이지 않는 접촉도 있으므로 ‘접촉이면 반드시 ROI 픽셀 변화가 있다’는 보장은 하지 않는다.
6. D-165의 ROI 전용 움직임 계산과 D-96의 분석 크롭 전체 연결 요소 확장은 조정할 계약이 남아 있다. **이 문서는 ROI 마스크를 정의할 뿐, 전체 전경 마스크를 항상 계산할지 여부를 확정하지 않는다.**
7. 채널 A의 이전 15초·이후 20초 처리와 추적 워밍업은 별도 항목이다. 공간 여유를 넓혔다고 해당 시간 전체에 물체가 관측됨을 보장하지 않는다.

## 10. 다른 방법과 비교

| 방법 | 장점 | 문제 | 제안 |
|---|---|---|---|
| bbox 고정 배수만 사용 | 가장 단순하고 입력 오차에 덜 민감 | 차량 방향·파손 변·구도를 충분히 반영 못 함 | 실패 시 대체안 및 비교 기준 |
| 바닥 네 점만으로 모든 영역 생성 | 방향·바닥 원근 반영 | 지붕·상체·외부 가림을 알 수 없음 | 단독 사용하지 않음 |
| 네 점 + 정면 + bbox | 기존 입력 활용, 방향별 띠와 세로 여유 자동화 | 구도·확장량 검증 필요 | **추천 기본안** |
| 촬영 구도 선택 추가 | 높낮이 추정 부담 감소 | 사용자마다 판단이 다르고 외부 가림은 설명 못 함 | 자동 구도 분류가 실패할 때 비교 |
| 파손 쪽 주변 공간의 보임 여부 추가 | ROI를 줄일 수 있는지에 직접 관련 | 입력 추가, 사용자의 오판 가능 | 안 보임 ROI 축소가 꼭 필요할 때 추천 |
| 지붕·차체 외곽 점 추가 | 화면상 차체 경계 정밀화 | 클릭 부담, 보이지 않는 부분의 오류 지속 | 처음부터 필수로 넣지 않음 |
| 차량 분할·3D 자세 모델 추가 | 외곽·자세 자동 추정 가능성 | 모델·성능·RC카 도메인 검증이 추가됨 | 규칙 기반 실패가 확인된 뒤 검토 |
| 실제 카메라 보정·실측 크기 사용 | 기하 계산 근거가 강해짐 | 사용자가 확보할 수 없는 정보 필요 | 이번 입력 조건에서 제외 |

## 11. 검증 방법과 완료 조건

### 11.1 비교할 세 가지 안

같은 영상·입력으로 다음을 비교한다.

1. 차량 bbox를 넓힌 단순 기준안.
2. 네 점·정면·bbox를 쓰되 구도에 따른 자동 축소를 하지 않는 안.
3. 2번에 검증한 구도 분류와 축소 규칙을 추가한 안.

3번이 ROI를 줄이면서 관측 가능한 사건 단서를 놓치지 않는지 확인해야 구도 추정의 이점이 입증된다. 작은 ROI가 그려졌다는 사실만으로 성공이라고 판단하지 않는다.

### 11.2 확인 자료

- 높은·중간·낮은 시점, 정면·측면·대각선, 보임·안 보임을 나눠 확인한다.
- 사람, 옆 차 문, 주행 차량, 카트·작은 물체를 구분한다. RC카만으로 사람 머리·문콕의 범용성을 검증했다고 말하지 않는다.
- 사람 눈으로 관측 가능한 접근·접촉·이탈의 시간과 위치를 표시한다.
- 네 점을 여러 사람이 다시 찍거나 점을 흔든 결과로 입력 민감도를 확인한다.
- 극단 구도는 합성 투영으로 계산의 성질을 시험할 수 있지만, 실제 영상 성능 검증을 대신하지 않는다.

### 11.3 개발용 확인 결과

원본 위에 차량 bbox, 네 점, 정면·파손 변, 각 ROI 구성요소, 최종 ROI, 두 크롭을 서로 다른 색으로 겹쳐 저장한다. 구도 판정, 사용한 가정, 대체 규칙 적용 이유, 화면 밖으로 잘린 범위도 확인 가능해야 한다.

이것은 **개발·검증용 표시**다. 기존 D-176의 사용자 크롭 미리보기 제외 결정을 바꾸는 것이 아니다. 실제 개인정보가 있는 원본 겹침 자료를 사용자에게 제공하거나 공유 저장소에 올리는 기능으로 확대하지 않는다.

### 11.4 확인할 항목

| 확인 항목 | 확인 이유 |
|---|---|
| 관측 가능한 사건 단서가 ROI 안에 들어오는지 | 공간 영역 설계가 신호를 놓치는지 확인 |
| 해당 시간에 채널 B가 실제로 동작하는지 | ROI 포함과 움직임 검출 성공을 구분 |
| 채널 A가 켜지고 물체가 검출되는지 | 트리거·해상도·모델 문제 분리 |
| 최종 후보가 생성되는지 | 전체 파이프라인 누락 확인 |
| ROI 면적과 무관한 움직임에 의한 활성 시간 | 넓은 보완 규칙의 비용 확인 |
| 입력 오차 후 ROI 변화·관측 단서 누락 | 가려진 네 점 추측의 영향 확인 |
| 차량·ROI·두 크롭의 포함 관계 | 크롭 조정 과정에서 관심 영역이 잘리는지 확인 |

영역별 진단 지표는 개발용이다. PRD의 공식 후보 누락률 정의나 평가 범위를 이 문서에서 바꾸지 않는다. 조정용과 최종 평가용 자료를 분리하고, 평가 전에 임계값·배수·예외 규칙을 고정한다.

### 11.5 설계 확정 전에 충족할 조건

1. 입력만으로 영역이 결정되고 같은 입력·같은 규칙 버전에서 같은 결과가 나온다.
2. 정상·낮은 시점·기하 계산 실패·화면 경계 각각에 실행 가능한 경로가 있다.
3. 화면 안의 ROI와 차량 bbox가 보여줄 영역에 포함되고, 그 영역이 분석 영역에 포함된다.
4. 지붕 위 움직임과 양 끝 출입을 별도로 검증한다.
5. 높은 시점에서 작은 ROI를 선택하는 조건을 조정용 자료로 뒷받침한다. 근거가 없으면 자동 축소를 활성화하지 않는다.
6. 실제 자료가 없는 상황은 미검증으로 남긴다. 모든 주차장에 통한다고 보고하지 않는다.

## 12. 아직 결정해야 할 사항

아래는 기존 15개 문답 중 영역 관련 항목을 세분화한 것이다. 새로운 질문 8개를 별도 누적한 것이 아니다.

| 항목 | 이 문서의 추천 | 상태 |
|---|---|---|
| 정면 입력 | 기존 네 변 중 하나 선택, 모름 허용 | 확정: 네 변 중 하나를 반드시 고르고 모름은 두지 않는다 (D-194) |
| 바닥점의 의미 | 차체 외곽을 바닥에 투영한 네 모서리로 통일 | 🚧 팀장 결정 |
| 구도 추정 | 종횡비 가정·눌림 지표·bbox 단서·민감도 검증, 각도 단정 금지 | 🚧 방법과 임계값 검증 |
| 초기 자동 축소 | 검증 전 비활성, 넓은 기준안부터 비교 | 🚧 팀장 결정 |
| 안 보임 ROI | 상단·출입 보완, 높은 구도만으로 축소하지 않음 | 🚧 팀장 결정 |
| 주변 보임 추가 입력 | 기본안에는 제외, 안 보임 ROI 축소가 필요할 때 도입 | 🚧 팀장 결정 |
| 확장 배수와 실패 기준 | 6.5의 시작값으로 실험하고 조정 후 고정 | 🚧 실측 |
| 16:9 원본 경계 예외 | 영역 보존 + 패딩, 실제 원본 범위와 구분 | 🚧 팀장 결정·계약 검토 |

👤 **팀원 1 결정 필요:** 위 입력 변경을 팀장이 승인하면 정면 선택·오류 안내의 화면 세부를 정한다. 개발용 겹침 그림을 사용자 화면에 추가하는 것으로 해석하지 않는다.

👤 **팀원 2 결정 필요:** 승인된 추가 입력의 버전·검증·저장 계약과 패딩 사용 시 크롭 기록 방식을 정한다. 현재 버전 5에 승인되지 않은 필드를 임의로 추가하지 않는다.

문서 내용 승인 후에만 관련 결정 기록과 각 설계 장을 별도 작업으로 반영한다.

### 기술 참고

- [OpenCV: Homography 설명](https://docs.opencv.org/4.13.0/d9/dab/tutorial_homography.html): 평면 점의 대응과 영상 변환. 바닥 평면 변환이 사람 머리·차체 높이를 자동 복원하는 것은 아니다.
- [OpenCV: PnP 자세 계산](https://docs.opencv.org/4.10.0/d5/d1f/calib3d_solvePnP.html): 카메라 정보와 실제 기준점으로 위치·자세를 구하는 문제. 이번 설계의 필수 입력 조건과는 다르다.

위 참고자료는 기하 원리를 뒷받침한다. 이 문서의 ROI 배수·구도 분류·실험 종횡비가 검증됐다는 근거는 아니다.

### 이전 대화에서 채택하지 않는 주장

1. 바닥 박스의 세로÷가로만으로 CCTV 높낮이를 알 수 있다는 주장.
2. 화면상 차 크기가 실제 거리를 유일하게 결정한다는 주장.
3. bbox에서 실제 차체 높이나 지붕 외곽을 정확히 얻는다는 주장.
4. 눈대중 네 점과 가정한 차량 치수로 얻은 높이·거리 수치를 정확도 검증 결과로 사용하는 것.
5. 높은 시점이면 파손 주변도 전부 보이므로 안 보임 ROI까지 무조건 줄일 수 있다는 주장.
6. 크롭을 넓혀도 탐지 성능·처리량에 비용이 거의 없다는 주장.

이 문서의 추천은 **관측 가능한 단서를 우선 포함하는 자동 영역 생성과, 검증된 조건에서만 영역을 줄이는 방식**이다. 실제 카메라 위치 복원이나 모든 가림의 해결을 전제로 하지 않는다.
