## 1.1 이 문서의 역할

- [PRD](../PRD.md)는 **무엇을, 왜** 만드는지 정한다. 설계 문서는 **어떻게** 만드는지 정한다.
- 팀원과 에이전트(Claude Code·Codex)가 모두 이 문서를 기준으로 개발한다.
- PRD는 목적·범위·우선순위, [SRS](../SRS.md)는 REQ별 요구사항·완료 조건, 설계 문서는 API·DB·처리 방법을 담당한다. 변경 시 관련 요구사항과 설계를 함께 맞춘다.
- 제출 보고서를 만들 때는 SRS 부록 A의 작성 규칙을 따른다. 업로드 용량 제한과 브라우저 분할 전송은 내부 설계 정보로만 관리한다.

## 1.4 작성 규칙

사람과 에이전트 모두 이 규칙을 따른다.

- 결정은 [11장](11-decisions.md)에 `D-01` 형식의 ID로 기록한다. 본문에는 결과만 적고 `(D-05)`처럼 근거를 링크한다.
- **결정 상태는 결정할 권한이 있는 사람이 승인했는지로 정한다 (D-135).** 기능 동작(기획)·공통 규칙·팀장 담당 영역의 결정은 팀장이 승인하면 바로 "확정"이다. 다른 장에 반영하는 일은 확정과 별개로 그 장의 담당자가 한다. 한 영역 안에서만 쓰는 구현 선택(도구, 쿼리, 내부 방식)은 그 담당자가 승인하면 "확정"이다. 결정할 사람이 아직 승인하지 않았으면 "확정 필요"로 적는다(다른 팀원이 기록했거나 에이전트가 제안만 한 경우). 확정된 결정에 이견이 있으면 새 결정으로 바꾼다. ([11장 상태 표기](11-decisions.md#목차))
- 결정을 바꿀 때는 기존 기록을 지우지 않는다. 새 결정을 추가하고 기존 결정에 "D-xx로 대체됨"을 표시한다.
- 미정 항목은 🚧로 표시하고 11장 미결정 목록에 `U-01` 형식의 ID로 올린다.
- 공통 규칙과 팀장 담당 영역(기획·비전·VLM·AWS 구조)은 팀장이 정한다. 한 영역 안에서만 쓰는 도구·구현 방식(예: 백엔드의 마이그레이션 도구, 프론트의 상태관리)은 그 영역 담당자가 정한다. 이런 항목은 👤로 표시하고 `👤 팀원 2 결정 필요 (U-36)`처럼 **누가 무엇을 정해야 하는지**를 적는다. 11장 미결정 목록에는 담당자와, 팀장이 이미 정한 조건·참고 추천을 함께 적는다.
- 수치 상수는 [1.6](#16-주요-상수)에만 적고 다른 곳에서는 이름으로 참조한다.
- API·파일 형식 같은 인터페이스는 설명보다 예시 JSON으로 적는다.
- 반드시 지켜야 하는 규칙(불변 조건)은 [02장 2.4](02-architecture.md#24-이중-경로와-불변-조건)에 모아 둔다. 코드와 테스트는 이 조건을 기준으로 작성한다.

## 1.5 용어집

문서와 코드에서 아래 용어를 이 뜻으로만 쓴다.

**사람·역할**

| 용어 | 뜻 |
|---|---|
| 사용자 (피해자) | 차량이 파손되어 CCTV를 확인하려는 사람. 서비스 계정의 주인이다. |
| 관리자 | 주차장 관리자. 사용자가 발급한 업로드 전용 일회용 링크로 CCTV 영상을 업로드한다. 로그인하지 않으며 결과를 볼 수 없다. (D-28) |

**영상·시간**

| 용어 | 뜻 |
|---|---|
| 원본 영상 | 관리자가 업로드한 파일 그대로의 영상. 분석에만 쓰고 사용자에게는 절대 보여주지 않는다. |
| 원본 시간 | 원본 영상 시작부터의 경과 시간(초). 모든 시간 정보의 기준이다. |
| 청크 | 디코딩을 여러 프로세스로 나눠 하려고 원본 영상을 시간 단위로 나눈 구간. 원본 시간 기준 시작·끝을 가진다. 탐지·추적은 청크로 나누지 않는다. (D-76) |
| 샘플링 fps | 분석할 때 초당 몇 장의 프레임을 뽑아 탐지할지 정한 값. |
| 정지 장면 | 차량 선택용 프레임. 원본 영상 **시작 장면(첫 프레임) 1장**이다. 1단계가 만드는 유일한 산출물이다 (D-67). 다른 시점으로 넘겨 보는 기능은 없다. (PRD 3.2, D-48) |
| 비식별화 | 번호판과 사람 **얼굴**을 모자이크 처리하는 작업. 얼굴을 찾지 못한 사람 트랙은 사람 전체를 가린다 (D-69). "마스킹"·"모자이크"와 같은 뜻이며, 문서에서는 "비식별화"로 통일한다. |
| 마스킹본 | 비식별화가 끝난 영상·이미지. 사용자에게는 마스킹본만 보여준다. |
| 이중 경로 | 분석은 원본 영상으로, 열람은 마스킹본으로 하는 원칙. (PRD 3.1) |

**분석**

| 용어 | 뜻 |
|---|---|
| 객체탐지 | 프레임에서 차·사람의 위치(bbox)를 찾는 작업. YOLO 계열 모델을 쓴다. |
| 추적 (트래킹) | 프레임마다 탐지된 bbox를 이어 붙여 같은 객체에 같은 ID를 주는 작업. ByteTrack을 쓴다. |
| 트랙 | 추적 결과로 만들어진 객체 하나의 시간별 bbox 목록(궤적). |
| 차량 영역 | 사용자가 정지 장면에서 **고른** 본인 차량의 사각형. 탐지 결과의 bbox다. 2단계 룰이 쓴다. (D-65) |
| 누끼 | 탐지 결과로 딴 차량 외곽(다각형). **쓰지 않는다** — 차량 영역은 bbox다. 겹친 차를 픽셀 단위로 가르려면 필요해진다 🚧 (D-65, U-09) |
| 탐지 목록 (`detections`) | 정지 장면에서 탐지된 차량들의 `det_id` + `bbox`. 화면이 이미지 위에 겹쳐 그리고 사용자가 하나를 고른다. (D-65) |
| 본인 차량 | 사용자가 정지 장면의 탐지 목록에서 골라 지정한 자신의 차량. (D-65) |
| 파손 부위 | 사용자가 입력한 본인 차량의 파손 위치. 정지 장면 위에 사각형을 드래그하고 **원본 화면 절대 좌표**(`damage_bbox`)로 저장한다. 파손이 CCTV에 안 보여도(`visible=false`) 화면상 그 위치를 같은 방식으로 입력한다. 보이면 고른 차량 영역 안으로 제한하고, 안 보이면 차량 밖도 허용한다. (D-65, D-92) |
| 인접 영역 | 파손 부위 주변에서 후보를 찾는 공간(옆 주차면, 통로). **사용자가 입력하지 않는다.** 워커가 파손 부위 좌표, `visible` 값, 바닥 네 모서리와 파손 변으로 계산한다. 계산 방식과 크기는 🚧 (U-13, U-30). (PRD 3.3, D-92) |
| 바닥 네 모서리 | 사용자가 정지 장면에서 찍는, 본인 차량이 바닥에 닿는 네 모서리. 보이지 않는 모서리는 짐작해 찍는다. 이 사각형이 찌그러진 정도로 CCTV 시야를, 크기로 카메라와의 거리를 파악한다. 계산 방법 🚧 (D-98, U-30) |
| 파손 변 | 바닥 네 모서리 사각형의 네 변 중 사용자가 고른, 파손이 있는 변. 한 변이거나, 모서리 파손이면 이웃한 두 변이다. (D-98) |
| 탐지 상황 | 사용자가 고르는 "파손이 CCTV에 **보임 / 안 보임**". 룰이 이 값으로 갈린다. (D-72) |
| 분석 크롭 | 본인 차량 주변을 넉넉히 잘라낸 고정 사각형. 채널 A·B와 비식별화 탐지가 이 위에서 돈다. 본인 차량 위치로 다시 계산되므로 저장하지 않는다. 크기 🚧 (D-95, U-30) |
| 보여줄 크롭 | 사용자 클립으로 잘라내는 영역. 분석 크롭보다 작고, 모자이크는 이 영역에만 입힌다. 크기 🚧 (D-70, D-95, U-30) |
| 근접 영역 (ROI) | 파손 변 주변에서 접근하는 물체가 화면에 나타나는 영역. 분석 크롭 안에 있다. 채널 B 움직임이 여기에 닿으면 채널 A를 켠다. 크기는 바닥 네 모서리로 파악한 시야·거리로 정한다 🚧 (D-71, D-97, D-98, U-30) |
| 채널 A / 채널 B | 후보 탐지의 두 경로. 둘 다 분석 크롭 위에서 돈다. A = 객체탐지 + 추적이며, 근접 영역에 움직임이 있는 구간(첫 감지 −15초 ~ 마지막 감지 +20초)에만 돈다. B = 움직임 감지이며 영상 전체에 돈다. 근접 영역에 닿은 움직임 덩어리는 A 트랙에 붙이거나 이어진 움직임 영역 전체로 넓혀 클래스 없는 트랙으로 만든다. (D-71, D-95, D-96, D-97) |
| 바닥점 | 트랙 bbox 아래 변의 가운데. 물체가 바닥에 닿는 자리로 본다. (D-71) |
| 바닥선 | 본인 차량이 바닥에 닿는 경계. 차량 bbox 아래 변에서 바닥 네 모서리 사각형으로 바꾼다. 구체 규칙 🚧 (D-71, D-98) |
| 띠 | 바닥선 바깥의 좁은 영역. 바닥점이 띠 안이면 근접 후보로 남긴다. 띠 밖이라는 이유만으로 제외하지 않는다. 네 모서리 기준의 모양과 폭은 🚧 (D-71, D-91, D-98, U-30) |
| 0단계 필터 | VLM 전에 트랙을 거르는 규칙. **확실히 관계없는 것만 빼고, 판단이 안 되면 남긴다.** (D-71) |
| 룰 | 트랙과 파손 부위·인접 영역의 위치 관계로 근접을 판정하는 규칙. 바닥점 필터와 0단계 필터로 이뤄진다 (D-71). 후보 병합 등은 🚧 (U-13) |
| 판정 시점 (기준점) | 룰이 후보로 판정한 원본 시간. 트랙 바닥점이 파손 부위에 가장 가까운 순간이다. VLM은 이 ±1초를 조밀하게 본다 ⚠️ (D-73, U-31) |
| 후보 | 룰이 판정한 근접 순간 하나. 판정 시점을 가진다. 연속된 판정을 하나로 합치는 규칙은 🚧 (U-13) |
| VLM 점수 | Bedrock VLM이 후보마다 따로 매긴 접촉 가능성 점수(0~100). 정렬에만 쓴다. **2차 VLM에서만 나온다.** 1차에서 탈락한 후보는 0점이다. 점수는 도구 강제 호출로 받는다. (D-74, D-93) |
| 후보군 목록 / 파싱 실패 목록 | 후보군 목록 = 점수가 나온 후보를 점수순으로 정렬한 목록. 파싱 실패 목록 = 2차에서 최대 3번 불러도 점수 형식을 받지 못한 후보의 목록. 0점으로 보내지 않고 따로 보여준다. 둘 다 10개 묶음이다. 목록 안 순서 🚧 (D-93) |
| 1차 VLM / 2차 VLM | 1차 = 싼 모델(Nova Lite, 잠정)이 확실히 아닌 후보(점수 기준 0~19에 확실히 해당)만 탈락시킨다. 2차 = Claude Haiku 4.5가 남은 후보에 점수를 매긴다. (D-74) |
| 안내 프레임 | VLM에 보내는 후보 구간 첫 프레임 1장. 파손 부위(안 보임이면 인접 영역) 테두리를 그려 "어디를 볼지" 알린다. (D-73) |
| 1단계 분석 | 업로드 직후 자동 실행하는 분석. 코덱 검사, 정지 장면 추출, 차량 탐지, 정지 장면 비식별화만 한다. 짧다(수십 초, 추정). GPU 워커가 실행한다. (D-67, D-14, D-65) |
| 2단계 분석 | 사용자 입력을 저장하면 실행하는 분석. 청크별 디코딩, 분석 크롭 위 채널 B(영상 전체)·채널 A(움직임 구간만)와 중간 저장, 0단계 필터, VLM 1차·2차, 정렬, 두 목록 각각 상위 20개 후보 클립 크롭·비식별화. 24시간 영상 약 30분(추정). GPU 워커가 실행한다. (D-67, D-76, D-14) |

| 후보 클립 | 사건 지점 전후 15초(판정 시점 −10초 ~ +20초), 총 30초 길이의 마스킹본 영상. **본인 차량 주변으로 크롭한다** (D-70). 영상 경계를 넘는 부분은 잘라낸다. |
