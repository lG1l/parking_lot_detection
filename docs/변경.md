- 작성일: 2026-11-12
- 근거: `docs/design/11-decisions.md` D-245, `docs/design/06-pipeline.md` 6.5

## 1. 한눈에 보기

| 영역 | 정할 것 | 코드 변경 |
|---|---|---|
| 팀장 (기획·비전) | 4개 (3장) | 없음. GPU 워커는 아직 구현 전이다 |
| 백엔드 (팀원 2) | 3개 (4장) | 있음. DB 마이그레이션, 12·15·25번 SQL, 가짜 워커, 테스트 (6장) |
| 프론트엔드 (팀원 1) | 없음 (5장) | 없음 |

- **API 응답 형식은 바뀌지 않는다.** 12·15·25번은 지금도 클립의 `start_sec`·`end_sec`만 준다. 값의 범위만 달라진다(클립 길이가 30초 고정이 아니라 13~30초 사이로 달라진다).
- **바뀌는 것은 DB의 `candidates` 테이블이다.** 후보 하나가 담는 내용이 달라졌기 때문이다.

## 2. 무엇이 바뀌었나

### 옛 설계와 새 설계

| 항목 | 옛 설계 | 새 설계 (D-245) |
|---|---|---|
| 후보 하나 | 트랙 하나가 파손 위치에 가장 가까워진 **순간 하나** | ROI 안에서 움직임이 있는 **시간대를 자른 클립 하나** |
| 기준 시각 | 판정 시점 하나 (`judged_at_sec`) | 유력 시점 여러 개 (클립에 든 트랙마다, 동률이면 더 여러 개) |
| 후보에 든 트랙 | 1개 (`track_id`) | 1개 이상 (같은 시간대의 트랙은 한 클립에 함께 들어간다) |
| 클립 구간 | 판정 시점 −10초 ~ +20초 (항상 30초, 영상 끝에서만 짧아짐) | 움직인 시간대 앞뒤에 여유 5초. 30초 이하. 길면 5초씩 겹쳐 여러 클립으로 나눈다 |
| 클립 구간이 정해지는 때 | 클립을 만들 때 (판정 시점에서 계산) | **후보를 만들 때** (VLM이 클립을 만들기 전에 이 구간을 쓴다) |

### 예

사람이 100초에 ROI에 들어와 112초까지 움직이고, 다른 사람이 110초부터 150초까지 움직였다.

| | 옛 설계 | 새 설계 |
|---|---|---|
| 후보 | 트랙마다 1개씩 2개 | 두 시간대가 겹치므로 100~150초를 먼저 하나로 잇는다. 50초라 30초 이하 클립 2개로 나눈다 |
| 클립 | 각 판정 시점 −10 ~ +20초 | 97.5~127.5초, 122.5~152.5초 (5초 겹침, 양끝 여유 2.5초) |
| 후보 하나에 든 트랙 | 1개 | 앞 클립 2개, 뒤 클립 1개 |

## 3. 팀장이 정할 것

### T1. 사건 지점의 뜻 (PRD 3.5) — 확정 (D-246, 2026-11-12)

- **결정**: "판정 시점 + 5초"라는 정의를 없앤다. 후보 클립은 "움직인 시간대 앞뒤 5초, 30초 이하"로 정의한다. "사건 지점 고정"이라는 말은 그대로 쓰고, 고정한 사건 지점 = 찾음으로 고른 후보 클립(원본 기준 시작~끝)이다.
- 지금 정의: "판정 시점 + 5초. 후보 클립의 가운데 시점". 판정 시점이 없어져 이 정의를 쓸 수 없다.
- 영향: PRD 3.4·3.5·User Flow, SRS(REQ 완료 조건), 01장 용어·상수, 04장 4.4·4.7, 10장 테스트 자료 계산식.
- 코드: 영향 없다. 코드에는 `incident_at_sec` 같은 값이 없고, 15·25번은 고정한 클립의 시작·끝을 준다.

### T2. 채널 A를 켜고 끄는 15초·20초 (06장 6.5, D-97·D-192) — 확정 (D-247, 2026-11-12)

- **결정**: 켤 때 거슬러 올라가는 시간 10초(클립 앞 여유 5초 + 추적 워밍업 5초), 끌 때 여유 5초(클립 뒤 여유 5초), 링 버퍼 10초.
- 옛 근거: "옛 클립(판정 시점 −10 ~ +20초)을 빠짐없이 덮는 길이".
- 이어서 하기 때 다시 디코딩하는 길이도 정했다 (D-248): `processed_sec` 1분 전부터 다시 읽어 MOG2만 돌리고, 마지막 10초는 링 버퍼에 담는다. 옛 규칙은 15초였다.
- 영향: 06장 6.5 "35초의 근거"·켜는 15초·끄는 20초, 6.7 "YOLO가 돌지 않은 부분" 설명, 01장 채널 A 용어·상수.

### T3. 후보에 남길 정보: 트랙 번호·채널·룰 이름 — 확정 (D-249)

**2026-11-12 팀장 확정: 아래 표의 추천대로 한다.** 트랙 번호는 모두 남기고, `channel`·`rule_name`은 뺀다. 내부 동작(탐지 뒤 단계, VLM, 정렬, 비식별화, 이어서 하기, 평가)에서 채널을 구분해 읽는 곳이 없음을 확인했다. 내부에서 갈리는 기준은 "클래스가 있는 트랙인가"이고 트랙 파일의 `cls` 키로 안다.

DB 칸의 형식은 백엔드가 정한다(B2).

| 지금 칸 | 문제 | 추천 |
|---|---|---|
| `track_id` 하나 | 한 후보에 트랙이 여러 개다 | 들어 있는 트랙 번호를 모두 남긴다. 평가할 때 "어느 트랙이 이 후보를 만들었나"를 찾는 데 쓴다 |
| `channel` (`A`·`B`) 하나 | 한 클립에 채널 A·B 트랙이 섞일 수 있다 | 후보 칸에서는 뺀다. 필요하면 트랙 파일(04장 4.8)에서 트랙 번호로 찾는다 |
| `rule_name` | 후보를 룰이 아니라 "ROI 안 움직임"으로 잡는다 | 뺀다. 뺀 트랙의 규칙 이름은 06장 "제외 기록"에 따로 남는다 |

- 잘못될 수 있는 것: 칸을 빼면 나중에 KPI 평가에서 채널별로 나눠 볼 때 트랙 파일을 함께 읽어야 한다.

### T4. 유력 시점·후보 구간을 DB에 남길지 — 확정 (D-250)

**2026-11-12 팀장 확정: 남긴다(아래 1번).** 함께 정한 것:

- 후보 구간은 트랙을 나누지 않고 **합쳐서** 남긴다.
- 후보(후보 구간 합치기·나누기, 클립, 유력 시점)는 **영상 전체 탐지가 끝난 뒤 한 번에** 계산해 DB에 넣고, 그다음 VLM을 시작한다.

**팀원 2에게 넘기는 내용: 후보 1개(= 클립 1개)에 담을 값** (시간은 모두 원본 영상 기준 초)

| 값 | 내용 | 개수 | 예 |
|---|---|---|---|
| 클립 구간 | 시작·끝 | 1쌍 | 100~122초 |
| 트랙 번호 | 그 클립 안에 후보 구간이 있는 트랙 전부 (D-249) | 1개 이상 | 31, 47 |
| 후보 구간 목록 | 합친 시작·끝 쌍 | 1쌍 이상 | 105~112초, 115~117초 |
| 유력 시점 목록 | 트랙 번호와 시각 | 0개 이상. 고정이 아니고 수십 개일 수 있다 | 트랙 31: 108.4초 / 트랙 47: 116.0초, 116.1초 |

- 워커만 쓰고 읽는다. 백엔드는 칸만 만들고, 내용을 검사하거나 API로 내보내지 않는다.
- 워커는 한 작업의 후보를 한꺼번에 넣는다.
- 일반 구간과 조밀 구간은 남기지 않는다(위 값에서 계산한다).

아래는 정하기 전의 선택지다.

- 누가 쓰나: GPU 워커의 VLM 단계만 쓴다. 백엔드 API와 화면은 쓰지 않는다.
- 선택지
  1. **남긴다 (추천)**: 후보 행에 "트랙별 유력 시점 목록, 클립 안의 후보 구간(움직인 시간대) 목록"을 한 칸으로 남긴다. 워커가 중간에 죽어 이어받을 때(D-94) 다시 계산하지 않아도 되고, 유력 시점 계산을 영상으로 검증할 때(U-31) 바로 꺼내 볼 수 있다.
  2. 남기지 않는다: 워커가 필요할 때 트랙 파일에서 다시 계산한다. DB가 단순하지만 재개·평가 때 계산을 다시 돌려야 한다.
- 잘못될 수 있는 것(1번): 백엔드가 읽지 않는 칸이라 내용 형식은 워커 쪽이 책임진다. 형식을 바꿀 때 백엔드와 맞출 일은 없지만, 04장에 형식을 적어 두어야 한다.

## 4. 백엔드(팀원 2)가 정할 것

### B1. 클립 구간(`start_sec`·`end_sec`)을 어느 테이블에 둘까

- 왜 정해야 하나: 지금은 클립 구간이 `candidate_clips`에만 있다(D-33: "후보는 판정 시점만, 구간은 클립에만"). 새 설계에서는 후보를 만들 때 구간이 정해지고, 클립 행을 만들기 전에 VLM과 파싱 실패 목록 정렬(6.7: `start_sec` 오름차순)이 이 값을 쓴다. 04장에도 "후보가 구간을 가져야 하면 그때 후보 구간 칼럼을 더한다(⚠️)"고 미리 적혀 있다.

| | 1. `candidates`로 옮긴다 (추천) | 2. 두 테이블에 모두 둔다 |
|---|---|---|
| 방법 | `candidates`에 `start_sec`·`end_sec`를 더하고 `candidate_clips`에서 뺀다 | `candidates`에 더하고, 클립을 만들 때 값을 복사한다 |
| 장점 | 값이 한 곳에만 있어 어긋날 수 없다 (D-33과 같은 원칙). 클립을 다시 만들어도 구간은 그대로다 | 12·15·25번 SQL을 고치지 않아도 된다 |
| 단점 | 12·15·25번 SQL이 `candidates`를 JOIN해서 읽도록 바꿔야 한다 (6장) | 같은 값이 두 곳에 있다. 복사를 빠뜨리면 화면 시간과 VLM이 본 시간이 다르다 |

- 어느 쪽이든 **응답 형식은 같다.**

### B2. 트랙 번호 여러 개·유력 시점의 칸 형식

T3·T4는 정해졌다 (D-249, D-250). 담을 값은 위 T4의 "팀원 2에게 넘기는 내용" 표다. 예: 트랙 번호는 `integer[]`, 유력 시점·후보 구간은 `jsonb` 한 칸. 04장 4.10의 타입 규칙("좌표·시간은 `double precision`, 픽셀 bbox는 JSONB 안의 정수 배열, JSONB가 아닌 칼럼은 `integer[]`")을 따른다.

### B3. 마이그레이션 방식

- 추천: **새 파일 `0003_...`을 만든다.** `0001_init.py`를 고치지 않는다. 이미 `0002_cases.py`처럼 변경을 새 파일로 쌓아 왔고(10장), AWS의 DB에 이미 테이블이 있으면 `0001`을 고쳐도 반영되지 않는다.
- 지금 DB의 후보 행은 가짜 워커가 만든 시험 데이터뿐이다. 칸을 빼고 더할 때 옮길 데이터가 없으므로, 기존 시험 데이터는 지워도 되는지만 확인한다.

## 5. 프론트엔드(팀원 1)

- **정할 것 없음, 코드 변경 없음.** 화면은 `start_sec ~ end_sec`를 그대로 보여준다 (`candidates_page.dart:469`, `results_page.dart:137`).
- 알고만 있으면 되는 것
  - 클립 길이가 13~30초로 달라진다. 30초를 가정한 코드는 없다.
  - 오래 움직인 장면은 5초씩 겹치는 클립 여러 개로 나뉘어, 같은 일이 후보 목록에 여러 개로 나온다. 점수순이라 서로 떨어진 순위에 있을 수 있다.
  - `demo_api.dart:127-128`(데모 클립 30초)과 `screens_test.dart`의 예시 시간은 형식이 같으므로 그대로 둬도 된다.

## 9. 백엔드(팀원 2)에게 공유할 내용

팀원 2에게 이 장만 전달해도 되도록 모았다. 자세한 이유는 앞 장에 있다.

### 9.1 먼저 알 것

- **API 응답 형식은 바뀌지 않는다.** 12·15·25번은 계속 클립의 `start_sec`·`end_sec`만 준다. 프론트는 고칠 것이 없다.
- **`judged_at_sec`는 DB에만 있는 값이다.** API 응답에 없고 `backend/app` 코드도 읽지 않는다. 05장 12번 SQL 예시에 이름만 남아 있어서 2026-11-12에 지웠다. 쓰는 곳은 `0001_init.py`(칸 정의)와 `fake_worker.py`(값을 넣고 ±15초로 클립 구간 계산) 두 곳이다.
- **바뀌는 것은 `candidates` 테이블이다.** 옛 설계는 "후보 = 트랙 하나 + 판정 시점 하나"였고, 새 설계는 "후보 = 클립 하나 + 트랙 여러 개 + 유력 시점 여러 개"다 (D-245).
- 클립 길이는 30초 고정이 아니라 13~30초다. 오래 움직인 장면은 5초씩 겹치는 클립 여러 개로 나뉜다.

### 9.2 `candidates`에서 빠지는 칸과 더해지는 값

| 구분 | 칸·값 | 상태 | 근거 |
|---|---|---|---|
| 뺀다 | `judged_at_sec` | 확정 | D-245, D-246 (판정 시점이 없어졌다) |
| 뺀다 | `channel` | 확정 | D-249 (읽는 곳이 없고, 한 클립에 채널 A·B 트랙이 섞인다) |
| 뺀다 | `rule_name` | 확정 | D-249 (후보를 만드는 룰이 없다) |
| 바꾼다 | `track_id` 하나 → 후보에 든 트랙 번호 전부 | 확정 | D-249 |
| 더한다 | 클립 구간 `start_sec`·`end_sec` (원본 시간, 초) | 값은 확정, 둘 테이블은 B1 | D-245 |
| 더한다 | 후보 구간 목록 (클립 안에서 움직인 시간대. 시작·끝 쌍 여러 개, 원본 시간, 초) | 확정 (칸 형식은 B2) | D-250 |
| 더한다 | 유력 시점 목록 (트랙 번호와 시각. 한 트랙에 여러 개일 수 있다. 원본 시간, 초) | 확정 (칸 형식은 B2) | D-250 |

- 후보 구간·유력 시점·트랙 번호는 **GPU 워커만 쓰고 읽는다.** 백엔드는 칸만 만들고, 내용을 검사하거나 API로 내보내지 않는다.
- 예 (후보 1개): 클립 100~122초, 트랙 번호 31·47, 후보 구간 105~112초·115~117초, 유력 시점 트랙 31: 108.4초 / 트랙 47: 116.0초·116.1초.
